# Backend rules: architecture, design, persistence, configuration

## Local first (Jakub 2026-10-28)
- Whatever can run in the browser runs there: rendering and computing from data the signed-in user already receives (QR codes, receipt PDFs, formatting, sorting and filtering a loaded list, summaries of the donor's own donations, resizing images before upload, the installed app's offline cache). The backend serves the data and keeps only what the browser cannot do: what grants or proves something (authentication, roles, rate limits, receipt numbers and the certified receipt data, pairing, the audit trail); what runs without a browser (the Fio import, scheduled jobs, e-mail, backups) or what the MCP connector also reads; aggregates over other people's data (the administration's overviews, the monthly report); and validating every input again. A new endpoint that renders or computes what the frontend could do from data it already holds names its reason in the PR. The payment QR and the receipt PDF still render on the backend until their roadmap items ship.

## Contexts and layers
- Contexts `content` (news, projects, media), `donors` (accounts, authentication, administrators, connected applications), `donations` (bank import, pairing, receipts, reports), `contact`, `operations` (how the server runs: settings and first setup, backups and restore, logs, log levels, diagnostics), kernel `shared`. Per context: `domain` depends on nothing (no Spring, JPA, Bean Validation); `application` → domain; `infrastructure` → domain, application; `interfaces/rest` → all. Contexts never depend on each other.
- ArchUnit: `architecture/DddLayeringRulesTest` (layers, context slices, framework-free domain, web-free application, controllers expose no infrastructure types, `MessageSource` only in adapters) and `AdapterLibraryRulesTest` (each third-party library confined to its adapter, e.g. the Fio client to `donations/infrastructure/fio`, webauthn4j to `donors/infrastructure/webauthn`, Caffeine to `..infrastructure..`). `shared` never imports a context (`shared_kernel_must_not_depend_on_any_context`). A new context goes into the slice rule's package list and the master changelog in the same PR.
- Name the owning context before writing code. A concept that fits two contexts means a wrong boundary or a missing context: say so, never force it.
- Cross-context only through `shared`: an event record in `shared/application/event/` (`DonorRegistered`, `DonorProfileChanged`, `DonorErased`, `AdminActionPerformed`) published with `ApplicationEventPublisher` and consumed with `@TransactionalEventListener` (`BEFORE_COMMIT` for a copy that must not be lost, `AFTER_COMMIT` + `@Async` for side effects like mail), or, for a read the consuming context cannot own, a port in `shared/application/<topic>/`, implemented in `shared/infrastructure/` when shared owns the data or library (`QrCodeEncoder` → `ZxingQrCodeEncoder`, `AdminActionTrail` → `JpaAdminActionTrail`) or by the owning context's infrastructure (`AlertRecipients` → `donations/infrastructure/report/ReportRecipientsAlertAdapter`); name a new port in the PR. A context keeps its own copy of foreign data (`donor_record` in donations). Events used inside one context live in `<context>/application/event/`.
- `shared` holds only stable concepts: value objects (`Money`, `Currency`, `EmailAddress`, `Iban`, `VariableSymbol`, `PostalAddress`, `LocaleCode`, `DonorType`, `ErasedPersonalData`) and the `UuidV7` generator; the sealed `DomainException` family; the cross-context events and ports above; cross-cutting infrastructure (security chain and JWT, `ApiExceptionHandler` + `ProblemTypes`, `FixedWindowRateLimiter`, `Clock`, scheduling, async, `BrandedEmails` + `EmailDraft`, `MailSenderProperties`, `PublicUrlProperties`, the audit log, `BuildRevision`).

## Domain
- Aggregates own their invariants and behaviour (no anemic entities); value objects are records that validate in the compact constructor; ids are records over `UUID`, generated by `UuidV7`. Domain services only for rules spanning aggregates (`PaymentPairingPolicy`, `ImportPlanner`, `ReceiptDocumentFactory`).
- Failures are sealed `DomainException` subtypes with a `code`: `RuleViolation` 400, `Conflict` 409, `NotFound` 404, `AuthenticationFailure` 401, `AccessDenied` 403. `ApiExceptionHandler` maps them to problem+json with `problem.<code>.title|detail` from `i18n/messages_{cs,en}.properties`; add both texts with the exception.
- `Clock` is injected, never `Instant.now()` (ArchUnit refuses every `now()` of the `java.time` types and `System.currentTimeMillis()`; `UuidV7.generate` takes the instant). The foundation's calendar is Prague's: the zone is `shared/domain/FoundationZone` (`ID` for `@Scheduled(zone = …)`, `ZONE`), never a `"Europe/Prague"` literal; donations' dates go through `FoundationCalendar`, `ReceiptCalendar` and `BankCalendar`. `Optional` for return values and for record components that may be absent; never `null` for absence, never an `Optional` field in a class, no new `Optional` parameters. Immutable by default.

## Application
- One application service per use case, or per tightly related group of use cases on one aggregate (`NewsAdminService`); never a service spanning unrelated aggregates. Commands, queries and views are records; the layer knows no HTTP, JPA entity or template. Ports are interfaces here, implemented in infrastructure (`BankStatementSource`, `BankImportRequests`, `DonationReceiptRenderer`, `MonthlyReportSender`).
- `@Transactional` on application services (`readOnly` for queries), never on controllers; short transactions. A use case that calls the network or decodes images keeps that work outside the transaction and writes through a short transactional collaborator (`BankStatementRecorder`) or a `TransactionTemplate` (`UploadImageService`); its public method has no `@Transactional`. Two exceptions are deliberate: receipt issuance renders under the donor lock because the PDF digest is part of the issued receipt (bounded by `concurrent-renders`), and the monthly report sends inside its transaction so a refused send leaves the month unsent. `REQUIRES_NEW` only where a separate transaction is the point: `DonationReceiptIssuer` (one transaction per download, even under a transactional caller), pairing called from an `AFTER_COMMIT` listener (`DonorRecordService`, `PaymentPairingService`).
- Retry-safe by design: imports keyed by bank transaction id, the monthly report recorded in the sending transaction, receipt numbers from a sequence under the donor lock (`reliability.md`).

## REST (`<context>/interfaces/rest`)
- Paths `/api/<context>/...`; the administration under `/api/admin/<context>/...` (role `ADMIN`, `security.md`). Request and response records only; Jakarta validation on requests with `@Size` limits from domain constants; `Accept-Language` selects texts.
- Errors are problem+json: types `https://nfnn.cz/problems/<context>/<code>` (`ProblemTypes`); validation 400 with `errors[{field,message}]`; 401/403 from the security chain (never a Basic challenge); 429 `rate-limited` from a limiter built like `SignInRateLimiter` (per client address, counted before any hashing or work). A failure outside the `DomainException` kinds (an upstream 502) gets a handler in the context's `interfaces/rest` (`AdminReportProblemHandler`).
- A public endpoint needs its `permitAll` line in `ApiSecurityConfiguration`; everything else needs the donor JWT. Another donor's resource answers 404.
- Every endpoint change updates `docs/api-contract.md` in the same PR.

## Persistence
- JPA entities and Spring Data repositories live in `<context>/infrastructure/persistence/` (the audit log in `shared/infrastructure/audit/`) and are package-private details of the adapter that implements the domain repository interface and maps domain ↔ entity; nothing outside that package uses them (ArchUnit: every `@Entity`, `@Embeddable` and Spring Data repository is non-public and in `..infrastructure..`; a test outside the package reads tables through `JdbcClient`).
- Liquibase: `db/changelog/<context>/NNN_<change>.xml` (next free number in that folder), changesets `id="NNN-<kebab-case>" author="nfnn"`, auto-included by the master. One file per logical change; a changeset touches only its own context's tables. A changeset's identity is id + author + file path, so never edit, rename or move a file that is on `main`: fix forward with a new one.
- Keep the previous image working against the new schema, because a rollback is the older image (a restore loses data, `reliability.md`). Safe: new tables, nullable columns, columns with a default that stays, wider types. Breaking: a new `NOT NULL` without a lasting default (add, fill and constrain in one changeset breaks an older image that inserts into the table), a dropped default, a new or narrowed `check`, unique or foreign-key constraint the older code can violate, a narrowed type, a rename or a drop. A breaking step lands one release after the code stops depending on it, named in the PR. Every new changelog also runs over data: `shared/infrastructure/schema/MigrationOverDataTest` migrates to `src/test/resources/migrations/baseline-changelog.xml`, inserts one row per table from `baseline-data.sql`, runs the master and expects every row kept; to move the baseline forward, add the merged files to the baseline changelog in master order and a row for each new table (the test fails on a baseline table without one).
- Constraints state invariants (unique, partial unique, `check`). Index every query path that grows with the data; every foreign key leads an index (`shared/infrastructure/schema/ForeignKeyIndexTest` fails on one that does not), so deleting a parent or reading its children never scans the child table. Types: `uuid` ids, `timestamp with time zone`, `date`, `varchar(n)` sized to the domain limit, `text` for long text, `bigint` amounts in minor units, `bytea` for binary content (images, passkey credentials), singleton tables with `smallint id check (id = 1)`.
- `open-in-view: false`: load what the use case needs inside it; no lazy access afterwards.

## Configuration and operations
- `@ConfigurationProperties` records under `app.*`, validated at startup (fail fast: `JWT_SECRET` outside dev, invalid IBAN, empty optional values). Production defaults in `application.yml`, dev overlay in `application-dev.yml`, local env names in `.env.example`. A value the server's operator must set is an `operations` `Setting` (first setup or `/sprava/nastaveni`, loaded under its env name by `DatabaseSettingsEnvironmentPostProcessor` in `prod`) with a label in `frontend/src/app/features/operations/setting-labels.ts`, never an env file line. Without `FIO_TOKEN` the import is off (`DisabledFioClient`, no scheduler bean).
- Scheduled work shares one thread: every cron job has a property that `-` turns off (tests pin them off, `CLAUDE.md` Gotchas), catches its own exceptions, logs the outcome and tolerates a missed run; one-off timers (import follow-ups, log-level resets) run on the same thread, so nothing on it may block beyond its call's timeout.
- Logging: SLF4J `log` field; content as `security.md` Logs; `warn` for expected failures; `error` with the stack trace only for unexpected failures whose message cannot carry personal data; mail and SQL failures log the id and the exception class. An `@Async` listener catches its own exceptions.
- Templates: Thymeleaf e-mails in `templates/email/<context>/` as `th:fragment="content"` fragments of the shared `templates/email/layout.html`, composed by `shared/infrastructure/mail/BrandedEmails` from an `EmailDraft` (text and HTML parts, `th:text` only, inline styles with theme colours only, sender `app.mail.sender-email`, links from `app.site.public-url`); receipts in `templates/pdf/`, rendered deterministically from the stored template bundle (skill `receipt-template`).
