# Backend rules: architecture, design, persistence, configuration

How each context works today is in `docs/system-overview.md`; this file is what a change must keep true.

## Local first (Jakub 2026-10-28)
- Whatever can run in the browser runs there: rendering and computing from data the signed-in user already receives (QR codes, receipt PDFs, formatting, sorting and filtering a loaded list, summaries of the donor's own gifts, the encrypted copy on the device, for donors and administrators alike). The backend serves the data and keeps only what the browser cannot do: what grants or proves something (authentication, roles, rate limits, receipt numbers and the certified receipt data, pairing, the audit trail); what runs without a browser (the Fio import, scheduled jobs, e-mail, backups) or what the MCP connector also reads; aggregates over other people's data that a job without a browser or the connector needs (the monthly report, the administration's overviews, until the administration's pages compute them from the device copy); and validating every input again.
- A new endpoint that renders or computes what the frontend could do from data it already holds names its reason in the PR. Logic that runs on both sides is proved by one shared set of cases (`testing-shared-cases.md`).
- The server draws no QR code and no receipt PDF: no production class uses openhtmltopdf, PDFBox or ZXing (ArchUnit), and none is on the test classpath (`ServerDrawingLibrariesTest`). Photos for news and projects stay converted on the backend for now (Jakub 2026-10-28: few administrators).

## Contexts and layers
- Contexts `content`, `donors`, `donations`, `contact`, `operations`, kernel `shared` (what each owns: `docs/system-overview.md`). Per context: `domain` depends only on the JDK's core and domain packages (no Spring, JPA, Bean Validation, logging, JSON or JDBC); `application` → domain; `infrastructure` → domain, application; `interfaces/rest` → application, domain and the `shared` infrastructure outside persistence, never a context's adapters or a port that persistence implements. Contexts never depend on each other, and `shared` never imports a context.
- ArchUnit holds this: `architecture/DddLayeringRulesTest` (anchored layers, every class in a layer, context slices derived from the packages, a domain on the JDK's core only, web-free application, controllers on no context infrastructure and no persistence port, no driven adapter on an application service, `MessageSource` only in adapters, `shared_kernel_must_not_depend_on_any_context`; each rule has a planted violation it must report), `FrameworkBindingRulesTest` (configuration binding and start-up triggers only in adapters) and `AdapterLibraryRulesTest` (each third-party library confined to its adapter). A new context needs no rule change, only its `includeAll` line in the master changelog; a new library gets its confinement rule.
- `architecture/StereotypeRulesTest` keeps each stereotype in its layer (meta-annotations included): controllers (named `…Controller`) and problem handlers in `interfaces/rest`, `@Service` in `application`, `@Repository`, `@Configuration` and `@Scheduled` in `infrastructure` (`@Configuration` also in `interfaces/rest`), no `@Transactional` in `interfaces` or `domain`, no injected field or setter, records for `@ConfigurationProperties`, requests, responses, request bodies and events (`LiveFeed` waits for the shared kernel cleanup), the SLF4J field `private static final Logger log` and no other logging API, and the console only for the first setup's code; each rule has a planted class it must report.
- No package depends on itself through other packages: `architecture/PackageCycleRulesTest` makes every package of `cz.novanadeje.app` its own slice, the root and every nested package included, and refuses a cycle; when two packages need each other, choose the direction that is right and move the piece both use into a package below both.
- Name the owning context before writing code. A concept that fits two contexts means a wrong boundary or a missing context: say so, never force it.
- Cross-context only through `shared`: an event record in `shared/application/event/` published with `ApplicationEventPublisher` and consumed with `@TransactionalEventListener` (`BEFORE_COMMIT` for a copy that must not be lost, `AFTER_COMMIT` + `@Async` for side effects like mail), or, for a read the consuming context cannot own, a port in `shared/application/<topic>/`, implemented in `shared/infrastructure/` when shared owns the data or library (`AdminActionTrail`) or by the owning context's infrastructure (`AlertRecipients`); name a new port in the PR. A context keeps its own copy of foreign data (`donor_record` in donations). Events used inside one context live in `<context>/application/event/`.
- `shared` holds only stable concepts: value objects (`Money`, `EmailAddress`, `VariableSymbol`, …), the `UuidV7` generator, the sealed `DomainException` family, the cross-context events and ports, and cross-cutting infrastructure (security, problem handling, rate limiting, clock, scheduling, async, branded e-mail, the audit log, `BuildRevision`).

## Domain
- Aggregates own their invariants and behaviour (no anemic entities); value objects are records that validate in the compact constructor; ids are records over `UUID`, generated by `UuidV7`. Domain services only for rules spanning aggregates (`PaymentPairingPolicy`).
- Failures are sealed `DomainException` subtypes with a `code`, declared in a domain package: `RuleViolation` 400, `Conflict` 409, `NotFound` 404, `AuthenticationFailure` 401, `AccessDenied` 403. `ApiExceptionHandler` maps them to problem+json with `problem.<code>.title|detail` from `i18n/messages_{cs,en}.properties`; add both texts with the exception.
- No class extends `IllegalArgumentException`, which the API answers 400 as the client's error, or `IllegalStateException`, which adapters catch generically around library calls (`architecture/DomainFailureRulesTest`); a failure of the code's own is a `DomainException` when the client caused it and a plain `RuntimeException` when the server did.
- `Clock` is injected, never `Instant.now()` (`architecture/TimeRulesTest` refuses every read of the system clock, a method reference included: a `now` of `java.time` without a `Clock`, a system `Clock` or `InstantSource` outside `ClockConfiguration`, `System.currentTimeMillis()`, a new `Date` or `Calendar` without arguments, `Calendar.getInstance`; `UuidV7.generate` takes the instant). The foundation's calendar is Prague's: the zone is `shared/domain/FoundationZone` (`ID` for `@Scheduled(zone = …)`, `ZONE`), never a `"Europe/Prague"` literal in the main Java sources (`TimeRulesTest`); donations' dates go through `FoundationCalendar`, `ReceiptCalendar` and `BankCalendar`.
- A case change names its locale (`toLowerCase(Locale.ROOT)`), because the default one changes the result (a Turkish locale lowers `I` to `ı`); `architecture/LocaleRulesTest` refuses `String.toLowerCase()` and `toUpperCase()` without one.
- `Optional` for return values and for record components that may be absent; never `null` for absence, never an `Optional` field in a class, no new `Optional` parameters. Immutable by default.

## Application
- One application service per use case, or per tightly related group of use cases on one aggregate (`NewsAdminService`); never a service spanning unrelated aggregates. Commands, queries and views are records; the layer knows no HTTP, JPA entity or template. Ports are interfaces here, implemented in infrastructure; an adapter translates its technology's failures and handles (a lost race, a file) into the port's own types. A driven adapter (one that implements a port of its own context's `application` or `domain`) builds on the domain and its technology and never calls an application service, which would turn the hexagon round (`DddLayeringRulesTest`, `driven_adapters_must_not_drive_a_use_case`); a use case is driven only from the driving side: a controller, a scheduler (`FioImportScheduler` also takes `BankImportRequests`, which only queue a run on its thread), a listener, or another context through a `shared` port, whose adapter in the owning context is that context's driving side (`FreshSecondFactorAdapter`). A failure only the driving side can see (the commit of a `REQUIRES_NEW` call) is caught there (`DonorRecordSynchronizer`). `architecture/ApplicationLayerRulesTest` refuses in `..application..` Spring's `dao`, `jdbc`, `orm`, `data` and `mail`, JPA, Hibernate, `java.sql`, `java.nio.file`, Jakarta Mail, Thymeleaf and `TransactionSynchronization*` (after-commit work goes through a port such as `AfterCommitWork`; `TransactionOperations` stays allowed); its one exception is `donations/application/receipt/AfterCommit` until the services of #612 move to the port.
- `@Transactional` on application services (`readOnly` for queries), never on controllers; an adapter's `@Transactional` only joins the use case's transaction (`Propagation.MANDATORY`, `architecture/TransactionRulesTest`, which checks the declared ones, not the transactions Spring Data's inherited `save` and `delete` open by themselves), and only Spring's `@Transactional` is used; short transactions. A use case that calls the network, decodes images or compares a password keeps that work outside the transaction and writes through a short transactional collaborator (`BankStatementRecorder`) or a `TransactionTemplate` (`UploadImageService`); its public method has no `@Transactional`. `architecture/PasswordHashingRulesTest` refuses a call or reference to `PasswordHasher` or `DonorConfirmations.confirm` in a `@Transactional` method or class, in a lambda of a method that runs a `TransactionOperations` or `CommittedRefusals` (so the hash before the transaction goes outside any lambda there), and in the application methods any of these call.
- Deliberate exceptions, each explained in `docs/system-overview.md`: receipt issuance freezes and signs under the donor lock, including the signatory's print portrait (`FoundationPeople.printPortraitOf`, also read inside `ReceiptSignatoryService`'s transactions); the monthly report sends inside its transaction, so a refused send leaves the month unsent.
- `REQUIRES_NEW` only where a separate transaction is the point: `DonationReceiptIssuer` (one transaction per issue), pairing called from an `AFTER_COMMIT` listener (`PaymentPairingService.pairPaymentsOf`, whose caller opens no transaction), the monthly report's figures (`MonthlyReportFigures`, a read-only `REPEATABLE READ` snapshot inside the `READ COMMITTED` sending transaction), the mail outage (`MailWatch`, so a refused send inside the monthly report's transaction, which rolls back, still opens the alert) and the audit of a refused backup key reveal (`BackupKeyRevealRefusals.record`, so the refusal stays whatever the reveal's transaction does). Each one is one more connection (`database.md`), and `architecture/TransactionRulesTest` refuses any other, by annotation or in code (`Propagation.REQUIRES_NEW`, `setPropagationBehavior`, a `DefaultTransactionDefinition` with a propagation); only the application opens a transaction in code (`TransactionTemplate`, `TransactionOperations`, `PlatformTransactionManager`).
- Retry-safe by design (`reliability.md`).

## REST (`<context>/interfaces/rest`)
- Paths `/api/<context>/...`; the administration under `/api/admin/<context>/...` (role `ADMIN`, `security.md`). Request and response records only; Jakarta validation on requests with `@Size` limits from domain constants; `Accept-Language` selects texts.
- Errors are problem+json: types `https://nfnn.cz/problems/<context>/<code>` (`ProblemTypes`); validation 400 with `errors[{field,message}]`; 401/403 from the security chain (never a Basic challenge); 429 `rate-limited` from a limiter built like `SignInRateLimiter` (per client address, counted before any hashing or work). A failure outside the `DomainException` kinds (an upstream 502) gets a handler in the context's `interfaces/rest` (`AdminReportProblemHandler`).
- A public endpoint needs its `permitAll` line in `ApiSecurityConfiguration`; everything else needs the donor JWT. Another donor's resource answers 404.
- Every endpoint change updates `docs/api-contract.md` in the same PR.

## API versions and compatibility (plan v3 2.3)
- Every `/api` answer names the server's build (`Nfnn-Revision`) and API generation (`Nfnn-Api`); the app names its own (`Nfnn-App`, `Nfnn-App-Api`); the server answers a write from another generation with 426 `app/update-required`, and the app holds its writes and offers to reload (`docs/system-overview.md`, shared and Frontend).
- Expand and contract: a new field, endpoint, table or meaning comes first, in a release the previous app and image keep working with; a field, endpoint, column or meaning is removed or changed only in a release after the last app, connector tool and image that used it are gone, never in the PR that stops using it (the schema half is Persistence below). A tab opened before a deploy is such an app, so "no longer used by the code on `main`" is not enough.
- A breaking API change (a removed or renamed field or endpoint the previous app calls, a changed meaning, a newly required request field, a new value in a closed list it switches on: an enum, a status word, a problem code it handles) and every contract step (nothing tells when the last tab of an older release is gone) bumps the generation in `VersionHeadersFilter.API_GENERATION`, `frontend/src/app/core/version/api-generation.ts` and `api-generation.json` together (`ApiGenerationTest`, `api-generation.spec.ts`) and names the break in the PR. A generation never goes back to a number it had. Prefer expand and contract, and bump on the contract step.
- Until the first real receipt (January 2027, plan v3 A2) a breaking step may skip expand and contract when its PR names it, but it still bumps the generation; from then on the whole rule holds, and the receipt path changes only by additions until 4 May 2027.

## Persistence
- Before changing the schema, a query, a lock, a transaction's isolation or the datasource, read `database.md` (it loads by itself only when such a file is opened).
- JPA entities and Spring Data repositories are package-private details of `<context>/infrastructure/persistence/` (the audit log in `shared/infrastructure/audit/`), behind the adapter that implements the domain repository and maps domain ↔ entity (ArchUnit); a test outside the package reads tables through `JdbcClient`.
- Liquibase: `db/changelog/<context>/NNN_<change>.xml` (next free number in that folder), changesets `id="NNN-<kebab-case>" author="nfnn"`, auto-included by the master. One file per logical change; a changeset touches only its own context's tables. Never edit, rename or move a file that is on `main` (its identity is id + author + path): fix forward with a new one.
- The previous image keeps working against the new schema, because a rollback is the older image (`reliability.md`). Safe: new tables, nullable columns, columns with a default that stays, wider types. Breaking: a new `NOT NULL` without a lasting default (add, fill and constrain in one changeset breaks an older image that inserts into the table), a dropped default, a new or narrowed `check`, unique or foreign-key constraint the older code can violate, a narrowed type, a rename or a drop. A breaking step lands one release after the code stops depending on it, named in the PR.
- Every changelog after the deployed revision runs over data (`MigrationOverDataTest`, which fails on a baseline table without a row, a baseline file out of master order, and a baseline revision (`BASELINE_REVISION`) other than `.github/deployed-revision`): the PR that sets `.github/deployed-revision` moves the baseline with it, to every changelog `git ls-tree -r --name-only <revision> backend/src/main/resources/db/changelog/` lists in `src/test/resources/migrations/baseline-changelog.xml`, in master order, with a row in `baseline-data.sql` for each new table and the new columns filled. A changeset that deletes rows on purpose names each table as a `ReviewedRowLoss`; once it is deployed, the baseline moves past it and retires the allowance, and a later changeset of its context waits for that.
- `admin_action` is append-only in the database: only a changeset (under Liquibase's lock) may rewrite the trail, and a test empties it only through `DatabaseCleaner` (`database.md`, Schema and migrations).
- Constraints state invariants (unique, partial unique, `check`). Index every query path that grows with the data; every foreign key leads a non-partial index (`ForeignKeyIndexTest`), so deleting a parent or reading its children never scans the child table. Types: `uuid` ids, `timestamp with time zone`, `date`, `varchar(n)` sized to the domain limit, `text` for long text, `bigint` amounts in minor units, `bytea` for binary content, singleton tables with `smallint id check (id = 1)`.
- `open-in-view: false`: load what the use case needs inside it; no lazy access afterwards.

## Configuration and operations
- `@ConfigurationProperties` records under `app.*`, validated at startup (fail fast: `JWT_SECRET` outside dev, invalid IBAN, empty optional values), live in infrastructure. A record the application needs is a plain record there, validated in its constructor, which the context's `infrastructure/config/<Context>ApplicationProperties` binds as a nested group (`@DefaultValue`, so a missing group still fails) and `<Context>ApplicationConfiguration` hands to the application as a bean; `StartupBindingSettingsValidator` checks stored settings against these bindings too. Reacting to the start is a driving adapter as well: an `ApplicationReadyEvent` listener lives in `<context>/infrastructure/startup` and calls an application method (`architecture/FrameworkBindingRulesTest`: no `org.springframework.boot`, framework lifecycle event or `Lifecycle` in application or domain). Production defaults in `application.yml`, dev overlay in `application-dev.yml`, local env names in `.env.example`. A value the server's operator must set is an `operations` `Setting` (first setup or `/sprava/nastaveni`, loaded under its env name by `DatabaseSettingsEnvironmentPostProcessor` in `prod`) with a label in `frontend/src/app/features/operations/setting-labels.ts`, never an env file line. Without `FIO_TOKEN` the import is off (`DisabledFioClient`, no scheduler bean). `architecture/RuntimeConventionRulesTest` holds the runtime conventions: ids only from `UuidV7`, configuration only from bound records (no `System.getenv`, system property or `@Value`), the JVM exited only by `ExitingApplicationRestarter`, every Caffeine cache with a maximum size or weight, every `HttpClient` with a connect timeout and `Redirect.NEVER`, and every `HttpRequest` with its timeout.
- Scheduled work shares one thread: every cron job has a property that `-` turns off (tests pin them off, `CLAUDE.md` Gotchas), catches its own exceptions, logs the outcome and tolerates a missed run; one-off timers (import follow-ups, log-level resets) run on the same thread, so nothing on it may block beyond its call's timeout.
- Logging: SLF4J `log` field; content as `security.md` Logs; `warn` for expected failures; `error` with the stack trace only for unexpected failures whose message cannot carry personal data; mail and SQL failures log the id and the exception class. An exception's message names the field and the rule, never the refused value, and the application reads no exception's message (`ApplicationLayerRulesTest`): an adapter hands it a closed value of its port (`docs/security-overview.md`, Logs). An `@Async` listener catches its own exceptions.
- E-mails are Thymeleaf fragments (`th:fragment="content"`) in `templates/email/<context>/` inside the shared `templates/email/layout.html`, composed by `BrandedEmails` from an `EmailDraft`: text and HTML parts, `th:text` only, inline styles with theme colours only, sender `app.mail.sender-email`, links from `app.site.public-url`. There is no receipt template: the browser draws the receipt (skill `receipt-template`).
