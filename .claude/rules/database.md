# Database rules (database audit 2026-11-06, #470)

What a change to the schema, a query, a lock, a transaction or the datasource must keep true, besides `backend.md` (Application, Persistence), `reliability.md` (retry-safe writes, "Every database wait ends") and `security.md` (Logs). The lock order, the session limits and the incident behind each issue number are in `docs/system-overview.md` (donors "Writes to the donor row"; donations, pairing; shared "Database sessions", "Schema migrations and the audit trail" and "Database incidents").

## Writes and locks
- Read-modify-write of an aggregate takes its row lock first and holds it to the commit, because the entities carry no `@Version` and Hibernate's UPDATE writes every updatable column back (#447). Use a `findByIdForUpdate` finder (`@Lock(PESSIMISTIC_WRITE)`, `for no key update` on PostgreSQL, so inserting a child row never waits for it). A check that counts sibling rows before acting (the last passkey, at most 10 passkeys, one open recovery) runs under the same lock.
- A column that only a conditional update may change is mapped `updatable = false` (`donor_device.ended_at`, `end_reason`; generated columns also `insertable = false`).
- A single-use secret, counter or step is spent by a conditional UPDATE whose row count is checked (`markUsed … where used_at is null` returns `boolean`; `SecondFactorRepository.recordUse` only moves the step forward, #441), never by load, change and save; a readable code is cleared in the same update (#485).
- Locks are taken in the documented order (`ADMINISTRATORS`, taken only by a revoke, then the donor row, then challenges, passkeys and second factor, then the donor's sessions lock, refresh tokens and devices, then push subscription writes, then the donations listeners' pairing lock and `donor_record`; pairing lock before `donor_record` in donations). A new lock or path takes its place in that order and `docs/system-overview.md` names it in the same PR; a path that cannot follow it is reordered, never left as an exception (#468, `SecondFactorRecoveryImportConcurrencyTest`). Several rows of one kind are locked in id order (`lockAllOfInIdOrder`, `lockSpentBeforeInIdOrder`), never in scan order (#453).
- Advisory locks only as constants of `shared/infrastructure/lock/AdvisoryLock`, each with a key of its own (`AdvisoryLockTest`, `AdvisoryLockRulesTest`; #452). The one-part form serializes a whole kind of write (`PAIRING`, `SETTINGS_CHANGES`, `ADMINISTRATORS`); the two-part form `acquireFor(entityManager, subject)` scopes it to a subject (`DONOR_SESSIONS`) or to a row that does not exist yet (`DONOR_EMAIL_ADDRESSES`, #450), whose key must fit an `int`. A session-level lock (`SCHEMA_MIGRATION`) is only tried, on a connection that is never pooled.
- A race on a unique key is serialized before the insert, so the loser answers as the winner's repeat (a double registration is 202 twice, a second confirmation of one address the existing 400, a second first-setup completion the existing 409 `operations/setup-completed`, #468), never a 500 from the constraint. `on conflict … do nothing` where a duplicate means "already done" (`MonthlyReportJpaRepository`, `PushKeyJpaRepository`).
- A sweep that deletes rows others may be about to reference locks its candidates `for update skip locked` and deletes those still unused in a second statement, or in one statement whose subquery takes them `for update skip locked`, never a plain `id in (select …)`, whose snapshot includes a row another transaction just changed (#455); every writer that links to such a row takes it `for key share` before its existence check (`MediaImageRepository.lockForUse`, #456). Deleting rows a running use case may hold (the erasure's challenges, recoveries and codes) uses `skip locked` too (`deleteAllOfWithoutWaiting`) and leaves the rest to the nightly cleanup.
- Replacing a row under a unique key updates the leftover row instead of delete-then-insert, because Hibernate flushes inserts before deletes (`JpaFormerSlugs`, #457).
- A check that guards an invariant over several rows or writers (at least one administrator left, the device still signed in, the mail password beside its server) runs after the lock every writer of those rows takes, and reads what it checks after taking it (#468). That read must not come from the persistence context, which returns entities loaded earlier with their old state: read the rows as values through a constructor expression (`SettingRow`) or take the lock before the first read.
- An adapter that runs its own locking SQL is a `@Repository`, so its failure becomes 503 `server-busy` through `ServerBusyHandler` (`PostgresPairingLock`, #449).

## Connections and waits
- The limits of `reliability.md` bind only the backend's pooled sessions, through pgjdbc `options` in `spring.datasource.hikari.data-source-properties`, never `ALTER ROLE` or a server setting (a restore as `novanadeje_app` would inherit it); Liquibase keeps its own connection (`MigrationDataSourceConfiguration`). A new datasource or connection sets the same `options` and `logServerErrorDetail=false` (`DatabaseWaitLimitsTest`).
- No connection is held across work that needs none (BCrypt, a network call, image decoding): split into short transactions as `DonorAuthenticationService.login` does, reading again and checking the row is unchanged before writing. Each `REQUIRES_NEW` under a caller's transaction is one more connection; count them (#449).

## Reading
- No query per row: load a page's related rows by their ids in one query and group them in Java (`PasskeyRepository.countByDonors`), `@BatchSize` on a collection read per row (`DonorJpaEntity.roles`), never `join fetch` with paging. A test with Hibernate statistics proves a page of many takes as many statements as a page of one (`DonorAdministrationSearchStatementsTest`, #465).
- Select only what is served: one photo variant, not the entity with every size (`findVariantAtLeast`, #456); never `bytea` or a frozen JSON document for a list or a sync. A summary a hot read needs from a large document is a stored generated column (`issued_receipt.gift_count`, `donations/027`, #489).
- On a hot path read rows through a JPQL constructor expression into a record (`IssuedReceiptSummaryRow`), not a Spring Data interface projection (#489).
- A large set loaded as entities inside a transaction that then runs more queries is mapped and detached (`JpaBankPaymentRepository.findUnpairedOrderedByBooking`, #451), because every auto-flush dirty-checks every managed entity.
- Human text a list shows or pages by (a name, a title) is ordered with the Czech ICU collation, `order by collate(x.name as …)` in HQL with the name `CzechCollation.NAME` in backticks (`DonorJpaRepository`, #461), then by a unique column, because the database's own `C.UTF-8` orders by code point; a list the browser sorts uses `Intl.Collator('cs')`, so both sides agree; a test over Czech names proves the order (`JpaDonorRepositoryTest`).
- Queries that must agree run in one `@Transactional(readOnly = true, isolation = REPEATABLE_READ)` snapshot (the sync services, `AdminOverviewService`). A transaction that also writes and whose `insert … on conflict do nothing` must answer "already done" stays `READ COMMITTED` (under `REPEATABLE READ` a conflicting row committed after the snapshot is a serialization failure), its reads in a read-only `REPEATABLE READ` `REQUIRES_NEW` collaborator (`MonthlyReportFigures`, #468).
- A cursor page over a column that can repeat continues from the last row's sort key and id, `(performed_at, id) < (:before, :beforeId)`, with an index on exactly those columns (#458).

## Schema and migrations
- `backend.md` Persistence says what the previous image survives. Hibernate's `validate` checks tables and column types, not keys, indexes or extra columns. When the new code can write a state the previous image misreads, prove it (run the previous adapter against the migrated schema in a throwaway test) and name the residual risk, what triggers it and how to clear it in the PR and in `deploy/README.md` "Návrat na předchozí verzi" (#479).
- Before adding or dropping an index, `EXPLAIN` the queries it serves on a schema migrated by the master changelog with realistic volumes, and put the plans in the PR (#486, #492). No plain index repeats the leading columns of another (`UnusedIndexTest`); every foreign key leads one that is not partial (`ForeignKeyIndexTest`, #462). A drop carries an `indexExists` precondition with `onFail="MARK_RAN"`.
- The changeset number is the next free one in its folder counting the open PRs (`gh pr list`, their `db/changelog/` files) (#479).
- A data changeset that rewrites rows gets a migration test from a changelog just before it (`ReportRecipientCountsMigrationTest`); it may rewrite `admin_action` only because Liquibase holds `SCHEMA_MIGRATION` (`AdminActionMigrationTest`).
- An invariant the domain keeps is a constraint too (#463): a column of a closed list or a value object's format gets a `check`, and a row that must agree with another row a composite foreign key to a `unique (id, …)` key of the other table (`donations/028`). Before adding one, list every value the code on `main` and the deployed revision (`.github/deployed-revision`) can write and every value an older changeset or code ever allowed (`git log -p` of the enum, value object and changesets); a value an older image writes or old rows hold stays allowed, even without a producer (`REFUNDED`, `MANUAL`), and where that cannot be proved the looser constraint is added. Add it `not valid` and `validate constraint` it in the same changeset, and give `migrations/baseline-data.sql` rows of each shape it must take (`MigrationOverDataTest`, whose baseline is the deployed revision, #462).
- A row that must not change after it is written (an issued receipt, the audit trail) gets a `before update or delete` row trigger and a `before truncate` statement trigger that name the columns that may change and the states they may leave (`issued_receipt_keeps_what_it_certifies`, `admin_action_append_only`); name the compared columns, not the whole row. Both pass a session that holds `SCHEMA_MIGRATION` (the `pg_locks` literal tied to `AdvisoryLock` by a test), so a changeset can still repair data; `DatabaseCleaner` empties the tables under `session_replication_role = replica`, and a test that plants a tampered row sets `set local session_replication_role = replica` first. No check that would refuse what the application deliberately detects and alarms about (a `receipt_signing_key` whose id does not match its key).

## Data that comes and goes
- Text from outside is normalised before it is stored: PostgreSQL refuses U+0000 in `varchar` and `text` (`BankTexts`, #464).
- A table of one-time secrets or sessions gets, in the same PR, a cleanup of spent and expired rows (#454), a delete in the erasure (`DonorErasureService`) and its line in `deploy/backup/revoke-restored-credentials.sql` or its reasoned exception (`RestoreRevocationSqlTest`). Every table, of this kind or not, is classified there exactly once (`ENDED_AS_SESSIONS`, `spend_one_time_secrets`, `KEPT_USABLE_AFTER_A_RESTORE`, `HOLD_NO_SESSION_OR_ONE_TIME_SECRET`), and the test fails on a new table in none (#462).
- A restore never takes back a decision made for security or GDPR after the dump (#459): a new table or column that holds a sign-in credential, a role, or something the erasure removes joins the facts of `deploy/backup/carry-forward.sql` (newest state wins, `RestoreCarryForwardSqlTest`), or the PR names why a restore may bring it back; the erasure itself is finished by `RestoredErasures` at the next start, so a new step of `DonorErasureService.erase` goes into its shared part, `removeAccessOf`, or into `completeRestoredErasure` too. `admin_action` is carried whole, so it stays append-only.
- Constraint violations keep their values out of every log: `logServerErrorDetail: false` on every connection (`ConstraintViolationLogTest`), and the database's own log is terse (`deploy/postgres/Dockerfile`, `deploy-ci.md`). `admin_action.details` is kept for good: counts and ids, never an e-mail address (#458).

## Operating the database
- The server side is in `deploy-ci.md` and `deploy/README.md` "Databáze": site data are queried as `novanadeje_app`, never as the superuser (#460); new clusters have data checksums and the built-in `C.UTF-8` locale, which a restore also gives its database (`DatabaseLocaleTest`, #461); `MigrationLockService` releases a changelog lock a dead backend left, so it is never deleted by hand; a PostgreSQL major is a deliberate PR with the dump and restore of "Nová hlavní verze PostgreSQL", never a Dependabot bump.

## Testing database changes
- A race is proved with two real transactions against PostgreSQL (`@IntegrationTest`, `TransactionTemplate`, an executor and latches): hold the first after its write, start the second, release once `pg_stat_activity` shows a backend with `wait_event_type = 'Lock'`, and assert the end state (`DonorRowLockConcurrencyTest`). It fails on the code before the fix with the error the issue names. Unit tests with mocks prove only the order of the lock calls.
- A budget for a slow path counts first what its regression changes, which no load moves: the statements (`Statistics.getPrepareStatementCount`, as a formula of the test's own data that states how they grow) and the entities the persistence context holds (`UnpairedBacklogPairingTest`, #737, Jakub 2026-11-14). A timed budget beside it asserts the fastest of several runs after warm-up, in the calling thread's CPU time (`ThreadMXBean`) where the work runs on that thread, so a loaded machine does not fail it, or relative to a plain read (`AdminDeviceSyncTest`); its message leads with the measured times, and its data hold what makes the path slow (#489).
