# Deployment and CI

Every operator step is in `deploy/README.md` (Czech); this file is what a change must keep true. Deploy is manual by decision (Jakub, 2026-10-17): a self-hosted runner with the Docker socket was rejected, so never run a PR's code on the server.

## Pipelines

How each workflow and job runs, step by step: `docs/system-overview.md` "CI in detail". What a change to them must keep true:

- `pr-check.yml` runs on every PR to `main` and on every push to `main` that changes more than `docs/`, `.claude/` or Markdown. Its `changes` job reads the PR's files and description through the API (`pull-requests: read`, no checkout): a docs-only PR skips every other job but `agent-context`, any other PR runs all of them, with no path filter per job (Jakub, 2026-10-29: a change to one area still runs every check). Its `gate` job passes only when every job succeeded on a change to code, or only `agent-context` ran and succeeded on a docs-only one, and refuses a skipped job on a change to code; `gate` and `roadmap` are what the ruleset `main` requires (since 2026-11-06: changes only through a PR merged by squash, no force push or deletion, nobody bypasses it; the workflows' default token is read-only and Actions may not approve a PR). A required check never comes from a workflow with `on.paths`, which would leave it pending for ever. On a PR a newer push cancels the running check; runs on `main` queue, so every push to `main` keeps its recording.
- A failed job does not cancel the others (that needs `actions: write` beside PR code), so read the first failed check run of the head commit rather than waiting for `gate`. Every job has a `timeout-minutes`; jobs are sized about as long as `release`, the longest, because every PR shares the account's runners and more jobs only add start-up time and queueing.
- `main-recording` (`actions: read`) checks out nothing, so no code of the PR runs beside that token; `compare-v2` needs only `contents: read` and fetches the commit in `BASELINE_COMMIT` anonymously, as `public-screens` does. The artifacts `backend-recording`, `frontend-inventory` and `mcp-inventory` of a push to `main` are kept 90 days as the next PRs' base (every other artifact 3 days). The backend uploads its test names, never its JUnit XML, whose captured output bypasses the transcript masking. `acceptance` fails when a feature wrote no result, and on a push to `main` it records twice and fails on a scenario whose recordings differ (`testing-regression.md`).
- `stack` first checks the compose invariants, so a broken one fails before any build: no `network_mode` or `links`, every service on the one network `nfnn-edge`, `no-new-privileges`, `read_only` and `cap_drop: ALL` everywhere with the reviewed `cap_add` list, the backend's `DB_USERNAME` `novanadeje_app` and `SPRING_PROFILES_ACTIVE` exactly `prod`, every `psql` and `pg_restore` of `deploy/backup/backup.sh` through `as_app` but the maintenance database's `server_psql` and `pg_restore --file=-`, every restore with `--no-owner --no-privileges`, and `deploy/postgres/own-by-app-role.sql` starting with `SET search_path = pg_catalog;` (more under Secrets and configuration). It then builds the five images and probes the running stack; the `echo` lines and `::error::` texts say what each probe asserts.
- The BuildKit layer cache and the Gradle cache are written only by runs on `main` (the `stack` job's `journeys` part, the `backend` and `acceptance` jobs); a PR only reads them, so nothing a PR builds reaches another run, and `images.yml` publishes without the layer cache.
- `release` ("Zkouška vydání") rehearses the deploy and its rollback through the reusable `release-rehearsal.yml` (`workflow_call`, `contents: read`), which the nightly calls too, from the revision in `.github/deployed-revision` (the one record of what the server runs, never a second variable; set it in the PR after each deploy's check) and from `latest`. The `latest` lane starts from the revision `ghcr.io/bzumik1/nfnn-mcp:latest` carries, because `images.yml` pushes the connector last, and each older image must exist under its short SHA and carry that revision label. No request reaches the real bank: the import runs against the fake Fio bank (`scripts/fake-fio.mjs` as `node` with `--read-only`, `--cap-drop ALL` and `no-new-privileges`, over https with a certificate made per run and trusted only through a copy of the older backend image's `cacerts`; its control port published only on the runner's loopback; the token a random value set in the first setup and masked in the log; any other token refused and counted), and `fioapi.fio.cz` resolves to the unroutable `192.0.2.1` in the rehearsal. A change to what the stack or the rehearsal does changes its probe. A change that cannot keep the older images working on its schema (a breaking changeset) changes this workflow in the same PR and says why.
- `agent-context` ("Kontext agenta") measures what every agent thread loads by the rules' `paths:` frontmatter, never a list of files, and fails on growth of the always-loaded rules, the skill and agent descriptions or the connector's tools and instructions, or on such a value no longer measured, unless the description has a line `Kontext agenta roste: <reason>`; nothing is committed, the base is measured in the job. The description reaches it only through the `changes` job (comments removed, the `Kontext agenta` lines, base64-encoded), its token is `contents: read`, and Dependabot's PRs and pushes to `main` only report.
- `visual` ("Vzhled") fails on a differing or removed shot the description's `Vzhled se mění: …` line does not name (`testing-regression.md`, Screens). The description reaches `visual` only through the `changes` job, which keeps only the lines that start with `Vzhled` and hands them on base64-encoded as an output; `visual`'s token is `contents: read`, and the description never reaches a shell except as that output. An edited description counts only after a push or "Re-run all jobs" (re-running the failed job alone reuses the old `changes` output).
- `suppressions.yml` ("Výjimky") is a tripwire, not a security boundary: it makes a relaxation of tests, checks or CI visible and declared with its reason in the PR description ("Done means" 4), and the PR diff and Jakub's review stay the boundary against a change obfuscated on purpose. It runs on `pull_request_target` (opened, synchronize, reopened, edited), never in `pr-check.yml`, whose copy a PR would run itself, with `contents: read` only and no `needs` or `if:`; it checks out the base, which supplies the guard, and the PR's head as data in a folder of its own, both with `persist-credentials: false`, diffs with `--text --no-ext-diff --no-textconv`, sets up Node with `package-manager-cache: false` and reads the description only through `env`, never `${{ }}` inside `run:`. Invariant: nothing of the PR's head ever runs there (no npm, build, script or action of it; its files are read as text only, and only regular files inside the head folder); a change that would run anything from the head is a security change. Judged whole, any change including removal or rename, one finding per file: the guard itself, every file under `.github/workflows/` and `.github/actions/`, the scripts that decide a required check (`CHECK_SCRIPTS` in the guard: a new script a required job runs or depends on joins it in the same PR), the build definition, the package manager's configuration, `t3.json` and every executable file; `.github/deployed-revision` stays out (it changes after every deploy). It blocks a merge only once Jakub adds `Výjimky` as a required check (source GitHub Actions) to the ruleset `main`, after it first shows on a PR. How it works, what it flags and its known limits: `docs/system-overview.md` "Suppression guard (Výjimky)".
- `nightly.yml`: its `report` job alone has `issues: write`, checks out nothing and runs only on `main`, so a run started by hand on a branch never opens, comments on or closes the issue; its table stays the same as `testing-nightly.md`'s.
- `safari.yml` (`contents: read` only) is no job of `pr-check.yml` and `gate` does not wait for it: read its run on a frontend PR before merging.
- `roadmap-check.yml` runs on every PR to `main` (no `on.paths`, so `roadmap` can be required) and again when the description is edited; one job without a checkout (`pull-requests: read`) skips Dependabot's PRs and passes a docs-only PR at once; it fails unless `docs/roadmap.md` changes or the description holds `Roadmapa: beze změny` on a line of its own (Jakub, 2026-10-28); a failed API call fails the step rather than reading as a missing update; the description reaches the shell only through an environment variable, never interpolated into the script.
- The Gradle cache comes from `pr-check.yml`'s `backend` and `acceptance` jobs on a push to `main`: `setup-gradle` writes it there, the only branch whose cache every PR can read (a cache written by a PR is visible to that PR only), and on a PR only reads it (its default on other branches). The image layer cache of the `stack` job works the same way, written by its `journeys` part only.
- Playwright's browsers: every CI job installs them with `frontend/scripts/install-playwright-browsers.sh [--only-shell|--no-shell] <browser>…` (from `frontend/` after `npm ci`), never `playwright install --with-deps`, because on 2026-11-05 apt's download of the font packages from `azure.archive.ubuntu.com` stalled and held every WebKit shard and `pwa` past its wait (#344). The script writes `/etc/apt/apt.conf.d/80-nfnn-ci-network` (`Acquire::Retries 5`, a 20 s `Acquire::http(s)::Timeout`, so a silent mirror fails over to the next one of the runner's `/etc/apt/apt-mirrors.txt`), then runs `playwright install-deps` as root and the browser download each up to 3 times under `timeout` (`PLAYWRIGHT_INSTALL_SECONDS`, 180 s, which also kills the apt it started; a normal install takes about 40 s); after a failed attempt at the system libraries it runs `dpkg --configure -a` and drops the Azure mirror from the list when another one remains. A job that waits for the install in the background waits up to 1200 s for its status file, so the script's own limits decide, and the jobs that install (`frontend`, `e2e`, `pwa`) have 30 minutes. `scripts/install-playwright-browsers.test.mjs` (in `npm run lint`) proves the retries, the cut-off and the mirror switch against a stub.
- The backend's log in CI: every check of `stack` and `release` reads the backend's log through `scripts/backend-log.sh <logs folder>` (the rotated `backend.log.<date>.<n>.gz` oldest first, then `backend.log`), never `backend.log` alone, because Logback rotates it at Prague midnight and by size, and a check that read only the current file lost the ready lines of the older images when a run of PR #318 crossed midnight (2026-11-06), and a check that a secret or an error is absent would miss it in a rotated file. Such checks pipe into `grep` without `-q` (`> /dev/null` or `-c`), so the reader is never cut off. `scripts/backend-log.test.mjs` proves the order and that the other services' logs are left out.
- `images.yml` runs on a push to `main` that changes `backend/`, `frontend/`, `deploy/backup/`, `deploy/postgres/`, `mcp/` or the workflow itself (a docs-only merge publishes nothing), and every Monday at 03:17 UTC so security fixes of the base images reach `latest` without a code change (Save in ZimaOS still pulls them). A run by hand (`workflow_dispatch`) on any other branch skips its job (`if: github.ref == 'refs/heads/main'`), so only reviewed code of `main` becomes `latest`. It pushes `ghcr.io/bzumik1/nfnn-backend`, `-frontend`, `-backup`, `-postgres` and `-mcp` as `latest` and the short SHA, with `--build-arg REVISION=<short sha>`. The packages are public (switched once on GitHub; a new package starts private and needs the switch once) so ZimaOS pulls without logging in; the images hold no secrets.
- Workflows: `persist-credentials: false`, minimal `permissions`, every action pinned to a full commit SHA with its version as the line's comment (`actions/checkout@<sha> # v7.0.1`; security audit 2026-11-06: a moved tag of a third-party action could otherwise run new code with the layer cache's write access on `main`), which Dependabot's GitHub Actions updates keep current. `dependabot.yml` covers GitHub Actions, npm in `/frontend` and `/mcp` and Gradle in `/backend`, and the Docker base images of the five build contexts (one grouped PR), monthly, the package ecosystems grouped, each with a `cooldown` of 7 days (plan v3, 2.5: a version update waits a week after its release, so a hijacked release is usually withdrawn before a PR takes it; security updates are not held back); the frontend and the connector ignore `@types/node` 27 and later, because CI and the images run Node 26 and the types follow the runtime; the frontend nginx stays on the stable branch (an even minor: 1.30), so the Docker update ignores the mainline minors 1.31, 1.33 and 1.35; `postgres` 18 and later are ignored too (issue #460), because a new major refuses the data folder of 17 (and 18 moved its path), so a major upgrade is a deliberate PR with the dump and restore of `deploy/README.md` ("Nová hlavní verze PostgreSQL"); versions in `extra[...]` of `build.gradle.kts` are not bumped by it.
- The repository is public since 2026-10-22: Actions minutes are free, and anything in a workflow log is public.

## ZimaOS install and update

- `deploy/compose.yml` is pasted unchanged into ZimaOS → App Store → Custom Install as the app "Nová naděje". It holds no `${...}`, no secrets and no per-server values, and no service reads an env file. A change to it reaches the server only by hand (uninstall + Custom Install with the new file): say so in the PR.
- New version: after "Publish Docker images" is green, Save the app's settings in ZimaOS without changes; that pulls the new `latest` and recreates the containers (Update and a plain restart keep the old image). Save reuses the compose of the last install. The settings in the database and `secrets/` survive both. Verify with `docker inspect` label `org.opencontainers.image.revision` or `nfnn_status`.
- The backend has `stop_grace_period: 75s` in both compose files (the PR check holds them to it): Spring drains requests for up to 30 s and then awaits a running bank import for up to 30 s (`spring.task.scheduling.shutdown`), and Docker's default 10 s would kill the import halfway.
- ZimaOS quirks the files are written around: it stores the compose without `$$` escapes (any `$` becomes an empty variable, so the compose holds no shell at all: logic lives in the images); it replaces the project name with `compose-<hash>` (every service sets `container_name: nfnn-<service>`); the app does not use the default `bridge` network, which every other app on the box shares: one named network `nfnn-edge` (fixed `name:` so the project name does not matter) gives service DNS to all five services, so no other container on the server reaches any NFNN service; ZimaOS attaches a service only to the first network it lists (a backend on a second, `internal: true` database network stayed on that one alone and nginx refused to start on the unresolvable `backend`, 2026-10-24), so every service lists exactly `edge` and a separate database network is not possible there; a new service joins `edge` too, never `network_mode` or `links:`, and every service sets `no-new-privileges` (the PR check enforces both and probes from the default bridge); a change of networks reaches the server only by uninstall + Custom Install; it starts the app once, so `depends_on` uses `service_started`, never `service_healthy` (the backend's entrypoint waits up to two minutes until Postgres accepts TCP connections, the backup script waits with `pg_isready`); it adds a memory reservation and silently never creates a container whose `limits.memory` is below it, so no limit goes under 256M; it re-types unquoted values as YAML (a date or a time becomes a timestamp), so schedule values stay out of the compose; port 8080 is taken on the box, the frontend publishes 8089.
- The local `docker-compose.yml` keeps a root `.env` (`.env.example`) for developers and is never used on the server. It must define every host `frontend/nginx.conf` proxies to (`backend`, `mcp`): nginx refuses to start on an unresolvable upstream, and CI does not start this file.

## Secrets and configuration

- No env file on the server (Jakub, 2026-10-23). Generated secrets live in `/DATA/AppData/nfnn/secrets/` (root, mode 600, created once, never overwritten, except `backup-key` when a restore from the first setup brings the old server's key, below, and `receipt-signing-key` after an administrator withdrew the server's own key: the backend writes the key id as `/restore/receipt-signing-key.renew` and restarts, and the entrypoint, before generating the secrets, keeps the seed as `receipt-signing-key.withdrawn-<key id>` (a time suffix if that exists) and removes the request; a request that names no 8-hex key id, or another key than the current seed's (computed with `openssl`, which `backend/Dockerfile` installs beside `age` rather than relying on the base image's copy), is removed and ignored, and the request only ever leads to a fresh random seed, so `app`, who can write `/restore`, cannot plant one; at every start the entrypoint computes the key id of each kept `withdrawn-` seed from its content and exports them for Java as `RECEIPT_SIGNING_KEYS_WITHDRAWN`, public ids only, so the backend keeps those keys withdrawn after a restore): `nfnn-postgres` (`deploy/postgres/`, on `postgres:17-alpine`) writes `db-password` (the superuser `novanadeje`) and `db-app-password` (the application role `novanadeje_app`), exports the first as `POSTGRES_PASSWORD` for the stock entrypoint only, and at every start, through a private instance on a temporary socket, sets both roles' passwords, creates `novanadeje_app` if missing (`app-role.sql`: login, no superuser, no role or database creation, no replication) and hands it the `public` schema and every table, view and sequence, while the database itself goes to (or stays with) the superuser and `CREATE` on it is revoked from the role, so the role can create no other schema, and sets the superuser's own `search_path` to `pg_catalog` (`ALTER ROLE CURRENT_USER SET`), so an operator's `psql -U novanadeje` never resolves a name to something the role planted (issue #460; site data are read as `novanadeje_app`, everywhere in CI too) (`own-by-app-role.sql`, which sets `search_path` to `pg_catalog` first: it runs as the superuser in a database whose `public` schema `novanadeje_app` can fill with operators and functions, and `<>(oid, regrole)` there would otherwise be picked over the built-in one), then touches `db-password.ready`; a new database gets the same from `/docker-entrypoint-initdb.d/nfnn-app-role.sh` and is initialised with data checksums and PostgreSQL's built-in `C.UTF-8` locale (`ENV POSTGRES_INITDB_ARGS="--data-checksums --locale-provider=builtin --builtin-locale=C.UTF-8"` in `deploy/postgres/Dockerfile`, never in the compose; an older cluster gets checksums only by hand and the locale for its site database at the next restore, whose `create_app_database` passes the same locale, `deploy/README.md`; `DatabaseLocaleTest` keeps the image, the backup script and the Testcontainers database equal, #461). `backend/docker-entrypoint.sh` waits for that marker, generates `jwt-secret`, `settings-key`, `receipt-signing-key` (the 32-byte Ed25519 seed that signs the receipts' verification QR codes, never in a backup or on another server) and `backup-key` (an age identity from `age-keygen`) and exports them with `db-app-password` as `JWT_SECRET`, `SETTINGS_KEY`, `RECEIPT_SIGNING_KEY`, `BACKUP_KEY`, `DB_PASSWORD` for Java only, so the backend is no superuser and its Java process (user `app`) can read no file in `secrets/`. The marker comes before a new database is even created, and neither initdb's server nor the password-sync instance listens on TCP, so the entrypoint starts Java only once the host and port of `DB_URL` accept a TCP connection (at most `DATABASE_PATIENCE_SECONDS`, 120 s, then it starts anyway and fails as before); without that wait a fresh install's backend reached the database between initdb and the real server, exited and restarted (three failed PR checks, 24.–28. 10. 2026); `nfnn-backup` waits for the same marker and reads `db-password` and `db-app-password` read-only inside its script: it dumps and creates, renames and drops databases as the superuser (`PGPASSWORD`, exported only inside the script, from the maintenance database `postgres` apart from `pg_dump`), and does everything else, every restore and every query of a site database, as `novanadeje_app` (`as_app`, the password passed to each command, never exported), below in Backups and rollback. Losing the folder means a new database password (synced again), new sign-ins and the sealed settings typed again.
- Every other per-server value is a setting stored in the database (`operations_setting`, contract "Settings and the first setup"): entered in the first setup at `/prvni-nastaveni`, changed at `/sprava/nastaveni`, loaded under its env name by the `prod` profile before the context starts. A new per-server value is a new `Setting` and a label in `setting-labels.ts`, never an env line; values that only a developer changes stay in `application.yml`.
- The compose's `environment:` holds only fixed values: `SPRING_PROFILES_ACTIVE`, `DB_URL`, `DB_USERNAME`, `JAVA_TOOL_OPTIONS`, `TZ`, the database names and `PGHOST`/`PGUSER`/`PGDATABASE`.
- The `stack` job fails when `deploy/compose.yml` holds a `$` or names a secret key (`POSTGRES_PASSWORD`, `PGPASSWORD`, `DB_PASSWORD`, `JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `RECEIPT_SIGNING_KEY`, `MAIL_PASSWORD`, `FIO_TOKEN`), when a service reads an `env_file`, when a service but the frontend publishes a port, when `secrets/` is mounted anywhere but postgres, backend and (read-only) backup, when postgres, backup, mcp or frontend sees `JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `RECEIPT_SIGNING_KEY`, `DB_PASSWORD`, `FIO_TOKEN` or `MAIL_PASSWORD` (in its configuration or its main process's environment), when a service uses `network_mode` or `links`, sits on another network than its own, or lacks `no-new-privileges`, `read_only: true` or `cap_drop: [ALL]`, when the `cap_add` lists differ from the reviewed ones, or when the backend's `DB_USERNAME` is not `novanadeje_app` or its `SPRING_PROFILES_ACTIVE` not exactly `prod` (without a profile the backend would start as dev, with the public development keys accepted and the stored settings unread). Its first setup also fails when `secrets/receipt-signing-key` is not 32 bytes of Base64 owned by root with mode 600, when `backend.log` lacks `Receipt signing key <id> registered and published`, or when the seed appears in `backend.log` in any of its spellings (Base64 with or without padding, Base64url, hex). After the restore probes it plants `receipt-signing-key.renew` naming `00000000` as `app`, restarts the backend and fails unless the seed is unchanged, nothing is kept aside and the entrypoint said it ignored the request. After the photo uploads the administrator withdraws the server's own key through `POST /api/admin/donations/receipt-signing-keys/{keyId}/withdrawal` with a fresh TOTP code, and the job fails unless the answer says `restarting`, mailpit holds the notice, the backend restarted, the request is gone, the old seed is kept as `receipt-signing-key.withdrawn-<id>` (root, 600), a new 32-byte seed replaced it, the container log carries the entrypoint's warning, `backend.log` registers a key with another id, Java's environment holds `RECEIPT_SIGNING_KEYS_WITHDRAWN` with the old id, `/api/donations/receipt-keys` lists the old key `revoked` and the new one `active`, and neither seed appears in `backend.log` or the container log in any spelling.
- Bind mounts under `/DATA/AppData/nfnn/`: postgres data; `secrets/` (postgres and backend read-write, backup read-only); `backups/` (read-write in backup; read-only in the backend except `backups/requests/`); `restore/` (read-write in backup and in the backend, which streams a backup uploaded in the first setup into it); `logs/` (read-write in backend, backup, frontend and mcp). The receipt signature image lives in the database (uploaded at `/sprava/nastaveni`), so no `config/` folder is mounted.
- Hardening (Jakub 2026-10-24): every service runs with a read-only root file system, `tmpfs` where it writes (`/tmp` everywhere, postgres `/var/run/postgresql`, the frontend `/run` and `/var/cache/nginx`; sizes capped where an upload could fill memory), and `cap_drop: ALL` plus only what its entrypoint needs: postgres `CHOWN DAC_OVERRIDE FOWNER SETGID SETUID` (the stock entrypoint fixes its folders and drops to `postgres`), backup `DAC_OVERRIDE FOWNER` (root in folders the backend owns: `/restore`, `/logs`), backend `CHOWN SETGID SETUID` (hands `/logs` and `/restore` to `app`, `setpriv`), mcp `CHOWN DAC_OVERRIDE FOWNER SETGID SETUID` (rotates its log in `/logs`, `su-exec`), frontend `CHOWN DAC_OVERRIDE NET_BIND_SERVICE SETGID SETUID` (port 80, workers as `nginx`). A new write path is a new `tmpfs` or volume, a new capability is reviewed in the PR check's list. Every `tmpfs` is `noexec` (Docker's default, kept), so a native library a Java library would extract into `/tmp` and load (libwebp of `webp-imageio`) is extracted at image build time into a read-only folder of the image and loaded from there (`/app/native`, `java.library.path`); never mount a `tmpfs` with `exec`. Without `DAC_OVERRIDE` root in the backend cannot write into `/restore` (owned by `app`): a probe or script writes there as `app`. With every capability dropped `/proc/1/environ` is unreadable to a plain `docker exec`, so the secret probe uses `docker exec --privileged` (nginx writes its title over its environment, so its check reads nothing). The frontend's `/logs` volume also carries the operator's service worker switch `service-worker.off` (slice 2.4, `deploy/README.md`): nginx's workers (`nginx`) must be able to stat it, so the folder keeps search permission for others, and a change that drops the frontend's `/logs` volume turns the switch off silently.
- Privileges: `backend/docker-entrypoint.sh` starts as root to read and generate `secrets/`, to wait on `/restore` and to hand `/logs` to `app`, then `exec setpriv --reuid=app --regid=app --clear-groups` into Java (PID 1), so the Dockerfile has no `USER` line; `mcp/docker-entrypoint.sh` starts as root for its log rotation and `exec su-exec node` into Node.

## Logs

Operator notes are in "Logy" in `deploy/README.md`; `CLAUDE.md` says how Claude reads them (the connector, through the backend; nothing serves the folder from outside).

- The backend logs to the console and, in the `prod` profile (`application-prod.yml`), to `${LOG_FILE:/logs/backend.log}` with Logback rotation (10 MB, 14 days, 200 MB cap); the backup script appends to `/logs/backup.log` (not rotated, a few lines a day); the frontend nginx writes `/logs/nginx-access.log` (format `anonymous`: time, method, path without the query string, status, bytes, request and upstream time, never the client address; `anonymous_unsized`, the same without the bytes, for `POST /api/donations/receipts/status`, whose five answers differ only in length (slice 1.8), and `POST /api/donors/devices/status`, whose five answers do too (slice 2.11, its own location with a 1 kB body cap like the receipt status); the console keeps the image's `main` format); the connector appends to `/logs/mcp.log` (`LOG_FILE`).
- The access and connector logs rotate by the UTC day with `rotate-log.sh` (one script, copied into `frontend/` and `mcp/` because they are separate build contexts; the PR check `cmp`s the copies): at start it moves a file left from an earlier day to `<file>.YYYY-MM-DD.gz`, then a background loop does that every midnight, has the writer reopen, and deletes archives older than 14 days (`LOG_KEEP_DAYS`). A folder the backend cannot write only costs the file log.
- The revision: `images.yml` passes `--build-arg REVISION=<short sha>`, the Dockerfile exports it as `APP_REVISION`, `app.build.revision` (`BuildProperties`, default `dev`) reaches `/actuator/info` as `build.revision` and the startup line `Backend revision … is ready` (`BuildRevision`). ## Backups and rollback

Operator steps are in "Zálohy" in `deploy/README.md` (Czech).

- What runs: the `backup` service is `ghcr.io/bzumik1/nfnn-backup` (`deploy/backup/Dockerfile`: `postgres:17-alpine` plus `backup.sh` as the entrypoint; 256M limit, `secrets/` read-only, `PGHOST=postgres`). At start the script waits for `pg_isready`, recovers an interrupted restore, restores a dump from `/restore` (below), handles waiting requests and dumps once; then it loops every 10 s (`POLL_SECONDS`, set only in the PR check's copy of the compose): requests, the schedule (`load_schedule`: `/backups/requests/schedule` from the backend, `backup_time=HH:mm`, `test_restore_day=1-7`, `test_restore_time=HH:mm`, each invalid or missing value falling back to its default, the plan in use written to `/backups/status/schedule` and logged when it changes; a time moved later than now resets that day's mark so the run happens again), the day's dump once the clock has reached the planned time, default `03:00` (`BACKUP_TIME`, `TZ: Europe/Prague`, a time that exists exactly once on both DST changes; a request running at 03:00 only delays it, and the dump at start counts for a day started after 03:00) and on the planned day once it has reached the planned time, default Sunday `04:00` (`TEST_RESTORE_DAY=7`, `TEST_RESTORE_TIME`; at start a Sunday whose `status/test-restore` is not from today catches up) a test restore of the newest dump into `nfnn_restore_test` (owned by and restored as `novanadeje_app`, below; tables and applied changesets counted, both must be above 0, and every table must hold as many rows as its `COPY` block in the dump, `compare_rows`; then dropped). The schedule defaults live in the script, never in the compose; the plan itself is chosen on `/sprava/zalohy` and stored in `operations_backup_schedule`, and the backend writes it again at every start (`BackupSchedulePublisher`).
- Encryption (Jakub, 2026-10-28: backups are always encrypted): `pg_dump` pipes into `age --encrypt --identity /secrets/backup-key`, so no plain dump is written to `/backups`; the script waits for a valid key (`age-keygen -y`) before anything else, a dump without one fails, and older plain `nfnn-*.dump` files are encrypted in place at start. A test restore or restore decrypts into a pipe (`restore_into`, `dumped_rows`) and never writes a plain copy, because `/backups` is what is copied off the server; the PR check fails on any `*.dump` or `work` in it. The key is shown to the administrator only in the first setup and on `/sprava/zalohy` with a fresh second factor (`security.md`), never in a log, a status file or the connector; the PR check asserts that.
- A dump goes to `nfnn.dump.age.part` and is renamed `nfnn-YYYY-MM-DD_HHMM[-rucni|-pred-obnovou].dump.age` only on success; `nfnn-*.dump.age` older than 30 days are deleted after each dump. Compression `zstd:19` (Jakub, 2026-10-22: the highest that works): it is the highest level that fits the 256M limit (20 needs 167 MB for no gain, 22 is OOM-killed); a higher level or a lower memory limit is measured first, and the PR check fails unless the decrypted dump reads `Compression: zstd`. `pg_restore` detects the compression, so older gzip dumps still restore.
- Status: every run writes `/backups/status/{backup,test-restore,restore}` (`key=value`: `outcome`, `started_at`, `finished_at`, `file`, `size`, `tables`, `request`, `admin`, `error`, and for a restore `sessions_ended`, `one_time_secrets_spent`, `erasures_carried`, `credentials_carried`, `roles_carried`, `admin_actions_carried` and `receipt_numbers_skipped`; written as `.part` and moved) besides the log line. The backend reads them (`operations/infrastructure/backup/FileBackupStore`, `StatusFiles`, `BackupHealth`), so a renamed key or file is an API change made in both places with their tests.
- Requests: `/backups/requests/` (`chmod 1777`; leftover `.backup` and `.test-restore` files are removed at start, a `.restore` file is kept) takes the `schedule` file (kept, read on every pass), empty `<id>.backup` and `<id>.test-restore` files and `<id>.restore` files with the lines `source=backup|upload`, `file=`, `admin=`. The backend drops them for `POST /api/admin/operations/backups/requests`, `POST .../backups/{file}/restore` and the first setup's `PUT /api/operations/setup/restore`; the script removes the file first (a restore writes `/backups/status/restore.running` before that) and records the id as `request=` (and `admin=` for a restore). It refuses a `file=` with a `/` or a leading dot: `backup` names a `nfnn-*.dump.age` in `/backups`, `upload` a `*.upload` in `/restore` (deleted afterwards; uploads older than 60 minutes are deleted anyway). An encrypted upload comes with the key it was made with as `<id>.key`; the script copies it into its `tmpfs` first, and after a successful restore records its recipient in `/backups/status/adopted-key` and writes it as `/restore/backup-key.adopt` (noclobber, after removing whatever stood there); `backend/docker-entrypoint.sh`, after its restore wait, makes it `secrets/backup-key` only when `age-keygen -y` of it equals the record (the backend mounts `/backups` read-only, while `app` can write `/restore`), keeps the previous one as `backup-key.replaced-<time>`, so the new server keeps reading the old dumps; the PR check plants a key as `app` and expects it ignored, and restores an upload with its own key and expects it adopted.
- No superuser over the site's data (security audit 2026-11-06): the backend owns the live tables, writes `/restore` and the request folder and holds the backup key, so a hole in it controls every dump the script restores and every row it reads. Whatever a dump or the site's data can run (a TOC entry, a trigger, a check, a default, an index expression, a function in a view) must never run as the superuser, or the next restore or the Sunday test restore would give it a shell as `postgres` (`COPY … TO PROGRAM`). So the staging and test databases are created from `template0` for `novanadeje_app`, which takes their `public` schema in its own session before the superuser takes the database itself from `postgres` (`create_app_database`, so a dump can create no other schema and set nothing on the database), `restore_into` runs `pg_restore --no-owner --no-privileges` logged in as that role (`SET ROLE` or `--role` is no boundary: a TOC entry can `RESET ROLE`) and then `ALTER SCHEMA public OWNER` to it in the same role, and every later query of a site database runs as that role too (table and row counts, `release_liquibase_lock`, `revoke_restored_credentials`, the receipt-number check, `keep_sequences_ahead`'s reads and `setval`s, `carry_forward` on both the retired and the staging database, `database_is_empty`). The superuser keeps only `pg_dump` (it reads every object whatever its owner and runs no function of the data: PostgreSQL 17 restricts it to tables, `restrict_nonsystem_relation_kind`) and the database-level steps from `postgres` (`createdb`, `dropdb`, rename, `ALLOW_CONNECTIONS`, `pg_terminate_backend`, the `pg_database` lookups). The backup no longer runs `own-by-app-role.sql`: `novanadeje_app` owns everything it restored. The `keys` part of `stack` proves it: as `app` it uploads, with its own key, a dump whose table checks its rows with a function that runs `COPY … TO PROGRAM 'touch /tmp/nfnn-pwned'`; as `novanadeje_app` it plants the same check in the live data, takes a backup, removes the check and test-restores that backup; and it plants a statement trigger on `donor_refresh_token` that runs the program, takes a backup, removes it and asks for that backup's restore. Each must fail with `permission denied to COPY to or from an external program` in its `.err` file, no `/tmp/nfnn-pwned` may exist in `nfnn-postgres`, the live rows, the server's backup key and the adoption record must be unchanged, nothing of the upload or a staging or test database may be left, and a clean backup must test-restore again. A plain upload (`PGDMP`) and a plain dump in the restore folder stay accepted (the contract keeps them for dumps from before the encryption, and `app` could encrypt to the server's key anyway); they restore as `novanadeje_app` like any other. The backup container cannot learn unforgeably whether the first setup is still open, so a `source=upload` request is taken at any time and the role is the boundary.
- Restores (Jakub 2026-10-23: only through the GUI, foolproof): `restore_dump` takes a `-pred-obnovou` dump when `public` has tables, creates `nfnn_restore_staging` for `novanadeje_app`, runs `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges` into it as that role, refuses it without tables or rows in `databasechangelog` (not a dump of this site), releases a Liquibase lock caught in the dump (`release_liquibase_lock`; the startup dump can run while the backend migrates), ends every session and spends every one-time secret in staging in one transaction (`revoke_restored_credentials` with `revoke-restored-credentials.sql`: every refresh token revoked, connected applications' too, every device ended as `EXPIRED`, plan v3 2.10, every push subscription deleted, and every unused reset or verification link, challenge and authorization code marked used, 2.34 (the 1 Kč recovery stays open), because a dump holds them as they were when it was taken; the counts go into the status file and the `BACKUP_RESTORED` record) and only then swaps: `ALLOW_CONNECTIONS false` on the live database, `pg_terminate_backend` and `ALTER DATABASE … RENAME` live → `nfnn_restore_retired` (retried 30 × 1 s, then connections are allowed again and the restore fails), `keep_sequences_ahead` (connections back on for the retired name, which no client uses, then every `public` sequence of staging set to the higher of its own and the retired value), `carry_forward` (`carry-forward.sql`, issue #459: the retired database's facts piped as JSON rows from `COPY … TO STDOUT` into one transaction on staging, never through a file, refused unless their closing row counts what arrived; for donors in both, the newest password hash, passkeys, second factor and roles win, an erasure since sets `erased_at` for the backend to finish at its start (`RestoredErasures`), every `admin_action` row staging lacks is inserted, and the receipt sequence moves 1000 further when the retired database holds no `issued_receipt`; the five counts go into the status file and `BACKUP_RESTORED`), staging → live (once; on failure the retired one is renamed back), then drops the retired one. A failure drops staging and leaves the live database as it was. At start `recover_interrupted_restore` removes a stale marker, renames `nfnn_restore_retired` back when the live database is missing, drops staging and deletes `*.upload.part`. `nfnn-postgres.sh` syncs the role password over `-d postgres`, so it works mid-swap. `backend/docker-entrypoint.sh` waits while the marker, a `*.restore` request or a `/restore/*.dump[.age]` exists and deletes a request older than 5 minutes when no marker exists, so Liquibase never runs against a swapped database and an unattended request never blocks the backend for good.
- A restore brings back everything as of the dump except the sequences, which never go back (and move 1000 further when the replaced database holds no issued receipt, as on a new server after a loss), and what the replaced database decided for security or GDPR since (the carry-forward above: erasures, credentials, roles, the audit trail): receipts issued since the dump disappear, but their numbers are never issued again (a new download gets a new number). Say so wherever a restore is offered. The `stack` probe (part `journeys`) erases a donor, changes a password and removes an administrator after the dump and expects all three to stay, with the audit entries written since, the donor registered since gone and the receipt numbers 1000 past the higher of the two values.
- Restore folder (by hand): `/restore` with exactly one `*.dump.age` (this server's key) or plain `*.dump` at container start (restored as `novanadeje_app` like every restore). Into an empty database it is restored as it is; into a non-empty one only when named `*.force.dump.age` (or `*.force.dump`; any other name is renamed `.skipped`); more than one dump skips them all; the same `restore_dump`; the file gets `.done` or `.failed` appended (the data stayed, the backend starts).

- Where: `/DATA/AppData/nfnn/backups/` on the same disk as the database, the only copy; the off-site copy is postponed until after the launch on nfnn.cz, Jakub would like it on iCloud (2026-10-23). The dump holds the settings (secrets sealed) and the receipt signature; `secrets/` is not backed up, but the database carries `settings-key` wrapped under a key derived from `backup-key` (`operations_carried_settings_key`, Jakub 2026-10-29), so after a restore on a new server that adopted the backup key `MAIL_PASSWORD` and `FIO_TOKEN` are read and sealed again under the new `settings-key`; only an older dump or one restored without the backup key leaves them unreadable, and `/sprava/nastaveni` names them. - Rollback: the older short-SHA image tag in the ZimaOS app settings; a restore only when the newer version made a breaking schema change (`backend.md`, Persistence).
