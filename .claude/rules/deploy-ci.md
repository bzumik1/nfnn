# Deployment and CI

Server setup and every operator step are in `deploy/README.md` (Czech); modelled on `bzumik1/kocarky`. Deploy is manual by decision (Jakub, 2026-10-17): a self-hosted runner with the Docker socket was rejected, so never run a PR's code on the server.

## Pipelines

- `pr-check.yml`, every PR to `main` except one that changes only `docs/`, `.claude/` or Markdown (`deploy/README.md` still counts: a backend test reads its SQL), GitHub runner: `./gradlew build` (Testcontainers works there), `npm run format:check`, `npm run lint`, `npm run lint:styles`, `ng test`, `npm run build`, Playwright e2e, `npm run check` in `mcp/` (Prettier, `tsc`, Vitest), then the six images built (`backend/`, `frontend/`, `deploy/backup/`, `deploy/postgres/`, `deploy/ops/`, `mcp/`) and `deploy/compose.yml` started without `cloudflared` (it needs a real tunnel token) and probed: the generated `secrets/` files are root's with mode 600; the first setup answers `codeRequired` false straight from the network and true with `X-Forwarded-For`, refuses a wrong code with 403, takes the code from `docker logs` (never from `backend.log`), stores seven settings, the backend restarts healthy and logs `Loaded 7 stored settings`, the tunnel token file appears, the stored token reads `v1:…` without the plain value, and a second setup answers 409; a role password changed behind the database's back is reset to `secrets/db-password` by a restart of `nfnn-postgres`; a dump exists after the start and reads `Compression: zstd`, a request file dropped from inside the backend container yields a `-rucni` dump and a test restore with a table count, then a `.force.dump` in `restore/` is restored on a restart (marker row gone, `-pred-obnovou` dump written, file renamed `.done`), both log files exist, the log reader lists them, serves byte ranges and passes `/info` and `/health`, publishes no port and gets no secret, Java runs as `app`, the frontend answers, and the MCP connector (`nfnn-mcp`, no port, no secret, no `env_file`, only the read-only logs mount) answers 401 with `WWW-Authenticate … resource_metadata=` on `/mcp`, serves the protected resource metadata (`resource`, `authorization_servers`, both scopes) under the issuer the backend's metadata names, and reports `UP` on `/health` once it has discovered that issuer. Its stack job fails when `deploy/compose.yml` names a secret key (`POSTGRES_PASSWORD`, `PGPASSWORD`, `DB_PASSWORD`, `JWT_SECRET`, `MAIL_PASSWORD`, `FIO_TOKEN`, `TUNNEL_TOKEN`), when a service reads an `env_file`, when `secrets/` is mounted anywhere but postgres, backend and (read-only) backup, when `cloudflared` mounts more than the read-only tunnel folder, when postgres, backup, ops or mcp receives a backend secret in its environment, or when the compose holds a `$`. Each job has a `timeout-minutes`; `setup-gradle` writes its cache from PRs too (`cache-read-only: false`), because no Gradle job runs on `main` to fill one.
- `images.yml`, push to `main` that changes `backend/`, `frontend/`, `deploy/backup/`, `deploy/postgres/`, `deploy/ops/`, `mcp/` or the workflow itself (the image build contexts; a docs-only merge publishes nothing): pushes `ghcr.io/bzumik1/nfnn-backend`, `-frontend`, `-backup`, `-postgres`, `-ops` and `-mcp` as `latest` and the short SHA, with `--build-arg REVISION=<short sha>` so the backend knows its revision (`APP_REVISION`, `/actuator/info`, the startup log line). The packages are public (switched once on GitHub, not by the workflow; a new package such as `nfnn-postgres` may start private and then needs the switch once) so ZimaOS pulls without logging in; the images hold no secrets.

## ZimaOS install and update

- `deploy/compose.yml` is pasted unchanged into ZimaOS → App Store → Custom Install as the app "Nová naděje". It holds no `${...}`, no secrets and no per-server values, and no service reads an env file. A change to it reaches the server only by hand (uninstall + Custom Install with the new file): say so in the PR.
- New version: after "Publish Docker images" is green, Save the app's settings in ZimaOS without changes; that pulls the new `latest` and recreates the containers (Update and a plain restart keep the old image). Save reuses the compose of the last install, so a changed compose needs uninstall + Custom Install; the settings in the database and `secrets/` survive both. Verify with `docker inspect` label `org.opencontainers.image.revision`.
- ZimaOS quirks the files are written around: it stores the compose without `$$` escapes (any `$` becomes an empty variable, so the compose holds no shell at all: the backup logic lives in the `nfnn-backup` image); it replaces the project name with `compose-<hash>` (every service sets `container_name: nfnn-<service>`); it runs the app on the default `bridge` network without service DNS (every service sets `network_mode: bridge` and reaches others through `links:`: backend → postgres, backup → postgres, frontend → backend and mcp, mcp → backend; a new service that talks to another needs a `links:` entry); it starts the app once, so `depends_on` uses `service_started`, never `service_healthy` (the backend restarts until Postgres accepts connections, the backup script waits with `pg_isready`); it adds a memory reservation and silently never creates a container whose `limits.memory` is below it, so no limit goes under 256M; port 8080 is taken on the box, the frontend publishes 8089.
- ZimaOS used to copy env files' values into its stored compose and re-type them as YAML (an unquoted `2025-01-01` reached the backend as `2025-01-01 00:00:00 +0000 UTC`); with no env files left that no longer happens, but `BankImportProperties` still accepts that form of `FIO_HISTORY_FROM`.

## Secrets and configuration

- No env file on the server (Jakub, 2026-10-23). Generated secrets live in `/DATA/AppData/nfnn/secrets/` (root, mode 600, created once, never overwritten): `nfnn-postgres` (`deploy/postgres/`, on `postgres:17-alpine`) writes `db-password`, exports it as `POSTGRES_PASSWORD` for the stock entrypoint only (never in the compose), sets the role's password to it through the local socket at every start (so a server migrated from `db.env` takes the new one) and touches `db-password.ready`; `backend/docker-entrypoint.sh` waits for that marker, generates `jwt-secret` and `settings-key` and exports the three as `DB_PASSWORD`, `JWT_SECRET`, `SETTINGS_KEY` for Java only; `nfnn-backup` waits for the same marker and reads `db-password` read-only into `PGPASSWORD` inside its script. Losing the folder means a new database password (synced again), new sign-ins and secrets in the settings that must be typed again.
- Every other per-server value is a setting stored in the database (`operations_setting`, contract "Settings and the first setup"): entered in the first setup at `/prvni-nastaveni`, changed at `/sprava/nastaveni`, loaded under its env name by the `prod` profile before the context starts. A new per-server value is a new `Setting` (with its group, format and length) and a label in `setting-labels.ts`, never an env line; values that only a developer changes stay in `application.yml`.
- The compose's `environment:` holds only fixed values: `SPRING_PROFILES_ACTIVE`, `DB_URL`, `DB_USERNAME`, `JAVA_TOOL_OPTIONS`, `TZ`, the database names and `PGHOST`/`PGUSER`/`PGDATABASE`. `JWT_SECRET` has a default only in `application-dev.yml`; any other profile without it stops at startup (the entrypoint always provides it in the image).
- The tunnel token: the backend writes the stored `TUNNEL_TOKEN` to `/DATA/AppData/nfnn/tunnel/token` at startup (`TunnelTokenWriter`) and `cloudflared` runs `tunnel --no-autoupdate run --token-file /tunnel/token` with that folder read-only; after a token change `cloudflared` keeps the old connection until it restarts (README).
- Bind mounts under `/DATA/AppData/nfnn/`: postgres data; `secrets/` (postgres and backend read-write, backup read-only); `tunnel/` (backend read-write, cloudflared read-only); `backups/` (read-write in backup, read-only in the backend except `backups/requests/`, which the backend writes request files into); `restore/` (read-write in backup, read-only in the backend, whose entrypoint waits while a `*.dump` or `*.dump.failed` lies there); `logs/` (read-write in backend and backup, read-only in `ops` and `mcp`); and `config/` mounted read-only as `/config` in the backend (meant for the receipt signature image, which has no setting yet).
- The local `docker-compose.yml` keeps a root `.env` (`.env.example`) for developers; it is never used on the server.

## Logs for Claude

Operator steps are in "Logy pro Clauda" in `deploy/README.md`; `CLAUDE.md` says how to read them. What a change must keep true:

- The backend logs to the console and, in the `prod` profile (`application-prod.yml`), to `${LOG_FILE:/logs/backend.log}` with Logback rotation (10 MB, 14 days, 200 MB cap); the backup script appends its lines to `/logs/backup.log`. `backend/docker-entrypoint.sh` starts as root, creates and chowns `/logs` to `app` (a bind mount is created root-owned by Docker) and `exec setpriv --reuid=app --regid=app --clear-groups` into itself, so Java (PID 1) runs as `app`; the Dockerfile has no `USER` line for that reason. A folder it cannot write only costs the file log (Logback reports the error and the app runs on).
- The revision: `images.yml` passes `--build-arg REVISION=<short sha>`, the Dockerfile exports it as `APP_REVISION`, `app.build.revision` (`shared/infrastructure/config/BuildProperties`, default `dev`) reaches `/actuator/info` as `build.revision` and the startup line `Backend revision … is ready` (`BuildRevision`).
- `nfnn-ops` (`deploy/ops/`, `nginx:1.29-alpine`) mounts `/logs` read-only, lists it at `/logs/` (`autoindex`, `text/plain`, `no-store`), serves byte ranges (nginx does that for static files), passes `/health` and `/info` to `backend:8080/actuator/...` through `links`, and publishes no port. `nfnn-cloudflared` (`cloudflare/cloudflared`, `tunnel --no-autoupdate run --token-file /tunnel/token`, `links: ops`) reads the token the backend wrote from the settings and only dials out; the hostname `ops.nfnn.cz` → `http://ops:80` and the Access policies (service token for Claude, Jakub's e-mail) live in Cloudflare, not in the repo. The PR check enforces the no-port, read-only and no-env-file invariants with `yq` and checks the log files and the reader on the running stack; `cloudflared` is left out of the stack job because it cannot start without a real token.
- Logs carry ids and outcomes only (`backend.md`): a new log line that would name a donor, an address or a token is a security change, not a logging change.

## MCP connector

Operator steps are in "MCP konektor" in `deploy/README.md`; the contract in `docs/api-contract.md` ("MCP connector"). What a change must keep true:

- `nfnn-mcp` (`mcp/Dockerfile`, `node:24-alpine`, user `node`, `npm ci` with `mcp/.npmrc` `legacy-peer-deps=true` because npm 10's resolver fails on Vitest's peers, `npm prune --omit=dev`; `ARG REVISION` → `APP_REVISION`) listens on 8081 inside the bridge network only; the frontend nginx proxies `location = /mcp` (HTTP/1.1, no buffering, `proxy_read_timeout 3600s` for the event stream, `limit_req zone=mcp` 10 r/s burst 20, 1 MB body) and `location = /.well-known/oauth-protected-resource/mcp` to `mcp:8081`, and `location = /.well-known/oauth-authorization-server` to the backend.
- The container gets no `env_file`, no secret and no per-server value: `BACKEND_URL` (`http://backend:8080`), `LOGS_DIR` (`/logs`), `PORT` and `APP_REVISION` are the image's defaults; the issuer (`PUBLIC_URL`) comes from the backend's metadata at runtime, so a changed `PUBLIC_URL` needs no change here. Volumes: `/DATA/AppData/nfnn/logs:/logs:ro` only. The PR check enforces the no-port, no-env-file and read-only-logs invariants with `yq` and `docker port`, and `nfnn-mcp` is among the containers that must not see `JWT_SECRET`, `FIO_TOKEN`, `MAIL_PASSWORD` or `TUNNEL_TOKEN`.
- Healthcheck `wget http://127.0.0.1:8081/health` with `start_period: 120s`: `/health` is 503 until the backend's metadata could be read (the backend starts slower than the connector), so compose `--wait` waits for the backend through it.
- Reaching the server: the service is new in `deploy/compose.yml`, so this version needs uninstall + Custom Install once; later versions arrive with Save in ZimaOS like the other images. Nothing in Cloudflare or Nginx Proxy Manager changes: `/mcp` is a path of the site.

## Proxy, headers, mail

- Nginx Proxy Manager terminates TLS for `nfnn.znamenacek.duckdns.org` (staging) and, after the switch, `nfnn.cz` behind Cloudflare, and forwards to 8089: "Přechod na skutečnou doménu" in `deploy/README.md`. `https://nfnn.cz` is the default `PUBLIC_URL` (`application.yml`) and the fixed origin of the canonical link, `og:url`, `og:image`, `public/robots.txt` and `public/sitemap.xml` (`core/seo/canonical-link.ts`, `SITE_ORIGIN`); a staging server enters its own address as "Adresa webu" in the first setup or at `/sprava/nastaveni`. `novanadeje.cz` belongs to someone else: never use it in addresses or URIs.
- The backend trusts forwarded headers from any peer (`server.forward-headers-strategy: framework`), so `frontend/nginx.conf` resolves the visitor itself: `set_real_ip_from` the private ranges, `real_ip_header X-Forwarded-For`, `real_ip_recursive on`, then sends `X-Forwarded-For $remote_addr` and an emptied `Forwarded`; a client cannot pick the address the per-address limits count. Behind Cloudflare, NPM must take the address from `CF-Connecting-IP` ("Obnova hesla" in the README).
- Cache headers in `frontend/nginx.conf`: `index.html` `no-cache`, hashed bundles immutable, `public/images/` one hour. A location with its own `add_header` drops the inherited ones, so each location includes `nginx-security-headers.conf`. That snippet also carries the Content-Security-Policy (rule in `security.md`); a change to it is verified against the production nginx before the PR (`docker run nginx:1.29-alpine` with `dist/`, `nginx.conf` and the snippet mounted, then the Playwright suite with `E2E_BASE_URL`), because the dev server sends no headers.
- Mail for `info@nfnn.cz` arrives through Cloudflare Email Routing; the backend sends through Brevo's SMTP relay ("E-maily" in the README; SPF stays Cloudflare's, Brevo aligns through DKIM). The mail health indicator is off, so `/actuator/health` (the Docker healthcheck) stays UP without SMTP.

## Backups and rollback

Operator steps are in "Zálohy" in `deploy/README.md` (Czech); this is what a change must keep true.

- What runs: the `backup` service is the image `ghcr.io/bzumik1/nfnn-backup` (`deploy/backup/Dockerfile`: `postgres:17-alpine` plus `backup.sh` as the entrypoint; 256M limit, `secrets/` read-only for the database password, `PGHOST=postgres`). The script waits for `pg_isready`, restores a dump from `/restore` (below), dumps once, then loops every 10 s: it handles request files, dumps at `03:00` (`BACKUP_TIME`, `TZ: Europe/Prague`, a time that exists exactly once on both DST changes) and on Sunday at `04:00` (`TEST_RESTORE_DAY=7`, `TEST_RESTORE_TIME`) restores the newest dump into `nfnn_restore_test`, counts its tables and drops it. A dump goes to `nfnn.dump.part` and is renamed `nfnn-YYYY-MM-DD_HHMM[-rucni|-pred-obnovou].dump` only on success (a failed run leaves no half file); `nfnn-*.dump` older than 30 days are deleted after each dump. Every run writes `/backups/status/{backup,test-restore,restore}` (`key=value`: `outcome`, `started_at`, `finished_at`, `file`, `size`, `tables`, `request`, `error`; written as `.part` and moved) besides the log line; the backend reads them (`operations/infrastructure/backup/FileBackupStore`), so a renamed key or file is an API change. The schedule env variables stay out of the compose (ZimaOS would re-type `03:00` as a time value); the defaults live in the script.
- Requests: `/backups/requests/` (`chmod 1777`, stale files removed at start) takes empty `<id>.backup` and `<id>.test-restore` files; the backend drops them for `POST /api/admin/operations/backups/requests`, the script removes the file first and records the id as `request=` in the status. The backend mounts only this subfolder writable.
- Restore folder: `/restore` with exactly one `*.dump` at container start. Into an empty database (`information_schema.tables` in `public` is empty) it is restored as it is; into a non-empty one only when named `*.force.dump`, after a `-pred-obnovou` dump (any other name is renamed `.skipped`); more than one dump skips them all. Other sessions are terminated, `DROP SCHEMA public CASCADE` + `CREATE SCHEMA public`, `pg_restore --exit-on-error --single-transaction`; the file ends as `.dump.done` or `.dump.failed`. `backend/docker-entrypoint.sh` waits while a `*.dump` or a `*.dump.failed` lies in `/restore`, so Liquibase never runs before the restore and a failed restore never becomes a fresh empty database; `depends_on: backup: service_started` only orders the start. That is also how a clean server gets its data: put the dump into `restore/` before the install.
- Compression (Jakub, 2026-10-22: highest that works): zstd 19 is the highest level that fits the 256M limit; measured on a synthetic 11 MB database: dump 750 kB vs 980 kB with the format's default gzip 6, 3 s vs 0.2 s on one core, peak 87 MB; level 20 needs 167 MB for no gain, 22 is OOM-killed, `long` mode needs 151 MB for 1 kB. A higher level or a lower memory limit must be measured first. The PR check fails unless the dump reads `Compression: zstd`. `pg_restore` detects the compression, so older gzip dumps still restore.
- Watching: the backend's daily check (`app.operations.backups.check-cron`, 07:15 Prague) turns the status files into problems (no, failed or stale backup: 26 h; no, failed or stale test restore: 8 days; folder not mounted) and e-mails the monthly report's recipients once per outage and once on recovery (`backup_alert_state`). The page `/sprava/zalohy` shows the same. A change to the script's status keys needs `StatusFiles`, `BackupHealth` and their tests changed with it.
- Where: `/DATA/AppData/nfnn/backups/` on the same disk as the database, the only copy. The dump holds the settings (secrets sealed); not backed up: `secrets/` and `config/` (keep `settings-key` in a password manager, or the restored secrets must be typed again). Off-site copy is still open (Cloudflare R2 or Google Drive undecided).
- Reaching the server: the script travels in the image (a merge publishes it, Save in ZimaOS pulls it), but the compose changed with it (new image, `restore/` and `requests/` mounts), so this version needs uninstall + Custom Install once, and `sudo install -d -m 755 /DATA/AppData/nfnn/backups /DATA/AppData/nfnn/restore` before it.
- Rollback: the older short-SHA image tag in the ZimaOS app settings, plus a restore when the newer version changed the schema (a Liquibase change cannot be rolled back otherwise).
