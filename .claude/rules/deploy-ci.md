# Deployment and CI

Every operator step is in `deploy/README.md` (Czech); this file is what a change must keep true. Deploy is manual by decision (Jakub, 2026-10-17): a self-hosted runner with the Docker socket was rejected, so never run a PR's code on the server.

## Pipelines

- `pr-check.yml` runs on every PR to `main` except one that changes only `docs/`, `.claude/` or Markdown (such a PR has no checks at all). Jobs, each with a `timeout-minutes`: `backend` (`./gradlew build`, Testcontainers works on the runner), `frontend` (`format:check`, `lint`, `lint:styles` with the theme token check, `ng test`, `build`, Playwright e2e with axe against that build, then the production build with the control theme and `e2e/theme.spec.ts` against it; both served by `frontend/scripts/serve-dist.mjs` through `E2E_DIST`), `mcp` (`npm run check`), and `stack`: it builds the five images (`backend/`, `frontend/`, `deploy/backup/`, `deploy/postgres/`, `mcp/`), checks the compose invariants (below, plus: no `network_mode` or `links`, every service on the one network `nfnn-edge`, `no-new-privileges`, `read_only` and `cap_drop: ALL` everywhere with the reviewed `cap_add` list, the backend's `DB_USERNAME` `novanadeje_app`, the two copies of `own-by-app-role.sql` identical) and starts `deploy/compose.yml`, then probes the first setup, the generated secrets, a restart with stored settings, that the backend logs in as the ordinary role `novanadeje_app` that owns every table, the database password resync and the hand-over of an older database to that role, backups, the restore paths, the log files and their rotation, the connector's discovery, the static files' caching (`frontend/scripts/probe-asset-caching.mjs`, Proxy, headers, mail), which container sees which secret (its configuration and its main process's environment), and that neither the backend nor the database answers from the default bridge. The `echo` lines and `::error::` texts of its Verify step say what each probe asserts; a change to what the stack does changes its probe.
- `roadmap-check.yml` runs on the same PRs as `pr-check.yml`, and again when the description is edited, except Dependabot's: one job, without a checkout, reads the PR's files through the API (`pull-requests: read`) and fails unless `docs/roadmap.md` is among them or the description holds `Roadmapa: beze změny` on a line of its own (Jakub, 2026-10-28; anchored so a quoted rule mid-sentence does not count, CRLF tolerated); a failed API call fails the step itself rather than reading as a missing update. The description reaches the shell only through an environment variable, never interpolated into the script.
- `gradle-cache.yml` runs on a push to `main` that changes `backend/`: it assembles, compiles the tests and runs the ArchUnit rules, so `setup-gradle` writes the Gradle cache from `main`, the only branch whose cache every PR can read (a cache written by a PR is visible to that PR only); the PR check only reads it (`setup-gradle`'s default on other branches).
- `images.yml` runs on a push to `main` that changes `backend/`, `frontend/`, `deploy/backup/`, `deploy/postgres/`, `mcp/` or the workflow itself (a docs-only merge publishes nothing), and every Monday at 03:17 UTC so security fixes of the base images reach `latest` without a code change (Save in ZimaOS still pulls them). It pushes `ghcr.io/bzumik1/nfnn-backend`, `-frontend`, `-backup`, `-postgres` and `-mcp` as `latest` and the short SHA, with `--build-arg REVISION=<short sha>`. The packages are public (switched once on GitHub; a new package starts private and needs the switch once) so ZimaOS pulls without logging in; the images hold no secrets.
- Workflows: `persist-credentials: false`, minimal `permissions`. `dependabot.yml` covers GitHub Actions, npm in `/frontend` and `/mcp` and Gradle in `/backend`, and the Docker base images of the five build contexts (one grouped PR), monthly, the package ecosystems grouped; versions in `extra[...]` of `build.gradle.kts` are not bumped by it.
- The repository is public since 2026-10-22: Actions minutes are free, and anything in a workflow log is public.

## ZimaOS install and update

- `deploy/compose.yml` is pasted unchanged into ZimaOS → App Store → Custom Install as the app "Nová naděje". It holds no `${...}`, no secrets and no per-server values, and no service reads an env file. A change to it reaches the server only by hand (uninstall + Custom Install with the new file): say so in the PR.
- New version: after "Publish Docker images" is green, Save the app's settings in ZimaOS without changes; that pulls the new `latest` and recreates the containers (Update and a plain restart keep the old image). Save reuses the compose of the last install. The settings in the database and `secrets/` survive both. Verify with `docker inspect` label `org.opencontainers.image.revision` or `nfnn_status`.
- The backend has `stop_grace_period: 75s` in both compose files (the PR check holds them to it): Spring drains requests for up to 30 s and then awaits a running bank import for up to 30 s (`spring.task.scheduling.shutdown`), and Docker's default 10 s would kill the import halfway.
- ZimaOS quirks the files are written around: it stores the compose without `$$` escapes (any `$` becomes an empty variable, so the compose holds no shell at all: logic lives in the images); it replaces the project name with `compose-<hash>` (every service sets `container_name: nfnn-<service>`); the app does not use the default `bridge` network, which every other app on the box shares: one named network `nfnn-edge` (fixed `name:` so the project name does not matter) gives service DNS to all five services, so no other container on the server reaches any NFNN service; ZimaOS attaches a service only to the first network it lists (a backend on a second, `internal: true` database network stayed on that one alone and nginx refused to start on the unresolvable `backend`, 2026-10-24), so every service lists exactly `edge` and a separate database network is not possible there; a new service joins `edge` too, never `network_mode` or `links:`, and every service sets `no-new-privileges` (the PR check enforces both and probes from the default bridge); a change of networks reaches the server only by uninstall + Custom Install; it starts the app once, so `depends_on` uses `service_started`, never `service_healthy` (the backend restarts until Postgres accepts connections, the backup script waits with `pg_isready`); it adds a memory reservation and silently never creates a container whose `limits.memory` is below it, so no limit goes under 256M; it re-types unquoted values as YAML (a date or a time becomes a timestamp), so schedule values stay out of the compose; port 8080 is taken on the box, the frontend publishes 8089.
- The local `docker-compose.yml` keeps a root `.env` (`.env.example`) for developers and is never used on the server. It must define every host `frontend/nginx.conf` proxies to (`backend`, `mcp`): nginx refuses to start on an unresolvable upstream, and CI does not start this file.

## Secrets and configuration

- No env file on the server (Jakub, 2026-10-23). Generated secrets live in `/DATA/AppData/nfnn/secrets/` (root, mode 600, created once, never overwritten, except `backup-key` when a restore from the first setup brings the old server's key, below): `nfnn-postgres` (`deploy/postgres/`, on `postgres:17-alpine`) writes `db-password` (the superuser `novanadeje`) and `db-app-password` (the application role `novanadeje_app`), exports the first as `POSTGRES_PASSWORD` for the stock entrypoint only, and at every start, through a private instance on a temporary socket, sets both roles' passwords, creates `novanadeje_app` if missing (`app-role.sql`: login, no superuser, no role or database creation, no replication) and hands it the database, the `public` schema and every table, view and sequence (`own-by-app-role.sql`), then touches `db-password.ready`; a new database gets the same from `/docker-entrypoint-initdb.d/nfnn-app-role.sh`. `backend/docker-entrypoint.sh` waits for that marker, generates `jwt-secret`, `settings-key` and `backup-key` (an age identity from `age-keygen`) and exports them with `db-app-password` as `JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `DB_PASSWORD` for Java only, so the backend is no superuser and its Java process (user `app`) can read no file in `secrets/`; `nfnn-backup` waits for the same marker, reads `db-password` read-only into `PGPASSWORD` inside its script and works as the superuser (dumps, test restores, the restore swap), and hands every restored database to `novanadeje_app` before swapping it in (its copy of `own-by-app-role.sql`, kept identical by the PR check). Losing the folder means a new database password (synced again), new sign-ins and the sealed settings typed again.
- Every other per-server value is a setting stored in the database (`operations_setting`, contract "Settings and the first setup"): entered in the first setup at `/prvni-nastaveni`, changed at `/sprava/nastaveni`, loaded under its env name by the `prod` profile before the context starts. A new per-server value is a new `Setting` and a label in `setting-labels.ts`, never an env line; values that only a developer changes stay in `application.yml`.
- The compose's `environment:` holds only fixed values: `SPRING_PROFILES_ACTIVE`, `DB_URL`, `DB_USERNAME`, `JAVA_TOOL_OPTIONS`, `TZ`, the database names and `PGHOST`/`PGUSER`/`PGDATABASE`.
- The `stack` job fails when `deploy/compose.yml` holds a `$` or names a secret key (`POSTGRES_PASSWORD`, `PGPASSWORD`, `DB_PASSWORD`, `JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `MAIL_PASSWORD`, `FIO_TOKEN`), when a service reads an `env_file`, when a service but the frontend publishes a port, when `secrets/` is mounted anywhere but postgres, backend and (read-only) backup, when postgres, backup, mcp or frontend sees `JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `DB_PASSWORD`, `FIO_TOKEN` or `MAIL_PASSWORD` (in its configuration or its main process's environment), when a service uses `network_mode` or `links`, sits on another network than its own, or lacks `no-new-privileges`, `read_only: true` or `cap_drop: [ALL]`, when the `cap_add` lists differ from the reviewed ones, or when the backend's `DB_USERNAME` is not `novanadeje_app`.
- Bind mounts under `/DATA/AppData/nfnn/`: postgres data; `secrets/` (postgres and backend read-write, backup read-only); `backups/` (read-write in backup; read-only in the backend except `backups/requests/`); `restore/` (read-write in backup and in the backend, which streams a backup uploaded in the first setup into it); `logs/` (read-write in backend, backup, frontend and mcp). The receipt signature image lives in the database (uploaded at `/sprava/nastaveni`), so no `config/` folder is mounted.
- Hardening (Jakub 2026-10-24): every service runs with a read-only root file system, `tmpfs` where it writes (`/tmp` everywhere, postgres `/var/run/postgresql`, the frontend `/run` and `/var/cache/nginx`; sizes capped where an upload could fill memory), and `cap_drop: ALL` plus only what its entrypoint needs: postgres `CHOWN DAC_OVERRIDE FOWNER SETGID SETUID` (the stock entrypoint fixes its folders and drops to `postgres`), backup `DAC_OVERRIDE FOWNER` (root in folders the backend owns: `/restore`, `/logs`), backend `CHOWN SETGID SETUID` (hands `/logs` and `/restore` to `app`, `setpriv`), mcp `CHOWN DAC_OVERRIDE FOWNER SETGID SETUID` (rotates its log in `/logs`, `su-exec`), frontend `CHOWN DAC_OVERRIDE NET_BIND_SERVICE SETGID SETUID` (port 80, workers as `nginx`). A new write path is a new `tmpfs` or volume, a new capability is reviewed in the PR check's list. Without `DAC_OVERRIDE` root in the backend cannot write into `/restore` (owned by `app`): a probe or script writes there as `app`. With every capability dropped `/proc/1/environ` is unreadable to a plain `docker exec`, so the secret probe uses `docker exec --privileged` (nginx writes its title over its environment, so its check reads nothing).
- Privileges: `backend/docker-entrypoint.sh` starts as root to read and generate `secrets/`, to wait on `/restore` and to hand `/logs` to `app`, then `exec setpriv --reuid=app --regid=app --clear-groups` into Java (PID 1), so the Dockerfile has no `USER` line; `mcp/docker-entrypoint.sh` starts as root for its log rotation and `exec su-exec node` into Node.

## Logs

Operator notes are in "Logy" in `deploy/README.md`; `CLAUDE.md` says how Claude reads them (the connector, through the backend; nothing serves the folder from outside).

- The backend logs to the console and, in the `prod` profile (`application-prod.yml`), to `${LOG_FILE:/logs/backend.log}` with Logback rotation (10 MB, 14 days, 200 MB cap); the backup script appends to `/logs/backup.log` (not rotated, a few lines a day); the frontend nginx writes `/logs/nginx-access.log` (format `anonymous`: time, method, path without the query string, status, bytes, request and upstream time, never the client address; the console keeps the image's `main` format); the connector appends to `/logs/mcp.log` (`LOG_FILE`).
- The access and connector logs rotate by the UTC day with `rotate-log.sh` (one script, copied into `frontend/` and `mcp/` because they are separate build contexts; the PR check `cmp`s the copies): at start it moves a file left from an earlier day to `<file>.YYYY-MM-DD.gz`, then a background loop does that every midnight, has the writer reopen, and deletes archives older than 14 days (`LOG_KEEP_DAYS`). A folder the backend cannot write only costs the file log.
- The revision: `images.yml` passes `--build-arg REVISION=<short sha>`, the Dockerfile exports it as `APP_REVISION`, `app.build.revision` (`BuildProperties`, default `dev`) reaches `/actuator/info` as `build.revision` and the startup line `Backend revision … is ready` (`BuildRevision`).
- Logs carry ids and outcomes only (`security.md`): a new log line or `log_format` field that would name a donor, an address or a token is a security change.

## MCP connector

Operator steps are in "MCP konektor" in `deploy/README.md`; the contract in `docs/api-contract.md` ("MCP connector").

- `nfnn-mcp` (`mcp/Dockerfile`, `node:24-alpine` plus `su-exec`, `npm ci` with `mcp/.npmrc`, `npm prune --omit=dev`; `ARG REVISION` → `APP_REVISION`) listens on 8081 inside `nfnn-edge` and publishes no port. The frontend nginx proxies `location = /mcp` (HTTP/1.1, no buffering, `proxy_read_timeout 3600s` for the event stream, `limit_req zone=mcp` 10 r/s burst 20, 1 MB body), `location = /mcp-photos` (same limit, 11 MB body) and `location = /.well-known/oauth-protected-resource/mcp` to `mcp:8081`, and `location = /.well-known/oauth-authorization-server` to the backend.
- The container gets no `env_file`, no secret and no per-server value: `BACKEND_URL` (`http://backend:8080`), `LOG_FILE` (`/logs/mcp.log`; empty logs to the console only), `PORT` and `APP_REVISION` are the image's defaults; the issuer (`PUBLIC_URL`) comes from the backend's metadata at runtime. Its only volume is `/logs`.
- Healthcheck `wget http://127.0.0.1:8081/health` with `start_period: 120s`: `/health` is 503 until the backend's metadata could be read, so compose `--wait` waits for the backend through it.

## Proxy, headers, mail

- Nginx Proxy Manager terminates TLS for `nfnn.znamenacek.duckdns.org` (staging) and, after the switch, `nfnn.cz` behind Cloudflare, and forwards to 8089 ("Přechod na skutečnou doménu" in `deploy/README.md`). `https://nfnn.cz` is the default `PUBLIC_URL` (`application.yml`) and the fixed origin of the canonical link, `og:url`, `og:image`, `public/robots.txt` and `public/sitemap.xml` (`core/seo/canonical-link.ts`, `SITE_ORIGIN`); a staging server enters its own address as "Adresa webu" in the first setup or at `/sprava/nastaveni`. `novanadeje.cz` belongs to someone else: never use it in addresses or URIs.
- The backend trusts forwarded headers from any peer (`server.forward-headers-strategy: framework`), so `frontend/nginx.conf` resolves the visitor itself: `set_real_ip_from` the private ranges, `real_ip_header X-Forwarded-For`, `real_ip_recursive on`, then sends `X-Forwarded-For $remote_addr` and an emptied `Forwarded`; a client cannot pick the address the per-address limits count. Behind Cloudflare, NPM must take the address from `CF-Connecting-IP` ("Obnova hesla" in the README).
- Cache headers in `frontend/nginx.conf`: `index.html`, the app routes and every unhashed file `no-cache`; the hashed bundles (anchored `^/(?:chunk|main|polyfills|styles)-[A-Za-z0-9_-]{8}\.(?:js|css)$`: the lazy chunks' hashes are mixed case with `_` and `-`, and a hashed file of another prefix, a web worker for example, stays `no-cache` until its prefix joins the rule) and `/media/` immutable for a year; `public/images/` an hour. The two asset rules are regex locations nested in `location /`, so they never catch `/api/`, `/media/` or `/images/`, and they use `try_files $uri =404`: a file that is gone (an old chunk after a deploy) answers 404, never `index.html` with 200, and the immutable header goes only on 200, 206 and 304 (`map $status $immutable_cache_control`; a 404 is `no-store`), so a browser or Cloudflare never keeps a 404 for a year and a rolled-back image finds its chunks; `/images/` keeps its hour only on those statuses too (`$image_cache_control`). `server_tokens off` keeps the nginx version out of the `Server` header and the error pages. The immutable rule must never match `index.html`, `ngsw*` or a manifest. The `stack` job checks all of it against the running frontend with `frontend/scripts/probe-asset-caching.mjs` on Node 24 (`actions/setup-node`): the immutable location found by its exact `add_header` line, every file the image serves, missing chunks, images and other assets, app routes, `/api/` and the `Server` header; run it locally against the production nginx (skill `visual-check`, "Headers") as `node scripts/probe-asset-caching.mjs http://localhost:8089 dist/frontend/browser nginx.conf`. A location with its own `add_header` drops the inherited ones, so each location includes `nginx-security-headers.conf`. That snippet carries the Content-Security-Policy (`security.md`); a change to it is verified against the production nginx before the PR (skill `visual-check`, "Headers"), because the dev server sends no headers.
- Mail for `info@nfnn.cz` arrives through Cloudflare Email Routing; the backend sends through Brevo's SMTP relay ("E-maily" in the README; SPF stays Cloudflare's, Brevo aligns through DKIM). The mail health indicator is off, so `/actuator/health` (the Docker healthcheck) stays UP without SMTP.

## Backups and rollback

Operator steps are in "Zálohy" in `deploy/README.md` (Czech).

- What runs: the `backup` service is `ghcr.io/bzumik1/nfnn-backup` (`deploy/backup/Dockerfile`: `postgres:17-alpine` plus `backup.sh` as the entrypoint; 256M limit, `secrets/` read-only, `PGHOST=postgres`). At start the script waits for `pg_isready`, recovers an interrupted restore, restores a dump from `/restore` (below), handles waiting requests and dumps once; then it loops every 10 s: requests, the schedule (`load_schedule`: `/backups/requests/schedule` from the backend, `backup_time=HH:mm`, `test_restore_day=1-7`, `test_restore_time=HH:mm`, each invalid or missing value falling back to its default, the plan in use written to `/backups/status/schedule` and logged when it changes; a time moved later than now resets that day's mark so the run happens again), the day's dump once the clock has reached the planned time, default `03:00` (`BACKUP_TIME`, `TZ: Europe/Prague`, a time that exists exactly once on both DST changes; a request running at 03:00 only delays it, and the dump at start counts for a day started after 03:00) and on the planned day once it has reached the planned time, default Sunday `04:00` (`TEST_RESTORE_DAY=7`, `TEST_RESTORE_TIME`; at start a Sunday whose `status/test-restore` is not from today catches up) a test restore of the newest dump into `nfnn_restore_test` (tables and applied changesets counted, both must be above 0, and every table must hold as many rows as its `COPY` block in the dump, `compare_rows`; then dropped). The schedule defaults live in the script, never in the compose; the plan itself is chosen on `/sprava/zalohy` and stored in `operations_backup_schedule`, and the backend writes it again at every start (`BackupSchedulePublisher`).
- Encryption (Jakub, 2026-10-28: backups are always encrypted): `pg_dump` pipes into `age --encrypt --identity /secrets/backup-key`, so no plain dump is written to `/backups`; the script waits for a valid key (`age-keygen -y`) before anything else, a dump without one fails, and older plain `nfnn-*.dump` files are encrypted in place at start. A test restore or restore decrypts into a pipe (`restore_into`, `dumped_rows`) and never writes a plain copy, because `/backups` is what is copied off the server; the PR check fails on any `*.dump` or `work` in it. The key is shown to the administrator only in the first setup and on `/sprava/zalohy` with a fresh second factor (`security.md`), never in a log, a status file or the connector; the PR check asserts that.
- A dump goes to `nfnn.dump.age.part` and is renamed `nfnn-YYYY-MM-DD_HHMM[-rucni|-pred-obnovou].dump.age` only on success; `nfnn-*.dump.age` older than 30 days are deleted after each dump. Compression `zstd:19` (Jakub, 2026-10-22: the highest that works): it is the highest level that fits the 256M limit (20 needs 167 MB for no gain, 22 is OOM-killed); a higher level or a lower memory limit is measured first, and the PR check fails unless the decrypted dump reads `Compression: zstd`. `pg_restore` detects the compression, so older gzip dumps still restore.
- Status: every run writes `/backups/status/{backup,test-restore,restore}` (`key=value`: `outcome`, `started_at`, `finished_at`, `file`, `size`, `tables`, `request`, `error`; written as `.part` and moved) besides the log line. The backend reads them (`operations/infrastructure/backup/FileBackupStore`, `StatusFiles`, `BackupHealth`), so a renamed key or file is an API change made in both places with their tests.
- Requests: `/backups/requests/` (`chmod 1777`; leftover `.backup` and `.test-restore` files are removed at start, a `.restore` file is kept) takes the `schedule` file (kept, read on every pass), empty `<id>.backup` and `<id>.test-restore` files and `<id>.restore` files with the lines `source=backup|upload`, `file=`, `admin=`. The backend drops them for `POST /api/admin/operations/backups/requests`, `POST .../backups/{file}/restore` and the first setup's `PUT /api/operations/setup/restore`; the script removes the file first (a restore writes `/backups/status/restore.running` before that) and records the id as `request=` (and `admin=` for a restore). It refuses a `file=` with a `/` or a leading dot: `backup` names a `nfnn-*.dump.age` in `/backups`, `upload` a `*.upload` in `/restore` (deleted afterwards; uploads older than 60 minutes are deleted anyway). An encrypted upload comes with the key it was made with as `<id>.key`; the script copies it into its `tmpfs` first, and after a successful restore records its recipient in `/backups/status/adopted-key` and writes it as `/restore/backup-key.adopt` (noclobber, after removing whatever stood there); `backend/docker-entrypoint.sh`, after its restore wait, makes it `secrets/backup-key` only when `age-keygen -y` of it equals the record (the backend mounts `/backups` read-only, while `app` can write `/restore`), keeps the previous one as `backup-key.replaced-<time>`, so the new server keeps reading the old dumps; the PR check plants a key as `app` and expects it ignored, and restores an upload with its own key and expects it adopted.
- Restores (Jakub 2026-10-23: only through the GUI, foolproof): `restore_dump` takes a `-pred-obnovou` dump when `public` has tables, creates `nfnn_restore_staging`, runs `pg_restore --exit-on-error --single-transaction` into it, refuses it without tables or rows in `databasechangelog` (not a dump of this site), releases a Liquibase lock caught in the dump (`release_liquibase_lock`; the startup dump can run while the backend migrates) and only then swaps: `ALLOW_CONNECTIONS false` on the live database, `pg_terminate_backend` and `ALTER DATABASE … RENAME` live → `nfnn_restore_retired` (retried 30 × 1 s, then connections are allowed again and the restore fails), `keep_sequences_ahead` (connections back on for the retired name, which no client uses, then every `public` sequence of staging set to the higher of its own and the retired value), staging → live (once; on failure the retired one is renamed back), then drops the retired one. A failure drops staging and leaves the live database as it was. At start `recover_interrupted_restore` removes a stale marker, renames `nfnn_restore_retired` back when the live database is missing, drops staging and deletes `*.upload.part`. `nfnn-postgres.sh` syncs the role password over `-d postgres`, so it works mid-swap. `backend/docker-entrypoint.sh` waits while the marker, a `*.restore` request or a `/restore/*.dump[.age]` exists and deletes a request older than 5 minutes when no marker exists, so Liquibase never runs against a swapped database and an unattended request never blocks the backend for good.
- A restore brings back everything as of the dump except the sequences, which never go back: receipts issued since the dump disappear, but their numbers are never issued again (a new download gets a new number). Say so wherever a restore is offered.
- Restore folder (by hand): `/restore` with exactly one `*.dump.age` (this server's key) or plain `*.dump` at container start. Into an empty database it is restored as it is; into a non-empty one only when named `*.force.dump.age` (or `*.force.dump`; any other name is renamed `.skipped`); more than one dump skips them all; the same `restore_dump`; the file gets `.done` or `.failed` appended (the data stayed, the backend starts).
- Watching: the backend's daily check (`app.operations.backups.check-cron`, 07:15 Prague) turns the status files into problems (no, failed or stale backup: 26 h; no, failed or stale test restore: 8 days; folder not mounted) and e-mails the monthly report's recipients once per outage and once on recovery (`backup_alert_state`). `/sprava/zalohy` shows the same.
- Where: `/DATA/AppData/nfnn/backups/` on the same disk as the database, the only copy; the off-site copy is postponed until after the launch on nfnn.cz, Jakub would like it on iCloud (2026-10-23). The dump holds the settings (secrets sealed) and the receipt signature; `secrets/` is not backed up, but the database carries `settings-key` wrapped under a key derived from `backup-key` (`operations_carried_settings_key`, Jakub 2026-10-29), so after a restore on a new server that adopted the backup key `MAIL_PASSWORD` and `FIO_TOKEN` are read and sealed again under the new `settings-key`; only an older dump or one restored without the backup key leaves them unreadable, and `/sprava/nastaveni` names them. The backup key itself never goes into a backup.
- Rollback: the older short-SHA image tag in the ZimaOS app settings; a restore only when the newer version made a breaking schema change (`backend.md`, Persistence).
