# Deployment and CI

Every operator step is in `deploy/README.md` (Czech); this file is what a change must keep true. Deploy is manual by decision (Jakub, 2026-10-17): a self-hosted runner with the Docker socket was rejected, so never run a PR's code on the server.

## Pipelines

- `pr-check.yml` runs on every PR to `main` except one that changes only `docs/`, `.claude/` or Markdown (such a PR has no checks at all). Jobs, each with a `timeout-minutes`: `backend` (`./gradlew build`, Testcontainers works on the runner), `frontend` (`format:check`, `lint`, `lint:styles`, `ng test`, `build`, Playwright e2e with axe), `mcp` (`npm run check`), and `stack`: it builds the five images (`backend/`, `frontend/`, `deploy/backup/`, `deploy/postgres/`, `mcp/`), checks the compose invariants (below, plus: no `network_mode` or `links`, the exact network of every service, `nfnn-internal` `internal: true`, `no-new-privileges` everywhere) and starts `deploy/compose.yml`, then probes the first setup, the generated secrets, a restart with stored settings, the database password resync, backups, the restore paths, the log files and their rotation, the connector's discovery, which container sees which secret (its configuration and its main process's environment), and that neither the backend nor the database answers from the default bridge. The `echo` lines and `::error::` texts of its Verify step say what each probe asserts; a change to what the stack does changes its probe.
- Caches: `setup-gradle` writes its cache from PRs (`cache-read-only: false`), but GitHub scopes a PR's cache to that PR, so a new PR starts cold; a shared cache would need a job on `main`.
- `images.yml` runs on a push to `main` that changes `backend/`, `frontend/`, `deploy/backup/`, `deploy/postgres/`, `mcp/` or the workflow itself (a docs-only merge publishes nothing), and every Monday at 03:17 UTC so security fixes of the base images reach `latest` without a code change (Save in ZimaOS still pulls them). It pushes `ghcr.io/bzumik1/nfnn-backend`, `-frontend`, `-backup`, `-postgres` and `-mcp` as `latest` and the short SHA, with `--build-arg REVISION=<short sha>`. The packages are public (switched once on GitHub; a new package starts private and needs the switch once) so ZimaOS pulls without logging in; the images hold no secrets.
- Workflows: `persist-credentials: false`, minimal `permissions`. `dependabot.yml` covers GitHub Actions, npm in `/frontend` and `/mcp` and Gradle in `/backend`, and the Docker base images of the five build contexts (one grouped PR), monthly, the package ecosystems grouped; versions in `extra[...]` of `build.gradle.kts` are not bumped by it.
- The repository is public since 2026-10-22: Actions minutes are free, and anything in a workflow log is public.

## ZimaOS install and update

- `deploy/compose.yml` is pasted unchanged into ZimaOS → App Store → Custom Install as the app "Nová naděje". It holds no `${...}`, no secrets and no per-server values, and no service reads an env file. A change to it reaches the server only by hand (uninstall + Custom Install with the new file): say so in the PR.
- New version: after "Publish Docker images" is green, Save the app's settings in ZimaOS without changes; that pulls the new `latest` and recreates the containers (Update and a plain restart keep the old image). Save reuses the compose of the last install. The settings in the database and `secrets/` survive both. Verify with `docker inspect` label `org.opencontainers.image.revision` or `nfnn_status`.
- ZimaOS quirks the files are written around: it stores the compose without `$$` escapes (any `$` becomes an empty variable, so the compose holds no shell at all: logic lives in the images); it replaces the project name with `compose-<hash>` (every service sets `container_name: nfnn-<service>`); the app does not use the default `bridge` network, which every other app on the box shares: two named networks (fixed `name:` so the project name does not matter) give service DNS, `nfnn-edge` (frontend, backend, mcp; the frontend's port and the outbound calls) and `nfnn-internal` (`internal: true`, no way out: postgres, backup, backend), so only the backend and the backup reach the database and no other container on the server reaches any NFNN service; a new service joins the network of the services it talks to, never `network_mode` or `links:`, and every service sets `no-new-privileges` (the PR check enforces both and probes from the default bridge); a change of networks reaches the server only by uninstall + Custom Install; it starts the app once, so `depends_on` uses `service_started`, never `service_healthy` (the backend restarts until Postgres accepts connections, the backup script waits with `pg_isready`); it adds a memory reservation and silently never creates a container whose `limits.memory` is below it, so no limit goes under 256M; it re-types unquoted values as YAML (a date or a time becomes a timestamp), so schedule values stay out of the compose; port 8080 is taken on the box, the frontend publishes 8089.
- The local `docker-compose.yml` keeps a root `.env` (`.env.example`) for developers and is never used on the server. It must define every host `frontend/nginx.conf` proxies to (`backend`, `mcp`): nginx refuses to start on an unresolvable upstream, and CI does not start this file.

## Secrets and configuration

- No env file on the server (Jakub, 2026-10-23). Generated secrets live in `/DATA/AppData/nfnn/secrets/` (root, mode 600, created once, never overwritten): `nfnn-postgres` (`deploy/postgres/`, on `postgres:17-alpine`) writes `db-password`, exports it as `POSTGRES_PASSWORD` for the stock entrypoint only, sets the role's password to it through the local socket at every start and touches `db-password.ready`; `backend/docker-entrypoint.sh` waits for that marker, generates `jwt-secret` and `settings-key` and exports the three as `DB_PASSWORD`, `JWT_SECRET`, `SETTINGS_KEY` for Java only; `nfnn-backup` waits for the same marker and reads `db-password` read-only into `PGPASSWORD` inside its script. Losing the folder means a new database password (synced again), new sign-ins and the sealed settings typed again.
- Every other per-server value is a setting stored in the database (`operations_setting`, contract "Settings and the first setup"): entered in the first setup at `/prvni-nastaveni`, changed at `/sprava/nastaveni`, loaded under its env name by the `prod` profile before the context starts. A new per-server value is a new `Setting` and a label in `setting-labels.ts`, never an env line; values that only a developer changes stay in `application.yml`.
- The compose's `environment:` holds only fixed values: `SPRING_PROFILES_ACTIVE`, `DB_URL`, `DB_USERNAME`, `JAVA_TOOL_OPTIONS`, `TZ`, the database names and `PGHOST`/`PGUSER`/`PGDATABASE`.
- The `stack` job fails when `deploy/compose.yml` holds a `$` or names a secret key (`POSTGRES_PASSWORD`, `PGPASSWORD`, `DB_PASSWORD`, `JWT_SECRET`, `SETTINGS_KEY`, `MAIL_PASSWORD`, `FIO_TOKEN`), when a service reads an `env_file`, when a service but the frontend publishes a port, when `secrets/` is mounted anywhere but postgres, backend and (read-only) backup, when postgres, backup, mcp or frontend sees `JWT_SECRET`, `SETTINGS_KEY`, `DB_PASSWORD`, `FIO_TOKEN` or `MAIL_PASSWORD` (in its configuration or its main process's environment), when a service uses `network_mode` or `links`, sits on another network than its own, or lacks `no-new-privileges`.
- Bind mounts under `/DATA/AppData/nfnn/`: postgres data; `secrets/` (postgres and backend read-write, backup read-only); `backups/` (read-write in backup; read-only in the backend except `backups/requests/`); `restore/` (read-write in backup and in the backend, which streams a backup uploaded in the first setup into it); `logs/` (read-write in backend, backup, frontend and mcp). The receipt signature image lives in the database (uploaded at `/sprava/nastaveni`), so no `config/` folder is mounted.
- Privileges: `backend/docker-entrypoint.sh` starts as root to read and generate `secrets/`, to wait on `/restore` and to hand `/logs` to `app`, then `exec setpriv --reuid=app --regid=app --clear-groups` into Java (PID 1), so the Dockerfile has no `USER` line; `mcp/docker-entrypoint.sh` starts as root for its log rotation and `exec su-exec node` into Node.

## Logs

Operator notes are in "Logy" in `deploy/README.md`; `CLAUDE.md` says how Claude reads them (the connector, through the backend; nothing serves the folder from outside).

- The backend logs to the console and, in the `prod` profile (`application-prod.yml`), to `${LOG_FILE:/logs/backend.log}` with Logback rotation (10 MB, 14 days, 200 MB cap); the backup script appends to `/logs/backup.log` (not rotated, a few lines a day); the frontend nginx writes `/logs/nginx-access.log` (format `anonymous`: time, method, path without the query string, status, bytes, request and upstream time, never the client address; the console keeps the image's `main` format); the connector appends to `/logs/mcp.log` (`LOG_FILE`).
- The access and connector logs rotate by the UTC day with `rotate-log.sh` (one script, copied into `frontend/` and `mcp/` because they are separate build contexts; the PR check `cmp`s the copies): at start it moves a file left from an earlier day to `<file>.YYYY-MM-DD.gz`, then a background loop does that every midnight, has the writer reopen, and deletes archives older than 14 days (`LOG_KEEP_DAYS`). A folder the backend cannot write only costs the file log.
- The revision: `images.yml` passes `--build-arg REVISION=<short sha>`, the Dockerfile exports it as `APP_REVISION`, `app.build.revision` (`BuildProperties`, default `dev`) reaches `/actuator/info` as `build.revision` and the startup line `Backend revision … is ready` (`BuildRevision`).
- Logs carry ids and outcomes only (`security.md`): a new log line or `log_format` field that would name a donor, an address or a token is a security change.

## MCP connector

Operator steps are in "MCP konektor" in `deploy/README.md`; the contract in `docs/api-contract.md` ("MCP connector").

- `nfnn-mcp` (`mcp/Dockerfile`, `node:24-alpine` plus `su-exec`, `npm ci` with `mcp/.npmrc`, `npm prune --omit=dev`; `ARG REVISION` → `APP_REVISION`) listens on 8081 inside `nfnn-edge` only. The frontend nginx proxies `location = /mcp` (HTTP/1.1, no buffering, `proxy_read_timeout 3600s` for the event stream, `limit_req zone=mcp` 10 r/s burst 20, 1 MB body), `location = /mcp-photos` (same limit, 11 MB body) and `location = /.well-known/oauth-protected-resource/mcp` to `mcp:8081`, and `location = /.well-known/oauth-authorization-server` to the backend.
- The container gets no `env_file`, no secret and no per-server value: `BACKEND_URL` (`http://backend:8080`), `LOG_FILE` (`/logs/mcp.log`; empty logs to the console only), `PORT` and `APP_REVISION` are the image's defaults; the issuer (`PUBLIC_URL`) comes from the backend's metadata at runtime. Its only volume is `/logs`.
- Healthcheck `wget http://127.0.0.1:8081/health` with `start_period: 120s`: `/health` is 503 until the backend's metadata could be read, so compose `--wait` waits for the backend through it.

## Proxy, headers, mail

- Nginx Proxy Manager terminates TLS for `nfnn.znamenacek.duckdns.org` (staging) and, after the switch, `nfnn.cz` behind Cloudflare, and forwards to 8089 ("Přechod na skutečnou doménu" in `deploy/README.md`). `https://nfnn.cz` is the default `PUBLIC_URL` (`application.yml`) and the fixed origin of the canonical link, `og:url`, `og:image`, `public/robots.txt` and `public/sitemap.xml` (`core/seo/canonical-link.ts`, `SITE_ORIGIN`); a staging server enters its own address as "Adresa webu" in the first setup or at `/sprava/nastaveni`. `novanadeje.cz` belongs to someone else: never use it in addresses or URIs.
- The backend trusts forwarded headers from any peer (`server.forward-headers-strategy: framework`), so `frontend/nginx.conf` resolves the visitor itself: `set_real_ip_from` the private ranges, `real_ip_header X-Forwarded-For`, `real_ip_recursive on`, then sends `X-Forwarded-For $remote_addr` and an emptied `Forwarded`; a client cannot pick the address the per-address limits count. Behind Cloudflare, NPM must take the address from `CF-Connecting-IP` ("Obnova hesla" in the README).
- Cache headers in `frontend/nginx.conf`: `index.html` `no-cache`, hashed bundles immutable, `public/images/` and `/media/` with their own lifetimes. A location with its own `add_header` drops the inherited ones, so each location includes `nginx-security-headers.conf`. That snippet carries the Content-Security-Policy (`security.md`); a change to it is verified against the production nginx before the PR (skill `visual-check`, "Headers"), because the dev server sends no headers.
- Mail for `info@nfnn.cz` arrives through Cloudflare Email Routing; the backend sends through Brevo's SMTP relay ("E-maily" in the README; SPF stays Cloudflare's, Brevo aligns through DKIM). The mail health indicator is off, so `/actuator/health` (the Docker healthcheck) stays UP without SMTP.

## Backups and rollback

Operator steps are in "Zálohy" in `deploy/README.md` (Czech).

- What runs: the `backup` service is `ghcr.io/bzumik1/nfnn-backup` (`deploy/backup/Dockerfile`: `postgres:17-alpine` plus `backup.sh` as the entrypoint; 256M limit, `secrets/` read-only, `PGHOST=postgres`). At start the script waits for `pg_isready`, recovers an interrupted restore, restores a dump from `/restore` (below), handles waiting requests and dumps once; then it loops every 10 s: requests, a dump when the clock reads `03:00` (`BACKUP_TIME`, `TZ: Europe/Prague`, a time that exists exactly once on both DST changes; a request still running through that whole minute skips the day's dump) and on Sunday at `04:00` (`TEST_RESTORE_DAY=7`, `TEST_RESTORE_TIME`) a test restore of the newest dump into `nfnn_restore_test` (tables counted, then dropped). The schedule defaults live in the script, never in the compose.
- A dump goes to `nfnn.dump.part` and is renamed `nfnn-YYYY-MM-DD_HHMM[-rucni|-pred-obnovou].dump` only on success; `nfnn-*.dump` older than 30 days are deleted after each dump. Compression `zstd:19` (Jakub, 2026-10-22: the highest that works): it is the highest level that fits the 256M limit (20 needs 167 MB for no gain, 22 is OOM-killed); a higher level or a lower memory limit is measured first, and the PR check fails unless the dump reads `Compression: zstd`. `pg_restore` detects the compression, so older gzip dumps still restore.
- Status: every run writes `/backups/status/{backup,test-restore,restore}` (`key=value`: `outcome`, `started_at`, `finished_at`, `file`, `size`, `tables`, `request`, `error`; written as `.part` and moved) besides the log line. The backend reads them (`operations/infrastructure/backup/FileBackupStore`, `StatusFiles`, `BackupHealth`), so a renamed key or file is an API change made in both places with their tests.
- Requests: `/backups/requests/` (`chmod 1777`; leftover `.backup` and `.test-restore` files are removed at start, a `.restore` file is kept) takes empty `<id>.backup` and `<id>.test-restore` files and `<id>.restore` files with the lines `source=backup|upload`, `file=`, `admin=`. The backend drops them for `POST /api/admin/operations/backups/requests`, `POST .../backups/{file}/restore` and the first setup's `PUT /api/operations/setup/restore`; the script removes the file first (a restore writes `/backups/status/restore.running` before that) and records the id as `request=` (and `admin=` for a restore). It refuses a `file=` with a `/` or a leading dot: `backup` names a `nfnn-*.dump` in `/backups`, `upload` a `*.upload` in `/restore` (deleted afterwards; uploads older than 60 minutes are deleted anyway).
- Restores (Jakub 2026-10-23: only through the GUI, foolproof): `restore_dump` takes a `-pred-obnovou` dump when `public` has tables, creates `nfnn_restore_staging`, runs `pg_restore --exit-on-error --single-transaction` into it, counts its tables and only then swaps: `ALLOW_CONNECTIONS false` on the live database, `pg_terminate_backend` and `ALTER DATABASE … RENAME` live → `nfnn_restore_retired` (retried 30 × 1 s, then connections are allowed again and the restore fails), staging → live (once; on failure the retired one is renamed back), then drops the retired one. A failure drops staging and leaves the live database as it was. At start `recover_interrupted_restore` removes a stale marker, renames `nfnn_restore_retired` back when the live database is missing, drops staging and deletes `*.upload.part`. `nfnn-postgres.sh` syncs the role password over `-d postgres`, so it works mid-swap. `backend/docker-entrypoint.sh` waits while the marker, a `*.restore` request or a `/restore/*.dump` exists and deletes a request older than 5 minutes when no marker exists, so Liquibase never runs against a swapped database and an unattended request never blocks the backend for good.
- A restore brings back everything as of the dump, sequences included: receipt numbers issued since the dump would be issued again. Say so wherever a restore is offered.
- Restore folder (by hand): `/restore` with exactly one `*.dump` at container start. Into an empty database it is restored as it is; into a non-empty one only when named `*.force.dump` (any other name is renamed `.skipped`); more than one dump skips them all; the same `restore_dump`; the file ends as `.dump.done` or `.dump.failed` (the data stayed, the backend starts).
- Watching: the backend's daily check (`app.operations.backups.check-cron`, 07:15 Prague) turns the status files into problems (no, failed or stale backup: 26 h; no, failed or stale test restore: 8 days; folder not mounted) and e-mails the monthly report's recipients once per outage and once on recovery (`backup_alert_state`). `/sprava/zalohy` shows the same.
- Where: `/DATA/AppData/nfnn/backups/` on the same disk as the database, the only copy; the off-site copy is postponed until after the launch on nfnn.cz, Jakub would like it on iCloud (2026-10-23). The dump holds the settings (secrets sealed) and the receipt signature; `secrets/` is not backed up, so after a restore on a new server `MAIL_PASSWORD` and `FIO_TOKEN` are unreadable and the administrator types them again on `/sprava/nastaveni`, which names them (Jakub 2026-10-23); the key never goes into a backup.
- Rollback: the older short-SHA image tag in the ZimaOS app settings; a restore only when the newer version made a breaking schema change (`backend.md`, Persistence).
