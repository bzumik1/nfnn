# Reliability rules (stability)

- Fail fast at startup, never at runtime: configuration validated by `@ConfigurationProperties`, schema validated by Hibernate against Liquibase, invalid IBAN or empty `PUBLIC_URL` stop the backend. Settings stored in the database are bound against the same records before they are saved (`StartupBindingSettingsValidator`), so a saved value can never put the backend into a restart loop. A feature without its secret is off, not broken (`FIO_TOKEN`, `MAIL_*`: the send is logged and skipped).
- Every write is retry-safe: idempotency keys (bank transaction id, report month, receipt fingerprint), locks where numbering or pairing races (the `donor_record` row for receipt numbers; `application/pairing/PairingLock`, `pg_advisory_xact_lock(20261022)`, taken first by every pairing writer and by the README reversal SQL), `AFTER_COMMIT` listeners for side effects, no partial state on failure.
- Scheduled work: one thread; a job logs its outcome, swallows its own exceptions, keeps a bookmark (`bank_import_state`, `donation_monthly_report`) so the next run completes a missed or failed one; shutdown drops delayed tasks and awaits a running import (`spring.task.scheduling.shutdown`).
- External calls have timeouts and bounded retries: Fio requests time out (`app.donations.fio.request-timeout`), rate refusals become follow-ups, never a blocked scheduler thread; mail failures are logged with the id and exception class only.
- Resources are bounded: receipt rendering limited to `app.donations.receipt.concurrent-renders` (3); rate-limit windows expire; container memory limits in `deploy/compose.yml` (backend 1 G with `MaxRAMPercentage=75`); log rotation 3 × 10 MB.
- Frontend: polls are capped (bank check 45 × 2 s, add-account watch 20 checks, paused when the tab is hidden); one silent refresh then a clean sign-in; every failure has a retry or a next step in the UI; nothing depends on the client clock for business rules (`yearlyReceiptsAvailableThrough` comes from the API).
- Migrations: backward-compatible steps when possible; a schema change in a release is noted in the PR because rollback means restoring a dump (`deploy/README.md`, Zálohy).
- Observability today: `/actuator/health` (Docker healthcheck, mail indicator off on purpose), container logs, the monthly report e-mail (import status, unpaired payments), and the import outage e-mail to `REPORT_RECIPIENT` (third counted failure in a row or a rejected Fio token, once per outage, kept in `bank_import_state.reported_outage`, plus one on recovery). Nothing else alerts; a change that could fail silently must log at `warn`/`error` with enough context to act on.
- CI gates every merge (`pr-check.yml`): backend build and tests, Stylelint, Vitest, production build, Playwright + axe, the six Docker images, the production compose started and probed (first setup and restart included), the compose invariants checked. Keep it green; never skip or weaken a test to get there.
