# Reliability rules (stability)

- Fail fast at startup, never at runtime: configuration validated by `@ConfigurationProperties`, schema validated by Hibernate against Liquibase, invalid IBAN or empty `PUBLIC_URL` stop the backend. Settings stored in the database are bound against the same records before they are saved (`StartupBindingSettingsValidator`), so a saved value can never put the backend into a restart loop. A feature without its secret is off, not broken (no Fio token: no import). Mail has no off switch: `MAIL_HOST` is required in the first setup; a failed send is logged with the id and the exception class and not retried, except the monthly report, which retries the next morning.
- Every write is retry-safe: idempotency keys (bank transaction id, report month, receipt fingerprint), row versions an administrator's write names (`If-Match`, 2.18: a write from a stale view is refused with 409 instead of overwriting), locks where numbering or pairing races (the `donor_record` row for receipt numbers; `application/pairing/PairingLock`, `pg_advisory_xact_lock(20261022)`, taken first by every pairing writer: the import and pairing after registration (`PaymentPairingService`), symbol-claim answers, manual pairing and unpairing, the administrator's symbol-claim reversals and resets, removing a learned account link, disconnecting and reconnecting one (the donor's own and the administrator's, since 2.18, so the version an administrator's write names is compared under the lock; reconnecting also keeps relying on the unique index `uq_donor_sender_account_live`), and the GDPR erasure (`DonorRecordService.erase`)), `AFTER_COMMIT` listeners for side effects, no partial state on failure.
- Scheduled work: one thread; a job logs its outcome, swallows its own exceptions, keeps a bookmark (`bank_import_state`, `donation_monthly_report`, `backup_alert_state`) so the next run completes a missed or failed one; shutdown drops delayed tasks and awaits a running import for up to 30 s (`spring.task.scheduling.shutdown`); the backend's `stop_grace_period: 75s` leaves room for both, and a run cut off anyway is completed by the next one (keyed by transaction id).
- Every external call has a timeout and bounded retries: Fio (`app.donations.fio.request-timeout`; rate refusals become follow-ups, never a blocked scheduler thread), the client metadata fetch (5 s), the connector's photo download (15 s), a Web Push message (10 s to connect and to answer, `HttpClientPushTransport`; the devices of one send at once, so a test alert waits for the slowest; the test alert is not retried, an operational alert is tried again 1, 5 and 15 minutes later for the devices that failed, only while it has not changed since, on the scheduler thread, slice 2.28), the settings' SMTP probe and every mail send (10 s to connect, read and write: `spring.mail.properties.mail.smtp.{connectiontimeout,timeout,writetimeout}`, `MailTransportConfigurationTest`), so a hanging SMTP server never holds the scheduler thread. A new external call gets its timeout in the same PR.
- Resources are bounded: the server draws no receipt since slice 1.10 (the browser does); rate-limit windows expire and each limiter keeps at most 50 000 keys by default, about 11 MB per limiter at worst (`FixedWindowRateLimiter` takes its `maximumTrackedKeys`; the administrator-only limiters (the backup key, the key withdrawal, the test push alert, the administration unlock and the administration's two device sync limiters) keep `ADMINISTRATOR_ONLY_MAXIMUM_TRACKED_KEYS`, 1 000), so the 29 limiters of today stay under about 252 MB of the backend's heap even when all are flooded, and a new limiter counts against it; container memory limits in `deploy/compose.yml` (backend 1 G with `MaxRAMPercentage=75`, nothing below 256M); container logs 3 × 10 MB (compose), `backend.log` 10 MB files for 14 days up to 200 MB (`application-prod.yml`), the access and connector logs daily for 14 days.
- Frontend: polls are capped (bank check for at most 90 s, read again on the live `bank-import` hint, else every 2 s without a stream and 15 s with one; add-account watch 20 checks 30 s apart, paused while the tab is hidden; backup job 20 × 3 s; restart wait 100 and restore wait 300 × 3 s; the key card's wait for a new signing key after a withdrawal 100 × 3 s); the live stream (`core/live/`, 2.16) only in a visible tab with a listening page, reopened after 1 s doubling to 60 s with jitter, never after a 401 or 403 until the session is renewed (a new sign-in or the next token refresh), and every page still works without it; the web as an app (slice 2.4) is bounded too: the boot watchdog waits 15 s, re-arms in 15 s steps up to 60 s while the app's code has arrived, then shows its panel, and reloads by itself at most once per 60 s per reason (`ReloadGuard` in `sessionStorage`: `boot`, `update`, `unrecoverable`, `chunk-load`), never without the storage; a new version reloads by itself only within `START_UP_WINDOW_MS` (10 s) of the start, and `loadNewVersion` waits at most `UPDATE_CHECK_TIMEOUT_MS` (10 s) for the worker's check; the service worker gives the network 5 s before it serves a kept public answer (only on a network failure or that timeout, never on a 5xx), and keeps at most 100 public answers for 30 days, the payment details for a day and 300 photos for 365 days; one silent refresh then a clean sign-in; every failure has a retry or a next step in the UI; the receipt PDF has no server fallback (plan v3, answer A3: the server draws no receipt since 1.10), so a drawing that fails tells the donor what to do next (try again, another browser, or write to info@nfnn.cz) and is reported to `/api/operations/client-errors` (1.20), where `nfnn_log_search` finds it; nothing depends on the client clock for business rules (`yearlyReceiptsAvailableThrough` comes from the API).
- Migrations: the previous image keeps working against the new schema (`backend.md`, Persistence), because a rollback means the older image and, only after a breaking change, restoring a dump (`deploy/README.md`, Zálohy), which loses everything since the dump. A breaking schema change is named in the PR.
- Observability: `/actuator/health` (Docker healthcheck, mail indicator off on purpose); the logs, log levels and diagnostics under `/api/admin/operations/` (the connector's `nfnn_log*` tools); the monthly report e-mail (import status, unpaired payments); the import outage e-mail (third counted failure in a row or a rejected Fio token, once per outage, kept in `bank_import_state.reported_outage`, plus one on recovery; queued in `donation_import_alert` and retried after every import run until the mail server takes it) and the backup watch e-mail (daily 07:15: no, failed or stale backup or test restore, folder not mounted; once per outage and recovery, `backup_alert_state`), both to the monthly report's recipients; the same outages and recoveries, and a refused e-mail, also go as push alerts to the administrators' devices that want them (slice 2.28). The browser's error reports (`/api/operations/client-errors`) also name a start the watchdog had to rescue (`boot` / `start-up`), a new version that failed to install (`sw-install`) and a running version the server no longer has (`sw-unrecoverable`, both `service-worker`), so `nfnn_log_search` finds them. Nothing else alerts; a change that could fail silently must log at `warn`/`error` with enough context to act on.
- CI gates every merge (`pr-check.yml`, plus `roadmap-check.yml` for the roadmap): backend build and tests; Prettier, ESLint, Stylelint, Vitest, the production build and Playwright + axe for the frontend; `npm run check` for the connector; the five Docker images; the production compose started and probed (first setup, restart, backups and restore included); the compose invariants checked. Keep it green; never skip or weaken a test to get there.
