# Reliability rules (stability)

How each mechanism works is in `docs/system-overview.md` (shared "Database sessions", donations pairing and import, operations) and `docs/frontend-overview.md` ("Bounds on client work"); this file is what a change must keep true.

- Fail fast at startup, never at runtime: configuration is a validated `@ConfigurationProperties` record, the schema is validated by Hibernate against Liquibase, an invalid IBAN or an empty `PUBLIC_URL` stops the backend. A setting stored in the database is bound against the same records before it is saved (`StartupBindingSettingsValidator`), so a saved value never puts the backend into a restart loop. A feature without its secret is off, not broken (no Fio token: no import). Mail has no off switch: `MAIL_HOST` is required in the first setup; a failed send is logged with the id and the exception class and not retried, except the monthly report, which retries the next morning.
- Every write is retry-safe: idempotency keys (bank transaction id, report month, receipt fingerprint); the row version an administrator's write names (`If-Match`: a write from a stale view gets 409 instead of overwriting); locks where numbering or pairing races (the `donor_record` row for receipt numbers; `PairingLock`, taken first by every pairing writer, the list in `docs/system-overview.md` donations); `AFTER_COMMIT` listeners for side effects; no partial state on failure. Advisory locks only as constants of `shared/infrastructure/lock/AdvisoryLock`, each with a key of its own (`AdvisoryLockTest`, `AdvisoryLockRulesTest`); more in `database.md`.
- Scheduled work runs on one thread. A job logs its outcome, swallows its own exceptions and keeps a bookmark (`bank_import_state`, `donation_monthly_report`, `backup_alert_state`), so the next run completes a missed or failed one. Shutdown drains requests for up to 20 s, waits up to 20 s for running `@Async` work, drops delayed tasks and awaits a running import for up to 30 s (`spring.task.scheduling.shutdown`); the backend's `stop_grace_period: 75s` leaves room for all three (`ShutdownBudgetTest`), and a run cut off anyway is completed by the next one (keyed by transaction id).
- Every external call has a timeout and bounded retries, and a new external call gets its timeout in the same PR. Today: Fio (`app.donations.fio.request-timeout`; a rate refusal becomes a follow-up, never a blocked scheduler thread), the client metadata fetch 5 s in all, name lookup included, fetched outside its cache's lock, the ČNB bank code list 10 s in all, name lookup included (checked daily, downloaded at most weekly, a failure keeps the stored list), a bank logo 10 s in all, name lookup included, at most 1 MB and no redirect (checked daily, downloaded at most weekly, a failure keeps the stored image), the ARES company lookup 3 s in all for the name lookup, the connection and the whole answer (`AresCompanyRegistry`; no retry, the donor types the data, and `CompanyRegistryBreaker` skips ARES for 5 minutes after 3 failures in a row), the connector's photo download 15 s, a Web Push message 10 s for the name lookup, to connect and to answer (`HttpClientPushTransport`; an operational alert is retried for the devices that failed, as `docs/system-overview.md` operations says, on the scheduler thread; the test alert is not retried), and the SMTP probe and every mail send 10 s to connect, read and write (`spring.mail.properties.mail.smtp.{connectiontimeout,timeout,writetimeout}`, `MailTransportConfigurationTest`), so a hanging SMTP server never holds the scheduler thread.
- Every database wait ends (`DatabaseWaitLimitsTest`): pooled sessions start with `lock_timeout=10s`, `statement_timeout=30s` and `idle_in_transaction_session_timeout=2min` through pgjdbc `options` in `spring.datasource.hikari.data-source-properties`, never `ALTER ROLE` or the server's settings (a restore as the same role would inherit them); at most 20 pooled connections, a request waits at most 10 s for one, a connection lives 30 min, one held over 60 s is reported at WARN; a lock, statement or connection wait that runs out answers 503 `server-busy` with `Retry-After: 5` (`ServerBusyHandler`), and a scheduled job logs it and runs again at its next time; Liquibase migrates on its own connection with no statement limit and a 2 min lock wait (`app.database.migration.lock-timeout`). No connection is held across slow work that needs none (`database.md`). A transaction that must stay open longer than these limits names why in its PR.
- Resources are bounded:
  - An uploaded photo or receipt signature is refused from its header above 8 000 px on a side, 48 million pixels or 8 bits per sample, and each adapter decodes one upload at a time.
  - Password hashing runs in one slot per processor, at most four requests per slot waiting up to 2 s, the rest 503 `server-busy` (`CpuSlots`).
  - Rate-limit windows expire; each `FixedWindowRateLimiter` keeps at most 50 000 keys by default (about 11 MB at worst) and an administrator-only limiter `ADMINISTRATOR_ONLY_MAXIMUM_TRACKED_KEYS` (1 000), so all limiters together stay under about 278 MB of the backend's heap even when flooded; a new limiter counts against that budget (the list and the arithmetic: `docs/security-overview.md` "Abuse limits").
  - Container memory limits in `deploy/compose.yml` (backend 1 G with a heap of `MaxRAMPercentage=60` on the entrypoint's `java` line, leaving room for the 280 to 370 MB Java keeps beside it, `stack` probe; nothing below 256M); container logs 3 × 10 MB (compose); `backend.log` 10 MB files for 14 days up to 200 MB (`application-prod.yml`); the access and connector logs daily for 14 days.
- Frontend: every poll, reconnect, wait and self-reload is capped, and the caps are in `docs/frontend-overview.md` "Bounds on client work". The live stream runs only in a visible tab with a listening page, backs off, and never reconnects after a 401 or 403 until the session is renewed; every page works without it. The app reloads by itself at most once per 60 s per reason (`ReloadGuard` in `sessionStorage`), never without that storage, and a new version reloads by itself only at a free moment (`AppUpdates`). The service worker serves kept public content at once and fetches it behind it, the kept payment details only on a network failure or after 1 s without one, never on a 5xx, and its caches are bounded. Nothing waits on a network `Connectivity` knows is gone: the probe gives up after 5 s and a session restore stops waiting at once. One silent refresh, then a clean sign-in. Every failure has a retry or a next step in the UI; the receipt PDF has no server fallback (plan v3, answer A3), so a drawing that fails tells the donor what to do next (try again, another browser, or write to info@nfnn.cz) and is reported to `/api/operations/client-errors`.
- Nothing depends on the client clock for a business rule (`yearlyReceiptsAvailableThrough` comes from the API).
- Migrations: the previous image keeps working against the new schema (`backend.md` Persistence), because a rollback means the older image and, only after a breaking change, restoring a dump, which loses everything since the dump (`deploy/README.md`, Zálohy). A breaking schema change is named in the PR.
- Observability: `/actuator/health` (Docker healthcheck, mail indicator off on purpose); the logs, log levels and diagnostics under `/api/admin/operations/`; the monthly report e-mail; the import outage e-mail and the backup watch e-mail (once per outage and once per recovery, to the monthly report's recipients); the same outages and recoveries, and a refused e-mail, as push alerts to the administrators' devices that want them; the browser's error reports (`/api/operations/client-errors`, read with `nfnn_log_search`). How each alert is kept and retried: `docs/system-overview.md` donations and operations. Nothing else alerts: a change that could fail silently logs at `warn` or `error` with enough context to act on.
- CI gates every merge (`pr-check.yml`, plus `roadmap-check.yml`; rules in `deploy-ci.md`, each job in `docs/system-overview.md` "CI in detail"). Keep it green; never skip or weaken a test to get there.
