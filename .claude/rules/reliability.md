# Reliability rules (stability)

- Fail fast at startup, never at runtime: configuration validated by `@ConfigurationProperties`, schema validated by Hibernate against Liquibase, invalid IBAN or empty `PUBLIC_URL` stop the backend. Settings stored in the database are bound against the same records before they are saved (`StartupBindingSettingsValidator`), so a saved value can never put the backend into a restart loop. A feature without its secret is off, not broken (no Fio token: no import; no SMTP: the send is logged and skipped).
- Every write is retry-safe: idempotency keys (bank transaction id, report month, receipt fingerprint), locks where numbering or pairing races (the `donor_record` row for receipt numbers; `application/pairing/PairingLock`, `pg_advisory_xact_lock(20261022)`, taken first by every pairing writer: the import, pairing after registration, symbol-claim answers, manual pairing, and the administrator's symbol-claim reversals and account-link changes), `AFTER_COMMIT` listeners for side effects, no partial state on failure.
- Scheduled work: one thread; a job logs its outcome, swallows its own exceptions, keeps a bookmark (`bank_import_state`, `donation_monthly_report`, `backup_alert_state`) so the next run completes a missed or failed one; shutdown drops delayed tasks and awaits a running import for up to 30 s (`spring.task.scheduling.shutdown`; Docker's stop timeout must exceed that, and `deploy/compose.yml` sets none yet, so on the server the next run completes a cut-off import).
- External calls have timeouts and bounded retries: Fio requests time out (`app.donations.fio.request-timeout`), rate refusals become follow-ups, never a blocked scheduler thread; mail failures are logged with the id and exception class only.
- Resources are bounded: receipt rendering limited to `app.donations.receipt.concurrent-renders` (3); rate-limit windows expire; container memory limits in `deploy/compose.yml` (backend 1 G with `MaxRAMPercentage=75`, nothing below 256M); container logs 3 × 10 MB (compose), `backend.log` 10 MB files for 14 days up to 200 MB (`application-prod.yml`), the access and connector logs daily for 14 days.
- Frontend: polls are capped (bank check 45 × 2 s, add-account watch 20 checks, paused when the tab is hidden); one silent refresh then a clean sign-in; every failure has a retry or a next step in the UI; nothing depends on the client clock for business rules (`yearlyReceiptsAvailableThrough` comes from the API).
- Migrations: the previous image keeps working against the new schema (`backend.md`, Persistence), because a rollback means the older image and, only after a breaking change, restoring a dump (`deploy/README.md`, Zálohy), which loses everything since the dump. A breaking schema change is named in the PR.
- Observability: `/actuator/health` (Docker healthcheck, mail indicator off on purpose); the logs, log levels and diagnostics under `/api/admin/operations/` (the connector's `nfnn_log*` tools); the monthly report e-mail (import status, unpaired payments); the import outage e-mail (third counted failure in a row or a rejected Fio token, once per outage, kept in `bank_import_state.reported_outage`, plus one on recovery) and the backup watch e-mail (daily 07:15: no, failed or stale backup or test restore, folder not mounted; once per outage and recovery, `backup_alert_state`), both to the monthly report's recipients. Nothing else alerts; a change that could fail silently must log at `warn`/`error` with enough context to act on.
- CI gates every merge (`pr-check.yml`): backend build and tests; Prettier, ESLint, Stylelint, Vitest, the production build and Playwright + axe for the frontend; `npm run check` for the connector; the five Docker images; the production compose started and probed (first setup, restart, backups and restore included); the compose invariants checked. Keep it green; never skip or weaken a test to get there.
