# Reliability rules (stability)

- Fail fast at startup, never at runtime: configuration validated by `@ConfigurationProperties`, schema validated by Hibernate against Liquibase, invalid IBAN or empty `PUBLIC_URL` stop the backend. Settings stored in the database are bound against the same records before they are saved (`StartupBindingSettingsValidator`), so a saved value can never put the backend into a restart loop. A feature without its secret is off, not broken (no Fio token: no import). Mail has no off switch: `MAIL_HOST` is required in the first setup; a failed send is logged with the id and the exception class and not retried, except the monthly report, which retries the next morning.
- Every write is retry-safe: idempotency keys (bank transaction id, report month, receipt fingerprint), locks where numbering or pairing races (the `donor_record` row for receipt numbers; `application/pairing/PairingLock`, `pg_advisory_xact_lock(20261022)`, taken first by every pairing writer: the import and pairing after registration (`PaymentPairingService`), symbol-claim answers, manual pairing and unpairing, the administrator's symbol-claim reversals and resets, removing a learned account link, and the GDPR erasure (`DonorRecordService.erase`); disconnect and reconnect rely on the unique index `uq_donor_sender_account_live` instead), `AFTER_COMMIT` listeners for side effects, no partial state on failure.
- Scheduled work: one thread; a job logs its outcome, swallows its own exceptions, keeps a bookmark (`bank_import_state`, `donation_monthly_report`, `backup_alert_state`) so the next run completes a missed or failed one; shutdown drops delayed tasks and awaits a running import for up to 30 s (`spring.task.scheduling.shutdown`); the backend's `stop_grace_period: 75s` leaves room for both, and a run cut off anyway is completed by the next one (keyed by transaction id).
- Every external call has a timeout and bounded retries: Fio (`app.donations.fio.request-timeout`; rate refusals become follow-ups, never a blocked scheduler thread), the client metadata fetch (5 s), the connector's photo download (15 s), the settings' SMTP probe and every mail send (10 s to connect, read and write: `spring.mail.properties.mail.smtp.{connectiontimeout,timeout,writetimeout}`, `MailTransportConfigurationTest`), so a hanging SMTP server never holds the scheduler thread. A new external call gets its timeout in the same PR.
- Resources are bounded: receipt rendering limited to `app.donations.receipt.concurrent-renders` (3); rate-limit windows expire and each limiter keeps at most 50 000 keys by default, about 11 MB per limiter at worst (`FixedWindowRateLimiter` takes its `maximumTrackedKeys`; the administrator-only backup key limiter keeps 1 000), so the 17 limiters of today stay under about 176 MB of the backend's heap even when all are flooded, and a new limiter counts against it; container memory limits in `deploy/compose.yml` (backend 1 G with `MaxRAMPercentage=75`, nothing below 256M); container logs 3 × 10 MB (compose), `backend.log` 10 MB files for 14 days up to 200 MB (`application-prod.yml`), the access and connector logs daily for 14 days.
- Frontend: polls are capped (bank check 45 × 2 s; add-account watch 20 checks 30 s apart, paused while the tab is hidden; backup job 20 × 3 s; restart wait 100 and restore wait 300 × 3 s; the key card's wait for a new signing key after a withdrawal 100 × 3 s); one silent refresh then a clean sign-in; every failure has a retry or a next step in the UI; nothing depends on the client clock for business rules (`yearlyReceiptsAvailableThrough` comes from the API).
- Migrations: the previous image keeps working against the new schema (`backend.md`, Persistence), because a rollback means the older image and, only after a breaking change, restoring a dump (`deploy/README.md`, Zálohy), which loses everything since the dump. A breaking schema change is named in the PR.
- Observability: `/actuator/health` (Docker healthcheck, mail indicator off on purpose); the logs, log levels and diagnostics under `/api/admin/operations/` (the connector's `nfnn_log*` tools); the monthly report e-mail (import status, unpaired payments); the import outage e-mail (third counted failure in a row or a rejected Fio token, once per outage, kept in `bank_import_state.reported_outage`, plus one on recovery; queued in `donation_import_alert` and retried after every import run until the mail server takes it) and the backup watch e-mail (daily 07:15: no, failed or stale backup or test restore, folder not mounted; once per outage and recovery, `backup_alert_state`), both to the monthly report's recipients. Nothing else alerts; a change that could fail silently must log at `warn`/`error` with enough context to act on.
- CI gates every merge (`pr-check.yml`, plus `roadmap-check.yml` for the roadmap): backend build and tests; Prettier, ESLint, Stylelint, Vitest, the production build and Playwright + axe for the frontend; `npm run check` for the connector; the five Docker images; the production compose started and probed (first setup, restart, backups and restore included); the compose invariants checked. Keep it green; never skip or weaken a test to get there.
