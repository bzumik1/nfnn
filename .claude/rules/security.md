# Security rules

Threat model: a public site (public repository) whose donor accounts yield tax receipts in the donor's name, with an administration reachable from the browser and from connected AI clients. Prevent: reading another donor's data, a receipt in another name, administrator takeover, abuse of e-mail sending, exhausting the server. How each mechanism works is in `docs/security-overview.md` (update it in the same PR); endpoints and problem codes in `docs/api-contract.md`. These rules hold whatever the task; weakening one needs Jakub's OK in the PR.

- Access: everything under `/api` needs the donor JWT unless listed `permitAll` in `ApiSecurityConfiguration`; resources are found by the JWT subject; another donor's resource answers 404, never 403. A new endpoint gets a 401 scenario and, for a donor resource, a 404 one for another donor; a new public endpoint also gets its `permitAll` line and a rate limiter.
- Administration: `/api/admin/**` needs `ADMIN`, which enters the JWT only for a session opened with the second factor (TOTP or passkey). The role is granted and removed only by another administrator in the web GUI (the first one from `ADMIN_EMAILS` while the site has none), never by oneself, never by SQL. Every administrator's change publishes `AdminActionPerformed`.
- Connected applications (a token with a `scope` claim): a change needs `admin:write`. The dangerous or irreversible actions stay web-only (Jakub 2026-10-23): deletions, older-symbol reversals, the administrator role, second-factor and passkey resets, GDPR erasure, secrets, the receipt signature (the connector only reads whether one is set), backup download and restore, approving a connection, the administrator's own account. Web-only means guarded by `BrowserSessionAuthorizationManager` in `ApiSecurityConfiguration` with a 403 scenario in `connected_apps.feature`; a missing MCP tool is not a control, because whoever holds a connector token can exchange it for an API token.
- MCP connector: holds no secret and validates no token itself (it exchanges every bearer token at the backend); it reaches only `/api/admin/**`; it has a tool for every setting and all data of the administration except the web-only list. A new tool that reveals names or addresses beyond what the API already returns to an administrator is a security change.
- Credentials and one-time secrets: passwords only through `BCryptPasswordHasher`; an unknown e-mail or a password-less account still costs the `UNKNOWN_DONOR_HASH` compare; no endpoint reveals whether an address is registered. Reset and verification links, challenges and codes are random, stored only as SHA-256, short-lived, single-use and marked used before any check; link secrets travel in the URL fragment. Changing the password, e-mail, second factor or passkeys needs the current password or the donor's own passkey, revokes the other sessions and e-mails the donor. Refresh tokens rotate; a replay ends every session.
- Abuse: every unauthenticated, credential-checking or mail-sending endpoint has a per-address limiter built like `SignInRateLimiter`, checked before any hashing or work (the table is in `docs/security-overview.md`). The client address is the one the frontend nginx resolved; the backend trusts forwarded headers from any peer, so port 8080 is never published, nothing else relays client headers to it, and a server-to-server call that hits a limiter must carry the visitor's address.
- Outbound requests (client metadata documents in the backend, photos in the connector): `https` only, every resolved address checked against private, loopback, link-local and reserved ranges, redirects none or re-checked, a timeout and a size cap.
- Input: Bean Validation with explicit `@Size` on every request record, value objects validate again, honeypot on public forms; JPA parameters only (no string-built queries).
- Output: `server.error.include-*: never`; problem+json carries no stack trace or exception text; Thymeleaf `th:text` only; Angular bindings only (no `innerHTML`).
- Secrets: never in compose, code, docs, tests, URLs, logs, PRs or commit messages; on the server generated into `secrets/` or sealed in `operations_setting`, never returned by an API, changed only from a browser session; locally only `.env`. `JWT_SECRET` and `SETTINGS_KEY` have defaults only in `application-dev.yml`. A record or class that holds a password, secret or token masks `toString` (`RawPassword`).
- Logs (backend, connector, nginx): ids and outcomes only, never names, e-mails, addresses, query strings, tokens or message bodies. A new log field, a new `log_format` or a log of a full exception whose message may carry data (SQL, SMTP) is a security change.
- Browser: the Content-Security-Policy in `frontend/nginx-security-headers.conf` allows no inline script and no third-party resource; an inline script, an external resource or a new kind of embed extends it in the same PR, verified against the production nginx (skill `visual-check`); `inlineCritical` stays off in `angular.json`; CORS stays unconfigured (same origin).
- Data protection: collect only what receipts and pairing need; contact messages are deleted after a year; the privacy policy changes with the feature that changes the data.
- Supply chain: supported majors only; a new dependency needs a reason in the PR and, for a library, an ArchUnit rule confining it to adapters; workflows use `persist-credentials: false` and minimal `permissions`; official base images; application processes run unprivileged (the entrypoints hand Java to `app` with `setpriv` and Node to `node` with `su-exec` after the root-only setup), and a new one does the same.
- Unsure whether something is sensitive? Treat it as sensitive and ask Jakub in the PR.
