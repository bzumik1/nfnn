# Security rules

Threat model: a public site whose donor accounts yield tax receipts in the donor's name. Attacks to prevent: reading another donor's gifts, a receipt in another name, abuse of e-mail sending, exhausting the server. These rules hold whatever the task.

- Authentication: e-mail + password (BCrypt cost 12; 12–128 characters, common-password list in `RawPassword`); access token HS256 JWT, 15 min, in memory only; refresh token 14 days in an HttpOnly Secure SameSite=Strict cookie on `/api/donors/auth`, stored hashed, rotated on use, reuse revokes every session. Password reset: 43-character secret in the URL fragment only, stored as SHA-256, single use, 1 h, at most 3 live per donor; confirm revokes all sessions.
- Authorization: everything under `/api` requires the donor JWT unless listed `permitAll` in `ApiSecurityConfiguration`; resources are found by the JWT subject; another donor's resource answers 404, never 403. Role `ADMIN` is reserved, no admin endpoint exists.
- Abuse limits (per client address, 429 before any work): contact 5/h, sign-in 10/15 min, registration 5/h, reset request 5/h; bank check 30 s global. The address comes from `X-Forwarded-For` set by the frontend nginx (`set_real_ip_from` private ranges, client values overwritten, `Forwarded` emptied); never trust a client header elsewhere. Unknown e-mail sign-in costs a real BCrypt compare (`UNKNOWN_DONOR_HASH`).
- Input: Bean Validation with explicit `@Size` on every request record, value objects validate again, honeypot on public forms; JPA parameters only (no string-built queries).
- Output: `server.error.include-*: never`; problem+json carries no stack trace or exception text; logs carry ids and outcomes only; Thymeleaf `th:text` only; Angular bindings only (no `innerHTML`); no secrets or tokens in URLs, logs, PRs or commit messages.
- Secrets: server env files `/DATA/AppData/nfnn/env/{db,backend}.env` (mode 600) and local `.env` only; never in compose, code, docs or tests; `JWT_SECRET` has a default only in `application-dev.yml`; the PR check fails when a secret name appears in `deploy/compose.yml` or reaches the database containers.
- Headers and transport: TLS ends at Nginx Proxy Manager (Cloudflare in front later); nginx adds `nosniff`, `X-Frame-Options SAMEORIGIN`, `Referrer-Policy`, `Permissions-Policy`; CORS stays unconfigured (same origin); the backend port is never published. A Content-Security-Policy is planned as its own PR (`script-src 'self'`, styles `'unsafe-inline'`); until then XSS defence is Angular's bindings and `th:text`.
- Data protection: collect only what receipts and pairing need; contact messages deleted after a year; the privacy policy changes with the feature that changes the data.
- Dependencies and supply chain: supported majors only; a new dependency needs a reason in the PR and, for a library, an ArchUnit rule confining it to adapters; workflows use `persist-credentials: false` and minimal `permissions`; official base images; the backend container runs as a non-root user.
- Unsure whether something is sensitive? Treat it as sensitive and ask Jakub in the PR.
