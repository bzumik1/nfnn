# Security rules

Threat model: a public site (public repository) whose donor accounts yield tax receipts in the donor's name, with an administration reachable from the browser and from connected AI clients. Prevent: reading another donor's data, a receipt in another name, administrator takeover, abuse of e-mail sending, exhausting the server. How each mechanism works is in `docs/security-overview.md` (update it in the same PR); endpoints and problem codes in `docs/api-contract.md`. These rules hold whatever the task; weakening one needs Jakub's OK in the PR.

- Access: everything under `/api` needs the donor JWT unless listed `permitAll` in `ApiSecurityConfiguration`; resources are found by the JWT subject; another donor's resource answers 404, never 403. A new endpoint gets a 401 scenario and, for a donor resource, a 404 one for another donor; a new public endpoint also gets its `permitAll` line and a rate limiter.
- Administration: `/api/admin/**` needs `ADMIN`, which enters the JWT only for a session opened with the second factor (TOTP or passkey). The role is granted only to an account with a confirmed e-mail, and granted and removed only by another administrator in the web GUI (the first one from `ADMIN_EMAILS` while the site has none), never by oneself, never by SQL. Every administrator's change publishes `AdminActionPerformed`. An administrator who holds a second factor changes a second factor or passkey only from a session opened with it, and reset-link recovery is refused to an administrator, so a stolen mailbox cannot enrol an attacker's factor.
- Connected applications (a token with a `scope` claim): a change needs `admin:write`. The dangerous or irreversible actions stay web-only (Jakub 2026-10-23): deletions, older-symbol reversals, the administrator role, second-factor and passkey resets, GDPR erasure, secrets and the site address (`PUBLIC_URL`), the receipt signatory and receipt signatures (choosing who signs, uploading or removing a person's receipt signature, reading a receipt signature's image or an issued receipt's image (`/api/admin/donations/receipt-images/*`), and changing the portrait or the name of the person who signs (the name since slice 1.22); the connector only reads who signs and whether a signature and a portrait are set, slice 1.16), backup download and restore, viewing and confirming the backup key (each view also needs a fresh second factor, Jakub 2026-10-28), withdrawing a receipt signing key (`/api/admin/donations/receipt-signing-keys/*/withdrawal`, with a fresh second factor, Jakub 2026-10-30; the connector only reads the keys), replacing an issued receipt (Jakub 2026-10-31), turning push alerts on or off for a device and the test alert (slice 2.27; the connector reads the devices and changes their alert switches only), unpairing a gift that the donor's active yearly receipt lists, which withdraws that receipt (slice 1.26), approving a connection, the administrator's own account, the administration's device copy (`GET /api/admin/donations/sync` and `/api/admin/donors/sync` with their `/chunks`: the whole administration at once, which the connector reads through its own tools; plan v3 2.17, approved by Jakub 2026-10-29) and unlocking it on a device and recording a stored copy (`POST /api/admin/donors/devices/current/unlock` and `/administration-copy`, slice 2.19). Web-only means guarded by `BrowserSessionAuthorizationManager` in `ApiSecurityConfiguration` (or, where one endpoint serves both kinds of token, a check of the `scope` claim: in the controller, as `AdminSettingsController` does for secrets, or passed to the application service when the refusal depends on stored data, as `AdminReceiptsController` does for receipt replacements and `AdminPaymentsController` for unpairing a gift on a yearly receipt) with a 403 scenario (`connected_apps.feature`; the secrets' in `settings.feature`). Every item on the list is guarded so (`BROWSER_ONLY_DELETES`, `BROWSER_ONLY_POSTS`, `BROWSER_ONLY_PUTS`, `BROWSER_ONLY_GETS`, security audit 2026-10-23), and a new endpoint for any item on the list gets the guard and its row in the scenario outline. Every handler under `/api/admin/` is classified as connector-reachable or browser-only in `shared/infrastructure/security/AdminHandlerReach` (test sources), and `AdminHandlerClassificationTest` fails on an unclassified handler, on a decision of the security chain that differs from its class and on an outline that is not exactly the browser-only handlers, so a new endpoint gets its row there; a class whose refusal comes after the security chain (`CONNECTOR_SECRETS_IN_BROWSER_ONLY`, `CONNECTOR_REPLACEMENTS_IN_BROWSER_ONLY`, `CONNECTOR_WITHDRAWALS_IN_BROWSER_ONLY`, `CONNECTOR_SIGNATORY_PORTRAIT_IN_BROWSER_ONLY`) is checked there only as connector-reachable, so its refusal needs its own 403 scenario. Connected applications with `admin:write` may issue receipts (A8, Jakub 2026-10-30) only on these conditions: through the donor's own issuer under the donor lock, idempotent (unchanged data return the active receipt), only a first receipt (a replacement is web-only, above; the yearly receipt issued after an unpairing withdrew the year's receipt counts as a first one, since it replaces nothing valid and only names the withdrawn one, slice 1.26), never for an erased donor, every new number audited with the `client`, and never a PDF to the connector; an erased donor's receipt reaches a connection without the name, company identifier, address and QR text (Jakub 2026-10-31). Three exceptions, each allowed by Jakub on 2026-10-30: removing the About photo (`nfnn_update_about`), because replacing it deletes the old one anyway and a quick takedown protects the child on it; removing any person of the foundation (`nfnn_remove_person`, decision card in the Lidé fondu thread), which deletes their portrait and web signature, except the person who signs the receipts, whom nobody removes until another is chosen (409 `content/person-signs-receipts`, slice 1.16); and setting and removing the web signature of a person of the foundation (`/api/admin/content/people/*/web-signature`, `nfnn_set_web_signature`, `nfnn_remove_web_signature`: "Klidně ať to konektor umí, to není nebezpečné"), a public image under the founders' note for the site only, never the receipt signature, which stays web-only. No image serves as both a portrait and a web signature (400 `content/person-image-in-use`). Member e-mails (`personalEmail`, `fundEmail`) are administration data: never in the home content, the audit details or a log. A missing MCP tool is not a control, because whoever holds a connector token can exchange it for an API token.
- MCP connector: holds no secret and validates no token itself (it exchanges every bearer token at the backend); its tools reach only `/api/admin/**` and `/actuator/{health,info}`, and it calls the token endpoint only to exchange tokens; it has a tool for every setting and all data of the administration except the web-only list. A new tool that reveals names or addresses beyond what the API already returns to an administrator is a security change.
- Credentials and one-time secrets: passwords only through `BCryptPasswordHasher`; an unknown e-mail or a password-less account still costs the `UNKNOWN_DONOR_HASH` compare; no endpoint reveals whether an address is registered. Reset and verification links, challenges and codes are random, stored only as SHA-256, short-lived, single-use and marked used before any check (one exception, Jakub 2026-10-24: the message code of the 1 Kč second-factor recovery is also kept readable, so starting the recovery again shows the same code; it unlocks nothing without the payment from the donor's verified account); link secrets travel in the URL fragment. The password and the e-mail change only with the current password (or the donor's own passkey) and revoke every other session; a new address is confirmed from that address and the old one is told. Turning the second factor on or off needs the password and a code and revokes every other session. Adding a passkey needs the current password or a passkey and e-mails the donor. A new credential change does at least as much as the closest of these. Refresh tokens rotate; a replay ends every session, except the 60 s reuse grace of a lost answer (a used, unexpired browser token whose successor was never used revokes and supersedes that successor and gets a new one, and the superseded successor presented later is a replay too; plan v3 decision D28 answering S-H4, allowed by Jakub on 2026-11-05 in PR #297; a used token presented again within those 60 s whose device, or its successor's device, has ended is only refused, 2.9), and a replay never asks a device to delete its data. Sign-out revokes the presented token and its unused successor, and a superseded one ends every session. Every browser session is a device (2.9): only `DeviceSignOuts` revokes refresh tokens in bulk, by donor or by device (ArchUnit), and it ends the device too, so a browser access token (claim `sid`) of an ended device is refused within the 30 s of `DeviceSessionLiveness` at most (401 `auth/session-ended`); signing out the other devices leaves connected applications alone (Q12, Jakub 2026-11-05); a change made from a session continues that session and ends every other one, a change from a link or by an administrator ends all; the device stores only the platform and browser of closed lists, never the `User-Agent` itself. The browser refreshes and signs out under a Web Lock, one tab at a time. A session's kind (2.10: the installed app 400 days, "Zapamatovat si mě" `SESSION_REMEMBER_DAYS`, a browser 12 h, "Cizí počítač" 1 h and at most 12 h from its sign-in, each from the last refresh) is the client's claim and grants nothing: roles and checks are the same for every kind, the app's token lives in its own cookie and one presented in the other cookie is refused without ending a session only after the replay checks, and a restore from a backup revokes every refresh token and ends every device.
- First setup (`/api/operations/setup…`): public only until completed (then 409); without the code only for `X-Nfnn-Direct` from the frontend nginx plus a private client address (`HomeNetworkRequests`); the setup code goes to standard output only, never to `backend.log` or the log API.
- Abuse: every endpoint that checks a guessable secret (password, TOTP code, setup code), sends mail or triggers an outbound request has a per-address limiter built like `SignInRateLimiter`, checked before any hashing or work (the table is in `docs/security-overview.md`); endpoints keyed only by a 256-bit secret need none. The client address is the one the frontend nginx resolved; the backend trusts forwarded headers from any peer, so port 8080 is never published, the containers sit on their own network `nfnn-edge` instead of the default bridge other apps on the server share (one network, because ZimaOS attaches a service only to its first), nothing else relays client headers to it, and a server-to-server call that hits a limiter must carry the visitor's address.
- Outbound requests (client metadata documents and Web Push messages in the backend, photos in the connector): `https` only, a push endpoint only on a host of the push services browsers use (`PushEndpoint`, the real control, since `java.net.http` cannot pin the checked address), every resolved address checked against private, loopback, link-local and reserved ranges, redirects none or re-checked, a timeout and a size cap.
- Input: Bean Validation with explicit `@Size` on every request record, value objects validate again, honeypot on public forms; JPA parameters only (no string-built queries).
- Output: `server.error.include-*: never`; problem+json carries no stack trace or exception text; Thymeleaf `th:text` only; Angular bindings only (no `innerHTML`).
- Secrets: never in compose, code, docs, tests, URLs, logs, PRs or commit messages; on the server generated into `secrets/` or sealed in `operations_setting`, never returned by an API, changed only from a browser session; the stored SMTP password goes only to the server it was saved for (moving host, port, user or STARTTLS needs the password in the same change, the mail test uses it only against the running server); locally only `.env`. `JWT_SECRET`, `SETTINGS_KEY` and `BACKUP_KEY` have defaults only in `application-dev.yml`, and outside development the backend refuses their public values at startup (and the public backup key in the first-setup upload), and runs only in development or with exactly `prod` (`DevelopmentKeysGuard`); with no profile at all it is development, so `deploy/compose.yml` sets `prod` and the PR check pins it. A value object, `@ConfigurationProperties` record or request/response record that holds a password, secret or token masks `toString` (`RawPassword`, `FioImportProperties`). The API transcripts and shared cases are public and their masking knows only the secret shapes it was taught, so a change that brings a new kind of secret (a signing seed, VAPID keys, a hex or standard-base64 token, a new secret field or setting) registers it in the same PR: a masked value, field or shape in `cucumber/transcript/TranscriptNormaliser`, its environment name refused while recording (`ApiTranscripts`; secret settings and the server's generated secrets already are), and a hygiene rule with a planted case that fails in `regression/BaselineHygieneTest` (`testing.md`, Hygiene).
- Logs (backend, connector, nginx): ids and outcomes only, never names, e-mails, addresses, query strings, tokens or message bodies. A new log field, a new `log_format` or a log of a full exception whose message may carry data (SQL, SMTP) is a security change. Framework loggers above INFO write request and response bodies, headers or SQL values into logs that connections read: `ProtectedLoggers` pins those that do at DEBUG at INFO, the ones that write the request line, the query string, a parameter's value or the client address at DEBUG included (`FilterChainProxy`, `DispatcherServlet`, `BearerTokenAuthenticationFilter`, Tomcat's `catalina.core.ContainerBase` with a multipart field name, and the like; Tomcat's `Http11Processor` and `http.parser.Cookie`, which write a refused request target with its query string or an invalid cookie at INFO, at WARN) and refuses to change them, TRACE is refused for every logger outside `cz.novanadeje.app` (ROOT included), and a logger found to leak data at DEBUG joins `ProtectedLoggers` with its pin in `application.yml`. Raise a level (`nfnn_set_log_level`, `/sprava/logy`) preferably for `cz.novanadeje.app…`. Browser error reports (`/api/operations/client-errors`) log only values from closed lists (the enums `ClientErrorVocabularyTest` keeps equal to `frontend/src/app/core/errors/error-vocabulary.ts`, the revision pattern, numeric ranges), never the error's message, stack, the page address or the user agent string; a new list value, field or free-text slot there is a security change.
- Edge cache: every answer the frontend nginx proxies (`/api/`, `/mcp`, `/mcp-photos`, `/.well-known/…`) carries `Cloudflare-CDN-Cache-Control: no-store`, public photos at `/api/content/media/{id}` too (plan v3 2.6 kept `/api` out of the edge cache, and the Cache Rules of `deploy/README.md` bypass it as well), so Cloudflare never stores one. At the edge only the shell and static files are kept, with `stale-if-error` in `Cloudflare-CDN-Cache-Control` (`deploy-ci.md`, Cache headers), never an answer that differs per visitor or sets a cookie. The outage Worker `deploy/cloudflare/nfnn-fallback-worker.mjs` is generated (`npm run edge:fallback`) and tested (`scripts/build-fallback-worker.test.mjs`): it answers only page navigations the origin fails with its static page (strict policy by hash, no script, no other origin) and passes everything else unchanged; a Worker that reads or changes a request or answer, holds a secret or binding, or calls another origin is a security change. Every `/api` answer the backend writes carries `Cache-Control` with `no-store`, except the photos (`public, max-age=31536000, immutable`, an id never changes its content), a 200 of `receipt-keys` (`public, max-age=3600`) and of `payment-details` (`private, max-age=300`), which set no cookie and answer everyone alike; answers nginx writes itself (a 413, 502 or 503) carry no `Cache-Control`. The `stack` probe asserts it; a new cacheable `/api` answer joins its list in the same PR.
- Browser: the Content-Security-Policy in `frontend/nginx-security-headers.conf` allows no inline script and no third-party resource, names `worker-src` and `manifest-src` `'self'` and requires Trusted Types with exactly two policies, the site's `default` (only `createScriptURL`: the site's own `/worker-<hash>.js` only for the worker constructor and `/ngsw-worker.js` only for the service worker registration) and Angular's `angular` (plan v3 2.5, Jakub's OK in its PR), and `'wasm-unsafe-eval'` in `script-src` only for WebAssembly a same-origin script compiles (the Argon2id worker, slice 2.13, Jakub 2026-11-05); never `'unsafe-eval'`, `'allow-duplicates'`, or `blob:` or `data:` in `script-src` or `worker-src`, and a new policy name, a new address the policy admits or a new sink that needs a policy is a security change; the registered worker is Angular's `ngsw-worker.js` with the site's payment route prepended (`frontend/service-worker/payment-route.js`: only the same-origin `/platba.spayd`, answered on the device, never the network, and only with a SPAYD text a page of the site reserved by a message, once within 10 s under a random id, so no address or link from elsewhere can make the site serve a payment; the policy sandboxes every answer), and any other code of the site in the worker is a security change; every e2e journey runs under these headers and fails on any CSP violation (`testing.md`); an inline script, an external resource or a new kind of embed extends it in the same PR, verified against the production nginx (skill `visual-check`); `inlineCritical` stays off in `angular.json`; CORS stays unconfigured (same origin).
- Push keys (plan v3, 2.27): the VAPID private key is generated by the backend at its first use, stored only sealed under `settings-key` (`operations_push_key`, its own associated data), never returned, logged or put into a transcript, and a key no sealer reads is replaced with every subscription deleted; a push message is encrypted to the browser (RFC 8291), padded to one length, sent without a `Topic` header, and carries only the version, the kind and a count; a device goes when its session ends (`DeviceSignedOut`) and when its administrator loses the role. A browser's `p256dh` and `auth` and the endpoint are capability secrets: never answered and never logged, and the transcripts mask the keys (the endpoints of the scenarios are fictional).
- Receipt signing key (plan v3, 1.5): the Ed25519 seed is generated by the backend entrypoint into `secrets/receipt-signing-key`, never in compose, the database, a backup, a log, an API, a transcript (masked as `<secret>`) or another server; it is required outside dev, which refuses every public RFC 8032 test seed at startup and never publishes or adopts a row of their key ids (`PublicTestKeyPolicy`), and dev and tests use only those. Only `ReceiptSigningKeyRegistration` and the web-only withdrawal `ReceiptSigningKeyWithdrawal` (slice 1.13: browser session, fresh second factor at every call, refusals audited and paused, audited, e-mailed to every administrator) write `receipt_signing_key` (ArchUnit: any repository method but `findAll`, the JPA classes outside their adapter, the table name outside them). Every read and start cross-checks the rows against the `REGISTER_`, `ADOPT_` and `WITHDRAW_RECEIPT_SIGNING_KEY` audit entries: a key the trail withdrew, or whose seed the entrypoint keeps aside as `secrets/receipt-signing-key.withdrawn-<key-id>` (passed as `RECEIPT_SIGNING_KEYS_WITHDRAWN`, public ids only), is published as `revoked`, and a missing or reverted row raises the alarm; whoever holds the database and the audit trail together is beyond this check (`docs/security-overview.md`). A withdrawn seed of the server is replaced only by the entrypoint, with a fresh random one, and only when the marker names the current seed's key; while it is withdrawn no receipt is issued, nor an issued one returned again by an issue request (409 `donations/receipt-signing-paused`); the reads of receipts issued before (`GET /api/donations/me/receipts[/{id}]`, the administration's and the connector's reads) still answer, their proof under the key now published as `revoked` (Jakub 2026-10-31). Only a row sealed under this server's `settings-key` whose key id is its public key's is published; any other row, and a missing own key, raises the alarm (ERROR, `/sprava`, `nfnn_status`), and while the server's own key is not published no receipt is issued or returned by an issue request either, refused before a number is taken (409 `donations/receipt-signing-key-unpublished`, slice 1.22). A row sealed by a restored backup's carried settings key is adopted only at the first start after a restore confirmed by the backup container's status file, audited (`ADOPT_RECEIPT_SIGNING_KEY`) and warned: whoever holds `settings-key`, or the backup key together with a restore, can add a key, and the audit trail and the key list in `/sprava/nastaveni` are how it is seen. JCA signing stays in `donations/infrastructure/signing`. A new key operation (rotation, revocation) is web-only and audited.
- Receipt status (`POST /api/donations/receipts/status`, public, plan v3 1.8): it takes only the SHA-256 of a proof's signed message and signature, answers only one of five words with `no-store` (`outdated` since 1.26), and keeps no record of the question: `ReceiptStatusController` and its service write no log line, audit entry or metric, the digest and the address are never logged or stored (the limiter keeps the address only as its in-memory counter), and neither a 400 nor a 429 writes a line (`docs/security-overview.md`, the verification page). A log line, audit entry, metric or stored value there is a security change.
- Device copies (plan v3, 2.13, `docs/security-overview.md` "Device copies"): the keys of a copy on a device never leave it and no endpoint, log or error report carries one, a PRF output or a password-derived key; the password wrap is an offline oracle for the account password, so it uses Argon2id with the memory the device allows (128 MiB within a second, else 64 MiB), the administration copy takes one only without a PRF passkey, and a weaker key derivation or a wrap without its additional data is a security change; copies do not expire by themselves (Jakub 2026-11-05) and end only by sign-out, a wipe directive, "Smazat data z tohoto zařízení", erasure or role removal; "Cizí počítač" stores nothing.
- Data protection: collect only what receipts and pairing need; contact messages are deleted after a year; the privacy policy changes with the feature that changes the data.
- Supply chain: supported majors only; every package manifest (`backend`, `frontend`, `mcp`) is covered by Dependabot, whose version updates wait 7 days after a release (`cooldown`), and the libraries that sign, verify, hash, encrypt or read untrusted bytes in the browser (`@noble/*`, `pdfkit`, `jsqr`, and `hash-wasm`, `idb`, `client-zip` when they come) are pinned to an exact version (`frontend/scripts/pinned-libraries.mjs`, `npm run lint`); a new dependency needs a reason in the PR and, for a library, an ArchUnit rule confining it to adapters; workflows use `persist-credentials: false` and minimal `permissions`; official base images; application processes run unprivileged (the entrypoints hand Java to `app` with `setpriv` and Node to `node` with `su-exec` after the root-only setup), and a new one does the same; every container runs read-only with `cap_drop: ALL` and only the capabilities its entrypoint needs (`deploy-ci.md`, Hardening); the backend logs in to PostgreSQL as `novanadeje_app`, an ordinary role that owns the site's tables, never as the superuser, which only the database and the backup containers use.
- Unsure whether something is sensitive? Treat it as sensitive and ask Jakub in the PR.
