# Security rules

Threat model: a public site whose donor accounts yield tax receipts in the donor's name. Attacks to prevent: reading another donor's gifts, a receipt in another name, abuse of e-mail sending, exhausting the server. These rules hold whatever the task.

- Authentication: e-mail + password (BCrypt cost 12 over the password's SHA-256 hex digest, so all 128 characters count; 12–128 characters, common-password list in `RawPassword`); access token HS256 JWT, 15 min, in memory only; refresh token 14 days in an HttpOnly Secure SameSite=Strict cookie on `/api/donors/auth`, stored hashed, rotated on use, reuse revokes every session. Password reset: 43-character secret in the URL fragment only, stored as SHA-256, single use, 1 h, at most 3 live per donor; confirm revokes all sessions. E-mail verification: the same kind of link, 24 h; an unconfirmed account cannot sign in (401 `auth/email-not-verified` only with the right password), has no `donor_record` and gets no reset link; registration always answers 202 (no address enumeration). Signed in, the password and the e-mail change only with the current password; a new address must be confirmed by the same kind of link, the old address is told, and both changes revoke every other session.
- Authorization: everything under `/api` requires the donor JWT unless listed `permitAll` in `ApiSecurityConfiguration`; resources are found by the JWT subject; another donor's resource answers 404, never 403. Role `ADMIN` (granted and taken away by another administrator under `/api/admin/donors/administrators`, never by oneself; the first one by `ADMIN_EMAILS` at startup; nothing by SQL, Jakub 2026-10-22) gates `/api/admin/**` (`hasRole`, 403 `auth/forbidden`; the role travels in the JWT, so it applies from the next sign-in or refresh); every administrator's change publishes `AdminActionPerformed` so `admin_action` records who did what and when. Second factor (TOTP, RFC 6238, `donors/domain/{SecondFactor,Totp}`): any donor may turn it on (password → secret and QR, the first code confirms; password + code turns it off; both revoke every other session), an administrator must: `ADMIN` enters the JWT only for a session opened with the code (`Donor.sessionRoles`, `donor_refresh_token.second_factor_verified`), so without it an administrator is a plain donor. With it on, the right password answers 401 `auth/second-factor-required` with a stored challenge (hash only, 5 min, 5 wrong codes, once) and `/login/second-factor` completes it; a code counts once per 30-second step (`last_used_step`); the TOTP secret is stored in plain text (the server needs it), so a database leak needs the password too; no recovery codes, a lost authenticator is turned off by another administrator (`POST /api/admin/donors/{id}/second-factor/reset`: factor deleted, every session ended, audited, e-mail to the donor); taking the role away also ends every session of the donor.
- Connected applications (OAuth 2.1 authorization server for the MCP connector, `donors/{domain,application}/…OAuth…`, `AuthorizationServerService`): clients only by Client ID Metadata Documents over `https` (no manual registration, private addresses refused, 5 s, 16 kB, no redirects), PKCE S256 required, the redirect must be listed in the document (loopback on any port only for a loopback-registered client), the resource must be `{public-url}/mcp`, only an administrator's session opened with the second factor may approve and the consent page grants `admin:write` only when the administrator ticks it (reading only by default; the connector's 401 challenge asks for both scopes but requires only `admin:read`), the code is single-use (marked used before any check), five minutes, hashed; the client's access token carries `aud` `{public-url}/mcp` and never opens the API, the API accepts only `aud` `{public-url}/api`; a connector token is swapped for an API token only by token exchange and only for that resource; the client's refresh token is a `donor_refresh_token` row tied to its client, rotated, a replay ends every session of the donor, a removed administrator cannot refresh; scopes `admin:read` and `admin:write` travel in the JWT `scope` claim and a change under `/api/admin/**` needs `admin:write` (`AdminWriteAuthorizationManager`; browser tokens have no claim); a token with a `scope` claim opens `/api/admin/**` only: every other path (the administrator's own account, `POST /api/donors/oauth/authorize`) and the backup download `GET /api/admin/operations/backups/*` accept only a token without the claim (`BrowserSessionAuthorizationManager`, 403), so a connection can never approve a wider connection for itself or export the database (security review 2026-10-23); the administrator can revoke a connection in the account card; the token endpoint is limited to 30/15 min per address.
- MCP connector (`mcp/`, container `nfnn-mcp`): a resource server only. It holds no secret and reads no env file; it learns the issuer from the backend's metadata and verifies a bearer token solely by exchanging it at the backend's token endpoint (RFC 8693), so a forged, expired or API token is refused by the backend and the connector never validates a signature itself. Every tool call reaches `/api/admin/**` with the exchanged API token (`aud` `/api`, the connection's `scope`, the administrator's roles), so authorization, auditing, rate limits and the `admin:write` rule stay the backend's; a writing tool without `admin:write` answers 403 `insufficient_scope`. The frontend nginx limits `/mcp` to 10 requests/s per address (burst 20) and the container publishes no port. The connector reads no file itself and writes only its own `/logs/mcp.log` (the same ids and outcomes as its console): the log tools call `GET /api/admin/operations/logs…` and the backend serves only files of its own `/logs` folder with safe names (`[A-Za-z0-9][A-Za-z0-9._-]*`, so no path), windows of at most 200 kB and at most 200 search matches; a log level raised through `PUT /api/admin/operations/loggers/{logger}` is audited, lasts at most 24 h and never survives a restart, so a forgotten DEBUG cannot keep writing more than the normal log into the files; the thread dump names code, never a donor. It has a tool for every setting and all data of the administration but none for what is dangerous or irreversible (Jakub 2026-10-23): deleting news, projects or account links, reversing or deleting an older-symbol answer, granting or taking away the administrator role, resetting a second factor, GDPR erasure and the backup download stay behind the browser session with the second factor. The connector logs ids and outcomes only; a new tool that would reveal names or addresses beyond what the API already returns to an administrator is a security change.
- Abuse limits (per client address, 429 before any work): contact 5/h, sign-in 10/15 min, registration 5/h, reset request 5/h, verification request 5/h, password change 10/15 min, e-mail change request 5/h, second-factor codes at sign-in 10/15 min, second-factor set-up/confirm/disable together 10/15 min, OAuth token endpoint 30/15 min; bank check 30 s global. The address comes from `X-Forwarded-For` set by the frontend nginx (`set_real_ip_from` private ranges, client values overwritten, `Forwarded` emptied); never trust a client header elsewhere. Unknown e-mail sign-in costs a real BCrypt compare (`UNKNOWN_DONOR_HASH`).
- Input: Bean Validation with explicit `@Size` on every request record, value objects validate again, honeypot on public forms; JPA parameters only (no string-built queries).
- Output: `server.error.include-*: never`; problem+json carries no stack trace or exception text; logs carry ids and outcomes only; Thymeleaf `th:text` only; Angular bindings only (no `innerHTML`); no secrets or tokens in URLs, logs, PRs or commit messages.
- Secrets: server env files `/DATA/AppData/nfnn/env/{db,backend,ops}.env` (mode 600) and local `.env` only; never in compose, code, docs or tests; `JWT_SECRET` has a default only in `application-dev.yml`; the PR check fails when a secret name appears in `deploy/compose.yml` or reaches the database, backup or log-reader containers. The frontend nginx writes its access log there without the client address and the query string (searches and OAuth parameters travel in it), so a new field in the `anonymous` format is a security change. Production logs (`/DATA/AppData/nfnn/logs/`) are readable from the internet only through the Cloudflare tunnel behind Cloudflare Access (service token for Claude, Jakub's e-mail); the log reader publishes no port and mounts the folder read-only; logs carry ids and outcomes only, so nothing in them is a secret or personal data, and that stays true for every new log line.
- Headers and transport: TLS ends at Nginx Proxy Manager (Cloudflare in front later); nginx adds `nosniff`, `X-Frame-Options SAMEORIGIN`, `Referrer-Policy`, `Permissions-Policy` and the Content-Security-Policy in `frontend/nginx-security-headers.conf` (`default-src 'self'`; scripts, fonts and connections only from the site; styles also `'unsafe-inline'` because Angular injects component styles; images also `data:` (the saved QR code is drawn through one); `object-src 'none'`, `base-uri`, `form-action` and `frame-ancestors` `'self'`). An inline script, an external resource or a new kind of embed needs the policy extended in the same PR, verified against the production nginx (skill `visual-check`); `inlineCritical` stays off in `angular.json` because its inline `onload` handler would be blocked. CORS stays unconfigured (same origin); the backend port is never published; XSS defence is the policy plus Angular's bindings and `th:text`.
- Data protection: collect only what receipts and pairing need; contact messages deleted after a year; the privacy policy changes with the feature that changes the data.
- Dependencies and supply chain: supported majors only; a new dependency needs a reason in the PR and, for a library, an ArchUnit rule confining it to adapters; workflows use `persist-credentials: false` and minimal `permissions`; official base images; the backend's Java process runs as the non-root user `app` (the entrypoint starts as root only to hand the log folder to `app` and drops privileges with `setpriv` before Java starts).
- Unsure whether something is sensitive? Treat it as sensitive and ask Jakub in the PR.
