# Security rules

Threat model: a public site whose donor accounts yield tax receipts in the donor's name. Attacks to prevent: reading another donor's gifts, a receipt in another name, abuse of e-mail sending, exhausting the server. These rules hold whatever the task.

- Authentication: e-mail + password (BCrypt cost 12 over the password's SHA-256 hex digest, so all 128 characters count; 12–128 characters, common-password list in `RawPassword`); access token HS256 JWT, 15 min, in memory only; refresh token 14 days in an HttpOnly Secure SameSite=Strict cookie on `/api/donors/auth`, stored hashed, rotated on use, reuse revokes every session. Password reset: 43-character secret in the URL fragment only, stored as SHA-256, single use, 1 h, at most 3 live per donor; confirm revokes all sessions. E-mail verification: the same kind of link, 24 h; an unconfirmed account cannot sign in (401 `auth/email-not-verified` only with the right password), has no `donor_record` and gets no reset link; registration always answers 202 (no address enumeration). Signed in, the password and the e-mail change only with the current password; a new address must be confirmed by the same kind of link, the old address is told, and both changes revoke every other session.
- Authorization: everything under `/api` requires the donor JWT unless listed `permitAll` in `ApiSecurityConfiguration`; resources are found by the JWT subject; another donor's resource answers 404, never 403. Role `ADMIN` (granted only by SQL, `deploy/README.md` "Správci") gates `/api/admin/**` (`hasRole`, 403 `auth/forbidden`; the role travels in the JWT, so it applies from the next sign-in or refresh); every administrator's change publishes `AdminActionPerformed` so `admin_action` records who did what and when; a second factor (TOTP) for administrators is decided (Jakub, 2026-10-22) and comes with the next PR.
- Abuse limits (per client address, 429 before any work): contact 5/h, sign-in 10/15 min, registration 5/h, reset request 5/h, verification request 5/h, password change 10/15 min, e-mail change request 5/h; bank check 30 s global. The address comes from `X-Forwarded-For` set by the frontend nginx (`set_real_ip_from` private ranges, client values overwritten, `Forwarded` emptied); never trust a client header elsewhere. Unknown e-mail sign-in costs a real BCrypt compare (`UNKNOWN_DONOR_HASH`).
- Input: Bean Validation with explicit `@Size` on every request record, value objects validate again, honeypot on public forms; JPA parameters only (no string-built queries).
- Output: `server.error.include-*: never`; problem+json carries no stack trace or exception text; logs carry ids and outcomes only; Thymeleaf `th:text` only; Angular bindings only (no `innerHTML`); no secrets or tokens in URLs, logs, PRs or commit messages.
- Secrets: server env files `/DATA/AppData/nfnn/env/{db,backend}.env` (mode 600) and local `.env` only; never in compose, code, docs or tests; `JWT_SECRET` has a default only in `application-dev.yml`; the PR check fails when a secret name appears in `deploy/compose.yml` or reaches the database containers.
- Headers and transport: TLS ends at Nginx Proxy Manager (Cloudflare in front later); nginx adds `nosniff`, `X-Frame-Options SAMEORIGIN`, `Referrer-Policy`, `Permissions-Policy` and the Content-Security-Policy in `frontend/nginx-security-headers.conf` (`default-src 'self'`; scripts, fonts and connections only from the site; styles also `'unsafe-inline'` because Angular injects component styles; images also `data:` for the QR codes; `object-src 'none'`, `base-uri`, `form-action` and `frame-ancestors` `'self'`). An inline script, an external resource or a new kind of embed needs the policy extended in the same PR, verified against the production nginx (skill `visual-check`); `inlineCritical` stays off in `angular.json` because its inline `onload` handler would be blocked. CORS stays unconfigured (same origin); the backend port is never published; XSS defence is the policy plus Angular's bindings and `th:text`.
- Data protection: collect only what receipts and pairing need; contact messages deleted after a year; the privacy policy changes with the feature that changes the data.
- Dependencies and supply chain: supported majors only; a new dependency needs a reason in the PR and, for a library, an ArchUnit rule confining it to adapters; workflows use `persist-credentials: false` and minimal `permissions`; official base images; the backend container runs as a non-root user.
- Unsure whether something is sensitive? Treat it as sensitive and ask Jakub in the PR.
