# Testing rules: backend

The general rules (TDD, given/when/then naming, what a new feature covers) are in `testing.md`; how the suite runs and why: `docs/system-overview.md` "Backend tests".

## Levels and test support
| Level | Tool and place | Rules |
|---|---|---|
| Unit | JUnit 5 + AssertJ + Mockito, `src/test/java/.../<context>/<layer>/` | Name `should_<expected>_when_<action>[_given_<state>]` plus `@DisplayName("Given X, when Y, then Z")` on every test (`architecture/TestNamingRulesTest`); a shared setup may be a `@Nested @DisplayName("Given …")` class whose tests read "when …, then …". AssertJ for assertions (MockMvc's `jsonPath` matchers excepted). Mockito for ports, framework collaborators (`ApplicationEventPublisher`, `JavaMailSender`, `TaskScheduler`) and the collaborating service of the class under test; never for aggregates, entities or value objects: build those with the fixtures (`Donations`, `Receipts`, `BankPayments`). Mockito loads as a `-javaagent` from `build.gradle.kts`, not by self-attaching (JDK 25 warns, a later JDK refuses) |
| Acceptance | Cucumber, `src/test/resources/features/<context>/<use_case>.feature` (English Gherkin), glue in `<context>/cucumber/`, shared steps in `cucumber/` | One feature per use case; scenarios go through HTTP with `cucumber/ApiClient`; two suites glue `cz.novanadeje.app`, `cucumber/DonorsOperationsContactAcceptanceTests` (`@donors`, `@operations`, `@contact`) and `cucumber/DonationsContentAcceptanceTests` (`@donations`, `@content`), split by measured scenario time so the forks end together, and the Gradle task `acceptanceTest` runs each in its own fork; every scenario is in exactly one suite (`AcceptanceSuitesPartitionTest`), so a new context tag joins one suite's `@IncludeTags` and that test; `CucumberSpringConfiguration` boots the app with Testcontainers PostgreSQL and `TestSupportConfiguration`. One area: `CUCUMBER_FILTER_TAGS=@<tag> ./gradlew acceptanceTest` (`-Dcucumber.*` does not reach the test JVM). Every feature carries the tag of its context folder (`@contact`, `@content`, `@donations`, `@donors`, `@operations`; `FeatureContextTagsTest` fails otherwise), and the connected applications also `@connected-apps`; a tag no feature carries runs nothing and still passes, so check the report's counts (or add a temporary `@wip`). A new feature carries its context tag |
| Integration | `@IntegrationTest` (the one `@SpringBootTest` configuration, with MockMvc) or `@PersistenceTest` (the one JPA slice configuration: `@DataJpaTest` with `PersistenceTestConfiguration`, which imports `TestcontainersConfiguration` and each context's `<Context>PersistenceTestConfiguration` with every adapter of the context) | Real PostgreSQL 17 only, never H2; the scheduler properties are pinned once in `@ScheduledWorkOff` (`architecture/TestContextRulesTest`); schema tests in `shared/infrastructure/schema/` (every foreign key led by a non-partial index, the changelogs after the deployed revision over a row in every table, every table classified for a restore; `backend.md` Persistence, `database.md`) |
| Architecture | ArchUnit, `architecture/` | A new invariant gets a rule; rules fail on an empty match |

Test support:
- External ports have fakes in `support/`, registered `@Primary` by `TestSupportConfiguration` (`FakeFioClient`, `RecordingMailSender`, `SynchronousBankImportRequests`, `FakeClientMetadataSource`, `FakeMailServerProbe`, `SwitchablePublicBackupKeyPolicy` for a scenario outside development, `SwitchablePublicTestKeyPolicy` for a server outside development, the `Recording…` timers and announcers); a new port adds its fake there. The password hasher is the real one: `CachingPasswordHashers` wraps `BCryptPasswordHasher` in `CachingPasswordHasher`, which asks it once per password and once per password and hash. `MailContents` reads sent mail; `FioMovements` builds bank movements. `AsyncTaskTracker` counts the unfinished tasks of the application executor (`@Async`, every mail sender), and nothing else: `AsyncTaskTrackingConfiguration` attaches it with a `ThreadPoolTaskExecutorCustomizer`, never as a `TaskDecorator` bean, which Boot would also hand to the task scheduler. Every `ApiClient` request, the steps that run the backup check or the registration reminder job directly, the scenario reset and the transcript recorder wait for it (a timeout fails the step and names the request and the unfinished count), so mails from separate requests and job steps are recorded in the order they were sent; two mails from one request, or from a new step that calls a service directly without `awaitIdleAfter`, keep the order their sends finish in. A task the pool rejects keeps its count, which happens only after the context closes.
- `CommonStepDefinitions.isolateScenario` (`@Before`) waits until the previous scenario's `@Async` work (the application task executor) is done, so none of its e-mail lands in the next one, then empties every table, children first, and restarts sequences (`DatabaseCleaner`; receipt numbers start at `000001`), clears mail, resets the fake Fio client and, on every acceptance run, recorded or not (so a local `./gradlew test` behaves as CI), sets `MutableClock` to `ApiTranscripts.RECORDING_CLOCK` and resets every rate-limit window, the company lookup's pause, the backup key's word draws, and `SwitchablePublicBackupKeyPolicy` and `SwitchablePublicTestKeyPolicy` back to development (`docs/system-overview.md`, Regression against v2 and shared cases). `Given today is {date}` sets the clock; `DonorSessions` signs a donor in again after the clock expired the token.
- `FakeFioClient` refuses history older than 90 days until `unlockHistory()` and throws on every bookmark call (`transactions().sinceBookmark()`, `bookmark().moveAfterTransaction/moveToDate`), so `/last/` can never pass.
- In tables `{Jana}` is Jana's variable symbol (`ScenarioDonors`); `{date}` is ISO (`ParameterTypes`). Each scenario sends from its own client address (`X-Forwarded-For`, trusted by the backend); `When the following requests come from another client address` switches; `When the following requests come from the client address {string}` sets a fixed one, safe because `isolateScenario` resets every limit window.
- Device orders (2.21): `donors/application/DeviceOrdersAcrossDevicesTest` (in `DonationRowsContext`, the one integration context with `MutableClock`, so it starts no context of its own) drives the services of two accounts through random sign-ins of every kind, refreshes, sign-outs here and from another device, replays, role grants and removals, an erasure and time passing with the nightly cleanup, and checks every device's status answer against a model and the invariants of the orders (never lowered or lifted, none across accounts, `unknown` only after the cleanup), each step kind, each answer and each transition the slice promises reached at least once (`DEVICE_ORDERS_SEEDS` seeds of 60 steps, 30 by default and never fewer, so the coverage case always holds; the session lengths and the 400 days are literals of its model, so a change to them fails it); `features/donors/erasure_and_role_removal_across_devices.feature` tells the same through HTTP, with `{int} days pass with the nightly clean-up` and the table step `the devices answer:`.

## Keeping the suite fast
- Passwords in tests go through `CachingPasswordHasher` over the real hasher; never a second real-cost hasher or a lower cost, because each BCrypt check at cost 12 costs a core a third of a second.
- E-mail and async waits use Awaitility's defaults, set once in `CommonStepDefinitions.pollWithoutDelay` (no delay, 10 ms interval); no own `pollDelay`, `pollInterval` or `Thread.sleep`. A step that checks nothing more arrives (no e-mail, exactly `n` e-mails) waits for the asynchronous work with `AsyncTaskTracker.awaitIdleAfter`, never for a fixed time: the work the request or job started is then finished, however slow the mail server (`contact_message.feature`, a mail server that takes 500 ms; Jakub 2026-11-14).
- A new `@SpringBootTest` is `@IntegrationTest` (`TestContextRulesTest`) and a new JPA slice is `@PersistenceTest` (`TestContextRulesTest`; a new adapter joins its context's `<Context>PersistenceTestConfiguration`), so it reuses a cached context and its PostgreSQL container instead of starting both. A test that needs other beans or properties starts a context of its own: say why in the PR.
- A new table needs nothing: `DatabaseCleaner` reads the tables and foreign keys from the catalogue. An integration test that commits cleans before it runs (`@BeforeEach`), because other classes share its database.
- State on disk is per fork: scenarios use the folders under `build/cucumber/fork-${org.gradle.test.worker}/`; a new folder follows suit.
- Where the time goes: the report (`build/reports/tests/{test,acceptanceTest}/index.html`, per class and per scenario), and per step the Cucumber `json:` plugin added for a run to the suite's `PLUGIN_PROPERTY_NAME` (sum `result.duration` per `match.location`, backgrounds included).

## Running
`./gradlew test` runs the unit and integration tests in the `test` task and then, as its finalizer, the scenarios in `acceptanceTest`, each task on two forks; `-PnoCucumber` skips `acceptanceTest`, and `--tests` filters only `test`. `./gradlew build` is what the PR check runs for the backend. In a cloud session: skill `cloud-session`.
