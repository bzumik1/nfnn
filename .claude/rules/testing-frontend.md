# Testing rules: frontend

The general rules (TDD, given/when/then naming) are in `testing.md`. How the e2e server, the fixtures, the device steps, the Safari runner and the web-app fixture work: `docs/frontend-overview.md` "Frontend conventions in detail", Testing.

## Frontend
- Vitest specs beside the code (`name.spec.ts`): `describe('Given …')` → `it('when …, then …')`, or a nested `describe('when …')` with `it('then …')` when outcomes share a setup. TestBed with `provideHttpClient()`, `provideHttpClientTesting()` (`http.verify()` in `afterEach`) and `provideRouter([])`; a spec that creates a root service with effects runs `TestBed.tick()` right after creating it, so its start-up effects run before the test as at bootstrap, never at whatever moment the scheduler's timer fires (#962); `src/test-setup.ts` clears `localStorage`, resets the TestBed and puts jsdom's own window properties back before every test, so a spec that leaks fails only itself; drive the DOM and assert visible text and ARIA, not internals; fixtures in `*/testing/`. `src/test-providers.ts` gives every TestBed the `cs` locale, `FakeLiveUpdates` and `FakeBankLogosApi` (an empty list), so no spec opens the live stream or asks for the bank logos unless it provides the real service.
- Playwright in `e2e/` by user journey, same naming. Nothing may reach a backend: `npm run e2e` serves the production build like the frontend nginx, under its security headers, and proxies nothing. Specs import `test` and `expect` from `e2e/fixtures.ts` (lint refuses `@playwright/test`), whose automatic fixture answers unmocked `/api` calls with a 404 problem, fails a journey that asks the server for a payment QR, and fails any test during which a page reported a CSP violation (a test that plants one on purpose asserts it and empties the list). Each spec mocks the calls its journey needs (`mockDonorApi`).
- An administrator's remembered session finds the administration locked: the automatic fixture unlocks it before a locator action or assertion, so a spec that first waits on a response or runs axe acts on the page (or calls `unlockAdministration(page)`) first, and a spec about the lock sets `test.use({ unlocksAdministration: false })`.
- CI fails a test that passed only on a retry (`failOnFlakyTests`). A test that fails only sometimes is a race in the app or the test: reproduce it and fix it test-first, never retry it away. Every test stands alone (3 workers, `fullyParallel`): no shared state, no order, each mocks what it needs. A browser service the headless shell lacks (password manager, passkeys) is stubbed with `page.addInitScript`.
- `signIn` at 1280 px, resize after; downloads through `page.waitForEvent('download')`; a new page or dialog gets its case in `accessibility.spec.ts` (axe, WCAG 2.2 AA).
- The project `iphone` (WebKit, `playwright.config.ts`) runs the receipt PDF, `/overit`, Přispět, authenticator and security-header (Trusted Types) journeys and `dialog-back`, `device-copy`, `app-shell`, `tab-bar-drag`, `largest-text`, `diagnostics`, `offline-sign-in`, `page-transitions`, `tab-switching`, `story-grid` (the story tiles in WebKit), `pressed-tint`, `back-keeps-scroll`, `back-motion-start`, `back-matrix` and, in the project `iphone-sprava` with its own two CI shards, `sprava-back-matrix` (helpers in `e2e/back-matrix.ts`), `admin-donor-search-names` (the donor search as VoiceOver reads it, #1684) `failure-and-loading` (its retry of a failed article) and `yearly-pdf-phone` (a yearly PDF row that keeps its height on a 390 pt phone) at phone size, where the helpers of `e2e/donor-session.ts` reach the account sections through `openAccountItem` and the tabs through `openSection`; a test that cannot run in WebKit skips with `test.skip(({ browserName }) => browserName !== 'chromium', reason)`, its reason naming what the device checklist covers instead. What WebKit in Playwright cannot show (a real share sheet, Files, the camera, printing) is Jakub's device checklist.
- Phones and tablets (`e2e/devices/`, `npm run e2e:devices`): every step of `STEPS` runs in every pose of `POSES` with the same layout checks. A finding the site has today is listed in `known-findings.ts` with its pose, steps, check, text and reason, and a step that cannot open in `KNOWN_BREAKS`; the test fails on any other finding and on a listed one that is gone, so a fix removes its entry in the same PR, and a new finding is fixed or, only by Jakub's decision, listed. The same steps run in real Safari (`npm run e2e:safari` on a Mac before merging a change to how a page behaves or looks on a phone or in Safari; `safari.yml` every Monday and by hand). The checks see no pixels: review the screens yourself before handing over a visible change (skill `visual-check`).
- Web as an app (`e2e/pwa/`, `npm run e2e:pwa`, CI's `pwa` job; not part of `npm run e2e`): specs import `pwaTest` and `expect` from `e2e/pwa/pwa-fixtures.ts` (lint refuses the others) and route only on the context (lint refuses `page.route`; helpers take the context). The fixture fails a test on any console error, uncaught error or CSP violation of a page or worker; `test.use({ allowedConsoleErrors: [/…/] })` allows a text with its reason beside it, and `browserProblems.expectOne(/…/)` names a problem the test causes on purpose. Its nginx containers run on the host's network, never a Docker bridge (`pwa-fixtures.spec.ts`). The worker option `cameraShows` is set with `test.use` at the top of a file of its own. Routing makes Chromium bypass its HTTP cache, so what the browser keeps by the cache headers is tested by the headers' probes (`probe-asset-caching.mjs`), not here. After a killed run, remove only this worktree's containers and folders, found by their mounts, from this worktree's root: `for c in $(docker ps -aq --filter label=nfnn-pwa); do src=$(docker inspect -f '{{range .Mounts}}{{.Source}} {{end}}' $c); case "$src" in *"$(pwd -P)/frontend/"*) for d in $(docker inspect -f '{{range .Mounts}}{{.Source}} {{end}}' $c); do case $d in */nfnn-pwa-*) rm -rf "$d";; esac; done; docker rm -f $c;; esac; done`; an `nfnn-pwa-*` temporary folder no container mounts and older than a day may also go.
- A drawn receipt PDF is tested by what it says and does, read back with `receipt-pdf/testing/pdf-reader.ts`; the certified text is the shared case `shared-cases/receipts/v1/printed.json`.
- A step's start and first half (D1 and R1 in `e2e/back-matrix.ts`) are judged on every PR in frames and on the screen, where the runner captures frames, never in time (vote 9, X1, a rule change): both copies placed within `PLACED_WITHIN_FRAMES` (9 frames: D1's 150 ms at 60 Hz) of the tap (`FIRST_OPENING_PLACED_WITHIN_FRAMES`, 18 frames: 300 ms, while the page's code loads), the first move within 3 frames of pace plus the ceiling of the screencast's p99 stamp lag of the placing (`movesWithinFramesOfThePlacing`), and, from a CDP screencast of a magenta line the probe puts on the moving page, every screencast frame judged by its time on the motion's curve (`judgedOnTheScreen`): never back by more than 0.5 % of the way or 2 device pixels of the screencast, whichever is more (two whole-pixel reads of the line differ by up to that much), never more than 1.5 steady frames plus the p99 stamp lag ahead (`aheadAtMostFrames`), its start, taken from the first moved frame but at most the p99 stamp lag after the start the browser set, at most one steady frame before the placing, and no two neighbouring frames further apart than its curve covers at its steepest in the time between them plus 1.5 steady frames and the p99 lag (vote 9 round 2, round 24). The lag is the larger of the Prodesk's p99 (`PRODESK_STAMP_LAG_P99_FRAMES`, 2.03, round 18, 2026-11-22) and CI's p99 over the frames of real steps (3.00, runs 45534955785 and 45547560058, 2026-11-25), both reviewed values in `e2e/stamp-lag.json`; `gate`'s summary logs each run's p99 and `gate` fails naming the new value when a run's step frames go above the reviewed one, so it is raised in a reviewed commit, and fails when no step frame's lag was measured at all; the screencast's frames are judged in the order of their time; the planted rows plant at that lag; the Prodesk/nightly rows use the Prodesk's lag. A step is not judged on this runner only when its screencast drew no frame for at least the motion's length less one frame (`screencastMissedTheMotion`, X1.2, the rule `top-area.ts` applies to the ground under the clock) while the probe's own frames saw the page move (`probeSawTheMotion`: a screencast draws nothing of a page that stands still); then the row gets an `nfnn-not-judged` annotation naming the gap, `skipWhereNotJudged` skips the passed row, and `gate`'s summary counts it beside the rows that judged screencast frames (WebKit rows and rows that judge no frame are not counted, `scripts/motion-judged-summary.mjs`); it must pass on the Prodesk for the head SHA. A step whose screencast drew frames during the motion is judged, so a page that stands still fails for too few frames on its way. Never not judged, they fail instead: the four planted regression rows (a start moved 150 ms later, a start in the past, a start set before the placing, and a still page whose motion is lost and which the time bound swaps; the judge must report each), reduced-motion rows, focus return, the scroll kept after a step back in every frame from the returned focus (`framesAwayFromTheKeptScroll`), announcements and axe. The PR gate measures no time, no long frame and no 60 Hz shape: the long-frame guard (`longFrameProblems`) is #1982's acceptance and runs only in the red nightly at 4×, and the 60 Hz checks (R1 on screen frames, the first frame's position, a freeze, every frame shown on its way) run in the rows tagged `@timed-motion`, which only the project `motion-timed` runs (`default: false`, `workers: 1`; `chromium` and `iphone` leave the tag out), on the Prodesk for the head SHA and in the nightly, with D1's 150 and 300 ms: a spec that judges them starts the gate in `beforeEach` (`startMotionGate(page, testInfo.tags)`) and asserts `runnerSpeedProblems` in `afterEach`; for a timed row the worse of an in-page benchmark's medians before and after the rows (its first two runs left out as warm-up, then the median of five) against the browser's reference scales the budgets by 1.0–1.5×, a slower runner fails naming the factor, and the first moving frame and reduced motion are never scaled; the references are recorded on the Prodesk with the browser's version and again in the PR that upgrades the browser (`docs/frontend-overview.md`, Motion).
- Test behaviour, text and accessibility, never style values. E2e runs against the production bundle; no spec relies on dev mode.
