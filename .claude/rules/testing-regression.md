# Testing rules: regression against v2

The general rules (TDD, given/when/then naming) are in `testing.md`.

## Regression against v2
Plan v3 is checked against v2 as recorded on `main` just before v3 work starts. `regression/v2/` holds the API transcripts and the test inventory, `shared-cases/<topic>/*.json` the cases both sides run (`{source, logic, cases: [{name, input, expected}]}`); every file named its source `v2-baseline` at the baseline commit, and a file changed since names it `edited` (`testing-shared-cases.md`, Logic on both sides). The baseline's anchor is `regression/v2/BASELINE_COMMIT`: it holds the id of the squash-merge commit of the PR that brought these files (#201, `c4a256c2`), whose tree equals the branch they were recorded on, so checking out that commit and running the commands below regenerates every file byte for byte. The file never changes. A tag `v2-baseline` may be put on the same commit, but nothing depends on it (pushing tags is refused to the sessions that build v3). Only fictional fixtures under a fixed clock go in, and the repository is public.
- Recording: `API_TRANSCRIPTS=record ./gradlew acceptanceTest --rerun` (`--rerun`, or `cleanAcceptanceTest` before it, so Gradle cannot skip the run as up to date; `./gradlew test` and `build` record too, since `acceptanceTest` finalizes `test`) writes `backend/build/api-transcripts/<context>/<feature>.json`; copy the folder to `regression/v2/api/`. Recording refuses to start while `MAIL_*`, `APP_*` (Spring's relaxed binding maps them onto `app.*`), `SPRING_APPLICATION_JSON`, a `SPRING_*` name holding `PASSWORD`, `TOKEN`, `SECRET` or `KEY`, a secret setting (`Setting.secrets()`, so a new one is refused without a change here) or a secret the server generates (`JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `RECEIPT_SIGNING_KEY`, `DB_PASSWORD`) is set in the environment (`env -u FIO_TOKEN …`; `ApiTranscriptsTest` fails when `application*.yml` binds a password, token, secret or key it would not refuse), and every scenario, recorded or not, starts at `ApiTranscripts.RECORDING_CLOCK` with every rate-limit window and the company register lookup's pause (`support/CompanyLookupPause`) reset and the backup key's word checks drawn from a fixed seed (`support/BackupKeyWordDraws`), so a transcript does not depend on which scenarios ran before it. On a checkout of the baseline commit, `GOLDEN_FILES=write ./gradlew test --tests "*QrGoldenCasesTest" -PnoCucumber` rewrites the QR cases (the generator is not on `main` since 0.6d). The inventory: `./gradlew test` for the backend JUnit XML (`build/test-results/test/`, and the Cucumber scenarios in `build/test-results/acceptanceTest/`, which `test-inventory.mjs` reads both by default); in `frontend/` `npx ng test --watch=false --reporters=json --output-file=$PWD/test-results/inventory-vitest.json` and `npx playwright test --list --reporter=json > test-results/inventory-playwright.json`; in `mcp/` `npx vitest run --reporter=json --outputFile=test-results/inventory-vitest.json`; then `node scripts/test-inventory.mjs` writes `regression/v2/test-inventory.json` (every test name per suite, sorted, a repeated name with `#n`). The test JVM is pinned to a zone, locale and charset (`-Duser.timezone=Etc/UTC -Duser.language=en -Duser.country=US -Dfile.encoding=UTF-8` in `build.gradle.kts`, guarded by `RecordingEnvironmentTest`), so a recording on another machine writes the same text. The baseline was recorded under `LC_ALL=C.UTF-8`, where the JDK reports `en` without a country; a recording with the pin writes the same bytes (checked with `diff -r` when the pin came in), and a change to the pin needs that check again. Record twice and compare (`diff -r`) before committing: two runs write the same bytes. A recording `acceptanceTest` empties `backend/build/api-transcripts/` before its forks start (Gradle, not the JVM, because the two suites write into the one folder at the same time), so no file of an earlier run survives; each feature runs in one fork, its scenarios in file order, so the ordinals `#n` are the same as in one JVM.
- Before merging the baseline PR: rebase onto the current `main`, record the whole suite again, `diff -r backend/build/api-transcripts regression/v2/api`, commit any difference (with the test inventory and the QR cases, if they changed too), and merge only if `main` has not moved since the rebase; if it has, repeat. So the squash-merge commit that carries the tag holds exactly what its tree records.
- Transcripts (`cucumber/transcript`): per scenario, keyed by its name, a scenario outline's row by its values (`name [GET | /api/x]`, so a new row renumbers nothing), then `#n`: every `ApiClient` call keyed `METHOD /path/{id} #n` (path and query, the sent `Authorization`, `Accept-Language`, `Cookie` and similar headers, the body with fields sorted; the status, every response header but `Date`, `Content-Length` and the connection ones, as a string or, sent several times, an array; the body as JSON, text, a PDF's pages and text, or a binary's size and SHA-256), every mail the scenario sent, also those a step cleared (addresses, subject, text part, the HTML part's visible text, links and SHA-256, attachments), and the `cz.novanadeje.app` log lines as `LEVEL logger: message [Exception]`. Normalised: ids `<id:n>` by first appearance (a passkey's `userHandle` and options `user.id` in base64url too), JWTs `<jwt>`, random mixed-case secrets of 32 or more characters `<token>` (CamelCase names stay), secret fields (`password`, `secret`, `otpauthUri`, tokens, codes; a boolean or number stays) and cookie values `<secret>`, the `value` of a setting whose `name` ends in `PASSWORD`, `TOKEN`, `SECRET` or `KEY` `<secret>`, a cookie's `Expires` `<time>`, image data URIs `<data:image/png size=… sha256=…>`, variable symbols `<vs:Alias>` (`<vs:n>` without an alias), the setup code `<setup-code>`, a recovery code `<recovery-code>` and the modules of a payment QR whose SPAYD carries one `<qr-of-masked-text>`, the name of the receipt signatory `<signatory-name>` (since 1.16 the fixture signatory `Josef Vzorový` of `support/ReceiptSignatories` and the name of the person chosen to sign by the scenario's end, throughout that scenario's transcript, so a person's answers in `manage_people` and the portrait scenario show it masked too), a backup key (`AGE-SECRET-KEY-1…` in any case, wherever it stands) and the backup key's words (fields `word`, and `words` when it lists strings) `<secret>`. Writing a transcript fails when any raw value it masked (eight characters or more), raw or URL-encoded, is still in it. What v2 leaves random is settled, and nothing else: object fields are sorted before ids are numbered (v2 writes some answers from maps whose order changes per JVM); field `errors` are sorted (v2 collects them in a set); mails and log lines are sorted with ids blanked (asynchronous listeners send and log in any order); consecutive list items equal in the fields their list is ordered by are sorted by content only on the lists in `UnorderedTie.V2` (request template, JSON path, those ordering fields, reason: the fields the server sorts by before a random id, so only items that differ in nothing but that id are re-sorted), each shown to change order between two recordings, so every other list keeps v2's order; the diagnostics and the thread dump keep only their shape, the modification times of log and backup files are `<file-time>`; a PDF keeps its text, not its bytes.
- Golden cases: `regression/QrGoldenCasesTest` asked v2 for every case of `shared-cases/qr/payment.json` (through `GET /api/donations/payment-qr`) and `totp.json` (through `QrCodeEncoder`) and wrote the SPAYD text or URI, the error correction, version, mode, ECI header, mask and matrix. It exists only at the baseline commit; on `main` the runners check the cases, split since 0.6d into `payment/spayd.json` and `qr/payment.json`, and `totp/uri.json` and `qr/totp.json`, with every value as v2 wrote it. Re-encoding the text with ZXing is a guard that the recorded mask and version are ZXing's for that matrix; decoding the matrix back to its text and header is the independent check.
- Data sets, receipts and screens (only on a checkout of the baseline commit, whose generators the script runs; anywhere else it stops before it changes a file): `env -u FIO_TOKEN scripts/record-baseline-data.sh` (no `MAIL_*`, `FIO_TOKEN`, `JWT_SECRET` or `SETTINGS_KEY` in the environment, as for recording; Docker, Node 24, Playwright's Chromium, `npm ci` in `frontend/` and `mcp/`; `GRADLE_INIT_SCRIPT` and `TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX` pass through) rewrites them in one step: it writes the backend files and checks the rendered receipts against `digests.json` (`scripts/receipts-check.mjs`), builds this checkout's frontend for production and serves it with `frontend/scripts/serve-dist.mjs` on a free port of its own (`E2E_BASE_URL`, `CI=1`, so never a server another checkout left on :4200; one retry on a new port; `--workers=2`, not CI's three), shoots the screens twice into separate folders and fails, naming the states, unless the second run has the pixels of the first, runs every suite with `GOLDEN_FILES=digests` so the recorded files read back, and regenerates the test inventory as above (an id in a test name written `<id>`), which the hygiene and data set checks then read once more. Only then it stages the shots and receipts in the store's `.incoming/`, checks them there, moves the files they replace to `.previous/` and the staged ones into place. On a failure it keeps its temporary folder and prints its path. `donations/infrastructure/pdf/ReceiptCorpusTest` (at the baseline commit; 1.10 retired it from `main` with the server drawing, so the corpus is checked only against that commit) freezes and renders 15 receipts (the four history samples and edge cases, among them 1, 40, 120 and 366 gifts and three gifts of one day for the tie order, signed by the fictional `Petr Vzorový`) into `regression/v2/receipts/<sample>.json`: frozen data, page count, fonts, page size and the text lines (U+00A0 written as a space) with the position of each line's first character rounded to whole points, so the layout is checked on every run, plus `refusals.json`. The PDF's SHA-256 and each page's RGB raster digest at 100 DPI change with PDFBox, openhtmltopdf and the JDK, so they sit apart in `digests.json`, checked only under `GOLDEN_FILES=digests` (the script); the rendered PDFs and page PNGs land in `backend/build/receipt-corpus/` and the store's `receipts/`. `regression/OverviewGoldenCasesTest` (at the baseline commit) inserts each case's rows through `regression/BaselineRows` (`JdbcClient`; on `main` the runners rebuild them from a case's `input` with `sharedcases/CaseRows.fromJson`, `CaseRowsTest`) and records what v2 answers: `shared-cases/admin-overview/year-overview.json` (`GET /api/admin/donations/overview`), `donor-summary/summary.json` (`GET /api/donations/me/summary`) and `monthly-report/report.json` (the compiled figures and the e-mail's text); `ReceiptFormattingCasesTest` and `MonthlyReportFormattingCasesTest` record `shared-cases/receipts/formatting.json` and `monthly-report/formatting.json`. `frontend/e2e/baseline/screens.spec.ts` runs in the Playwright project `baseline` only (skipped unless `BASELINE_SCREENS` is set; the browser gets a Czech system locale for date fields and rasters on one thread without the GPU, since otherwise a few anti-aliased edges came out differently between two runs) and shoots the routes and states of `SCREENS` (43 at the baseline, 50 since 0.6c) at 390 and 1280 px with the e2e mocks under a fixed clock; a comparison run accepts up to 0.2 % of a page's pixels and none of an element shot. The PNGs are too large for the repository and stay in `/mnt/project-files/nfnn-ux/snimky/v2-baseline/`; `regression/v2/screens/manifest.json` records the SHA-256 of each shot's decoded pixels, because a file store may add chunks to a PNG (the project-files mount adds a C2PA `caBX` chunk). To compare: `node scripts/screens-manifest.mjs --check <folder>` checks digests; for pixels copy the store to a temporary folder and, with `E2E_BASE_URL` at this checkout's own build served by `node scripts/serve-dist.mjs dist/frontend/browser <port>`, run `BASELINE_SCREENS=1 BASELINE_SCREENS_DIR=<copy> npx playwright test e2e/baseline/screens.spec.ts --project=baseline --update-snapshots=none`. A digest that differs means comparing pixels, never recording again. `regression/BaselineDataSetsTest` checks the case files' shape, that the manifest has exactly the states of the spec's `SCREENS` at both widths, and that no real-looking fixture value is in them (the values are listed only as SHA-256 digests of their lowercased tokens).
- Screens added since the baseline (0.6c): for Phase 1 the spec also shoots the Přispět section at 1 000 Kč, at an own amount (1 234 Kč), for a signed-in donor (the symbol in the QR) and with the QR failed, the TOTP enrolment, the add-account 1 Kč dialog and the recovery by payment, and inside these and `home` the QR code and the bank details as element shots (`element('<state>--<part>', selector)`, file `<state>--<part>-<width>.png`, the skip link, the site header and the donor top bar hidden while shooting) compared with `maxDiffPixels: 0`, because 0.2 % of a page hides a changed digit or a re-masked QR. A section shot (`region`) first scrolls its section to the top, so the sticky photo beside Přispět always stands at the same place, and a page shot first scrolls the page to its top, because Chromium's full-page capture lays the page out for a moment in a 1 × 1 viewport under load, which moved a page scrolled down by its scroll anchoring (Přispět at 390 px, after the click that unfolds its QR) and never moves one at the top; the add-account dialog's page shot masks its two paragraphs (`masked`, Playwright's `mask`), because two recordings at 1280 px differed by a sub-pixel shift of their last lines while the rest of the dialog, its QR and bank details never did; masked, six shots in a row and both recordings were identical. A state waits for its own content (`ready`) instead of `networkidle`, which flaked (`donor-overview-error`, `admin-older-symbols`). The payment QR answers of the new states come from the shared cases by name (`servePaymentQrCases` in `screen-mocks.ts`: the SPAYD text and recipient from `payment/spayd.json`, the symbol from its namesake in `qr/payment.json`, refused when the two disagree), so a browser encoder of the same cases draws the same symbol. A shot is v2 truth only when recorded from `BASELINE_COMMIT`. The slice's spec additions are kept as `regression/v2/additions/<slice>.patch` (`git diff $(cat regression/v2/BASELINE_COMMIT) -- frontend/e2e/baseline` when recording, which must apply to that commit; once committed it never changes, even when a later change, such as 0.6d's split of the QR cases, makes the spec on `main` differ from it); `node scripts/compare-screens.mjs --base=$(cat regression/v2/BASELINE_COMMIT) --patch=regression/v2/additions/<slice>.patch --v2-only --base-only` shoots that commit with only the patch applied; it runs twice, and `--add` refuses unless every shot of the second run has the pixels of the first (as `record-baseline-data.sh` checks); then `node scripts/screens-manifest.mjs --add <first run's base-shots> <second run's base-shots> <slice>` appends the new shots to `manifest.json`, each with `addedIn: <slice>`, after the existing entries, which never change (it refuses a run in which a listed shot is missing or has other pixels, so the same run reproduced all 86 earlier shots digest for digest, and it refuses a slice without its patch); their PNGs go into the store beside the old ones, never over one. The changes file lists the addition as `{"kind": "baseline-addition", "file": "regression/v2/screens/manifest.json", "recordedFrom": <BASELINE_COMMIT>, "patch": "regression/v2/additions/<slice>.patch", "record": "<the commands>", "reason"}`, `record` holding the exact commands, run from the root of the PR's checkout: `out=$(mktemp -d) && for run in 1 2; do node scripts/compare-screens.mjs --base=<BASELINE_COMMIT> --patch=regression/v2/additions/<slice>.patch --v2-only --base-only --out=$out/$run || exit 1; done && node scripts/screens-manifest.mjs --add $out/1/base-shots $out/2/base-shots <slice>` (`0.6c.json`); the new PNGs are then copied from `$out/1/base-shots` into the store, never over a file there, and `screens-manifest.mjs --check` on the store must pass. `screens-manifest.mjs --check <folder>` reads `manifest.json`, and `BaselineDataSetsTest` checks that it holds every state and element shot of `SCREENS` at both widths and that every added shot comes after the baseline's and names a slice whose patch exists. A state v2 did not have (the Poslat dar card of #207) sits in `SCREENS_SINCE_V2`, skipped under `BASELINE_SCREENS=v2` and never in a manifest: it is compared only against the merge base.
- Screens against the merge base: a slice proves "screenshots equal" against its merge base, not against v2, because the non-v3 UX PRs #197 and #205–#208 moved 54 shots after the baseline. In `frontend/`, `npm run screens:compare` (`node ../scripts/compare-screens.mjs [--base=<commit>] [--out=<folder>] [--head-spec | --patch=<file>] [--v2-only] [--base-only] [--keep]`, the last four for recording additions as above; needs `npm ci` in `frontend/` and Playwright's Chromium, no Docker) checks out `git merge-base origin/main HEAD` in a temporary worktree (`node_modules` linked when the lock files are equal, `npm ci` otherwise), builds the base and this checkout (working tree included) for production, serves each on a port of its own, shoots the spec on each with `BASELINE_SCREENS=1`, and compares pixel for pixel: a page may differ in up to 0.2 % of its pixels (the spec's `maxDiffPixelRatio`), an element shot in none, and a changed size always counts as a difference. When the base's lock file differs, its own `npm ci` runs and then its Playwright packages are replaced by the head's (`useHeadPlaywright`), so both sides are shot by the one Chromium the head installed and a Playwright bump does not break the base run. It writes `report.md` (each differing shot with its count, share and box, crops of the base, the head and a diff of red pixels over the faded base around the difference, the shots only one side has) and the shots into a scratch folder (by default a new `nfnn-screens-*` in the system temp folder; a folder inside the repository is refused), and exits 1 on a difference beyond the tolerance, a removed shot or a failed run. `--head-spec` shoots the base with this checkout's `e2e/baseline/` too, so the states the slice adds are compared as well. The report's summary goes into the PR under "Srovnání s v2", a visible change named with its crop; `node --test scripts/compare-screens.test.mjs` tests the comparison.
- The `visual` job ("Vzhled", slice 2.0, `deploy-ci.md`) runs the same comparison on every PR against the PR's base and on every push to `main` against its parent, with `--declared` reading the description: it fails on a differing or removed shot the line `Vzhled se mění: …` does not name, by route (the pathname the spec recorded for the shot under `BASELINE_SCREENS_ROUTES`, `*` at the end matching the rest), by state (`sign-in-dialog`, every width and element shot of it) or by shot (`home--donate-qr`); `Vzhled: beze změny` or no line lets nothing differ, a new shot passes, and the report ends with the line that would declare what it found undeclared. Declare only what the slice means to change; a difference it did not mean is a bug. `compare-screens.test.mjs` tests the reading of the line and the judgement.
- Hygiene: `regression/BaselineHygieneTest` scans `regression/` and `shared-cases/` and fails on an id (a passkey's user handle in base64url too), a JWT, a random secret that no backend test spells out, a TOTP secret (`[A-Z2-7]{32}`) or a `secret=` parameter other than the five test secrets of `shared-cases/totp/uri.json`, an unmasked secret setting, an unmasked refresh cookie, an e-mail address that no backend test uses outside `info@nfnn.cz`, `example.cz`, `.com`, `.org`, `.net` and the reserved `.example`, a JSON file that does not parse, the surname family of the foundation's people (diacritics and whitespace folded), a backup key other than the dev default of `application-dev.yml` and the keys the tests and `test-cases/` spell out, a backup key word (`word`, `words`) that is not `<secret>`, a receipt signing seed of the tests (either RFC 8032 seed, in hex, unpadded Base64 or base64url, any case), a JSON field named after a seed, signing key or private key (`seed`, `signingKey`, `privateKey`, optionally with `Hex`, `Base64` or `Base64url`) that is not `<secret>` or empty, a word of those keys or a word a feature quotes, a BCrypt hash, lowercase hex of 32 or more characters outside a `sha256` field or `sha256=` (and, in `shared-cases/verification/` only, a `payloadHex`, `signatureHex` or `publicKeyHex` field and the digits of a `qrText`) (QR rows of 0 and 1, one repeated letter and `regression/v2/BASELINE_COMMIT` aside, together with the commit id it holds, which a baseline addition's `recordedFrom` and `record` name; only that exact path is trusted, so another file named `BASELINE_COMMIT`, in `regression/` or `shared-cases/`, and its id are still reported), standard base64 of 32 or more characters (with `+`, `/` or `=`), a recovery code `OBNOVA …` and a setup code (12 characters of `SetupCode.ALPHABET`, plain or in groups of four) outside their slots, and an IBAN or a `number/bank` account other than the foundation's (`application.yml`), the ISO example IBANs and those the tests spell out (feature table cells too); a value counts as spelled out when it is in `backend/src/test` or `test-cases/`. A change that brings a new kind of secret (a signing seed, VAPID keys, a hex or standard-base64 token, a new field or setting name) teaches it to `TranscriptNormaliser` as a masked value, field or shape, refuses its environment name while recording, and adds a hygiene rule with a planted case that fails, all in the same PR (`security.md`, Secrets).
- A baseline file is never regenerated to get a check green, and a PR never edits `regression/v2/api/` or `regression/v2/test-inventory.json` (the comparison fails on it, and CI also diffs them against the anchored commit). In `regression/v2/receipts/` and `regression/v2/screens/` an existing file never changes and is never deleted, and an entry of `screens/manifest.json`, `receipts/digests.json` or `receipts/refusals.json` stays as recorded (`compare-v2-baseline.mjs` compares them with the anchored commit, and at the baseline commit `GoldenFiles.assertMatches` refuses under `GOLDEN_FILES=write` to rewrite a corpus file that exists; `main` has no `GoldenFiles` since 1.10); an entry or a file added after the baseline commit is frozen the same way once it is on `main` (`compare-v2-baseline.mjs --base=HEAD^1` also compares the three indexes and the files with the PR's base). A new sample or screen state comes only from a checkout of the baseline commit, as a new file `regression/v2/receipts/<sample>.json` (any other new file under `receipts/` or `screens/` fails) or new entries in one of those three indexes, and the PR lists it in its changes file as `{"kind": "baseline-addition", "file": "regression/v2/screens/manifest.json", "recordedFrom": "<the id in BASELINE_COMMIT>", "patch": "regression/v2/additions/<name>.patch", "record": "<the command that recorded it>", "reason": …}` (`file` starts with the literal folder, `*` allowed after it). `patch` is the change made to that checkout before recording (`git diff` there: a new scenario, a new screen state), committed under `regression/v2/additions/` by the same PR; the baseline guard fails when it is missing or does not apply on the baseline commit (`git apply --check` on its tree), a patch file no entry of this PR names fails the comparison, and an existing one never changes. The report prints the `record` command that records the addition again, under the commit and the patch it starts from; `record` runs from the root of the PR's checkout and prepares the baseline commit with the patch itself (as `compare-screens.mjs --base=<commit> --patch=<patch>` makes its own worktree), because the baseline commit has none of the scripts written since. The comparison fails on an addition no such entry of a file this PR adds or changes names. The PR that created the baseline (the combined 0.1 PR, merged before the comparison existed) was the only exception to this guard; every later PR that touches these files fails. A v3 slice, and any other PR merged after the baseline commit, that changes recorded behaviour declares it in `regression/v2/changes/<slice-or-PR>.json` (`0.5.json`, `pr-183.json`; one file per slice or PR so parallel branches never touch the same file, and the comparison merges them all): a list of `{path, scenario, kind, reason, contract}`. Every pattern starts with a literal anchor, and `*` (any text) is allowed only after it: `path` is a request template starting with `METHOD /api/<context>/` (`GET`, `POST`, `PUT`, `PATCH`, `DELETE` or the literal upper-case method a scenario sends, such as `QKZW1561`; `content`, `donors`, `donations`, `contact`, `operations` or `admin`), `METHOD /actuator/`, `METHOD /.well-known/` or `METHOD /oauth` (the `#n` may be left out; an `added` entry, or a `headers` entry with its `field`, may instead name the exact template, without `*`, of a request outside every context, such as `GET /api/nowhere`, whose answer gained or changed a header that every `/api` answer carries), `scenario` starts with the literal `<context>/<feature>: ` (`donors/admin_donors: *` is the whole feature), `kind` is one of `status`, `headers`, `body`, `request` (what the scenario sends), `mails`, `logs`, `removed` (a request that is gone, or, without `path`, the whole scenario) and `added` (a request the baseline cannot have, such as a scenario added after the baseline commit that the connector check needs; additions pass without it, and it counts only in the scenarios it names), `reason` names the decision and `contract` the contract or overview section. `body` and `headers` take an optional `field`, a glob over the changed JSON path (`$.items[*].receiptAvailable`, starting with the literal `$`) or the header name (`cache-control`), and then cover only those fields of the request; `added` takes either, or a mail's `subject`, and then covers only that added field, header or mail. `mails` and `logs` belong to the scenario and take no `path`; `mails` takes `subject`, the v2 mail's subject (`*` allowed after its first letter), and covers only that mail (required in a file the PR adds or changes; an older entry without it still covers every mail of its scenarios); `logs` takes `line`, the v2 line without its level, starting with the literal logger name (`donors.application.X: E-mail of donor * verified`). `retired` takes `suite` (the literal suite name), `test` (starting with its literal class or file and ` > `) and `replacement`, the id of the test that takes over as the inventory lists it (`<class or file> > <name>`); in a file the PR adds or changes the comparison fails on a replacement that is no test id or, given the inventory, not in it (an older entry is marked in the report, such as `pr-199.json`, whose replacement is the Gradle task that empties the recording folder). `shared-case` takes `caseFile` (a file under `shared-cases/` the PR changes, `*` allowed after that literal start), `reason` and `contract`, and no `path` or `scenario` (`testing-shared-cases.md`, Logic on both sides). An entry without its anchor stops the comparison. A log change, `logs` or `log-field` (`line`: the exact shape of the new kind of log line as the report printed it, without `*`), also carries `security: {"approvedIn": "PR #<number>, Jakub <YYYY-MM-DD>", "fields": {"<slot>": "what it holds"}}`, written only once Jakub approved it (`security.md`, Logs), with the PR and the day of his approval in exactly that form; every slot of the new line (`<id>`, `<n>`, `<digits:N>`, `<enum>`, `<vs>`…) must be in `fields`, or the comparison fails. An invalid entry stops the comparison with exit 2. For example:
  ```json
  [{"path": "POST /api/donors/auth/login", "scenario": "donors/donor_sign_in: Sign-in is limited per client address*", "kind": "status",
  ```

- Comparison: `node scripts/compare-v2.mjs` compares a recording (`backend/build/api-transcripts`, recorded as above) with `regression/v2/api` and, given `--inventory=<file>` from `node scripts/test-inventory.mjs --out=<file>`, the test inventory with `regression/v2/test-inventory.json`; `--changed=<file>` (the PR's files as `git diff --name-status --no-renames <base> HEAD` lists them; a line without a status counts as changed) adds the PR's own checks, and `--report=<file>` writes the Markdown "Srovnání s v2" that goes into the PR body. `--main=<folder>` also compares the recording with a recording of `main` (`--main-commit=<id>` names its commit, `--main-changed=<file>` lists the files changed since that commit in the same form, `--changed` when left out): there a removal or a change fails unless an entry of a changes file added or changed since that commit explains it, so an older declaration explains only the v2 comparison, which stays the cumulative report. Without `--main` (`--main-missing=<why>` says why) the report and a warning say that only the v2 comparison ran. Additions pass (a scenario, a request, a response field or header, a mail, a log line of a shape v2 wrote, a test) and are listed; against `main` an added mail, response field or response header fails unless an `added` entry of a changes file this PR adds or changes names it by `subject` or `field` (added requests and scenarios still pass), and, with `--main-inventory=<file>` (the inventory of the `main` recording, collected as above from its artifacts), a test that `main` has and the fresh inventory lacks fails unless such a file retires it with a `replacement` that is a test id of the fresh inventory. A removal or a change fails unless declared: exit 1 names every undeclared difference with its scenario, request and JSON path or mail line. A log line's shape is the line without its level, with masked values as their kind (`<id>`, `<vs>`, `<token>`…), numbers of up to 4 digits as `<n>` and longer ones as `<digits:N>` (so an account or phone number written where an id was is a new shape), and an upper-case word as `<enum>` only when it holds `_` or v2 wrote it somewhere; a shape no v2 transcript holds is a new log field. The log gate sees only what the transcripts hold: lines of the `cz.novanadeje.app` loggers, as formatted messages, from the code the Cucumber suite runs. Every recorded log line fails, approved or not, when it holds `@`, a fixture alias (any `<vs:Alias>` of the transcripts: `Jana`, `Petr`…), a fixture's full name (any string literal of two or more capitalised words in the Java sources under `backend/src/test/java/**/cucumber/`, `--fixture-sources`: `Jana Nováková`, `Petr Svoboda`…), a word of four or more letters starting with a capital that the transcripts record for a person or an address (a `fullName`, `payerName`, `street`, `city` or `counterparty…` field, or a `name` beside `street`, `city`, `email`, `variableSymbol` or `companyIdentifier` in the same object, so the names of passkeys, devices and connected applications never count; a capitalised token, so `backend` or `donor` in a message never trips it), the masked `<vs>`, `<token>`, `<secret>`, `<jwt>`, `<signatory-name>`, `<setup-code>` or `<recovery-code>`, a number of six or more digits next to `/` (an account number), or an IBAN: two letters directly before `<digits:N>` with N of 10 or more, or a literal IBAN (`CZ65 0800 …`, with or without spaces). The words leave out the erasure placeholders `Vymazaný` and `Vymazáno` (`ErasedPersonalData`) and `COMMON_WORDS` in `compare-v2.mjs`, each with its reason here: `Nová`, `Nové` and `Nový` belong to the foundation's own name and street; `Most` is a fixture city and also an English word, kept rather than renamed because renaming it would change the recordings against v2.
