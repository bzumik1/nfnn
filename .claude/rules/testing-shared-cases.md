# Testing rules: logic on both sides

The general rules (TDD, given/when/then naming) are in `testing.md`.

## Logic on both sides
- A computation the backend and the frontend both perform (local first, `backend.md`) is specified once as shared test cases, inputs and expected outputs in one data file, and the backend and the frontend suites both run every case (Jakub 2026-10-28). A change to the computation changes the cases first, so neither side can pass with its own idea of the result. A case is read from its file, never copied: `sharedcases/SharedCaseFilesTest` fails on a file outside `shared-cases/` that holds a case file or a case's expected value as JSON (any field order or spacing, nested anywhere; an expected value of one field is too common to count), equals a case file's text, or holds a case's QR matrix (also split over string pieces), and e2e reads its payment QR matrices from `qr/payment.json` (`e2e/qr-matrices.ts`).
- The case files are the living specification of these computations, not frozen v2 data, and are changed by hand: a PR that changes what one of them gives changes its cases first, in the same PR as the computation. Its first commit edits the cases (and, when the shape changes, the schema), sets the file's `source` from `v2-baseline` to `edited` if it is not already, and the runners fail on exactly the cases that change; the next commits change the computation on each side that has it, until both suites pass. The PR declares every case file and schema it changes in `regression/v2/changes/<slice-or-PR>.json` as `{"kind": "shared-case", "caseFile": "shared-cases/…", "reason", "contract"}` (`*` allowed after the literal `shared-cases/`): `compare-v2.mjs --changed` fails on a changed file under `shared-cases/` that no entry of a changes file the same PR changes names (an older declaration never covers a later PR), and the report lists each with its reason. The case file's diff is the reviewed statement of the new behaviour. Rewriting a case to match code that was not meant to change, or without the computation change it describes, is refused in review. A runner compares the whole value (`SharedCaseRunner.assertGives`), so a field the computation gains or loses fails until the cases carry it, and a new field also fails the schema until the schema names it.
- Files: `shared-cases/<topic>/<name>.json`, `{source, logic, cases: [{name, input, expected}]}` with names unique in the file and `source` `v2-baseline` (still what the v2 generator wrote at the baseline commit) or `edited` (changed by a PR since), each with its JSON Schema (draft 2020-12) `shared-cases/schemas/<topic>/<name>.schema.json` (parts used by several in `schemas/defs/`; `$id` under `https://nfnn.cz/shared-cases/`, resolved from the folder, never fetched). Vitest checks every file against its schema with ajv (`src/testing/shared-cases.spec.ts`; the backend takes no schema library, plan decision 6), so a new file comes with its schema and an expected value of the wrong shape fails even where only the backend computes it yet; the backend's `SharedCaseFilesTest` checks the envelope (the three fields, a known source, every case with `name`, `input` and `expected`, names once) and that every case file has its schema and every schema its file.
- What both sides run, and from which slice (a later slice adds its file and a line here: the verification payload 1.5, frozen receipts `receipts/v1` 1.6, the sync manifest 2.12). A file holds one computation, so each side runs the whole value of every case: one that two sides compute in different slices, or only one side computes, is split where they part, as the payment QR is into `payment/spayd.json` (inputs to SPAYD text) and `qr/payment.json` (SPAYD text to symbol), and the authenticator QR into `totp/uri.json` (secret, issuer and account to URI, which only the backend computes) and `qr/totp.json` (URI to symbol). - The split files chain by case name: the text a case of `payment/spayd.json` gives is the input of the case of the same name in `qr/payment.json`, and the URI a case of `totp/uri.json` gives the input of its namesake in `qr/totp.json`; `shared-cases.spec.ts` fails when a value and its QR case part, so 1.4 runs `spayd()` and then the encoder through both payment files. ZXing was a `testImplementation` from 1.4, which removed its last production use, until 1.10 retired the backend runners of `qr/*.json`, `QrSymbols` and `QrCodes` with `retired` entries and dropped it; `AdapterLibraryRulesTest` refuses it, openhtmltopdf and PDFBox in every production class, and `ServerDrawingLibrariesTest` finds none of them on the test classpath.
- Placement: a runner lives beside the code it calls, in that context's test package (an endpoint's runner in its `interfaces/rest`, `TotpSecret`'s in `donors/domain`); `sharedcases/` holds only the infrastructure: the runner base `SharedCaseRunner`, the reader `SharedCases` (with the repository root), the envelope and pairing checks `SharedCaseFilesTest`, the copy guard `SharedCaseCopies`, and the readers of a case's input rows (`CaseRows`, `MonthlyReportState`). `architecture/SharedCaseRulesTest` keeps every runner in a context's or `shared`'s package and `sharedcases/` free of `regression/`.
- Rows and the device copy: a case over database rows names only the columns the computation reads (`sharedcases/CaseRows`, `schemas/defs/rows.schema.json`), under the names the sync projection carries (`unpairedByAdminAt`, the instant or null). `CaseRows` gives every row a fixed id (donors, then payments, then the donations by position: `donor:<alias>`, `payment:<alias>`, `donation:<n>`) and `aliased` puts those names back into an answer, so a case can state rows that carry ids. 2.12 added the donor's sync projection: `shared-cases/sync/manifest.json` specifies rows to chunks (the donations chunks and the summary), and the donor-summary runner checks the manifest's summary against the same cases; the browser runner of a topic reads the same cases through those chunks into the device copy and computes from there (2.13 for the donor, 2.17 for the administration's overview and report, whose chunks come then), so both sides chain through one set of cases from the rows to the result. `donations/interfaces/rest/DonorDeviceSyncTest` drives the protocol itself: three simulated devices of one donor sync at random moments between seeded random changes to two donors' gifts, bank account links and symbol answers (receipts come only from the issuer, so their chunks are covered by `donor_device_sync.feature`), a quarter of the syncs with a change landing between the manifest and the chunks, where the device follows the contract's rules (stores each chunk with its own digest and syncs again when a digest, `missing` or the summary shows a change), and must each end with what a fresh download gives (`SYNC_CONVERGENCE_SEEDS` seeds, 30 by default, 300 in the nightly job `sync-convergence`), a device that synced before a restore from a backup downloads exactly the chunks the restore changed, a symbol answer committed by another thread between two reads of one answer stays out of it (the `REPEATABLE READ` snapshot, through a spy on `SymbolClaimRepository` in `DonationRowsContext`), bank account and symbol rows come by account number and symbol whatever their ids, and the manifest of a donor with a thousand gifts, half of them from the bank, answers within 50 ms (median of 21 after 5 warm-up runs). `donations/interfaces/rest/AdminDeviceSyncTest` (2.17, in `DonationRowsContext` too) does the same for the administration's donations copy: three administration devices sync between seeded random changes to three donors' payments, gifts, bank accounts, symbol answers and profiles, unpairings, refunds, corrected amounts and erasures (through `DonorRecordService.erase`), and must each end with what a fresh download gives (the same seeds variable); a symbol answer committed between two reads stays out of the answer; and the manifest over 200 donors (each with a linked account, half with a symbol answer) and a thousand gifts and payments answers within 100 ms (the fastest of 21 after 5 warm-up runs: a load on the runner only ever adds time, and the median of 21 went over the budget when the other fork and its PostgreSQL shared the CI runner's cores; the whole administration in about a dozen queries; `docs/system-overview.md`). `donors/interfaces/rest/AdminDonorsSyncTest` (2.17, in `DonationRowsContext`, which spies on `AdminActionTrail` for it) does the same for the accounts copy: an action committed between the role check and the trail's read stays out of the answer, an account and an action just after a Prague midnight stand in the Prague month, and the manifest over 200 accounts and a thousand actions answers within 100 ms (the fastest of 21, as for the donations copy).
- Backend: a runner extends `sharedcases/SharedCaseRunner`, whose `@TestFactory` (named like any test, `TestNamingRulesTest`) reads the file through Jackson 3 into `SharedCaseFile` and `SharedCase` and makes one dynamic test per case named `Given <case name>, when …, then …`; the runner hands what the backend gives and `expected` to `assertGives`, which compares their canonical JSON as a whole. A case over database rows writes them with `sharedcases/CaseRows.fromJson` through `JdbcClient` and asks the real endpoint or service, so the selecting queries run as well as the compiling code. The runners over donation rows extend `donations/DonationRowsSharedCaseRunner`, whose configuration is the annotation `donations/DonationRowsContext` (`@IntegrationTest`, `TestSupportConfiguration`, first receipt year 2026, spies on `MonthlyReportSender`, `SymbolClaimRepository` and `AdminActionTrail`), which `DonorDeviceSyncTest` carries too, so a fork starts one context for all of them; the runner resets the rate-limit windows with each case's rows, since the case ids repeat across cases and files. `build.gradle.kts` declares `../shared-cases` as the test input `sharedCases`, so a changed case or schema runs the tests again.
- Frontend: Vitest's global setup `src/testing/shared-cases-setup.ts` (named in `vitest.config.mts`, the `runnerConfig` of `ng test`) runs in Node, outside the app build and every spec bundle (so `npm run lint` type-checks it and `vitest.config.mts` with `tsconfig.node.json`, Node's types and nothing of the app), finds the folder from its own URL, reads each file once and provides it to the specs (once per Vitest process: a watch run does not read an edited case file again, so restart it after editing a case); `src/testing/shared-cases.ts` hands out a deep-frozen copy (specs share it, so a spec that edits a case for a negative test clones it first), types each file in `SharedCaseTopics` (a new file is registered there, or the spec fails) and validates it against its schema before `sharedCases(file)` returns its cases; a spec runs each as `describe('Given the shared case <name>')`. One table in `eslint-confinement.js` (`CONFINED_IMPORTS`, used by `eslint.config.js`) keeps ajv in `shared-cases.ts`, Node's built-in modules (with or without `node:`, static or dynamic `import()`) in the setup, and test support (`testing` folders and libraries' testing entry points) and the development libraries (Vitest, fast-check, fake-indexeddb, pdf.js, Playwright) out of the app, and jsQR (a runtime library since 1.8) in `features/donations/verification/qr-decoding.ts`, which only the QR decoder worker loads, and hash-wasm (since 2.13) in `core/device/crypto/argon2.ts`, which only the Argon2id worker `argon2.worker.ts` loads; `scripts/eslint-confinement.test.mjs` (run by `npm run lint`) proves every entry refused outside its scopes and allowed inside (`.claude/rules/frontend.md`, Lint).
- Generators and runners: the generator tests (`QrGoldenCasesTest`, `OverviewGoldenCasesTest` and the generator halves of `ReceiptFormattingCasesTest` and `MonthlyReportFormattingCasesTest`) wrote the v2 files from inputs held in Java. They exist only at the baseline commit: 0.6d retired them from `main` together with `GoldenFiles.generateSharedCases` and the helpers only they used (`retired` entries in `regression/v2/changes/0.6d.json` name the runner that took over each), because on `main` they could only fail on an `edited` file or write v3 output labelled `v2-baseline`. A v2 file is re-recorded on a checkout of `BASELINE_COMMIT` (`testing-regression.md`, Regression against v2); on `main` a case file changes only by hand. The runners read input and expected from the file and check every case, so they keep checking when v2's code is gone and they run the cases a later slice writes by hand. A wrong expected value fails the runner of its case on each side that runs the topic.
