# Testing rules (TDD, given/when/then)

Write the test first, watch it fail for the right reason, make it pass with the smallest change, refactor green. Every behaviour has a test at the lowest level that can prove it.

## Backend
| Level | Tool and place | Rules |
|---|---|---|
| Unit | JUnit 5 + AssertJ + Mockito, `src/test/java/.../<context>/<layer>/` | Name `should_<expected>_when_<action>[_given_<state>]` plus `@DisplayName("Given X, when Y, then Z")` on every test (`architecture/TestNamingRulesTest`); a shared setup may be a `@Nested @DisplayName("Given …")` class whose tests read "when …, then …". AssertJ for assertions (MockMvc's `jsonPath` matchers excepted). Mockito for ports, framework collaborators (`ApplicationEventPublisher`, `JavaMailSender`, `TaskScheduler`) and the collaborating service of the class under test; never for aggregates, entities or value objects: build those with the fixtures (`Donations`, `Receipts`, `BankPayments`, `QrCodes`). Mockito loads as a `-javaagent` from `build.gradle.kts`, not by self-attaching (JDK 25 warns, a later JDK refuses) |
| Acceptance | Cucumber, `src/test/resources/features/<context>/<use_case>.feature` (English Gherkin), glue in `<context>/cucumber/`, shared steps in `cucumber/` | One feature per use case; scenarios go through HTTP with `cucumber/ApiClient`; two suites glue `cz.novanadeje.app`, `cucumber/DonorsAcceptanceTests` (`@donors`) and `cucumber/OtherContextsAcceptanceTests` (every other feature), and the Gradle task `acceptanceTest` runs each in its own fork; `CucumberSpringConfiguration` boots the app with Testcontainers PostgreSQL and `TestSupportConfiguration`. One area: `CUCUMBER_FILTER_TAGS=@<tag> ./gradlew acceptanceTest` (`-Dcucumber.*` does not reach the test JVM). Every feature carries the tag of its context folder (`@contact`, `@content`, `@donations`, `@donors`, `@operations`; `FeatureContextTagsTest` fails otherwise), and the connected applications also `@connected-apps`; a tag no feature carries runs nothing and still passes, so check the report's counts (or add a temporary `@wip`). A new feature carries its context tag |
| Integration | `@IntegrationTest` (the one `@SpringBootTest` configuration, with MockMvc) or `@DataJpaTest` + the context's `<Context>PersistenceTestConfiguration` (`TestcontainersConfiguration` and every adapter of the context) | Real PostgreSQL 17 only, never H2; the scheduler properties are pinned once in `@ScheduledWorkOff` (`architecture/TestContextRulesTest`); schema tests in `shared/infrastructure/schema/` (every foreign key indexed, new changelogs over baseline data, `backend.md` Persistence) |
| Architecture | ArchUnit, `architecture/` | A new invariant gets a rule; rules fail on an empty match |

Test support:
- External ports have fakes in `support/`, registered `@Primary` by `TestSupportConfiguration` (`FakeFioClient`, `RecordingMailSender`, `SynchronousBankImportRequests`, `FakeClientMetadataSource`, `FakeMailServerProbe`, `SwitchablePublicTestKeyPolicy` for a server outside development, the `Recording…` timers and announcers); a new port adds its fake there. The password hasher is the real one: `CachingPasswordHashers` wraps `BCryptPasswordHasher` in `CachingPasswordHasher`, which asks it once per password and once per password and hash. `MailContents` reads sent mail; `FioMovements` builds bank movements. `AsyncTaskTracker` counts the unfinished tasks of the application executor (`@Async`, every mail sender), and nothing else: `AsyncTaskTrackingConfiguration` attaches it with a `ThreadPoolTaskExecutorCustomizer`, never as a `TaskDecorator` bean, which Boot would also hand to the task scheduler. Every `ApiClient` request, the steps that run the backup check or the registration reminder job directly, the scenario reset and the transcript recorder wait for it (a timeout fails the step and names the request and the unfinished count), so mails from separate requests and job steps are recorded in the order they were sent; two mails from one request, or from a new step that calls a service directly without `awaitIdleAfter`, keep the order their sends finish in. A task the pool rejects keeps its count, which happens only after the context closes.
- `CommonStepDefinitions.isolateScenario` (`@Before`) waits until the previous scenario's `@Async` work (the application task executor) is done, so none of its e-mail lands in the next one, then empties every table, children first, and restarts sequences (`DatabaseCleaner`; receipt numbers start at `000001`), clears mail, resets the fake Fio client and, on every acceptance run, recorded or not (so a local `./gradlew test` behaves as CI), sets `MutableClock` to `ApiTranscripts.RECORDING_CLOCK` and resets every rate-limit window, the company lookup's pause and the backup key's word draws (Regression, Recording). `Given today is {date}` sets the clock; `DonorSessions` signs a donor in again after the clock expired the token.
- `FakeFioClient` refuses history older than 90 days until `unlockHistory()` and throws on every bookmark call (`transactions().sinceBookmark()`, `bookmark().moveAfterTransaction/moveToDate`), so `/last/` can never pass.
- In tables `{Jana}` is Jana's variable symbol (`ScenarioDonors`); `{date}` is ISO (`ParameterTypes`). Each scenario sends from its own client address (`X-Forwarded-For`, trusted by the backend); `When the following requests come from another client address` switches; `When the following requests come from the client address {string}` sets a fixed one, safe because `isolateScenario` resets every limit window.

A new feature covers: happy path and each rule as scenarios; validation and problem types; 401 without token and 404 for another donor's resource; rate limits; time boundaries with `MutableClock`; scheduler on and off; a repository test for every derived or hand-written query; a rendering test per new template; `cs` and `en` texts for every new key.

## Frontend
- Vitest specs beside the code (`name.spec.ts`): `describe('Given …')` → `it('when …, then …')`; nested `describe('when …')` with `it('then …')` (or `it('and …, then …')`) when outcomes share a setup. TestBed with `provideHttpClient()`, `provideHttpClientTesting()` (`http.verify()` in `afterEach`), `provideRouter([])`; drive the DOM (events, `fixture.whenStable()`) and assert visible text and ARIA, not internals; fixtures in `*/testing/` (excluded from the app build); `src/test-setup.ts` polyfills `<dialog>` for jsdom and `src/test-providers.ts` (the `providersFile` in `angular.json`) gives every TestBed `LOCALE_ID` `cs`.
- Playwright in `e2e/` by user journey, same naming (`test.describe('Given …')`, `test('when …, then …')`). Nothing may reach a backend: `npm run e2e` builds the production bundle and serves it on :4200 with `scripts/serve-dist.mjs`, which answers like the frontend nginx (`index.html` for app routes, 404 for a missing file) and proxies nothing, and specs import `test` and `expect` from `e2e/fixtures.ts` (lint refuses them from `@playwright/test`): its automatic fixture answers every `/api` request no spec mocked with a 404 problem and serves the setup status and an empty home, and each spec mocks the calls its journey needs (`mockDonorApi` in `e2e/donor-session.ts` for donor and admin pages). CI fails a test that passed only on a retry (`failOnFlakyTests`); with `E2E_DIST` set it serves that folder without building (CI, after its build steps), with `E2E_BASE_URL` set it tests that server and starts none, and locally it reuses a server already on :4200 (`npm start` while editing). `signIn` at 1280 px (the header button is hidden on phones), resize after; downloads via `page.waitForEvent('download')`; `accessibility.spec.ts` runs axe with WCAG 2.2 AA tags, so a new page or dialog gets a case there.
- Test behaviour, text and accessibility, never style values.
- Keeping the suite fast: e2e runs against the production bundle, the code nginx serves, because the dev server compiles again for every run and is slower per page; no spec relies on dev mode (the suite reads no console). CI runs 3 workers with `fullyParallel`, so every test stands alone: no state shared between tests, no order dependence, each mocks what it needs. A test that fails only sometimes is a race in the app or the test: reproduce it, fix it test-first, never retry it away (`failOnFlakyTests` stays). A browser service the headless shell lacks (the password manager, passkeys) is stubbed with `page.addInitScript`, never left to answer on its own. Playwright needs only Chromium's headless shell (`npx playwright install --only-shell chromium`).

## Connector (`mcp/`)
- Vitest specs in `mcp/test/*.spec.ts`, same naming (`describe('Given …')` → `it('when …, then …')`); the backend is `test/fake-backend.ts`, never a real one.

## Logic on both sides
- A computation the backend and the frontend both perform (local first, `backend.md`) is specified once as shared test cases, inputs and expected outputs in one data file, and the backend and the frontend suites both run every case (Jakub 2026-10-28). A change to the computation changes the cases first, so neither side can pass with its own idea of the result. A case is read from its file, never copied: `sharedcases/SharedCaseFilesTest` fails on a file outside `shared-cases/` that holds a case file or a case's expected value as JSON (any field order or spacing, nested anywhere; an expected value of one field is too common to count), equals a case file's text, or holds a case's QR matrix (also split over string pieces), and e2e reads its payment QR matrices from `qr/payment.json` (`e2e/qr-matrices.ts`).
- The case files are the living specification of these computations, not frozen v2 data, and are changed by hand: a PR that changes what one of them gives changes its cases first, in the same PR as the computation. Its first commit edits the cases (and, when the shape changes, the schema), sets the file's `source` from `v2-baseline` to `edited` if it is not already, and the runners fail on exactly the cases that change; the next commits change the computation on each side that has it, until both suites pass. The PR declares every case file and schema it changes in `regression/v2/changes/<slice-or-PR>.json` as `{"kind": "shared-case", "caseFile": "shared-cases/…", "reason", "contract"}` (`*` allowed after the literal `shared-cases/`): `compare-v2.mjs --changed` fails on a changed file under `shared-cases/` that no entry of a changes file the same PR changes names (an older declaration never covers a later PR), and the report lists each with its reason. The case file's diff is the reviewed statement of the new behaviour. Rewriting a case to match code that was not meant to change, or without the computation change it describes, is refused in review. A runner compares the whole value (`SharedCaseRunner.assertGives`), so a field the computation gains or loses fails until the cases carry it, and a new field also fails the schema until the schema names it.
- Files: `shared-cases/<topic>/<name>.json`, `{source, logic, cases: [{name, input, expected}]}` with names unique in the file and `source` `v2-baseline` (still what the v2 generator wrote at the baseline commit) or `edited` (changed by a PR since), each with its JSON Schema (draft 2020-12) `shared-cases/schemas/<topic>/<name>.schema.json` (parts used by several in `schemas/defs/`; `$id` under `https://nfnn.cz/shared-cases/`, resolved from the folder, never fetched). Vitest checks every file against its schema with ajv (`src/testing/shared-cases.spec.ts`; the backend takes no schema library, plan decision 6), so a new file comes with its schema and an expected value of the wrong shape fails even where only the backend computes it yet; the backend's `SharedCaseFilesTest` checks the envelope (the three fields, a known source, every case with `name`, `input` and `expected`, names once) and that every case file has its schema and every schema its file.
- What both sides run, and from which slice (a later slice adds its file and a line here: the verification payload 1.5, frozen receipts `receipts/v1` 1.6, the sync manifest 2.12). A file holds one computation, so each side runs the whole value of every case: one that two sides compute in different slices, or only one side computes, is split where they part, as the payment QR is into `payment/spayd.json` (inputs to SPAYD text) and `qr/payment.json` (SPAYD text to symbol), and the authenticator QR into `totp/uri.json` (secret, issuer and account to URI, which only the backend computes) and `qr/totp.json` (URI to symbol). - The split files chain by case name: the text a case of `payment/spayd.json` gives is the input of the case of the same name in `qr/payment.json`, and the URI a case of `totp/uri.json` gives the input of its namesake in `qr/totp.json`; `shared-cases.spec.ts` fails when a value and its QR case part, so 1.4 runs `spayd()` and then the encoder through both payment files. ZXing (`core`, which production uses until 1.10, and `javase` for decoding in `QrCodes`) stays a `testImplementation` until 1.10 for the backend runners of `qr/*.json` and `QrSymbols`: a slice that removes the last production use before then moves `core` to `testImplementation` instead of dropping it, and 1.10 retires those runners with `retired` entries and drops both.
- Placement: a runner lives beside the code it calls, in that context's test package (an endpoint's runner in its `interfaces/rest`, `ReceiptFormats`'s in `donations/infrastructure/pdf`, the encoders' in `shared/infrastructure/qr`, `TotpSecret`'s in `donors/domain`); `sharedcases/` holds only the infrastructure: the runner base `SharedCaseRunner`, the reader `SharedCases` (with the repository root), the envelope and pairing checks `SharedCaseFilesTest`, the copy guard `SharedCaseCopies`, and the readers of a case's input rows (`CaseRows`, `MonthlyReportState`). `architecture/SharedCaseRulesTest` keeps every runner in a context's or `shared`'s package and `sharedcases/` free of `regression/`.
- Rows and the device copy: a case over database rows names only the columns the computation reads (`sharedcases/CaseRows`, `schemas/defs/rows.schema.json`), under the names the 2.12 sync projection will carry (`unpairedByAdminAt`, the instant or null). 2.12 adds a sync and manifest projection; from then on the backend runner of a topic over rows also projects each case's rows into the canonical chunks and checks them against the case (`shared-cases/sync/manifest.json`), and the browser runner of that topic reads the same cases through those chunks into the device copy and computes from there, so both sides chain through one set of cases from the rows to the result.
- Backend: a runner extends `sharedcases/SharedCaseRunner`, whose `@TestFactory` (named like any test, `TestNamingRulesTest`) reads the file through Jackson 3 into `SharedCaseFile` and `SharedCase` and makes one dynamic test per case named `Given <case name>, when …, then …`; the runner hands what the backend gives and `expected` to `assertGives`, which compares their canonical JSON as a whole. A case over database rows writes them with `sharedcases/CaseRows.fromJson` through `JdbcClient` and asks the real endpoint or service, so the selecting queries run as well as the compiling code. The runners over donation rows extend `donations/DonationRowsSharedCaseRunner`, whose configuration (`TestSupportConfiguration`, first receipt year 2026, a spy on `MonthlyReportSender`) they share, so a fork starts one context for all three. `shared/infrastructure/qr/QrSymbols` describes a QR symbol from the production matrix (version from its side, mask and error correction from its format bits) and checks it against ZXing's encoding and decoding. `build.gradle.kts` declares `../shared-cases` as the test input `sharedCases`, so a changed case or schema runs the tests again.
- Frontend: Vitest's global setup `src/testing/shared-cases-setup.ts` (named in `vitest.config.mts`, the `runnerConfig` of `ng test`) runs in Node, outside the app build and every spec bundle, finds the folder from its own URL, reads each file once and provides it to the specs (once per Vitest process: a watch run does not read an edited case file again, so restart it after editing a case); `src/testing/shared-cases.ts` hands out a deep-frozen copy (specs share it, so a spec that edits a case for a negative test clones it first), types each file in `SharedCaseTopics` (a new file is registered there, or the spec fails) and validates it against its schema before `sharedCases(file)` returns its cases; a spec runs each as `describe('Given the shared case <name>')`. One table in `eslint-confinement.js` (`CONFINED_IMPORTS`, used by `eslint.config.js`) keeps ajv in `shared-cases.ts`, Node's built-in modules (with or without `node:`, static or dynamic `import()`) in the setup, and test support (`testing` folders and libraries' testing entry points) and the development libraries (Vitest, fast-check, fake-indexeddb, pdf.js, Playwright) out of the app; `scripts/eslint-confinement.test.mjs` (run by `npm run lint`) proves every entry refused outside its scopes and allowed inside (`.claude/rules/frontend.md`, Lint).
- Generators and runners: the generator tests (`QrGoldenCasesTest`, `OverviewGoldenCasesTest` and the generator halves of `ReceiptFormattingCasesTest` and `MonthlyReportFormattingCasesTest`) wrote the v2 files from inputs held in Java. They exist only at the baseline commit: 0.6d retired them from `main` together with `GoldenFiles.generateSharedCases` and the helpers only they used (`retired` entries in `regression/v2/changes/0.6d.json` name the runner that took over each), because on `main` they could only fail on an `edited` file or write v3 output labelled `v2-baseline`. A v2 file is re-recorded on a checkout of `BASELINE_COMMIT` (Regression against v2); on `main` a case file changes only by hand. The runners read input and expected from the file and check every case, so they keep checking when v2's code is gone and they run the cases a later slice writes by hand. A wrong expected value fails the runner of its case on each side that runs the topic.

## Regression against v2
Plan v3 is checked against v2 as recorded on `main` just before v3 work starts. `regression/v2/` holds the API transcripts and the test inventory, `shared-cases/<topic>/*.json` the cases both sides run (`{source, logic, cases: [{name, input, expected}]}`); every file named its source `v2-baseline` at the baseline commit, and a file changed since names it `edited` (Logic on both sides). The baseline's anchor is `regression/v2/BASELINE_COMMIT`: it holds the id of the squash-merge commit of the PR that brought these files (#201, `c4a256c2`), whose tree equals the branch they were recorded on, so checking out that commit and running the commands below regenerates every file byte for byte. The file never changes. A tag `v2-baseline` may be put on the same commit, but nothing depends on it (pushing tags is refused to the sessions that build v3). Only fictional fixtures under a fixed clock go in, and the repository is public.
- Recording: `API_TRANSCRIPTS=record ./gradlew acceptanceTest --rerun` (`--rerun`, or `cleanAcceptanceTest` before it, so Gradle cannot skip the run as up to date; `./gradlew test` and `build` record too, since `acceptanceTest` finalizes `test`) writes `backend/build/api-transcripts/<context>/<feature>.json`; copy the folder to `regression/v2/api/`. Recording refuses to start while `MAIL_*`, `APP_*` (Spring's relaxed binding maps them onto `app.*`), `SPRING_APPLICATION_JSON`, a `SPRING_*` name holding `PASSWORD`, `TOKEN`, `SECRET` or `KEY`, a secret setting (`Setting.secrets()`, so a new one is refused without a change here) or a secret the server generates (`JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `RECEIPT_SIGNING_KEY`, `DB_PASSWORD`) is set in the environment (`env -u FIO_TOKEN …`; `ApiTranscriptsTest` fails when `application*.yml` binds a password, token, secret or key it would not refuse), and every scenario, recorded or not, starts at `ApiTranscripts.RECORDING_CLOCK` with every rate-limit window and the company register lookup's pause (`support/CompanyLookupPause`) reset and the backup key's word checks drawn from a fixed seed (`support/BackupKeyWordDraws`), so a transcript does not depend on which scenarios ran before it. On a checkout of the baseline commit, `GOLDEN_FILES=write ./gradlew test --tests "*QrGoldenCasesTest" -PnoCucumber` rewrites the QR cases (the generator is not on `main` since 0.6d). The inventory: `./gradlew test` for the backend JUnit XML (`build/test-results/test/`, and the Cucumber scenarios in `build/test-results/acceptanceTest/`, which `test-inventory.mjs` reads both by default); in `frontend/` `npx ng test --watch=false --reporters=json --output-file=$PWD/test-results/inventory-vitest.json` and `npx playwright test --list --reporter=json > test-results/inventory-playwright.json`; in `mcp/` `npx vitest run --reporter=json --outputFile=test-results/inventory-vitest.json`; then `node scripts/test-inventory.mjs` writes `regression/v2/test-inventory.json` (every test name per suite, sorted, a repeated name with `#n`). The test JVM is pinned to a zone, locale and charset (`-Duser.timezone=Etc/UTC -Duser.language=en -Duser.country=US -Dfile.encoding=UTF-8` in `build.gradle.kts`, guarded by `RecordingEnvironmentTest`), so a recording on another machine writes the same text. The baseline was recorded under `LC_ALL=C.UTF-8`, where the JDK reports `en` without a country; a recording with the pin writes the same bytes (checked with `diff -r` when the pin came in), and a change to the pin needs that check again. Record twice and compare (`diff -r`) before committing: two runs write the same bytes. A recording `acceptanceTest` empties `backend/build/api-transcripts/` before its forks start (Gradle, not the JVM, because the two suites write into the one folder at the same time), so no file of an earlier run survives; each feature runs in one fork, its scenarios in file order, so the ordinals `#n` are the same as in one JVM.
- Before merging the baseline PR: rebase onto the current `main`, record the whole suite again, `diff -r backend/build/api-transcripts regression/v2/api`, commit any difference (with the test inventory and the QR cases, if they changed too), and merge only if `main` has not moved since the rebase; if it has, repeat. So the squash-merge commit that carries the tag holds exactly what its tree records.
- Transcripts (`cucumber/transcript`): per scenario, keyed by its name, a scenario outline's row by its values (`name [GET | /api/x]`, so a new row renumbers nothing), then `#n`: every `ApiClient` call keyed `METHOD /path/{id} #n` (path and query, the sent `Authorization`, `Accept-Language`, `Cookie` and similar headers, the body with fields sorted; the status, every response header but `Date`, `Content-Length` and the connection ones, as a string or, sent several times, an array; the body as JSON, text, a PDF's pages and text, or a binary's size and SHA-256), every mail the scenario sent, also those a step cleared (addresses, subject, text part, the HTML part's visible text, links and SHA-256, attachments), and the `cz.novanadeje.app` log lines as `LEVEL logger: message [Exception]`. Normalised: ids `<id:n>` by first appearance (a passkey's `userHandle` and options `user.id` in base64url too), JWTs `<jwt>`, random mixed-case secrets of 32 or more characters `<token>` (CamelCase names stay), secret fields (`password`, `secret`, `otpauthUri`, tokens, codes; a boolean or number stays) and cookie values `<secret>`, the `value` of a setting whose `name` ends in `PASSWORD`, `TOKEN`, `SECRET` or `KEY` `<secret>`, a cookie's `Expires` `<time>`, image data URIs `<data:image/png size=… sha256=…>`, variable symbols `<vs:Alias>` (`<vs:n>` without an alias), the setup code `<setup-code>`, a recovery code `<recovery-code>` and the modules of a payment QR whose SPAYD carries one `<qr-of-masked-text>`, the receipts' default signatory `<signatory-name>`, a backup key (`AGE-SECRET-KEY-1…` in any case, wherever it stands) and the backup key's words (fields `word`, and `words` when it lists strings) `<secret>`. Writing a transcript fails when any raw value it masked (eight characters or more), raw or URL-encoded, is still in it. What v2 leaves random is settled, and nothing else: object fields are sorted before ids are numbered (v2 writes some answers from maps whose order changes per JVM); field `errors` are sorted (v2 collects them in a set); mails and log lines are sorted with ids blanked (asynchronous listeners send and log in any order); list items stamped with the same instants are sorted by content only on the lists in `UnorderedTie.V2` (request template, JSON path, reason), each shown to change order between two recordings, so every other list keeps v2's order; the diagnostics and the thread dump keep only their shape, the modification times of log and backup files are `<file-time>`; a PDF keeps its text, not its bytes.

## Keeping the suite fast (backend)
- Passwords in tests go through `CachingPasswordHasher` over the real hasher; never a second real-cost hasher or a lower cost, because each BCrypt check at cost 12 costs a core a third of a second.
- E-mail and async waits use Awaitility's defaults, set once in `CommonStepDefinitions.pollWithoutDelay` (no delay, 10 ms interval); no own `pollDelay`, `pollInterval` or `Thread.sleep`. A deliberate "nothing more arrives" wait stays explicit (`pollDelay(SETTLE)`).
- A new `@SpringBootTest` is `@IntegrationTest` (`TestContextRulesTest`) and a new JPA slice imports its context's `<Context>PersistenceTestConfiguration`, so it reuses a cached context and its PostgreSQL container instead of starting both. A test that needs other beans or properties starts a context of its own: say why in the PR.
- A new table needs nothing: `DatabaseCleaner` reads the tables and foreign keys from the catalogue. An integration test that commits cleans before it runs (`@BeforeEach`), because other classes share its database.
- State on disk is per fork: scenarios use the folders under `build/cucumber/fork-${org.gradle.test.worker}/`; a new folder follows suit.
- Where the time goes: the report (`build/reports/tests/{test,acceptanceTest}/index.html`, per class and per scenario), and per step the Cucumber `json:` plugin added for a run to the suite's `PLUGIN_PROPERTY_NAME` (sum `result.duration` per `match.location`, backgrounds included).

## Running
What to run before "done" is in `CLAUDE.md` (Done means); `./gradlew build` is what the PR check runs for the backend. `./gradlew test` runs the unit and integration tests in the `test` task and then, as its finalizer, the scenarios in `acceptanceTest`, each task on two forks; `-PnoCucumber` skips `acceptanceTest`, and `--tests` filters only `test`. In a cloud session: skill `cloud-session`.
