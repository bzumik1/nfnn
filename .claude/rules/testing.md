# Testing rules (TDD, given/when/then)

Write the test first, watch it fail for the right reason, make it pass with the smallest change, refactor green. Every behaviour has a test at the lowest level that can prove it.

## Backend
| Level | Tool and place | Rules |
|---|---|---|
| Unit | JUnit 5 + AssertJ + Mockito, `src/test/java/.../<context>/<layer>/` | Name `should_<expected>_when_<action>[_given_<state>]` plus `@DisplayName("Given X, when Y, then Z")` on every test (`architecture/TestNamingRulesTest`); a shared setup may be a `@Nested @DisplayName("Given …")` class whose tests read "when …, then …". AssertJ for assertions (MockMvc's `jsonPath` matchers excepted). Mockito for ports, framework collaborators (`ApplicationEventPublisher`, `JavaMailSender`, `TaskScheduler`) and the collaborating service of the class under test; never for aggregates, entities or value objects: build those with the fixtures (`Donations`, `Receipts`, `BankPayments`, `QrCodes`). Mockito loads as a `-javaagent` from `build.gradle.kts`, not by self-attaching (JDK 25 warns, a later JDK refuses) |
| Acceptance | Cucumber, `src/test/resources/features/<context>/<use_case>.feature` (English Gherkin), glue in `<context>/cucumber/`, shared steps in `cucumber/` | One feature per use case; scenarios go through HTTP with `cucumber/ApiClient`; two suites glue `cz.novanadeje.app`, `cucumber/DonorsAcceptanceTests` (`@donors`) and `cucumber/OtherContextsAcceptanceTests` (every other feature), and the Gradle task `acceptanceTest` runs each in its own fork; `CucumberSpringConfiguration` boots the app with Testcontainers PostgreSQL and `TestSupportConfiguration`. One area: `CUCUMBER_FILTER_TAGS=@<tag> ./gradlew acceptanceTest` (`-Dcucumber.*` does not reach the test JVM). Every feature carries the tag of its context folder (`@contact`, `@content`, `@donations`, `@donors`, `@operations`; `FeatureContextTagsTest` fails otherwise), and the connected applications also `@connected-apps`; a tag no feature carries runs nothing and still passes, so check the report's counts (or add a temporary `@wip`). A new feature carries its context tag |
| Integration | `@IntegrationTest` (the one `@SpringBootTest` configuration, with MockMvc) or `@DataJpaTest` + the context's `<Context>PersistenceTestConfiguration` (`TestcontainersConfiguration` and every adapter of the context) | Real PostgreSQL 17 only, never H2; the scheduler properties are pinned once in `@ScheduledWorkOff` (`architecture/TestContextRulesTest`); schema tests in `shared/infrastructure/schema/` (every foreign key indexed, new changelogs over baseline data, `backend.md` Persistence) |
| Architecture | ArchUnit, `architecture/` | A new invariant gets a rule; rules fail on an empty match |

Test support:
- External ports have fakes in `support/`, registered `@Primary` by `TestSupportConfiguration` (`FakeFioClient`, `RecordingMailSender`, `SynchronousBankImportRequests`, `FakeClientMetadataSource`, `FakeMailServerProbe`, the `Recording…` timers and announcers); a new port adds its fake there. The password hasher is the real one: `CachingPasswordHashers` wraps `BCryptPasswordHasher` in `CachingPasswordHasher`, which asks it once per password and once per password and hash. `MailContents` reads sent mail; `FioMovements` builds bank movements.
- `CommonStepDefinitions.isolateScenario` (`@Before`) waits until the previous scenario's `@Async` work (the application task executor) is done, so none of its e-mail lands in the next one, then empties every table, children first, and restarts sequences (`DatabaseCleaner`; receipt numbers start at `000001`), clears mail, resets the fake Fio client and advances `MutableClock` a day. `Given today is {date}` sets the clock, and an `@After` in `FioImportStepDefinitions` moves it forward again so tokens and rate windows never go backwards; `DonorSessions` signs a donor in again after the clock expired the token.
- `FakeFioClient` refuses history older than 90 days until `unlockHistory()` and throws on every bookmark call (`transactions().sinceBookmark()`, `bookmark().moveAfterTransaction/moveToDate`), so `/last/` can never pass.
- In tables `{Jana}` is Jana's variable symbol (`ScenarioDonors`); `{date}` is ISO (`ParameterTypes`). Each scenario sends from its own client address (`X-Forwarded-For`, trusted by the backend); `When the following requests come from another client address` switches; `When the following requests come from the client address {string}` sets a fixed one, safe because `isolateScenario` moves the clock a day forward, past every limit window.

A new feature covers: happy path and each rule as scenarios; validation and problem types; 401 without token and 404 for another donor's resource; rate limits; time boundaries with `MutableClock`; scheduler on and off; a repository test for every derived or hand-written query; a rendering test per new template; `cs` and `en` texts for every new key.

## Frontend
- Vitest specs beside the code (`name.spec.ts`): `describe('Given …')` → `it('when …, then …')`; nested `describe('when …')` with `it('then …')` (or `it('and …, then …')`) when outcomes share a setup. TestBed with `provideHttpClient()`, `provideHttpClientTesting()` (`http.verify()` in `afterEach`), `provideRouter([])`; drive the DOM (events, `fixture.whenStable()`) and assert visible text and ARIA, not internals; fixtures in `*/testing/` (excluded from the app build); `src/test-setup.ts` polyfills `<dialog>` for jsdom and `src/test-providers.ts` (the `providersFile` in `angular.json`) gives every TestBed `LOCALE_ID` `cs`.
- Playwright in `e2e/` by user journey, same naming (`test.describe('Given …')`, `test('when …, then …')`). Nothing may reach a backend: `npm run e2e` builds the production bundle and serves it on :4200 with `scripts/serve-dist.mjs`, which answers like the frontend nginx (`index.html` for app routes, 404 for a missing file) and proxies nothing, and specs import `test` and `expect` from `e2e/fixtures.ts` (lint refuses them from `@playwright/test`): its automatic fixture answers every `/api` request no spec mocked with a 404 problem and serves the setup status and an empty home, and each spec mocks the calls its journey needs (`mockDonorApi` in `e2e/donor-session.ts` for donor and admin pages). CI fails a test that passed only on a retry (`failOnFlakyTests`); with `E2E_DIST` set it serves that folder without building (CI, after its build steps), with `E2E_BASE_URL` set it tests that server and starts none, and locally it reuses a server already on :4200 (`npm start` while editing). `signIn` at 1280 px (the header button is hidden on phones), resize after; downloads via `page.waitForEvent('download')`; `accessibility.spec.ts` runs axe with WCAG 2.2 AA tags, so a new page or dialog gets a case there.
- Test behaviour, text and accessibility, never style values.
- Keeping the suite fast: e2e runs against the production bundle, the code nginx serves, because the dev server compiles again for every run and is slower per page; no spec relies on dev mode (the suite reads no console). CI runs 3 workers with `fullyParallel`, so every test stands alone: no state shared between tests, no order dependence, each mocks what it needs. A test that fails only sometimes is a race in the app or the test: reproduce it, fix it test-first, never retry it away (`failOnFlakyTests` stays). A browser service the headless shell lacks (the password manager, passkeys) is stubbed with `page.addInitScript`, never left to answer on its own. Playwright needs only Chromium's headless shell (`npx playwright install --only-shell chromium`).

## Connector (`mcp/`)
- Vitest specs in `mcp/test/*.spec.ts`, same naming (`describe('Given …')` → `it('when …, then …')`); the backend is `test/fake-backend.ts`, never a real one.

## Logic on both sides
- A computation the backend and the frontend both perform (local first, `backend.md`) is specified once as shared test cases, inputs and expected outputs in one data file, and the backend and the frontend suites both run every case (Jakub 2026-10-28). A change to the computation changes the cases first, so neither side can pass with its own idea of the result. A case is read from its file, never copied: `sharedcases/SharedCaseFilesTest` fails on a file outside `shared-cases/` that holds a case file or a case's expected value as JSON (any field order or spacing, nested anywhere; an expected value of one field is too common to count), equals a case file's text, or holds a case's QR matrix (also split over string pieces), and e2e reads its payment QR matrices from `qr/payment.json` (`e2e/qr-matrices.ts`).
- The case files are the living specification of these computations, not frozen v2 data, and are changed by hand: a PR that changes what one of them gives changes its cases first, in the same PR as the computation. Its first commit edits the cases (and, when the shape changes, the schema), sets the file's `source` from `v2-baseline` to `edited` if it is not already, and the runners fail on exactly the cases that change; the next commits change the computation on each side that has it, until both suites pass. The PR declares every case file and schema it changes in `regression/v2/changes/<slice-or-PR>.json` as `{"kind": "shared-case", "caseFile": "shared-cases/…", "reason", "contract"}` (`*` allowed after the literal `shared-cases/`): `compare-v2.mjs --changed` fails on a changed file under `shared-cases/` that no entry names, and the report lists each with its reason. The case file's diff is the reviewed statement of the new behaviour. Rewriting a case to match code that was not meant to change, or without the computation change it describes, is refused in review. A runner compares the whole value (`SharedCaseRunner.assertGives`), so a field the computation gains or loses fails until the cases carry it, and a new field also fails the schema until the schema names it.
- Files: `shared-cases/<topic>/<name>.json`, `{source, logic, cases: [{name, input, expected}]}` with names unique in the file and `source` `v2-baseline` (still what the v2 generator wrote at the baseline commit) or `edited` (changed by a PR since), each with its JSON Schema (draft 2020-12) `shared-cases/schemas/<topic>/<name>.schema.json` (parts used by several in `schemas/defs/`; `$id` under `https://nfnn.cz/shared-cases/`, resolved from the folder, never fetched). Vitest checks every file against its schema with ajv (`src/testing/shared-cases.spec.ts`; the backend takes no schema library, plan decision 6), so a new file comes with its schema and an expected value of the wrong shape fails even where only the backend computes it yet; the backend's `SharedCaseFilesTest` checks the envelope (the three fields, a known source, every case with `name`, `input` and `expected`, names once) and that every case file has its schema and every schema its file.
- What both sides run (a later slice adds its file and a line here: payment messages 1.2, the verification payload 1.5, frozen receipts `receipts/v1` 1.6, the sync manifest 2.12):

  | File | Backend runner | Browser |
  |---|---|---|
  | `qr/payment.json` | `QrSharedCasesTest` (`PaymentQrCases`): `GET /api/donations/payment-qr` for the foundation's account, `GeneratePaymentQrService` for another recipient; SPAYD text, symbol and matrix, or the refusal (an HTTP problem of that endpoint, which 1.4 removes: it rewrites the refusals as the browser's own or retires them, the schema's description says so) | 1.4 (`spayd.ts` and the encoder) |
  | `qr/totp.json` | `QrSharedCasesTest` (`TotpQrCases`): `TotpSecret.otpauthUri` and `QrCodeEncoder` | 1.4 |
  | `receipts/formatting.json` | `ReceiptFormattingSharedCasesTest`: `ReceiptFormats` and `ReceiptData` | Czech amounts as `formatMinorUnits` and `\u00a0Kč` (`donation-amount.spec.ts`); the rest with `receipt-format.ts` (1.9) |
  | `donor-summary/summary.json` | `OverviewSharedCasesTest` (`DonorSummaryCases`): the rows, then `GET /api/donations/me/summary` (the real query, then `DonationSummary`); a case's `firstReceiptYear` must be the context's 2026 | from the device copy (Phase 2) |
  | `admin-overview/year-overview.json` | `OverviewSharedCasesTest` (`AdminOverviewCases`): the rows, then `GET /api/admin/donations/overview` (the real queries, then `YearOverview.compile`) | 2.20b |

- Rows and the device copy: a case over database rows names only the columns the computation reads (`regression/BaselineRows`, `schemas/defs/rows.schema.json`), under the names the 2.12 sync projection will carry (`unpairedByAdminAt`, the instant or null). 2.12 adds a sync and manifest projection; from then on the backend runner of a topic over rows also projects each case's rows into the canonical chunks and checks them against the case (`shared-cases/sync/manifest.json`), and the browser runner of that topic reads the same cases through those chunks into the device copy and computes from there, so both sides chain through one set of cases from the rows to the result.
- Backend: a runner extends `sharedcases/SharedCaseRunner`, whose `@TestFactory` (named like any test, `TestNamingRulesTest`) reads the file through Jackson 3 into `SharedCaseFile` and `SharedCase` and makes one dynamic test per case named `Given <case name>, when …, then …`; the runner hands what the backend gives and `expected` to `assertGives`, which compares their canonical JSON as a whole. A case over database rows writes them with `regression/BaselineRows.fromJson` through `JdbcClient` and asks the real endpoint or service, so the selecting queries run as well as the compiling code. `OverviewSharedCasesTest` has the configuration of `OverviewGoldenCasesTest` (`TestSupportConfiguration`, first receipt year 2026, a spy on `MonthlyReportSender`), so a fork that runs both starts one context for them. `QrSymbols` describes a QR symbol from the production matrix (version from its side, mask and error correction from its format bits) and checks it against ZXing's encoding and decoding. `build.gradle.kts` declares `../shared-cases` as the test input `sharedCases`, so a changed case or schema runs the tests again.
- Frontend: Vitest's global setup `src/testing/shared-cases-setup.ts` (named in `vitest.config.mts`, the `runnerConfig` of `ng test`) runs in Node, outside the app build and every spec bundle, finds the folder from its own URL, reads each file once and provides it to the specs; `src/testing/shared-cases.ts` hands out a deep-frozen copy (specs share it, so a spec that edits a case for a negative test clones it first), types each file in `SharedCaseTopics` (a new file is registered there, or the spec fails) and validates it against its schema before `sharedCases(file)` returns its cases; a spec runs each as `describe('Given the shared case <name>')`. One table in `eslint.config.js` (`CONFINED_IMPORTS`) keeps ajv in `shared-cases.ts`, Node's built-in modules (with or without `node:`, static or dynamic `import()`) in the setup, and test support (`testing` folders and libraries' testing entry points) out of the app.
- Generators and runners: the generator tests (`QrGoldenCasesTest`, `OverviewGoldenCasesTest`, `ReceiptFormattingCasesTest`, `MonthlyReportFormattingCasesTest`) wrote the v2 files from inputs held in Java. A normal run skips them; `GOLDEN_FILES=write` (or `scripts/record-baseline-data.sh`) rebuilds a file only while its `source` is `v2-baseline` and refuses one marked `edited`, so nothing rewrites a hand-edited case (`GoldenFiles.generateSharedCases`). The runners read input and expected from the file and check every case, so they keep checking when v2's code is gone and they run the cases a later slice writes by hand. A wrong expected value fails the runner of its case on each side that runs the topic.

## Regression against v2
Plan v3 is checked against v2 as recorded on `main` just before v3 work starts. `regression/v2/` holds the API transcripts and the test inventory, `shared-cases/<topic>/*.json` the cases both sides run (`{source, logic, cases: [{name, input, expected}]}`); every file named its source `v2-baseline` at the baseline commit, and a file changed since names it `edited` (Logic on both sides). The baseline's anchor is `regression/v2/BASELINE_COMMIT`: it holds the id of the squash-merge commit of the PR that brought these files (#201, `c4a256c2`), whose tree equals the branch they were recorded on, so checking out that commit and running the commands below regenerates every file byte for byte. The file never changes. A tag `v2-baseline` may be put on the same commit, but nothing depends on it (pushing tags is refused to the sessions that build v3). Only fictional fixtures under a fixed clock go in, and the repository is public.
- Recording: `API_TRANSCRIPTS=record ./gradlew acceptanceTest --rerun` (`--rerun`, or `cleanAcceptanceTest` before it, so Gradle cannot skip the run as up to date; `./gradlew test` and `build` record too, since `acceptanceTest` finalizes `test`) writes `backend/build/api-transcripts/<context>/<feature>.json`; copy the folder to `regression/v2/api/`. Recording refuses to start while `MAIL_*`, `FIO_TOKEN`, `JWT_SECRET` or `SETTINGS_KEY` is set in the environment (`env -u FIO_TOKEN …`), and every scenario starts at `ApiTranscripts.RECORDING_CLOCK` with every rate-limit window and the company register lookup's pause (`support/CompanyLookupPause`) reset and the backup key's word checks drawn from a fixed seed (`support/BackupKeyWordDraws`), so a transcript does not depend on which scenarios ran before it. `GOLDEN_FILES=write ./gradlew test --tests "*QrGoldenCasesTest" -PnoCucumber` rewrites the QR cases while they are still `v2-baseline`. The inventory: `./gradlew test` for the backend JUnit XML (`build/test-results/test/`, and the Cucumber scenarios in `build/test-results/acceptanceTest/`, which `test-inventory.mjs` reads both by default); in `frontend/` `npx ng test --watch=false --reporters=json --output-file=$PWD/test-results/inventory-vitest.json` and `npx playwright test --list --reporter=json > test-results/inventory-playwright.json`; in `mcp/` `npx vitest run --reporter=json --outputFile=test-results/inventory-vitest.json`; then `node scripts/test-inventory.mjs` writes `regression/v2/test-inventory.json` (every test name per suite, sorted, a repeated name with `#n`). The test JVM is pinned to a zone, locale and charset (`-Duser.timezone=Etc/UTC -Duser.language=en -Duser.country=US -Dfile.encoding=UTF-8` in `build.gradle.kts`, guarded by `RecordingEnvironmentTest`), so a recording on another machine writes the same text. The baseline was recorded under `LC_ALL=C.UTF-8`, where the JDK reports `en` without a country; a recording with the pin writes the same bytes (checked with `diff -r` when the pin came in), and a change to the pin needs that check again. Record twice and compare (`diff -r`) before committing: two runs write the same bytes. A recording `acceptanceTest` empties `backend/build/api-transcripts/` before its forks start (Gradle, not the JVM, because the two suites write into the one folder at the same time), so no file of an earlier run survives; each feature runs in one fork, its scenarios in file order, so the ordinals `#n` are the same as in one JVM.
- Before merging the baseline PR: rebase onto the current `main`, record the whole suite again, `diff -r backend/build/api-transcripts regression/v2/api`, commit any difference (with the test inventory and the QR cases, if they changed too), and merge only if `main` has not moved since the rebase; if it has, repeat. So the squash-merge commit that carries the tag holds exactly what its tree records.
- Transcripts (`cucumber/transcript`): per scenario, keyed by its name, a scenario outline's row by its values (`name [GET | /api/x]`, so a new row renumbers nothing), then `#n`: every `ApiClient` call keyed `METHOD /path/{id} #n` (path and query, the sent `Authorization`, `Accept-Language`, `Cookie` and similar headers, the body with fields sorted; the status, every response header but `Date`, `Content-Length` and the connection ones, as a string or, sent several times, an array; the body as JSON, text, a PDF's pages and text, or a binary's size and SHA-256), every mail the scenario sent, also those a step cleared (addresses, subject, text part, the HTML part's visible text, links and SHA-256, attachments), and the `cz.novanadeje.app` log lines as `LEVEL logger: message [Exception]`. Normalised: ids `<id:n>` by first appearance (a passkey's `userHandle` and options `user.id` in base64url too), JWTs `<jwt>`, random mixed-case secrets of 32 or more characters `<token>` (CamelCase names stay), secret fields (`password`, `secret`, `otpauthUri`, tokens, codes; a boolean or number stays) and cookie values `<secret>`, the `value` of a setting whose `name` ends in `PASSWORD`, `TOKEN`, `SECRET` or `KEY` `<secret>`, a cookie's `Expires` `<time>`, image data URIs `<data:image/png size=… sha256=…>`, variable symbols `<vs:Alias>` (`<vs:n>` without an alias), the setup code `<setup-code>`, a recovery code `<recovery-code>` and the modules of a payment QR whose SPAYD carries one `<qr-of-masked-text>`, the receipts' default signatory `<signatory-name>`. Writing a transcript fails when any raw value it masked (eight characters or more), raw or URL-encoded, is still in it. What v2 leaves random is settled, and nothing else: object fields are sorted before ids are numbered (v2 writes some answers from maps whose order changes per JVM); field `errors` are sorted (v2 collects them in a set); mails and log lines are sorted with ids blanked (asynchronous listeners send and log in any order); list items stamped with the same instants are sorted by content only on the lists in `UnorderedTie.V2` (request template, JSON path, reason), each shown to change order between two recordings, so every other list keeps v2's order; the diagnostics and the thread dump keep only their shape, the modification times of log and backup files are `<file-time>`; a PDF keeps its text, not its bytes.
- Golden cases: `regression/QrGoldenCasesTest` asked v2 for every case of `shared-cases/qr/payment.json` (through `GET /api/donations/payment-qr`) and `totp.json` (through `QrCodeEncoder`) and wrote the SPAYD text or URI, the error correction, version, mode, ECI header, mask and matrix; since 0.2 it runs only under `GOLDEN_FILES=write`, and `QrSharedCasesTest` checks the cases. Re-encoding the text with ZXing is a guard that the recorded mask and version are ZXing's for that matrix; decoding the matrix back to its text and header is the independent check.
- Data sets, receipts and screens (on a checkout of the baseline commit; from 0.2 on the script stops at the shared case files marked `edited` instead of rewriting them): `env -u FIO_TOKEN scripts/record-baseline-data.sh` (no `MAIL_*`, `FIO_TOKEN`, `JWT_SECRET` or `SETTINGS_KEY` in the environment, as for recording; Docker, Node 24, Playwright's Chromium, `npm ci` in `frontend/` and `mcp/`; `GRADLE_INIT_SCRIPT` and `TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX` pass through) rewrites them in one step: it writes the backend files and checks the rendered receipts against `digests.json` (`scripts/receipts-check.mjs`), builds this checkout's frontend for production and serves it with `frontend/scripts/serve-dist.mjs` on a free port of its own (`E2E_BASE_URL`, `CI=1`, so never a server another checkout left on :4200; one retry on a new port; `--workers=2`, not CI's three), shoots the screens twice into separate folders and fails, naming the states, unless the second run has the pixels of the first, runs every suite with `GOLDEN_FILES=digests` so the recorded files read back, and regenerates the test inventory as above (an id in a test name written `<id>`), which the hygiene and data set checks then read once more. Only then it stages the shots and receipts in the store's `.incoming/`, checks them there, moves the files they replace to `.previous/` and the staged ones into place. On a failure it keeps its temporary folder and prints its path. `donations/infrastructure/pdf/ReceiptCorpusTest` freezes and renders 15 receipts (the four history samples and edge cases, among them 1, 40, 120 and 366 gifts and three gifts of one day for the tie order, signed by the fictional `Petr Vzorový`) into `regression/v2/receipts/<sample>.json`: frozen data, page count, fonts, page size and the text lines (U+00A0 written as a space) with the position of each line's first character rounded to whole points, so the layout is checked on every run, plus `refusals.json`. The PDF's SHA-256 and each page's RGB raster digest at 100 DPI change with PDFBox, openhtmltopdf and the JDK, so they sit apart in `digests.json`, checked only under `GOLDEN_FILES=digests` (the script); the rendered PDFs and page PNGs land in `backend/build/receipt-corpus/` and the store's `receipts/`. `regression/OverviewGoldenCasesTest` inserts each case's rows through `regression/BaselineRows` (`JdbcClient`; `BaselineRows.fromJson` rebuilds them from a case's `input`, `BaselineRowsTest`) and records what v2 answers: `shared-cases/admin-overview/year-overview.json` (`GET /api/admin/donations/overview`), `donor-summary/summary.json` (`GET /api/donations/me/summary`) and `monthly-report/report.json` (the compiled figures and the e-mail's text); `ReceiptFormattingCasesTest` and `MonthlyReportFormattingCasesTest` record `shared-cases/receipts/formatting.json` and `monthly-report/formatting.json`. `frontend/e2e/baseline/screens.spec.ts` runs in the Playwright project `baseline` only (skipped unless `BASELINE_SCREENS` is set; the browser gets a Czech system locale for date fields and rasters on one thread without the GPU, since otherwise a few anti-aliased edges came out differently between two runs) and shoots 43 routes and states at 390 and 1280 px with the e2e mocks under a fixed clock; a comparison run accepts up to 0.2 % of pixels. The PNGs are too large for the repository and stay in `/mnt/project-files/nfnn-ux/snimky/v2-baseline/`; `regression/v2/screens/manifest.json` records the SHA-256 of each shot's decoded pixels, because a file store may add chunks to a PNG (the project-files mount adds a C2PA `caBX` chunk). To compare: `node scripts/screens-manifest.mjs --check <folder>` checks digests; for pixels copy the store to a temporary folder and, with `E2E_BASE_URL` at this checkout's own build served by `node scripts/serve-dist.mjs dist/frontend/browser <port>`, run `BASELINE_SCREENS=1 BASELINE_SCREENS_DIR=<copy> npx playwright test e2e/baseline/screens.spec.ts --project=baseline --update-snapshots=none`. A digest that differs means comparing pixels, never recording again. `regression/BaselineDataSetsTest` checks the case files' shape, that the manifest has exactly the states of the spec's `SCREENS` at both widths, and that no real-looking fixture value is in them (the values are listed only as SHA-256 digests of their lowercased tokens).
- Hygiene: `regression/BaselineHygieneTest` scans `regression/` and `shared-cases/` and fails on an id (a passkey's user handle in base64url too), a JWT, a random secret that no backend test spells out, a TOTP secret (`[A-Z2-7]{32}`) or a `secret=` parameter other than the five test secrets of `totp.json`, an unmasked secret setting, an unmasked refresh cookie, an e-mail address that no backend test uses outside `info@nfnn.cz`, `example.cz`, `.com`, `.org`, `.net` and the reserved `.example`, a JSON file that does not parse, and the surname family of the foundation's people (diacritics and whitespace folded).
- A baseline file is never regenerated to get a check green, and a PR never edits `regression/v2/api/` or `regression/v2/test-inventory.json` (the comparison fails on it, and CI also diffs them against the anchored commit). The PR that created the baseline (the combined 0.1 PR, merged before the comparison existed) was the only exception to this guard; every later PR that touches these files fails. A v3 slice, and any other PR merged after the baseline commit, that changes recorded behaviour declares it in `regression/v2/changes/<slice-or-PR>.json` (`0.5.json`, `pr-183.json`; one file per slice or PR so parallel branches never touch the same file, and the comparison merges them all): a list of `{path, scenario, kind, reason, contract}`. Every pattern starts with a literal anchor, and `*` (any text) is allowed only after it: `path` is a request template starting with `METHOD /api/<context>/` (`GET`, `POST`, `PUT`, `PATCH` or `DELETE`; `content`, `donors`, `donations`, `contact`, `operations` or `admin`), `METHOD /actuator/`, `METHOD /.well-known/` or `METHOD /oauth` (the `#n` may be left out), `scenario` starts with the literal `<context>/<feature>: ` (`donors/admin_donors: *` is the whole feature), `kind` is one of `status`, `headers`, `body`, `request` (what the scenario sends), `mails`, `logs`, `removed` (a request that is gone, or, without `path`, the whole scenario) and `added` (a request the baseline cannot have, such as a scenario added after the baseline commit that the connector check needs; additions pass without it, and it counts only in the scenarios it names), `reason` names the decision and `contract` the contract or overview section. `mails` and `logs` belong to the scenario and take no `path`; `logs` takes `line`, the v2 line without its level, starting with the literal logger name (`donors.application.X: E-mail of donor * verified`). `retired` takes `suite` (the literal suite name), `test` (starting with its literal class or file and ` > `) and `replacement` (the test that takes over, or why none does). `shared-case` takes `caseFile` (a file under `shared-cases/` the PR changes, `*` allowed after that literal start), `reason` and `contract`, and no `path` or `scenario` (Logic on both sides). An entry without its anchor stops the comparison. A log change, `logs` or `log-field` (`line`: the exact shape of the new kind of log line as the report printed it, without `*`), also carries `security: {"approvedIn": "<PR or review and date>", "fields": {"<slot>": "what it holds"}}`, written only once Jakub approved it (`security.md`, Logs); every slot of the new line (`<id>`, `<n>`, `<digits:N>`, `<enum>`, `<vs>`…) must be in `fields`, or the comparison fails. An invalid entry stops the comparison with exit 2. For example:
  ```json
  [{"path": "POST /api/donors/auth/login", "scenario": "donors/donor_sign_in: Sign-in is limited per client address*", "kind": "status",
    "reason": "0.5 counts IPv6 clients per /64, so the 11th request from the same /64 is 429", "contract": "docs/api-contract.md, Rate limits"},
   {"kind": "log-field", "line": "donors.application.DonorAuthenticationService: Sign-in of donor <id> refused after <n> attempts",
    "reason": "1.x logs refused sign-ins", "security": {"approvedIn": "PR #201, Jakub 2026-11-12", "fields": {"<id>": "the donor id", "<n>": "the attempt count"}}}]
  ```
- Comparison: `node scripts/compare-v2.mjs` compares a recording (`backend/build/api-transcripts`, recorded as above) with `regression/v2/api` and, given `--inventory=<file>` from `node scripts/test-inventory.mjs --out=<file>`, the test inventory with `regression/v2/test-inventory.json`; `--changed=<file>` (one changed path per line, as `git diff --name-only` lists them) adds the PR's own checks, and `--report=<file>` writes the Markdown "Srovnání s v2" that goes into the PR body. Additions pass (a scenario, a request, a response field or header, a mail, a log line of a shape v2 wrote, a test) and are listed; a removal or a change fails unless declared: exit 1 names every undeclared difference with its scenario, request and JSON path or mail line. A log line's shape is the line without its level, with masked values as their kind (`<id>`, `<vs>`, `<token>`…), numbers of up to 4 digits as `<n>` and longer ones as `<digits:N>` (so an account or phone number written where an id was is a new shape), and an upper-case word as `<enum>` only when it holds `_` or v2 wrote it somewhere; a shape no v2 transcript holds is a new log field. The log gate sees only what the transcripts hold: lines of the `cz.novanadeje.app` loggers, as formatted messages, from the code the Cucumber suite runs. The report lists every security-approved declaration and every changed or added log line in sections of their own, names any change to the recorder, the masking, the comparison scripts, the `pr-check.yml` jobs, the test JVM settings in `build.gradle.kts` or `BASELINE_COMMIT`, and fails when the PR touches the baseline. An unused declaration fails when its file is one the PR adds or changes and is only listed otherwise, because a declaration stays valid for every later recording. `node --test scripts/*.test.mjs` runs the scripts' own tests.
- Connector shapes: `mcp/test/backend-shapes.spec.ts` collects every backend call in `mcp/src` (each `backend.get|getText|post|put|delete|postPhoto` path, plus the authorization metadata and the token endpoint; an interpolated id becomes `{id}`, which matches only the recorder's `{id}` segments, and an `encodeURIComponent(…)` name becomes `{name}`, which matches only a literal segment) and fails when one has no transcript, or when the fake backend (`test/fake-backend.ts`, every `case` label and the routes listed beside them) answers a call with a status no transcript of that call records, or with a field or type that no recorded answer of that status has (fewer fields are fine; a field recorded only as `null` takes another value only when `RECORDED_ONLY_AS_NULL` in the spec lists it with the reason). It reads `regression/v2/api`, where a call recorded only since v2 needs an `added` declaration, or, with `API_TRANSCRIPTS_DIR` (absolute, or relative to the repository) set to a fresh recording, that recording, where every call must be.
- CI: the `backend` job records while it tests (`API_TRANSCRIPTS=record ./gradlew build`) and keeps the transcripts and its part of the inventory (`test-inventory.mjs --part=backend`: test names only, never the JUnit XML with its logs), the `frontend` and `mcp` jobs keep their test lists, and the job `compare-v2` lists the PR's changed files (`git diff --name-only HEAD^1 HEAD` on the merge commit), runs `node scripts/compare-v2-baseline.mjs --base=HEAD^1`, which fetches the commit in `BASELINE_COMMIT` anonymously (`git fetch --depth=1`), fails when `regression/v2/api` or the test inventory differs from it, when the PR changes or removes `BASELINE_COMMIT`, when the commit cannot be fetched, or when a tag `v2-baseline` exists and points at another commit (it never skips), runs the scripts' tests, collects the inventory (`--backend=` the backend part), runs the connector shapes against the fresh recording and the comparison, and writes the report into the job summary and the artifact `srovnani-s-v2`; paste it into the PR body under "Srovnání s v2".

## Keeping the suite fast (backend)
- Passwords in tests go through `CachingPasswordHasher` over the real hasher; never a second real-cost hasher or a lower cost, because each BCrypt check at cost 12 costs a core a third of a second.
- E-mail and async waits use Awaitility's defaults, set once in `CommonStepDefinitions.pollWithoutDelay` (no delay, 10 ms interval); no own `pollDelay`, `pollInterval` or `Thread.sleep`. A deliberate "nothing more arrives" wait stays explicit (`pollDelay(SETTLE)`).
- A new `@SpringBootTest` is `@IntegrationTest` (`TestContextRulesTest`) and a new JPA slice imports its context's `<Context>PersistenceTestConfiguration`, so it reuses a cached context and its PostgreSQL container instead of starting both. A test that needs other beans or properties starts a context of its own: say why in the PR.
- A new table needs nothing: `DatabaseCleaner` reads the tables and foreign keys from the catalogue. An integration test that commits cleans before it runs (`@BeforeEach`), because other classes share its database.
- State on disk is per fork: scenarios use the folders under `build/cucumber/fork-${org.gradle.test.worker}/`; a new folder follows suit.
- Where the time goes: the report (`build/reports/tests/{test,acceptanceTest}/index.html`, per class and per scenario), and per step the Cucumber `json:` plugin added for a run to the suite's `PLUGIN_PROPERTY_NAME` (sum `result.duration` per `match.location`, backgrounds included).

## Running
What to run before "done" is in `CLAUDE.md` (Done means); `./gradlew build` is what the PR check runs for the backend. `./gradlew test` runs the unit and integration tests in the `test` task and then, as its finalizer, the scenarios in `acceptanceTest`, each task on two forks; `-PnoCucumber` skips `acceptanceTest`, and `--tests` filters only `test`. In a cloud session: skill `cloud-session`.
