# API Contract — NFNN

Agreed HTTP API contract between Angular 22 frontend and Spring Boot 4 + DDD backend. This document is the source of truth for endpoint shape, auth flow, error format, and bounded-context allocation. It came out of a frontend/backend design pass against the original prototype (removed from the repo in October 2026) and the architecture in `CLAUDE.md`; how the system works today is in `docs/system-overview.md`.

When adding a new endpoint, update this file in the same change.

## Conventions

- All endpoints under `/api/<context>/...`. Contexts: `content`, `donors`, `donations`, `contact`, `operations` (how the server runs: settings and the first setup, backups and restore, logs and diagnostics). No cross-context HTTP calls — use `ApplicationEvent` for behavioral coordination.
- JSON in / JSON out. Exception: PDF receipts return `application/pdf`, media returns image binary.
- Errors follow RFC 7807 `application/problem+json` (Spring `ProblemDetail`). `type` URI namespace: `https://nfnn.cz/problems/<context>/<code>`. Per-field validation errors carried in an `errors: [{ field, message }]` array.
- Identifiers: UUIDv7 (string) for all entity IDs. Public URLs for content use `slug` (kebab-case, unique; an administrator may still change it after publishing, the old address then answers 404); admin URLs use `id`.
- Money: `{ amountMinor: long, currency: "CZK" }`. Domain value object `Money` lives in `shared/domain/`. Sealed `Currency` (CZK only for now).
- Dates: ISO-8601. `LocalDate` as `YYYY-MM-DD`, instants as `YYYY-MM-DDTHH:MM:SSZ`. UI formatting (e.g. `15. 03. 2026`) is the frontend's job.
- Locale signaling: frontend sends `Accept-Language: cs` (default) or `en` on every request via HTTP interceptor. Used for `ProblemDetail` titles/details and (later) translated CMS content. **Exception:** a PDF receipt is rendered in the donor's `preferredLocale` at the time it is issued and keeps it, never in `Accept-Language` (see "PDF receipts").
- Lists answer an object with `items`: paged lists add `hasMore` (`{ "items": [...], "hasMore": true }`, offset or `before` paging), the public content pages also `page`, `size` and `total`; short lists are `{ "items": [...] }`. Each endpoint below gives its shape.
- CORS: not configured. Production is same-origin via the nginx in `frontend/Dockerfile`; dev uses Angular's `proxy.conf.json`. Re-evaluate if a non-browser client appears.
- Text bodies (news and projects) are stored as typed: plain text or a small Markdown subset (below), rendered by the site's own parser into Angular elements and bindings; HTML is never rendered, a tag shows as text.
- Caching: media `Cache-Control: public, max-age=31536000, immutable`; receipt and backup downloads `private, no-store`; the OAuth answers `no-store`; the payment details `private, max-age=300` with a strong `ETag` (a request with `If-None-Match` of the current one gets 304, see "`GET /api/donations/payment-details`"); every other API answer carries Spring Security's default `no-cache, no-store, max-age=0, must-revalidate`. No other ETags. The frontend nginx adds `Cloudflare-CDN-Cache-Control: no-store` to every `/api`, `/mcp` and `/.well-known` answer, errors included, so Cloudflare never stores one (`docs/security-overview.md`, Browser and transport). The static files' caching is the frontend nginx's (`frontend/nginx.conf`).

## Authentication

JWT-based, scoped to `donors` bounded context. Roles in JWT claims: `DONOR`, `ADMIN` (no separate admin bounded context — admins are donors with elevated role).

Everything under `/api/admin/**` needs the `ADMIN` role (`ApiSecurityConfiguration`, `hasRole(ADMIN_ROLE)`): a donor without it gets 403 `auth/forbidden`, no token 401 `auth/unauthenticated`. The role is granted by another administrator in the administration (`POST /api/admin/donors/administrators`, see "Administrators") or, for the first administrator, by the e-mail entered as `ADMIN_EMAILS` in the first setup (applied at start and when that address confirms its registration, only while the site has no administrator; nothing is done by SQL, Jakub, 2026-10-22); it travels in the JWT, so it takes effect at the donor's next sign-in or token refresh (at most 15 minutes), and taking it away ends every session of the donor. Each context exposes its administration under `/api/admin/<context>/...`; see "Administration". The administration is reachable from the internet, so an administrator signs in with a second factor: `ADMIN` is put into the JWT only for a session opened with the code from an authenticator app (TOTP, see "Second factor"); an administrator without the second factor signs in as a plain donor (`roles: ["DONOR"]`, `secondFactor.neededForAdministration: true`) and gets 403 under `/api/admin/**` until they turn it on (Jakub, 2026-10-22).

| Token | Lifetime | Storage (frontend) | Transport |
|---|---|---|---|
| Access | ~15 min | In-memory only (no localStorage) | `Authorization: Bearer ...` header |
| Refresh | 14 days | HttpOnly + Secure + SameSite=Strict cookie, path `/api/donors/auth` | Set-Cookie on register/login/refresh; sent automatically by the browser to refresh and logout |

Refresh tokens are stored server-side as hashes (`donor_refresh_token` table) and rotated on every refresh; presenting an already rotated token revokes every session of the donor. Logout invalidates the current refresh token.

Password rules: 12–128 characters; refused when it is one of the 10,000 most common passwords of 12 characters or more (SecLists, MIT; `donors/domain/common-passwords.txt`, compared in lower case); stored as BCrypt (cost 12) of the password's SHA-256 hex digest, so the whole password counts (BCrypt alone reads 72 bytes).

Every access token carries an audience (`aud`, `app.security.jwt.audience` = `{app.site.public-url}/api`) and the resource server accepts only that one; a token issued for the MCP connector (`aud` `{app.site.public-url}/mcp`, see "Connected applications") does not open the API. A token issued to a connected application also carries a `scope` claim (`admin:read`, `admin:write`), and a token with that claim is confined to the administration: `GET` and `HEAD` under `/api/admin/**` need the `ADMIN` role alone, every other method there additionally needs `admin:write` in the `scope` claim (`shared/infrastructure/security/AdminWriteAuthorizationManager`), and every path outside `/api/admin/**` (the donor's own account under `/api/donors/me/**`, `/api/donations/me/**`, approving a connection at `POST /api/donors/oauth/authorize`) as well as the backup download `GET /api/admin/operations/backups/{fileName}`, the restore `POST …/backups/{fileName}/restore` and every dangerous or irreversible change of the administration (`DELETE /api/admin/donors/{id}`, `POST /api/admin/donors/administrators`, `DELETE …/administrators/{id}`, `POST /api/admin/donors/{id}/second-factor/reset`, `DELETE /api/admin/donors/{id}/passkeys`, `DELETE /api/admin/content/news/{id}` and `…/projects/{id}`, `DELETE /api/admin/donations/donors/{donorId}/bank-accounts/{linkId}`, `POST /api/admin/donations/symbol-claims/{id}/reverse` and `DELETE …/symbol-claims/{id}`, `POST` and `DELETE /api/admin/donations/receipt-signature`; `ApiSecurityConfiguration` checks the role first, so they stay 403 for a donor too) accept only a browser session's token, one without a `scope` claim (`BrowserSessionAuthorizationManager`, 403 `auth/forbidden` otherwise; security review 2026-10-23: before it an exchanged token could approve a new connection with `admin:write` for itself and download the whole database). A browser session's token has no `scope` claim, so nothing changes for the web. A read-only connector token answers 403 `auth/forbidden` to a write.

## Bounded contexts and endpoints

### `content` — public CMS

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/content/news?page=0&size=10` | Published news (`publishedOn` ≤ today in Prague), newest `publishedOn` first, then newest created; `page` ≥ 0, `size` 1–50 (400 `validation` outside). 200 `{ "items": [article…], "page": 0, "size": 10, "total": 12, "hasMore": true }`. |
| `GET` | `/api/content/news/{slug}` | One published article. | `GET` | `/api/content/projects?page=0&size=10` | Published projects (`publishedOn` ≤ today in Prague), newest `year` first, then newest `publishedOn`, then newest created; `page` and `size` as for the news. 200 `{ "items": [project…], "page", "size", "total", "hasMore" }`. |
| `GET` | `/api/content/projects/{slug}` | One published project; a former slug answers it with its current `slug`, as for the news. 404 `content/project-not-found` for a draft, a future date, an unknown or malformed slug. |
| `GET` | `/api/content/home` | What the home page shows: `{ "news": [article…], "projects": [project…] }`, the three newest published news articles and the three newest published projects in the public order (newest year first), in one request; the rest is on `/api/content/news` and `/api/content/projects`. |
| `GET` | `/api/content/media/{id}?w=960` | The WebP variant of an uploaded photo at least `w` pixels wide (the largest one when none is that wide or `w` is absent; `w` ≥ 1, 400 otherwise). 200 `image/webp`, `Cache-Control: public, max-age=31536000, immutable` (an id is never reused), `X-Image-Width`, `X-Image-Height`. 404 `content/media-not-found`. |

Article (`NewsArticleResponse`, the same shape on the public and the admin endpoints):

```json
{
  "id": "0199f3e0-…",
  "slug": "zahrada-pro-deti",
  "title": "Zahrada pro děti",
  "tag": "Projekt",
  "perex": "Stavíme zahradu…",
  "body": "První odstavec.\n\nDruhý odstavec.",
  "coverImage": { "id": "0199f3e0-…", "url": "/api/content/media/0199f3e0-…", "alt": "Děti sázejí stromek" },
  "publishedOn": "2026-10-20",
  "live": true,
  "createdAt": "2026-10-19T09:00:00Z",
  "updatedAt": "2026-10-20T07:30:00Z"
}
```

`tag`, `coverImage` and `publishedOn` are null when absent. `live` says whether the site shows the article today: published and `publishedOn` ≤ today in Prague, by the server's clock (`Clock`, `FoundationZone`), so a draft and an article published with a later date are `false` until that day; the public endpoints answer only live articles, so there it is always `true` (Jakub, 2026-10-24: the administration shows "Na webu" or "Zveřejní se …" from it, never from the browser's clock). Request (`NewsArticleRequest`): `title` (1–120), `slug` (optional; `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 80; blank or absent means made from the title: diacritics stripped, lower case, anything else a hyphen, cut to 80), `tag` (optional, at most 40, blank means none), `perex` (1–300), `body` (1–20 000; plain text or Markdown, see below), `coverImageId` (optional), `coverImageAlt` (optional, at most 200; the photo's description for screen readers, the `alt` of the image; blank means none, and it is dropped without a photo; the response carries it as `coverImage.alt`, null when absent). Texts are trimmed.

Markdown (Jakub, 2026-10-23: an editor with a preview and a warning to check the look; plain text keeps working, no HTML): the site understands paragraphs separated by an empty line (a single line break stays a break), headings `#`/`##` (shown as `h2`) and `###`… (`h3`), lists `- `/`* `/`+ ` and `1. `/`1) ` (an indented line continues the item), quotes `> `, `**bold**`/`__bold__`, `*italic*`/`_italic_`, links `[text](https://…)` with only `http`, `https`, `mailto:` and site-relative `/…` addresses (any other link stays text), bare `https://` addresses, and `\` escapes. Anything else, HTML included, shows as typed. The backend stores the text unchanged and never parses it. The `url` of a cover image is the variant endpoint without `w`; the site adds `?w=` for the size it shows.

Project (`ProjectResponse`): the same shape as an article plus `"year": 2024` after the title: the year the project belongs to, 2005 (the fund's founding) to 2100, which orders the public list and the project cards on the home page (8c). Request (`ProjectRequest`): the article's fields plus `year` (required, 2005–2100, `ck_content_project_year` in the database too); the `tag` is meant for the project's area (for example "Kompenzační pomůcky"), the `perex` for its card.

#### Registration request

```json
{
  "type": "COMPANY",
  "name": "Stavby Novák s.r.o.",
  "companyIdentifier": "45274649",
  "address": { "street": "Průmyslová 5", "city": "Teplice", "postalCode": "415 01" },
  "email": "ucetni@stavby.example.cz",
  "password": "correct horse battery",
  "preferredLocale": "cs",
  "returnTo": "/#prispet"
}
```

- `type` is `PERSON` or `COMPANY`. A company must send `companyIdentifier` (IČO: 8 digits with a valid check digit, spaces allowed); a person must not. Both go on the gift confirmation, which is why `address` is required.
- `name`: `@NotBlank`, max 160; the person's full name or the company name.
- `email`: `@Email`, max 254; stored trimmed and lowercased, so uniqueness is case-insensitive.
- `password`: 12–128 characters, not on the common-password list, or `null` for an account that will sign in with passkeys only (see "Accounts without a password"); stored as BCrypt (cost 12) of the SHA-256 hex digest of the UTF-8 password (`infrastructure/security/BCryptPasswordHasher`), so every character counts: BCrypt alone reads the first 72 bytes and refuses longer input, which 128 Czech letters exceed.
- `preferredLocale`: `cs` (default) or `en`.
- `returnTo` (optional, Jakub 24 October 2026): where the visitor continues after confirming the e-mail. Only the paths of `donors/domain/RegistrationReturn` are accepted, today `/#prispet` (a registration started in the "Přispět" section); anything else is 400 `validation` on `returnTo`, so the e-mail never carries a text or address the registrant chose. It is not stored: the verification link carries it (see "E-mail verification").

#### Company lookup (ARES)

Jakub, 24 October 2026: a company registering in the sign-in dialog types its IČO first, and the backend fills in the name and the registered seat from ARES, so the donor only checks them. The lookup is a convenience the registration never depends on: whenever ARES is slow, down or answers anything unexpected, the form behaves as if the feature did not exist.

```json
{
  "companyIdentifier": "45274649",
  "name": "Stavby Novák s.r.o.",
  "address": { "street": "Dlouhá 12", "city": "Ústí nad Labem", "postalCode": "400 01" }
}
```

- The browser never calls ARES (the Content-Security-Policy forbids it); `GET /api/donors/company-lookup` is public (`permitAll` in `ApiSecurityConfiguration`) because registration happens signed out.
- The IČO is validated (`@NotBlank`, at most 16 characters, `@ValidCompanyIdentifier`: 8 digits with the mod-11 check digit, spaces stripped) before anything else; then `CompanyLookupRateLimiter` counts the request (20 per 15 minutes per client address, like the client metadata documents, since each lookup may cause an outbound request); then `CompanyLookupService` asks the port `CompanyRegistry`.
- `infrastructure/ares/AresCompanyRegistry` calls `GET https://ares.gov.cz/ekonomicke-subjekty-v-be/rest/ekonomicke-subjekty/{ico}` (the Ministry of Finance's free REST API, limit 500 requests per minute): a fixed `https` address, every resolved address checked by `PublicAddresses` (`shared/infrastructure/net`), no redirects, 3 s for the connection and 3 s for the whole answer, body included, at most 64 KiB, `application/json` only. Answers (a company and "not found") are cached for 10 minutes, at most 1 000 IČOs (Caffeine); failures are not cached.
- Mapping (`AresAnswers`): `obchodniJmeno` becomes the name (spaces tidied, at most 160 characters like a donor's name); `sidlo` becomes the address only when it is in Czechia (`kodStatu` `CZ`) and has every part: the street line is `nazevUlice` (or `nazevCastiObce` in a village without streets) with `cisloDomovni` (`č. ev.` before a registration number, `typCisloDomovni` 2) and `/cisloOrientacni` with its letter; the city is `nazevMestskehoObvodu` when present (Prague's "Praha 4"), else `nazevObce`; `psc` `14000` becomes `140 00`. Otherwise `address` is `null` and only the name comes back.
- ARES 404 is "not found": 204, nothing logged. A timeout, an unreachable host, any other status (429 and 5xx included), a body that is not the asked company's JSON, a missing name or an oversized body is a failure: 204 as well, and one `warn` with the outcome only (`timeout`, `status 503`, `unexpected response`, …), never the IČO (a sole trader's IČO identifies a person).
- Circuit breaker: after 3 failures in a row (each within 5 minutes of the previous one) `CompanyLookupService` skips ARES for 5 minutes and answers 204 at once; the third failure's warning says so. The first lookup after the pause asks ARES again, and one more failure pauses again. The state lives in memory and starts closed after a restart.
- Frontend (`features/donors/company-lookup-api.ts`, the sign-in dialog): the lookup starts once the IČO field holds 8 digits with a valid check digit (the same check as the field's validator), never waits on registration and is dropped when the registration is sent, the donor switches to a person or the dialog closes. It fills only the name, street, postal code and city fields that are empty or still hold what an earlier lookup put there (so correcting the IČO replaces them, and nothing the donor typed is overwritten), and only then shows "Údaje jsme doplnili z obchodního rejstříku (ARES). Zkontrolujte je." (`donor.register.companyFilled`) in a `role="status"` region. A 204, a 429, a 5xx or a network failure changes nothing and says nothing: no spinner, no alert.
- Tests: `AresCompanyRegistryTest` (a local HTTP server: mapping, not found, cache, statuses, garbage, oversized, stalled body and headers, unreachable, private address and plain `http` refused), `CompanyLookupServiceTest` (breaker and logs), `CompanyLookupRateLimiterTest`, `features/donors/company_lookup.feature` with `support/FakeCompanyRegistry`, the dialog's specs and `e2e/donor-account.spec.ts`.

#### Auth response (e-mail confirmation, login, second factor, refresh, password change, second-factor change)

```json
{
  "user": { "...": "the GET /api/donors/me body" },
  "accessToken": "eyJ...",
  "accessTokenExpiresAt": "2026-10-17T10:15:00Z"
}
```

The access token is an HS256 JWT (`iss`, `sub` = donor id, `roles`, 15 minutes; `app.security.jwt.*`). `roles` are the session's roles: `ADMIN` is in them only when the session was opened with the second factor (`Donor.sessionRoles(secondFactorVerified)`), and a refresh keeps what its refresh token recorded (`donor_refresh_token.second_factor_verified`), so a session never gains `ADMIN` without the code. It is signed with `JWT_SECRET` (`app.security.jwt.secret`, at least 32 characters, `shared/infrastructure/security/JwtProperties`); only the dev profile has a default, and any other profile without it stops at startup with an error naming `JWT_SECRET`. The refresh token is **not** in the body: it ships as the `refresh_token` cookie (`HttpOnly; Secure; SameSite=Strict; Path=/api/donors/auth`, 14 days; `app.donors.session.refresh-token-ttl`), so only the auth endpoints ever receive it. The backend stores its SHA-256 hash in `donor_refresh_token`.

#### Sign-in and registration limits

- `POST /api/donors/auth/login`: 10 requests per 15 minutes per client address (`SignInRateLimiter`); `POST /api/donors/auth/register`: 5 requests per hour per client address (`RegistrationRateLimiter`). Both sit in `donors/interfaces/rest`, each with its own `FixedWindowRateLimiter`, like `PasswordResetRateLimiter`; the limits are constants in those classes. The window is fixed: it starts with the address's first request and closes after the whole period, whatever came in between.
- Every request that reaches the controller counts, successful or not: a right password, a wrong one, an unknown e-mail, a taken e-mail, an unconfirmed account. A body that fails validation is answered 400 before the controller runs and does not count; it costs no hashing.
- A limited request answers 429 with type `donors/rate-limited` and the generic title and detail of `RateLimitExceededException`, before any password is hashed or any registration work is done. Sign-ins and registrations have separate counters, and both are separate from the password reset's.
- The client address is `getRemoteAddr()` after `ForwardedHeaderFilter`; the nginx in `frontend/` resolves the visitor's address itself and rewrites `X-Forwarded-For`, so a client cannot choose it (see "Password reset"). The counters live in memory per backend instance and start empty after a restart. Visitors behind one shared address (an office, a school, a mobile carrier's NAT) share the limits, accepted.
- The limits brake password guessing and mass registration from one address. They are not an account lockout, so nobody can lock a donor out of the account; guessing spread over many addresses is not covered, and a CAPTCHA or a per-account delay is the escalation if it appears.
- An unknown e-mail costs the same as a real one: the password is compared against a fixed BCrypt cost-12 hash of a random string (`UNKNOWN_DONOR_HASH` in `DonorAuthenticationService`), so both run one BCrypt comparison and answer the same 401. A malformed e-mail or a password the password rules refuse (shorter than 12 characters or on the common list) is answered 401 without hashing; that depends only on what was sent and says nothing about the account.

Frontend: the sign-in dialog answers a 429 on sign-in or registration with "Příliš mnoho pokusů z této adresy. Zkuste to prosím za chvíli znovu." (`donor.login.error.tooManyAttempts`). Cucumber: `features/donors/donor_login.feature` and `donor_registration.feature`.

#### E-mail verification

An account opens only once its owner has opened the link from the verification e-mail (Jakub, 22 October 2026: before the launch on nfnn.cz). Until then the donor cannot sign in, `donations` has no record of the donor and no payment can be paired to the symbol. Donors registered before this change were marked confirmed by the migration (`email_verified_at` = `registered_at`).

`POST /api/donors/auth/register` (the "Registration request" above) stores the donor with `email_verified_at` null, issues a verification link and answers 202 without a body. The same request for an address that already has an account also answers 202, so the answer never says whether an address is registered:

- An address whose account is confirmed: nothing is stored, and the account's owner gets the e-mail "Váš dárcovský účet už existuje – Nová naděje" (`templates/email/donors/registration-repeated.html`, `donors.registrationRepeated.email.*`): someone tried to register with the address, the account already exists, sign in or reset the password; it links the site root and carries no token. Whoever knows the address can trigger this e-mail within the registration limit, accepted.
- An address whose account is not confirmed yet: the earlier registration is deleted (its links go with it, `ON DELETE CASCADE`; it had no sessions and no `donor_record`) and the new one is stored with a new symbol and a new link, so a donor who mistyped something or never received the e-mail simply registers again, and the newest data wins. The flush after the delete frees the unique address before the insert (`JpaDonorRepository.delete`). Someone who knows a pending address can replace that registration with their own password until the owner confirms; the owner then sees a name they did not enter or cannot sign in and resets the password, which ends every session. Accepted for the minutes a registration waits.

`POST /api/donors/auth/email-verification/request` with `{ "email": "jana@example.cz" }`: the same validation and address handling as the password reset request (trimmed, lowercased, `EmailAddress.SHAPE_REGEX`); always 202; a new link only for an account whose e-mail is not confirmed (an unknown address and a confirmed account get nothing, logged at DEBUG and INFO); at most 3 live links per donor (`app.donors.email-verification.max-live-links`), the earlier ones stay valid; 5 requests per hour per client address (`EmailVerificationRateLimiter`) → 429 `donors/rate-limited`.

The e-mail (`templates/email/donors/email-verification.html`, `donors.emailVerification.email.*`, subject "Potvrďte svůj e-mail – Nová naděje", title "Vítejte v Nové naději") is also the welcome e-mail: it names the account's address, carries the link `{app.site.public-url}/potvrzeni-emailu#token=<secret>` (with `&returnTo=%2F%23prispet` appended when the registration or the request for a new link named that `returnTo`; the reminder after a day carries none), says the link is valid for `app.donors.email-verification.token-ttl` (PT24H, written in hours) and once, and that an unconfirmed account stays inactive. Like the reset e-mail it carries nothing from the profile (the name is unverified free text) and the token travels in the fragment.

`POST /api/donors/auth/email-verification/confirm` with `{ "token": "<43 base64url characters>" }`:

- `token`: `@NotBlank`, `^[A-Za-z0-9_-]{43}$`, else 400 `validation` with a field error.
- 400 `donors/invalid-email-verification-token` for a well-formed token that is unknown, expired, already used, or whose donor is gone or already confirmed (one code, no distinction; the lookup is by the SHA-256 of the presented value).
- 200 on success with the auth response and the refresh cookie: the token is marked used atomically (a concurrent confirm loses and answers 400), the donor's `email_verified_at` is set, every verification link of the donor is deleted (a confirmed account keeps none), `DonorRegistered` is published (so `donor_record` is created and the donor's payments are paired in this transaction, exactly as the registration did before) and a session opens, so the page can take the donor straight to the overview.
- A token issued by `POST /api/donors/me/email-change` (its row carries `new_email`) confirms an e-mail change instead: the donor must be confirmed and the new address still free (else 400 `donors/invalid-email-verification-token`), the donor's `email` becomes the new address, every verification link and every refresh token of the donor goes, `DonorEmailChanged` is published (the notice to the previous address) and a session opens; 200 with the auth response, whose `user.email` is the new address. See "Changing the password and the e-mail".
- Not rate-limited, for the same reasons as the reset confirm.

Reminder (Jakub, 23 October 2026): a registration that stays unconfirmed gets one reminder. `infrastructure/reminder/RegistrationReminderScheduler` runs `DonorRegistrationReminderService.remindUnconfirmed` at `app.donors.registration-reminder.cron` (`0 20 * * * *`, hourly at twenty past, Prague; `-` turns it off and every test pins it off) for the accounts registered between `window` (P7D) and `delay` (P1D) ago that are neither confirmed nor erased and have no reminder yet (`RegistrationReminders.dueFor`, at most 100 a run, oldest first). Each gets a fresh link through `DonorEmailVerificationService.issueReminderLink` (the same token, lifetime and limit of 3 live links as above; at the limit no link and no e-mail) and the event `DonorRegistrationReminderDue`; the e-mail "Připomínka: dokončete registraci – Nová naděje" (`templates/email/donors/registration-reminder.html`, `donors.registrationReminder.email.*`) carries the link and says no other reminder follows. The reminder is recorded in `donor_registration_reminder` (`donors/012_remind_unconfirmed_registrations.xml`: `donor_id` primary key with `ON DELETE CASCADE`, `sent_at`; plus the index `ix_donor_registered_at`) in the same transaction whether or not a link went out, so a donor is reminded at most once and a registration replaced by a new one starts again. The job logs the count at INFO and a failure at ERROR with the exception class only, and the next run picks up what a missed one left.

Sign-in with the right password at an unconfirmed account answers 401 `auth/email-not-verified` (title "E-mail ještě není potvrzený", detail asks to open the link or have a new one sent); a wrong password at such an account answers `auth/invalid-credentials` like anywhere else, so the code never reveals an unconfirmed address to someone without the password. A password reset request for an unconfirmed account sends nothing (the donor confirms the e-mail first, or registers again).

Table `donor_email_verification_token` (`donors/004_add_donor_email_verification.xml`, which also adds `donor.email_verified_at` and fills it for existing donors): the same columns, FK and cleanup as `donor_password_reset_token`.

Domain: `Donor.verifyEmail(at)` / `isEmailVerified()` / `emailVerifiedAt()`, `EmailVerificationToken`, `EmailVerificationTokenRepository`, `InvalidEmailVerificationToken` (`RuleViolation`), `EmailNotVerified` (`AuthenticationFailure`); `LinkSecret` is the 43-character secret shared with the password reset (formerly `PasswordResetSecret`). Application: `DonorEmailVerificationService` (`issueLink`, `requestVerification`, `confirm`), `DonorEmailVerificationProperties`, the events `DonorEmailVerificationRequested` and `DonorRegistrationRepeated` in `donors/application/event`; `DonorRegistrationService.register` no longer opens a session nor publishes `DonorRegistered`. Infrastructure: `infrastructure/mail/DonorRegistrationEmailSender` (`@Async AFTER_COMMIT`, both e-mails) and the JPA trio. REST: `interfaces/rest/DonorEmailVerificationController`, `EmailVerificationRateLimiter`, the masked request records, `SessionResponses` shared with `DonorAuthController`. Cucumber: `features/donors/donor_email_verification.feature`; the shared glue `cucumber/DonorRegistrations` registers and confirms a donor through the e-mail, which every "registered" Given step uses.

Frontend: after a registration the dialog shows "Zkontrolujte si e-mail" with the address (`role="status"`) and a way back to the sign-in tab; a sign-in answered `auth/email-not-verified` shows the problem and a "Poslat ověřovací e-mail znovu" button that posts the request and confirms in a `role="status"` line. The public route `potvrzeni-emailu` (`features/donors/email-verification/`) reads the token from the fragment, replaces the URL, posts the confirm at once ("Potvrzujeme váš e-mail"), adopts the session and offers "Přejít do přehledu", or "Pokračovat k příspěvku" to `/#prispet` when the link's `returnTo` is on the frontend's own list (`core/auth/confirmation-return.ts`; any other value is ignored); an invalid link or a missing token shows a form that asks for the address and posts the request ("E-mail odeslán"); another failure offers a retry.

#### Changing the password and the e-mail

Both actions need the donor JWT and the current password (Jakub, 22 October 2026). `interfaces/rest/DonorCredentialsController`, `application/DonorCredentialsService`; the request records `ChangePasswordRequest` and `EmailChangeRequest` mask every field in `toString`.

`PUT /api/donors/me/password` with `{ "currentPassword": "…", "newPassword": "…" }`:

- `currentPassword`: `@NotBlank`, max 128; `newPassword`: `@NotBlank`, 12–128; else 400 `validation` with field errors. A malformed current password (shorter than 12 characters or on the common list) is answered as a wrong one, without hashing.
- 400 `donors/wrong-password` (title "Nesprávné současné heslo") when the current password does not match; 400 `donors/password-too-common` for a new password on the list. Nothing changes in either case.
- 200 on success with the auth response and a fresh `refresh_token` cookie: the new hash is stored, every refresh token of the donor is revoked (the other devices lose their session at their next refresh, within 15 minutes) and a new session opens for this device, so the donor stays signed in where the change was made. `DonorPasswordChanged` is published and the donor gets "Heslo k vašemu účtu bylo změněno – Nová naděje" (`templates/email/donors/password-changed.html`, `donors.passwordChanged.email.*`, `infrastructure/mail/DonorPasswordChangedEmailSender`, `@Async AFTER_COMMIT`): the password changed, every other sign-in ended, and what to do if it was not them (a reset and a message to `app.mail.sender-email`); it never carries the password (Jakub, 23 October 2026).
- 10 attempts per 15 minutes per client address (`PasswordChangeRateLimiter`) → 429 `donors/rate-limited`, counted before any hashing; separate from the sign-in counter.

`POST /api/donors/me/email-change` with `{ "newEmail": "jana.nova@example.cz", "password": "…" }`:

- `newEmail`: trimmed, `@Email`, `EmailAddress.SHAPE_REGEX`, max 254, stored lowercased; `password`: `@NotBlank`, max 128; else 400 `validation`.
- 400 `donors/wrong-password` when the password does not match (checked before the address is looked at); 400 `donors/email-unchanged` (title "Tuto adresu už váš účet má") when the new address equals the current one, case-insensitively.
- 202 without a body otherwise, so the answer never says whether an address is registered:
  - A free address gets the e-mail "Potvrďte novou e-mailovou adresu – Nová naděje" (`templates/email/donors/email-change.html`, `donors.emailChange.email.*`) with the link `{app.site.public-url}/potvrzeni-emailu#token=<secret>&change=email` (the marker only tells the page to word its success as a changed address and to skip the first-passkey step; the token alone decides what the confirmation does): the same `donor_email_verification_token` row as a registration link, with the new address in `new_email`, valid `app.donors.email-verification.token-ttl` (24 h), once, `DonorEmailChangeRequested` → `infrastructure/mail/DonorEmailChangeEmailSender`. The e-mail names only the new address.
  - An address another account has: the change is stored the same way (so the profile shows it pending either way), but no link is sent; that account's owner gets "Vaši adresu chtěl použít jiný účet – Nová naděje" (`email-in-use.html`, `donors.emailInUse.email.*`, in the owner's locale, no link; `DonorEmailAddressInUse`), which names the address and says nothing changed.
- A donor has at most one pending change: a new request deletes every earlier change link of the donor first (registration links stay), so only the newest link works. `GET /api/donors/me` shows it as `pendingEmailChange` until it is confirmed, cancelled or expires.
- 5 requests per hour per client address (`EmailChangeRateLimiter`) → 429 `donors/rate-limited`, before any hashing.

`POST /api/donors/me/email-change/resend` (no body) re-issues the pending change: the earlier change link is deleted, a new random secret is stored as its SHA-256 with a fresh 24-hour expiry, and the e-mail goes out again to the pending address (or, for an address another account has, the owner's notice again). It needs no password, because it only repeats what the password allowed. 202 without a body; 409 `donors/no-pending-email-change` (title "Žádná změna e-mailu nečeká na potvrzení") when nothing is pending (`NoPendingEmailChange`, `Conflict`); it counts toward the same `EmailChangeRateLimiter` window as the request, checked before any work.

`DELETE /api/donors/me/email-change` deletes the donor's change links: the sent link stops working and the account keeps its address. 204 every time (idempotent); it sends no mail, so it has no limiter.

- Until the link is opened the account keeps its current address: sign-in, the reset and every e-mail use it. Opening the link (`POST /api/donors/auth/email-verification/confirm`, above) switches the address, revokes every refresh token, opens a session and sends "E-mail vašeho dárcovského účtu byl změněn – Nová naděje" (`email-changed.html`, `donors.emailChanged.email.*`, `DonorEmailChanged`) to the previous address, naming both addresses and `app.mail.sender-email` to write to if it was not the donor. A link whose address was registered meanwhile answers 400 `donors/invalid-email-verification-token` and changes nothing. `donations` keeps no e-mail, so no cross-context event is needed.

Schema: `donors/005_add_new_email_to_verification_token.xml` adds the nullable `new_email varchar(254)` to `donor_email_verification_token`. Domain: `Donor.changeEmail(newEmail)` (confirmed donors only; `EmailUnchanged` for the same address), `EmailVerificationToken.issueForChange` / `isForChange()` / `newEmail()`, `WrongPassword` and `EmailUnchanged` (`RuleViolation`). Cucumber: `features/donors/donor_credentials.feature`.

Frontend: the "Přihlášení a zabezpečení" card on `/darce/udaje` (`features/donors/dashboard/account-card/`) has an E-mail row with the address and "Změnit e-mail" (new address + current password, "Poslat potvrzovací odkaz"; on 202 a `role="status"` line says where the link went and that the current address stays until it is opened, and the profile is read again); while `pendingEmailChange` is set the row shows "Čeká na potvrzení: <adresa>", the link's expiry, "Poslat znovu" (`POST …/email-change/resend`) and "Zrušit" (`DELETE …/email-change`) and "Změnit heslo" (current, new and new again with the 12-character hint; mismatch is a form-level alert; on 200 `AuthStore.changePassword` adopts the new session and the line says the other sign-ins ended). Backend refusals appear as a form-level `role="alert"` through `describeProblem`; `auth/unauthenticated` sends the donor to sign in like the other cards. The link opens the existing `/potvrzeni-emailu` page, which signs the donor in with the new address and, seeing `&change=email`, says "E-mail je změněný" with the address now in use.

#### Second factor

Any donor can protect the account with a time-based one-time code (TOTP, RFC 6238: HMAC-SHA1, 6 digits, 30-second steps, one step of tolerance each way) from an authenticator app; an administrator has to (Jakub, 2026-10-22). `domain/SecondFactor` (aggregate per donor: the 20-byte secret as 32 base32 characters in `TotpSecret`, `confirmedAt`, `lastUsedStep`), `domain/Totp` (`codeAt`, `matchingStep`; `TotpTest` checks the RFC 6238 vectors), `domain/SecondFactorChallenge`, `application/DonorSecondFactorService`, `DonorAuthenticationService.completeSecondFactor`, `interfaces/rest/DonorSecondFactorController`; the request records mask every field in `toString`, `code` is validated as exactly six digits (`Totp.CODE_SHAPE`).

Turning it on, signed in:

- `POST /api/donors/me/second-factor/setup` with the current password (400 `donors/wrong-password`; 409 `donors/second-factor-already-enabled` while it is on) stores a pending factor with a fresh secret (a second call replaces a pending one) and answers `{ "secret": "GEZD…", "otpauthUri": "otpauth://totp/Nov%C3%A1%20nad%C4%9Bje:jana%40example.cz?secret=…&issuer=Nov%C3%A1%20nad%C4%9Bje&algorithm=SHA1&digits=6&period=30", "qrCode": { "size": 53, "modules": "1111111…" } }` (`SecondFactorEnrolmentResponse`; the issuer is `app.donors.second-factor.issuer`, the label the donor's e-mail; `qrCode` is the link encoded by the shared `QrCodeEncoder` with error correction level M, in the same shape as the QR payment's, drawn plain by the frontend). A pending factor changes nothing about sign-in.
- `POST /api/donors/me/second-factor/confirm` with the first code the app shows (400 `donors/second-factor-not-pending` without a set-up, 400 `donors/second-factor-code-rejected`, title "Nesprávný kód", for a code that does not match) marks it confirmed, remembers the step the code came from, revokes every refresh token and opens a session **with** the second factor verified: 200 with the auth response and a fresh cookie, so an administrator is an administrator at once (`roles` contain `ADMIN`).
- `POST /api/donors/me/second-factor/disable` with the password and a fresh code (400 `donors/wrong-password`, 400 `donors/second-factor-not-enabled`, 400 `donors/second-factor-code-rejected` for a wrong or already used code) deletes the factor, revokes every refresh token and opens a plain session (an administrator loses `ADMIN` until they turn it on again). Either change publishes `donors/application/event/DonorSecondFactorEnabled` or `DonorSecondFactorDisabled(donorId, email, locale)` in its transaction, and `infrastructure/mail/DonorSecondFactorEmailSender` sends `AFTER_COMMIT` the e-mail "Dvoufaktorové ověření vašeho účtu bylo zapnuto – Nová naděje" (template `email/donors/second-factor-enabled`, texts `donors.secondFactorEnabled.email.*`) or "… bylo vypnuto – Nová naděje" (`email/donors/second-factor-disabled`, `donors.secondFactorDisabled.email.*`), cs and en: what the donor just did, where the setting is and whom to write if it was not them. A refused attempt (wrong password or code) sends nothing. These security e-mails cannot be switched off.
- The three endpoints share one counter: 10 requests per 15 minutes per client address (`SecondFactorChangeRateLimiter`) → 429 `donors/rate-limited`, before any hashing.

Signing in with it on:

- `POST /api/donors/auth/login` with the right password answers 401 with type `auth/second-factor-required` (title "Zadejte kód z aplikace") whose problem carries `challenge` (a 43-character secret) and `challengeExpiresAt`; no session opens and no cookie is set. The challenge is stored as its SHA-256 in `donor_second_factor_challenge`, valid `app.donors.second-factor.challenge-ttl` (5 minutes), for at most `app.donors.second-factor.challenge-attempts` (5) wrong codes, once. A wrong password, an unknown e-mail and an unconfirmed e-mail are answered as before, so the answer says nothing about the second factor until the password is right.
- `POST /api/donors/auth/login/second-factor` with `{ "challenge", "code" }`: 200 with the auth response and the refresh cookie when the code matches the current step or the one before or after and that step is newer than the last one used (a code is accepted once; the step is stored in `donor_second_factor.last_used_step`). 401 `auth/invalid-second-factor-code` ("Nesprávný kód") counts one attempt on the challenge; 401 `auth/invalid-second-factor-challenge` ("Přihlášení vypršelo") for a malformed, unknown, expired, used or exhausted challenge, after which the donor starts over with the password. 10 codes per 15 minutes per client address (`SecondFactorRateLimiter`), separate from the sign-in counter.
- The session opened with the code, and every refresh of it, carries the donor's full roles; a session opened by a password change, an e-mail confirmation or the reset keeps what it had (`DonorCredentialsService.changePassword(donorId, secondFactorVerified, …)` reads it from the JWT's roles).

Schema: `donors/006_add_second_factor.xml` adds `donor_second_factor` (`donor_id` PK and FK with cascade, `secret varchar(32)` stored in plain text because the server has to compute the code from it, `created_at`, `confirmed_at`, `last_used_step`), `donor_second_factor_challenge` (`id`, `donor_id` FK, `secret_hash` unique, `issued_at`, `expires_at`, `failed_attempts`, `used_at`; indexed by `donor_id`) and `donor_refresh_token.second_factor_verified boolean not null default false`. A lost authenticator is solved by hand: `delete from donor_second_factor where donor_id = …` in `deploy/README.md` ("Správci"); there are no recovery codes (decided for this version, Claude's default). Spent challenges are not deleted yet (a row per sign-in attempt at an account with the factor on). Cucumber: `features/donors/donor_second_factor.feature`; `admin_import_state.feature` proves the gate opens only after the code. Test glue: `cucumber/TotpCodes` computes codes from the scenario clock, `SecondFactorEnrolments.enable(alias)` turns it on through the API, `DonorSessions.signInAgain` answers a challenge with the code.

Frontend: the sign-in dialog answers `auth/second-factor-required` with a code step ("Přihlášení dokončíte kódem z ověřovací aplikace", field "Kód z aplikace" with `autocomplete="one-time-code"`, "← Zpět na heslo"); a wrong code keeps the step with the problem in the alert line, an invalid challenge goes back to the password form with "Přihlášení vypršelo. Zadejte prosím znovu e-mail a heslo." (`AuthStore.completeSecondFactor`). The "Přihlášení a zabezpečení" card on `/darce/udaje` has a Dvoufaktorové ověření row: "Zapnuté, kód z ověřovací aplikace" / "Vypnuté", for an administrator without it "Správa se vám otevře, až zapnete dvoufaktorové ověření a přihlásíte se s kódem z aplikace.", and offers "Zapnout dvoufaktorové ověření" (password → QR code, the key in groups of four with a copy button, the first code → `AuthStore.confirmSecondFactor` adopts the new session) or "Vypnout dvoufaktorové ověření" (password + code → `AuthStore.disableSecondFactor`).

#### Recovery by payment

A donor who lost the authenticator turns the second factor off without the administrator by paying 1 Kč from a bank account the foundation already knows as theirs (Jakub, 23 October 2026). It holds for every donor, administrators included; the reset by another administrator (`POST /api/admin/donors/{donorId}/second-factor/reset`) stays.

- Start: after the right password the code step offers "Nemáte telefon s aplikací? Obnovit přístup platbou" → `POST /api/donors/auth/login/second-factor/recovery` with the sign-in challenge. `SecondFactorRecoveryService.start` checks the challenge like the code does (unknown, expired, used or out of attempts → 401 `auth/invalid-second-factor-challenge`) but spends no attempt, asks `donations` through the port `shared/application/recovery/SecondFactorRecoveryTargets` where to pay, and then returns the donor's open recovery when there is one (Jakub, 24 October 2026): the same code, start and expiry with `resumed: true`, so a payment already sent with that message still counts. Only without an open one (none yet, used, expired, or stored before codes were kept) does it open a new recovery, which replaces any other open one, with `resumed: false`.
- Code: `shared/domain/SecondFactorRecoveryCode`, eight characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0/O, 1/I), generated by `SecureRandom`; the payment message is `OBNOVA XXXXXXXX`. The payment is found by its SHA-256 (`code_hash`); the code itself is kept too (`code`), only to show the open recovery again. That is no easier to abuse than the TOTP secret stored in plain text next to it: the code turns nothing off without the 1 Kč from the donor's own bank account. `toString` is masked everywhere it travels. It is found in the bank's message for the recipient ignoring case, diacritics and a space or dash in the middle, and only as a whole word.
- Instructions: `message`, `startedAt` and `expiresAt` (the recovery is open `app.donors.second-factor.recovery-ttl`, 14 days, from its start), `resumed`, `accountNumber` and `iban` of the foundation, `amountMinor` 100 and `currency` `CZK`, `usableFrom`, the first Prague day a payment counts, or `null` when that is today or earlier, and the payment as a QR code: `spayd` (`SPD*1.0*ACC:<iban>*AM:1.00*CC:CZK*RN:<recipient>*MSG:OBNOVA XXXXXXXX`, no variable symbol, because the payment is recognised by the message and the sender account) and `qrCode` `{ size, modules }` like `GET /api/donations/payment-qr`. `donations` draws it through the same port (`SecondFactorRecoveryTargets.paymentQrFor`, `GeneratePaymentQrService.generateForRecovery`, `QrPayment.secondFactorRecovery`); the public `payment-qr` endpoint has no such purpose, so it never encodes a message the caller chose. No account of the donor is named: the page is reached with the password alone.
- Which accounts count: `donations` answers from the donor's copy (`SecondFactorRecoveryPolicy.usableFrom`): the earliest of the active, not excluded (`PAIRING_EXCLUDED_ACCOUNTS`) account links, each usable from the Prague day it was proven plus 7 days. Without such a link the start answers 409 `donors/second-factor-recovery-unavailable` and opens nothing.
- Payment: after every import pairs the new payments, `BankStatementRecorder` hands them to `donations/application/recovery/SecondFactorRecoveryPayments.inspect`. A payment carrying a code counts only when it is exactly 1 Kč, has a sender account that is not excluded, exactly one donor holds an active link covering its booking day, and that link was proven at least 7 days before the booking day; otherwise it is logged with its transaction id and the reason (`RecoveryRefusal`) and nothing else happens. The payment itself stays a gift like any other and pairs as usual.
- Turning off: a counted payment publishes `SecondFactorRecoveryPaid`; `donors/infrastructure/recovery/SecondFactorRecoveryPaymentListener` runs `SecondFactorRecoveryService.complete` in the import's transaction. It finds the open recovery of that donor by the code's hash, marks it used, deletes the second factor, revokes every refresh token and e-mails the donor (`second-factor-recovered`, naming the account as `…5399/0800`). A code of another donor, an expired or used recovery, or a factor already off changes nothing. For an administrator it also records `RECOVER_SECOND_FACTOR` (by and on the administrator themself) and e-mails every other administrator (`administrator-second-factor-recovered`). A failure rolls the import back, so the next run tries again.
- Schema: `donors/014_recover_second_factor_by_payment.xml` adds `donor_second_factor_recovery` (`id`, `donor_id` FK with cascade and its index, `code_hash varchar(64)` unique, `created_at`, `expires_at`, `used_at`); `donors/015_keep_second_factor_recovery_code.xml` adds the nullable `code varchar(8)` (rows from before stay without it and are replaced at the next start).
- Logs: the donor, recovery and transaction ids and the reason only, never the code or an account.
- Tests: `features/donors/second_factor_recovery.feature`; units `SecondFactorRecoveryCodeTest`, `SecondFactorRecoveryPolicyTest`, `SecondFactorRecoveryPaymentsTest`, `SecondFactorRecoveryServiceTest`, `SecondFactorRecoveryTest`, `JpaSecondFactorRecoveryRepositoryTest`, `DonorSecondFactorRecoveredEmailSenderTest`, `DonorAuthControllerTest`.

Frontend: the code step of the sign-in dialog offers "Nemáte telefon s aplikací? Obnovit přístup platbou" (`AuthApi.startSecondFactorRecovery`); the instructions show "Tuto obnovu už jste zahájili … Pošlete platbu s tímto kódem." when `resumed`, the account number and the message with copy buttons, "1 Kč", then the QR code ("QR platba 1 Kč se zprávou pro obnovu přístupu", always after the details), "Platbu pošlete nejdříve …" while `usableFrom` is set, "Zpráva pro příjemce platí do …", that starting again before then shows the same details, and "← Zpět na kód"; 409 stays on the code step with the problem in the alert line, an invalid challenge goes back to the password.

#### Passkeys

A passkey (WebAuthn, "přístupový klíč" in the UI) is an optional way to sign in without the password (Jakub, 23 October 2026). Nothing changes for a donor who never adds one; an account may also drop the password (see "Accounts without a password"). The server side is `donors/application/DonorPasskeyService` (adding, listing, removing), `DonorPasskeySignInService` (sign-in) and the port `PasskeyCeremonies`, implemented by `donors/infrastructure/webauthn/WebAuthnPasskeyCeremonies` over `com.webauthn4j:webauthn4j-core` (ArchUnit confines `com.webauthn4j..` to that package).

- Relying party: the id is the host of `app.site.public-url` (`nfnn.cz`), the expected origin its scheme and authority, the name `app.donors.passkeys.relying-party-name` ("Nová naděje"). A passkey therefore works only on the site it was created on: keys made on the staging host do not work on `nfnn.cz`.
- Adding: `POST /api/donors/me/passkeys/options` checks the password (`donors/wrong-password`), deletes expired challenges and stores a registration challenge for the donor (43-character secret, kept as SHA-256 in `donor_passkey_challenge`, `app.donors.passkeys.challenge-ttl` 5 minutes, once). It answers the creation options as `PublicKeyCredentialCreationOptionsJSON`: `rp { id, name }`, `user { id, name, displayName }` (the id is the base64url of the donor UUID's 16 bytes, the name the e-mail), `pubKeyCredParams` ES256, EdDSA and RS256 (-7, -8, -257), `timeout` in milliseconds, `excludeCredentials` (the donor's passkeys with their transports, so a device that already holds one says so), `authenticatorSelection { residentKey: "required", requireResidentKey: true, userVerification: "required" }`, `attestation: "none"`.
- `POST /api/donors/me/passkeys` marks the challenge used before any check (a failed attempt cannot be replayed), checks the limit (`app.donors.passkeys.max-per-donor` 10, 409 `donors/passkey-limit-reached`), verifies the attestation (type `webauthn.create`, challenge, origin, RP id hash, user presence and user verification; any attestation statement is accepted without trust, as with `none`), refuses a credential id already stored and saves `donor_passkey` (credential id, attested credential data with the public key, signature counter, transports, name, `created_at`, `last_used_at`, and `relying_party_id`, the host the key was made for; changelog `donors/013`). At every start the backend deletes the keys made for another host than the one of `PUBLIC_URL` (a key stored before the column counts as made for the current host), so after the switch from the staging address to nfnn.cz the old keys disappear from `GET /api/donors/me/passkeys` by themselves (`PasskeySiteCleanupService`, `PasskeySiteCleanupAtStart`). Any refusal is 400 `donors/passkey-rejected` ("Přístupový klíč se nepodařilo přidat"). `DonorPasskeyAdded` sends `AFTER_COMMIT` the e-mail "K vašemu účtu přibyl přístupový klíč – Nová naděje" (template `email/donors/passkey-added`, texts `donors.passkeyAdded.email.*`) naming the key and what to do if the donor did not add it.
- Signing in: `POST /api/donors/auth/passkey/options` stores a sign-in challenge without a donor; `POST /api/donors/auth/passkey` marks it used, finds the passkey by credential id, checks that `userHandle` names its donor, that the donor is neither erased nor unconfirmed, verifies the assertion (type `webauthn.get`, challenge, origin, RP id hash, user verification, signature with the stored key, a counter that only grows when the authenticator keeps one) and stores the new counter and `last_used_at`. The session opens like one completed with the code from the app (`second_factor_verified = true`), so an administrator gets `ADMIN` without the TOTP code and a donor with the TOTP factor on is not asked for it (Jakub, 23 October 2026). Every failure is the same 401 `auth/invalid-passkey` ("Přístupový klíč neznáme").
- Renaming: `PATCH /api/donors/me/passkeys/{id}` changes only the name the donor sees (the device keeps its own label), without the password: the name opens nothing. Logged as the passkey and donor ids only.
- Removing: `DELETE /api/donors/me/passkeys/{id}` without the password (a stolen session could add a key only with the password, and removing one only weakens the attacker). Other sessions stay. `DonorPasskeyRemoved` sends `AFTER_COMMIT` the e-mail "Z vašeho účtu byl odebrán přístupový klíč – Nová naděje" (template `email/donors/passkey-removed`, texts `donors.passkeyRemoved.email.*`, cs and en) naming the key and what to do if the donor did not remove it; it cannot be switched off.
- An administrator who already holds a second factor (the code from the app turned on, or at least one passkey) adds or removes a passkey and starts the code set-up only in a session opened with it (the JWT carries `ADMIN`); a session opened with the password alone gets 403 `donors/second-factor-session-required` ("Nejdřív se přihlaste přístupovým klíčem"). Otherwise whoever reads the administrator's mailbox could reset the password and enrol a factor of their own to reach the administration. An administrator with no factor yet enrols the first one from a password session as before (`SecondFactorSessionGuard`).
- Limits: 20 sign-in requests (options and answers together) per 15 minutes per client address (`PasskeySignInRateLimiter`), 10 creation options per 15 minutes (`PasskeyChangeRateLimiter`), both counted before any work.
- Administration: `DELETE /api/admin/donors/{donorId}/passkeys` → `AdministratorService.removePasskeys(adminId, donorId)` deletes every passkey of the donor (400 `donors/no-passkeys` when there is none), revokes every refresh token, publishes `AdminActionPerformed("REMOVE_PASSKEYS")` and `DonorPasskeysRemoved`, which sends the e-mail "Přístupové klíče k vašemu účtu byly odebrány – Nová naděje" (template `email/donors/passkeys-removed`). The donor card `/sprava/darci/{id}` shows "Přístupové klíče" with the count and "Odebrat přístupové klíče" with a confirmation. It is a web-only action (the MCP connector has no tool for it). The GDPR erasure deletes the passkeys too.
- Logs: ids and outcomes only ("Passkey … added for donor …", "Donor … signed in with passkey …", the class name of a refused ceremony).

#### Accounts without a password

A donor may have no password and sign in with passkeys only (Jakub, 23 October 2026, after #113). `donor.password_hash` is nullable (`donors/011_optional_password.xml`); `Donor.passwordHash()` is an `Optional`, `hasPassword()` and `removePassword()` say and do the rest. A password sign-in at such an account answers the usual 401 `auth/invalid-credentials` after a real BCrypt compare with `UNKNOWN_DONOR_HASH`, so the answer says nothing about the account.

- Registration: `password: null` registers without one. The e-mail link opens a session as before; in it the first passkey needs no confirmation (`POST /api/donors/me/passkeys/options` with `{}`), because the donor has neither a password nor a key to confirm with. The page `/potvrzeni-emailu` offers "Vytvořit přístupový klíč" right away.
- Confirmation: every change that asked for the current password (adding a passkey, the code from the app on or off, a new e-mail, setting or removing the password) takes either `password` or `passkey: { "challenge", "credential" }`, a sign-in assertion over a challenge from `POST /api/donors/auth/passkey/options` (`application/Confirmation`, `DonorConfirmations`). The challenge is marked used before any check; the key must be the donor's own, its user handle must name the donor and its signature must verify, else 400 `donors/passkey-confirmation-rejected` ("Přístupový klíč změnu nepotvrdil"). Neither field → 400 `donors/confirmation-required`; a password at an account without one → 400 `donors/wrong-password`. A confirmation records the key's use like a sign-in.
- The last way in stays: removing the last passkey of an account without a password and removing the password of an account without a passkey answer 409 `donors/last-sign-in-method` ("Přišli byste o poslední způsob přihlášení"). `POST /api/donors/me/password/remove` drops the hash, revokes every refresh token and opens a new session for this device with the same second-factor flag; `PUT /api/donors/me/password` sets a password again (`currentPassword` left out, `passkey` instead).
- Recovery: the reset e-mail ("Obnovit přístup") leads to `/obnova-hesla`, which sets a new password as before or adds a new passkey. `POST /api/donors/auth/password-reset/passkey/options` checks the link without spending it, then, when the donor's code from the app is on, the six-digit `code` (400 `donors/second-factor-code-required` without it, `donors/second-factor-code-rejected` for a wrong one; the code counts once per 30-second step as at sign-in), and answers the creation options. `POST /api/donors/auth/password-reset/passkey` spends the link (marked used first), stores the key, deletes the donor's other reset links and revokes every session; the usual e-mail about a new key tells the donor. An administrator never recovers by e-mail (403 `donors/administrator-recovery-refused`, "Účet správce se takto neobnovuje"): another administrator removes the lost keys or resets the code in `/sprava/darci`, and the reset link can still set a password, which alone opens no administration. With the code off, the link alone recovers the account, as a password reset always did; the overview recommends a key in two devices.
- Cucumber: `features/donors/donor_passwordless.feature`; units `DonorConfirmationsTest`, `DonorPasskeyRecoveryServiceTest`, `DonorCredentialsServiceTest`, `DonorTest`.

Frontend: the registration form asks "Jak se budete přihlašovat" (Heslem / Přístupovým klíčem) when the browser supports passkeys; `AuthStore.confirmWith(password | null)` builds the confirmation, running the device's sign-in prompt when the donor has no password. The account card shows "Heslo: Nastavené / Bez hesla, jen přístupové klíče", "Nastavit heslo" instead of "Změnit heslo" and "Odebrat heslo" once a passkey exists (the dashboard passes the count from the passkeys card); its forms show "Po odeslání vás zařízení požádá o potvrzení…" instead of the password field. The passkeys card warns when an account has neither, keeps the only key from removal and recommends a second device. `/obnova-hesla` offers "Nové heslo" or "Nový přístupový klíč" and asks for the code when the server says so.

Frontend: `core/auth/PasskeyAuthenticator` wraps `navigator.credentials.create/get` (base64url both ways; `NotAllowedError`/`AbortError` → cancelled, `InvalidStateError` → already registered). The sign-in dialog offers "Přihlásit se přístupovým klíčem" under the password form when the browser supports passkeys (`AuthStore.signInWithPasskey`); a dismissed prompt says "Přihlášení přístupovým klíčem neproběhlo. Zkuste to prosím znovu, nebo se přihlaste heslem." The Přístupové klíče row of the "Přihlášení a zabezpečení" card ("Žádný", "2 klíče"; "Spravovat přístupové klíče" opens `features/donors/dashboard/passkeys-panel`) explains them, lists the keys with "přidáno" and "naposledy použito", adds one (name prefilled from the device, current password, then the device's prompt) and removes one after "Odebrat klíč …?". Cucumber: `features/donors/donor_passkeys.feature` (a software authenticator, `donors/SoftwarePasskey`, signs real P-256 assertions) and the last scenario of `admin_donors.feature`. The removal of other hosts' keys: `PasskeySiteCleanupServiceTest`, `PasskeySiteCleanupAtStartTest` and `JpaPasskeyRepositoryTest`.

#### Password reset

A donor who forgot the password asks for a link from the sign-in dialog, opens it from the e-mail and sets a new password on the public page `/obnova-hesla`, then signs in by hand. Both endpoints take JSON and answer without a body.

`POST /api/donors/auth/password-reset/request` with `{ "email": "jana@example.cz" }`:

- `email`: `@NotBlank @Email`, max 254, and the shape `EmailAddress` requires (`EmailAddress.SHAPE_REGEX`, a dot in the domain, so `jana@localhost` is a field error and not a domain exception), else 400 `validation` with a field error for `email`. Surrounding spaces are stripped before validation (registration still rejects them) and the address is lowercased, so `"  JANA@Example.cz "` reaches the donor registered as `jana@example.cz`.
- Always 202, whether or not the address belongs to a donor and whether or not an e-mail is sent. Nothing expensive runs on the request thread (no hashing, no mail: the e-mail is sent after the commit, asynchronously); the remaining timing difference between a known and an unknown address is a few database statements, accepted.
- 5 requests per hour per client address (`FixedWindowRateLimiter`, like the contact form) → 429 with type `donors/rate-limited` and the generic title and detail of `RateLimitExceededException`. The limit is a brake on how many e-mails the foundation's SMTP account sends, not an identity check. The backend trusts forwarded headers from any peer (`server.forward-headers-strategy: framework`), so the nginx in `frontend/` resolves the visitor's address itself (`real_ip` from the private proxy ranges) and rewrites `X-Forwarded-For` to it, dropping any client-sent `Forwarded` header. A CAPTCHA is the escalation if abuse appears (requirements: none until needed).
- At most 3 live links per donor (`app.donors.password-reset.max-live-links`): while the donor holds three unused, unexpired links, a further request answers 202 and sends nothing. A request never cancels an earlier link, so nobody can lock a donor out of a link already received; whoever knows the address can keep the three links occupied for up to an hour, accepted. The count is taken without a lock on the donor, so requests for one address that arrive at the same instant can each send a link (a few extra e-mails within the per-address limit), accepted.
- The e-mail (`templates/email/donors/password-reset.html`, multipart plain text + HTML, `From` "Nová naděje – nadační fond" with the address of `app.mail.sender-email`, no `Reply-To`, subject and body in the donor's `preferredLocale` from the `donors.passwordReset.email.*` bundle keys) names the account's address and carries the link `{app.site.public-url}/obnova-hesla#token=<secret>`. It contains nothing from the donor's profile (the registered name is unverified free text and could carry a phishing sentence under the foundation's sender); the only image is the foundation's logo, attached inline (`cid:logo`) by the shared layout, never loaded from the network. The token travels in the URL fragment, so it never reaches an access log or a `Referer`; the page reads it and removes it from the address bar.
- A send failure (no SMTP configured, a rejected address) is logged at ERROR with the donor id and the exception class only; the request already answered 202 and the donor can ask again.

`POST /api/donors/auth/password-reset/confirm` with `{ "token": "<43 base64url characters>", "password": "new passphrase" }`:

- `token`: `@NotBlank`, `^[A-Za-z0-9_-]{43}$`; `password`: `@NotBlank`, 12–128 characters (the same annotations as registration), else 400 `validation` with field errors.
- 400 `donors/password-too-common` for a password on the common list, checked before the token is consumed, so a weak password does not burn the link.
- 400 `donors/invalid-password-reset-token` for a well-formed token that is unknown, expired or already used (one code, no distinction; the lookup is by the SHA-256 of the presented value).
- 204 on success: the password is replaced, the token is marked used atomically (a concurrent confirm with the same token loses and answers 400), the donor's other reset links are deleted, every refresh token of the donor is revoked and the response clears the `refresh_token` cookie. Two different live links of one donor confirmed at the same instant can cross their row locks in PostgreSQL: the loser answers 500 instead of 400 while the end state is the same (one password, one used link, the others deleted), accepted. No session is opened: the donor signs in with the new password. The same "Heslo k vašemu účtu bylo změněno" e-mail as after a change goes out (`DonorPasswordChanged`). Access tokens already issued stay valid until they expire (at most 15 minutes); there is no denylist.
- Not rate-limited: 256-bit tokens, a hash lookup, and no hashing before a valid token is found.

Table `donor_password_reset_token` (`donors/003_create_donor_password_reset_token.xml`): `id` (UUIDv7), `donor_id` (cascade), `secret_hash` (SHA-256 hex, unique), `issued_at`, `expires_at` (`issued_at` + `app.donors.password-reset.token-ttl`, PT1H), `used_at`. A request first deletes the donor's used and expired rows and a confirm deletes the donor's other rows, so the table holds at most the live links plus the last used one and needs no cleanup job.

Domain: `PasswordResetToken` aggregate, `LinkSecret` (generated like `RefreshTokenSecret`; the two are never interchangeable: a reset secret presented as the refresh cookie answers 401 `auth/invalid-refresh-token`), `PasswordResetTokenRepository`, `InvalidPasswordResetToken` (`RuleViolation`). Application: `DonorPasswordResetService` (`requestReset`, `confirmReset`), `DonorPasswordResetProperties`, the event `DonorPasswordResetRequested` in `donors/application/event`. Infrastructure: `infrastructure/mail/PasswordResetEmailSender` (`@Async AFTER_COMMIT`) and the JPA trio. REST: `interfaces/rest/DonorPasswordResetController` and `PasswordResetRateLimiter`; the request records mask every field in their `toString()` (Spring MVC logs request bodies at DEBUG in the dev profile), and `LoginRequest` and `RegisterDonorRequest` now mask the address, the name, the postal address and the password too (the type, the company identifier and the locale stay readable). Configuration: `PUBLIC_URL` → `app.site.public-url` (`shared/infrastructure/config/PublicUrlProperties`, validated: absolute `http(s)` URL without a query or a fragment, trailing slash stripped; default `https://nfnn.cz` (the staging server sets `PUBLIC_URL=https://nfnn.znamenacek.duckdns.org`), `http://localhost:4200` in the dev profile), `MAIL_FROM` → `app.mail.sender-email` (`shared/infrastructure/mail/MailSenderProperties`, shared with the contact form; falls back to `CONTACT_RECIPIENT`). Cucumber: `features/donors/donor_password_reset.feature`.

Frontend: the dialog's reset step ("Zapomněli jste heslo?") posts the request and shows "Zkontrolujte si e-mail" with the address on 202, with "Poslat znovu" (its own sentence on 429); the public route `obnova-hesla` under the public shell (`features/donors/password-reset/`) reads the token from the fragment, replaces the URL, asks for the new password once, posts the confirm, clears a session the browser still holds and offers the sign-in dialog on success; an invalid or missing link offers the dialog's reset tab (`LoginDialogService.open('reset')`).

#### Connected applications (OAuth 2.1 authorization server)

The site is the authorization server of the MCP connector (Jakub, 2026-10-23: reading and writing from the start): an administrator connects Claude (claude.ai or Claude Code) to the administration by signing in on the site and approving the connection, and the connector then acts under the administrator's account with every action audited like the web's. Clients are identified by Client ID Metadata Documents (the client id is an `https` URL whose document names the client and its redirect addresses: `https://claude.ai/.well-known/oauth-client` for Claude, `https://claude.ai/oauth/claude-code-client-metadata` for Claude Code, whose loopback redirects `http://localhost/…` and `http://127.0.0.1/…` match on any port); the document is fetched over HTTPS with a 5 s timeout, at most 16 kB, no redirects, private addresses refused, cached for an hour (`infrastructure/oauth/HttpClientMetadataSource`, parsed by `ClientMetadataDocuments`), and nothing is registered by hand.

- The flow: the client sends the browser to `{public-url}/pripojeni?client_id=&redirect_uri=&response_type=code&code_challenge=&code_challenge_method=S256&scope=&resource={public-url}/mcp&state=`; the page asks the signed-in administrator (a session opened with the second factor, else "Připojit aplikaci může jen správce"), lets them choose the extent (reading is always granted; the changes, `admin:write`, only when the administrator ticks "Změny", unticked by default), asks for a fresh second factor (a new code from the app, or a passkey) and posts the decision with the granted scopes and that proof to `POST /api/donors/oauth/authorize`, which stores the authorization code (`oauth_authorization_code`: SHA-256 of a 43-character `LinkSecret`, the client, the redirect, the PKCE challenge, the scopes, the resource, `second_factor_verified`, five minutes, used once) and answers the redirect address to go to. The client exchanges the code at `POST /api/donors/oauth/token` with its verifier: a wrong verifier, another client or redirect, a used or expired code and a code of an erased donor all answer `invalid_grant`, and a code is marked used before any of those checks, so a second attempt fails whatever the first one said.
- Tokens: the access token is the same HS256 JWT as the browser's (15 minutes, `ROLE_ADMIN` only because the code remembers the second factor) but with `aud` `{public-url}/mcp`, a `scope` claim and a `client` claim (the host of the client id, e.g. `claude.ai`; the API token a token exchange issues carries the same `client`, so `admin_action.client` names the application, see "Audit trail"), so it cannot be used at `/api` as it is (whoever holds it can still exchange it at the public token endpoint, so the boundary is the scope and the browser-session guard, not the audience); the refresh token is a `donor_refresh_token` row with `client_id`, `scope` and `granted_at` (14 days, rotated on use, a replayed one revokes every session of the donor, the browser's included), tied to its client, and never accepted as the browser's cookie nor the other way round. A refresh also checks that the donor still administers: a removed administrator's connection ends at the next refresh (and every session ends at once when the role is taken away).
- Token exchange (RFC 8693): the connector presents a connector access token as `subject_token` with `resource={public-url}/api` and gets an API access token (`aud` `{public-url}/api`, the same expiry, the same `scope`, no refresh token); a token that was not issued for the connector answers `invalid_grant`, another resource `invalid_target`. The `scope` rules of "Authentication" then decide what the API token may change, and the token opens `/api/admin/**` only: it cannot approve another connection, change the administrator's account or download a backup (403 `auth/forbidden`).
- `admin:read` lets the connector read the administration, `admin:write` also change it (pair and unpair payments, send the report, request a backup, publish content: the writing tools of "MCP connector" below); an unknown scope answers `invalid-authorization-request`. The granted scope may be narrower than the client asked for: the consent page posts only the scopes it knows and the administrator ticked, the code, the tokens and the `scope` of the token response carry that set (RFC 6749 §5.1), and a request with no known scope cannot be allowed. Widening a connection later means disconnecting it and connecting again.
- The administrator sees the connections on `/darce/udaje` in the card "Připojené aplikace" (`features/donors/dashboard/connected-apps-card`: host, granted, last used, permissions, "Odpojit" → `DELETE /api/donors/me/connections/{id}`). Every decision, exchange and refresh is logged with ids and hosts only.

Configuration `app.donors.oauth` (`application/OAuthProperties`): `issuer` (`{app.site.public-url}`), `authorization-path` (`/pripojeni`), `authorization-code-ttl` (`PT5M`), `mcp-resource` (`{public-url}/mcp`), `api-resource` (`{public-url}/api`); `app.security.jwt.audience` (`{public-url}/api`). Changelogs `donors/008_connected_apps.xml` and `donors/009_refresh_token_used_at.xml` (`donor_refresh_token.used_at`: a rotated token is used, a token ended by sign-out, a password change or a disconnection is revoked; only a replayed used token ends every session, a revoked one just answers 401 / `invalid_grant`). Domain: `ClientId`, `ClientMetadata`, `CodeChallenge`, `AuthorizationCode(+Repository)`, `OAuthScope`, `RefreshToken.issueForClient`, the exceptions `InvalidClient`, `InvalidAuthorizationRequest`, `InvalidGrant`, `InvalidTarget`, `AdministratorRequired`, `ConnectedAppNotFound`. Application: `AuthorizationServerService` (`describeClient`, `decide`, `exchangeCode`, `refresh`, `exchangeToken`), `ConnectedAppsService`, the ports `ClientMetadataSource`, `AccessTokenIssuer`, `AccessTokenVerifier`. REST: `OAuthMetadataController`, `OAuthController`, `OAuthTokenRateLimiter`, `ConnectedAppsController`. Tests: `features/donors/connected_apps.feature` (`@connected-apps`: the metadata, the client description, approval and exchange, the fresh second factor (none, a wrong code, the same code twice, a passkey instead), read-only vs. writing scope under `/api/admin`, an exchanged API token confined to the administration (no new connection, no account, no backup download, no dangerous or irreversible change even with `admin:write`), a donor without the role, declining, a client whose document cannot be read or lacks the redirect, a wrong resource, scope or missing challenge, Claude Code's loopback port, a code used once and only with its verifier, client and redirect and within five minutes, refresh rotation and replay ending the browser session too, a refresh token tied to its client and refused as the cookie, disconnecting, a removed administrator, the 31st token request) with `support/FakeClientMetadataSource`; units `AuthorizationServerServiceTest`, `FreshSecondFactorCheckTest`, `ConnectedAppsServiceTest`, `OAuthPropertiesTest`, `ClientMetadataDocumentsTest`, `HttpClientMetadataSourceTest`, `AdminWriteAuthorizationManagerTest`, `BrowserSessionAuthorizationManagerTest`, `JwtPropertiesTest`, `OAuthScopeTest`.

#### MCP connector (`mcp/`, container `nfnn-mcp`)

The connector is a separate Node 24 container (`mcp/`, TypeScript, MCP TypeScript SDK v2: `@modelcontextprotocol/server`, `@modelcontextprotocol/node`, zod; Vitest) that the frontend nginx exposes at `{public-url}/mcp` (Streamable HTTP, `limit_req` 10 requests/s with a burst of 20 per address), `{public-url}/mcp-photos` (the photo upload below, the same limit, 11 MB bodies) and `{public-url}/.well-known/oauth-protected-resource/mcp`. It holds no secret and reads no env file: at startup it fetches `GET http://backend:8080/.well-known/oauth-authorization-server` to learn the issuer (`BACKEND_URL`, default `http://backend:8080`; retried on every request until it succeeds and read again when the last answer is older than 30 s, so an address saved in the first setup or in `/sprava/nastaveni` reaches the connector without a restart while a backend that is restarting leaves the last known one in place; `/health` answers 503 `{"status":"DOWN"}` until then and 200 `{"status":"UP","issuer":…}` after) and derives everything from it: the resource `{issuer}/mcp`, the API audience `{issuer}/api`, the token endpoint.

- Discovery: the protected resource metadata (RFC 9728) names `resource` `{issuer}/mcp`, `authorization_servers` `[{issuer}]`, `scopes_supported` `["admin:read","admin:write"]`, `resource_name` "Správa Nové naděje"; `GET {public-url}/.well-known/oauth-authorization-server` stays the backend's. A request to `/mcp` without a token or with an unknown, expired or foreign one answers 401 `WWW-Authenticate: Bearer error="invalid_token", resource_metadata="{issuer}/.well-known/oauth-protected-resource/mcp", scope="admin:read admin:write"` (the client therefore asks for both and the administrator chooses on `/pripojeni`; the connector itself requires only `admin:read`, so a read-only connection works); a writing tool called by a connection without `admin:write` changes nothing and answers a tool error saying the connection may only read and that the administrator must disconnect the connector in claude.ai and connect it again with „Změny“ ticked (claude.ai offers no step-up for a granted connection, so a bare 403 only showed "Forbidden"). Other paths answer 404.
- Tokens: the connector verifies a bearer token by exchanging it at the backend's token endpoint (RFC 8693, `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `subject_token_type=…:access_token`, `resource={issuer}/api`, posted to the backend's internal address with the public endpoint's path) and keeps the API token in memory under the SHA-256 of the connector token until it expires (the backend never lets it outlive the connector token); a 400 from the backend becomes `invalid_token`, an unreachable backend `server_error`. Every tool call then goes to `/api/admin/...` with that API token and `Accept-Language: cs`, so the backend audits it under the administrator who connected, applies the `scope` rule of "Authentication" and its rate limits; a problem+json answer is returned to the model as text ("The administration refused the request (403 auth/forbidden): …"). The exchange carries the visitor's address that nginx passed as `X-Real-IP` (only a valid IP) as `X-Forwarded-For`, so the token endpoint's 30 per 15 minutes counts per visitor and a stranger's forged tokens cannot use up the administrator's limit (before: every exchange counted against the connector container's address).

#### Frontend session handling

`core/auth/AuthStore` keeps the donor and the access token in memory only. `authInterceptor` adds `Authorization: Bearer` to every `/api/**` call except `/api/donors/auth/**`; on a 401 whose problem type ends with `auth/expired-token` it refreshes once (one request even for parallel calls) and retries. A `localStorage` flag (`nfnn.donor-session`) only records that a session may exist, so the app calls `refresh` on start for returning donors and skips it for everyone else; `donorGuard` waits for that restore before opening `/donor/**` and otherwise sends the visitor home with the sign-in dialog open.

#### `GET /api/donations/me` and `GET /api/donations/me/summary`

Both read the caller's donations, found by the donor id in the JWT subject (`donor_record.donor_id`); 401 `unauthenticated` without a token. A donor the `donations` context has no record of, or one with no donations yet, gets 200 with an empty list and zero totals, never 404. Another donor's donations are never visible: there is no id parameter, the caller is the only filter.

`GET /api/donations/me?year=` lists the donations, newest first (`receivedAt`, then `recordedAt`, then `id`, descending; the id breaks the tie between donations paired in one import run, which share their `recordedAt`). `year` is optional; when given it must be a four-digit year (`@Min(1000) @Max(9999)`, else 400 `validation`) and only donations received in that year are returned, with `totalAmountMinor` and `count` covering the returned items. An empty `year=` counts as absent. A year with no donations gives an empty list.

```json
{
  "items": [
    {
      "id": "0192f0f1-...",
      "receiptNumber": null,
      "receivedAt": "2026-03-15",
      "amountMinor": 50000,
      "currency": "CZK",
      "purpose": "Obecný příspěvek",
      "status": "RECEIVED",
      "source": "BANK_TRANSFER",
      "pairedBy": "SENDER_ACCOUNT",
      "senderAccount": "2900233333/2010",
      "confirmedSymbol": null,
      "accountVerification": false,
      "receiptAvailable": true
    }
  ],
  "totalAmountMinor": 375000,
  "currency": "CZK",
  "count": 4
}
```

- `receiptNumber` is the number of the donation's active single receipt (the one its last download issued and nothing has replaced), `null` before the first download and for a `REFUNDED` donation; see "PDF receipts".
- `receiptAvailable` is `true` when the donation's single receipt can be downloaded: the donation is `RECEIVED`, is not an account verification and was received on or after 1 January of the first receipt year (`app.donations.receipt.first-year`, 2026). Older donations and account verifications stay in the list, the totals and the summary, but have no single receipt, so the frontend offers no PDF for them.
- `accountVerification` is `true` for a donation with the purpose `ACCOUNT_VERIFICATION` (below), so the frontend shows it as a verification rather than a gift and never as the last gift (Jakub 2026-10-29).
- `purpose` is the text to show for the donation's `donation.purpose`, resolved by `Accept-Language` from the message bundles (`donation.purpose.<PURPOSE>`): `GENERAL` is "Obecný příspěvek", `ACCOUNT_VERIFICATION` is "Ověření účtu". The pairing sets `ACCOUNT_VERIFICATION` when the payment is exactly 1 Kč and its message for the recipient, without diacritics, case and repeated spaces, contains `OVERENI UCTU` (the QR payment that adds a bank account sends "OVERENI UCTU NADACNI FOND NOVA NADEJE"); every other payment, a larger one with that message included, is `GENERAL`. A verification payment still counts in the totals, the summary and the yearly receipt like any other donation, but it has no single receipt of its own (Jakub 2026-10-29; until then it was an ordinary gift with its own receipt). A project-bound purpose comes with the admin.
- `pairedBy` is `VARIABLE_SYMBOL`, `SENDER_ACCOUNT` or `CONFIRMED_SYMBOL` (`null` for a manual donation). `senderAccount` is the account (`number/bank code`) a donation paired by account or by a confirmed symbol was paired through, `null` otherwise. `confirmedSymbol` is the older variable symbol (matching form, without leading zeros) of a `CONFIRMED_SYMBOL` donation, `null` otherwise (see "Older variable symbol confirmation"). The dashboard tags a donation paired by account „bez VS · …5399/0800“ and one paired by a confirmed symbol „VS 6123456789 · …5399/0800“.
- `totalAmountMinor` and `count` add up `RECEIVED` donations only; a `REFUNDED` one stays in `items` with its status. `currency` is `CZK` even for an empty list (every imported donation is CZK).

`GET /api/donations/me/summary` feeds the dashboard's stat cards and the year toggle:

```json
{
  "totalAmountMinor": 375000,
  "currency": "CZK",
  "count": 4,
  "lastReceivedAt": "2026-03-15",
  "byYear": [
    { "year": 2026, "count": 2, "totalAmountMinor": 150000 },
    { "year": 2025, "count": 2, "totalAmountMinor": 225000 }
  ],
  "yearlyReceiptsAvailableThrough": 2025,
  "receiptsAvailableFrom": 2026
}
```

- Same counting rule as the list: `RECEIVED` donations only.
- `lastReceivedAt` is the newest `receivedAt`, `null` when there is none.
- `byYear` holds one entry per calendar year with at least one counted donation, newest year first; empty when there are none.
- `yearlyReceiptsAvailableThrough` is the last completed calendar year in Prague time (`2025` during 2026): the yearly receipt can be downloaded for that year and earlier, so the frontend decides nothing from its own clock.
- `receiptsAvailableFrom` is the first receipt year (`app.donations.receipt.first-year`, `2026`): receipts, single and yearly, are issued only for donations received from 1 January of that year, so the yearly receipt can be downloaded for the years from `receiptsAvailableFrom` through `yearlyReceiptsAvailableThrough`.

Enums:
- `DonationStatus`: `RECEIVED`, `REFUNDED`.
- `DonationSource`: `BANK_TRANSFER`, `MANUAL` (admin-recorded).

#### PDF receipts

`GET /api/donations/me/{id}/receipt` returns the receipt of one `RECEIVED` donation of the caller ("Potvrzení o přijetí daru"); `GET /api/donations/me/receipts/yearly?year=YYYY` returns the receipt of every `RECEIVED` donation the caller gave in a completed calendar year ("Potvrzení o přijatých darech za rok YYYY"). Both find the caller by the JWT subject; 401 `auth/unauthenticated` without a token. Nothing is e-mailed.

Receipts are issued only for donations received from 1 January of the first receipt year (`app.donations.receipt.first-year`, `RECEIPT_FIRST_YEAR`, default `2026`; `domain/receipt/FirstReceiptYear`): the foundation may have issued receipts for earlier gifts itself, so the web issues none for them. Older donations are still listed (`receiptAvailable` is `false` for them, `receiptsAvailableFrom` in the summary names the year), and both endpoints refuse them with 400 `donations/receipt-before-first-year` (`ReceiptBeforeFirstYear`, a `RuleViolation`), title "Za dary z této doby potvrzení na webu nevystavujeme". The title cannot name the year, because the problem handler resolves titles without arguments; the frontend takes the year from `receiptsAvailableFrom`. A receipt issued before the floor was raised stays issued, but is no longer served.

Response:

- `200`, `Content-Type: application/pdf`, `Content-Length`, `Cache-Control: private, no-store`, `Content-Disposition: attachment; filename="<ascii>"; filename*=UTF-8''<urlencoded>` (both forms, as Spring's `ContentDisposition` writes them).
- File names are ASCII, resolved in the controller from the message bundle (`receipt.fileName.single`, `receipt.fileName.yearly`) in the receipt's language: Czech `potvrzeni-o-daru-2027-000001.pdf` (single, with the receipt number) and `potvrzeni-o-darech-2026.pdf` (yearly, with the year); English `donation-receipt-2027-000001.pdf` and `donation-summary-2026.pdf`.

Single receipt:

- 404 `donations/donation-not-found` for an id that does not exist or belongs to another donor (one query, no existence leak; there is no 403).
- 404 `donations/receipt-not-available` for a `REFUNDED` donation.
- 400 `donations/verification-without-receipt` (`VerificationWithoutReceipt`, a `RuleViolation`) for an account verification (`purpose` `ACCOUNT_VERIFICATION`), title "K ověření účtu samostatné potvrzení nevystavujeme", detail that the 1 Kč payment is included in the receipt for the whole year. A single receipt issued for one before 29 October 2026 stays issued but is no longer served.
- 400 `donations/receipt-before-first-year` for a `RECEIVED` donation received before 1 January of the first receipt year. The checks run in this order (not found or foreign, refunded, account verification, before the first receipt year), so the answer never tells another donor's donation from a missing one.
- 400 `validation` for an id that is not a UUID.

Yearly receipt:

- `year` is required and four digits (`@Min(1000) @Max(9999)`), else 400 `validation`.
- 400 `donations/receipt-before-first-year` for a year before the first receipt year, checked first.
- 400 `donations/year-not-yet-completed` while `year` is the current Prague calendar year or later: a receipt covers a completed year and is available from 1 January.
- 404 `donations/yearly-receipt-not-available` for a completed year in which the caller has no `RECEIVED` donation.

A receipt is a frozen document. The first download issues it: the PDF is rendered and gets a receipt number and an issue date, and `donation_receipt` keeps what it was rendered from instead of the file (see "Receipts kept as template and data"); every later download renders the same bytes again, so a number always denotes one document. When the data the receipt certifies has changed since it was issued (a late-paired payment of that year, a changed donor name or address; the certified data is hashed into `fingerprint`), the next download issues a replacement with a new number that states which receipt it replaces, and the old one is marked superseded (`superseded_at`). A changed signatory, template or preferred language never re-issues. Issuing is serialised per donor: a transaction of its own first locks the donor's `donor_record` row and only then reads the donations and the donor record and computes the fingerprint, so two parallel downloads yield one receipt, and a download that had to wait certifies what was committed meanwhile (a profile change holds that row until it commits, and so does an import that stored a donation of the donor, through the foreign key); a replacement is therefore never issued from older data than the receipt it replaces. A receipt is voided only by its replacement: when a certified donation later becomes `REFUNDED`, the single receipt answers 404 `donations/receipt-not-available` (the yearly one 404 `donations/yearly-receipt-not-available` once no `RECEIVED` donation of the year remains) and the stored receipt keeps `superseded_at` empty, so the foundation deals with a receipt of a refunded gift by hand; nothing marks a donation `REFUNDED` yet.

Receipt numbers are `YYYY-NNNNNN`: the year of issue and a six-digit serial from the sequence `donation_receipt_number_seq`, which never resets (`2027-000001`, `2027-000002`, ..., at most 999 999). A gap is possible (a render that failed consumed a serial) and acceptable.

The language of a receipt is the donor's `preferredLocale` at first issue, stored on the receipt; a later change of the preference does not re-issue, and a replacement keeps the language of the receipt it replaces. An `en` receipt is bilingual, every Czech label and paragraph with its English rendering beneath; a `cs` receipt is Czech only. `Accept-Language` plays no part.

The document (Thymeleaf template `templates/pdf/donation-receipt.html`, rendered by openhtmltopdf with embedded DejaVu Sans) carries the title, number and issue date; the replaced receipt when there is one; the foundation (name, IČO, seat, registry court and file); the donor (person: name and residence; company: name, IČO and seat; always the variable symbol); the gift or gifts: one donation with its form, date of crediting, amount and the foundation's account, or the yearly table of dates and amounts oldest first with the count and the total; the declaration that the gifts were given without consideration for the statutory purposes, naming § 15 odst. 1 and § 20 odst. 8 of zákon č. 586/1992 Sb.; place and date of issue, the signature image when an administrator uploaded one (see "Receipt signature"), the signatory's name and role; and a running footer with the foundation line and the receipt number on every page. The texts live under `receipt.*` in the message bundles.

#### Receipts kept as template and data

A receipt stores no PDF. Issuing freezes it into a snapshot: the template bundle, the logo and the signature image are each stored once by the SHA-256 of their content (`receipt_template`: `sha256`, `content`, `first_used_at`; `receipt_image`: `sha256`, `media_type`, `content`, `first_used_at`; insert if absent), and the receipt row holds their digests, its `data` (about 1 kB, 15 kB for 120 gifts) and `render_profile`. The template bundle is canonical JSON `{"html":…,"texts":{"cs":{…},"en":{…}}}` with `templates/pdf/donation-receipt.html` and every `receipt.*` text of the message bundles except `receipt.fileName.*`, so changing the markup or a text adds a new bundle and leaves issued receipts on theirs. A download of an active receipt whose fingerprint still matches renders the snapshot again (40–125 ms); the PDF is deterministic, with `CreationDate` set to `issued_at` and the document `/ID` derived from the number, so the bytes equal those first served. Receipts stored as PDF files during the test run before `008` were deleted by `009`, which also dropped `content`; their donors get a new receipt with a new number on the next download. The fingerprint keeps its role: it decides whether the certified data changed and a replacement is due; `pdf_sha256` only records the issued file. A stored template or image whose content no longer matches its digest, an unknown digest or an unknown render profile fails the download with 500 instead of serving a different document.

Rendering is capped at `app.donations.receipt.concurrent-renders` (3) at a time across the backend, so a wave of downloads (the New Year) queues instead of exhausting memory; each waiting download holds no database connection until its turn. A download waits for its turn before it opens its transaction and locks the donor, so the 404s (an unknown, foreign or refunded donation, a completed year without a `RECEIVED` donation) and the 400 for a single donation received before the first receipt year are answered only after that wait too, behind the renders running at the moment; only the two 400s of the yearly receipt (a year before the first receipt year, a year not yet completed) are answered before it.

What may change and what may not: a new template or text is fine (a new bundle); a new logo or signature is fine (a new image); a change to how `data` is formatted affects only receipts issued afterwards. A change to the fonts, to openhtmltopdf's output or to `ThymeleafPdfReceiptRenderer` that alters the layout of an existing bundle would change issued receipts, so it needs a new `render_profile` that keeps profile 1 rendering as before. `ReceiptTemplateHistoryTest` guards this: `src/test/resources/receipts/history/<sha256>/` keeps every template bundle that was ever current, with sample data and the text of each sample page, and the test renders each from its stored data and compares the text; it fails when the current bundle is not recorded and writes the candidate folder to `backend/build/receipt-history/`, which is reviewed and committed with the change. It also pins the SHA-256 of both fonts.

#### `GET /api/donations/payment-qr`

```
GET /api/donations/payment-qr?amount=500&variableSymbol=1234567890
```

- `amount`: whole CZK, required, 1 to 1 000 000.
- `variableSymbol`: optional, 1 to 10 digits. The frontend sends the signed-in donor's `variableSymbol` from `GET /api/donors/me`; the backend does not look the donor up, so the endpoint stays public and stateless.
- `purpose`: optional, `DONATION` (default, message "Dar Nadační fond Nová naděje") or `ACCOUNT_VERIFICATION` (message "Ověření účtu Nadační fond Nová naděje", for the payment that adds a bank account, see "Donor's bank accounts"). `ACCOUNT_VERIFICATION` needs `variableSymbol`, else 400 `donations/verification-needs-variable-symbol`; another value answers 400 `validation` for `purpose`. The purpose changes only the message: the import pairs the payment by its symbol either way.
- A missing, non-numeric or out-of-range parameter answers 400 `validation` with `errors: [{ field, message }]`, `field` being the query parameter name.

Response:
```json
{
  "spayd": "SPD*1.0*ACC:CZ2620100000005544332217*AM:500.00*CC:CZK*X-VS:1234567890*RN:NADACNI FOND NOVA NADEJE*MSG:DAR NADACNI FOND NOVA NADEJE",
  "qrCode": { "size": 49, "modules": "1111111011…" },
  "bankAccount": {
    "accountNumber": "5544332217/2010",
    "iban": "CZ2620100000005544332217",
    "recipientName": "Nadační fond Nová naděje"
  }
}
```

SPAYD 1.0 rules the backend follows (`donations/domain/payment/QrPayment`): fields joined by `*` in the order `ACC` (IBAN, no spaces), `AM` (two decimals, `.` separator), `CC:CZK`, `X-VS` (only when a variable symbol was given), `RN` (recipient name, max 35 characters), `MSG` (the purpose's message, max 60 characters). `RN` and `MSG` are uppercase ASCII without diacritics, limited to the QR alphanumeric set (`0-9 A-Z space $ % + - . / :`). `qrCode` is the QR symbol of the SPAYD as data, not as a picture: `size` modules per side (21 to 177, without the quiet zone) and `modules`, `size × size` characters row by row from the top left, `1` dark and `0` light. It is encoded with error correction level H, so the badge the frontend draws over the centre leaves the code readable; the frontend draws it (`shared/ui/qr-code`) and makes the PNG for "Uložit QR kód" itself.

The bank account comes from `app.donations.bank-account.{account-number,iban,recipient-name}` in `application.yml`: the foundation's Fio account 5544332217/2010. It is not a setting, so it changes only by a PR; an IBAN that fails the mod-97 check, an account number whose prefix or number fails the modulo 11 check or is zero, and an IBAN that is not the one the account number gives (`donations/domain/CzechAccountNumber`) stop the backend at startup.

#### `GET /api/donations/payment-details`

```
GET /api/donations/payment-details
If-None-Match: "…"   (optional, the ETag of an earlier answer)
```

Public and stateless, no parameters: it answers everyone alike, a signed-in donor as a visitor, and sets no cookie. The browser composes the SPAYD text of a payment QR from it (`SPD*1.0*ACC:<iban>*AM:<amount>*CC:<currency>[*X-VS:<symbol>]*RN:<recipientName>*MSG:<message>`, leaving `RN` out when it is empty), so it needs no text rules of its own; until slice 1.4 switches the browser over, the frontend still asks `GET /api/donations/payment-qr`, whose answers are unchanged.

Response 200:
```json
{
  "account": {
    "number": "5544332217/2010",
    "iban": "CZ2620100000005544332217",
    "recipientName": "NADACNI FOND NOVA NADEJE"
  },
  "currency": "CZK",
  "messages": {
    "donation": "DAR NADACNI FOND NOVA NADEJE",
    "accountVerification": "OVERENI UCTU NADACNI FOND NOVA NADEJE"
  },
  "accountVerificationAmountMinor": 100
}
```

- `account.number` and `account.iban`: the foundation's account as configured (see below); the backend refuses at startup an IBAN that is not the IBAN of the account number, so the account the page shows is always the one the QR pays.
- `account.recipientName`, `messages.donation`, `messages.accountVerification`: SPAYD text (`donations/domain/payment/SpaydText`), the `RN` and the two `MSG` values the QR sends: diacritics stripped, upper case, every character outside `0-9 A-Z $ + - . / :` written as a space (so `%` and `*` become spaces, which keeps the QR in alphanumeric mode and leaves no `%` that a URL-decoding reader takes for an escape), spaces collapsed and trimmed, then cut to 35 characters for the recipient and 60 for a message and trimmed again. The recipient may be empty (a name of symbols only), a message never is. They equal the `RN` and `MSG` of today's `payment-qr` answers for the foundation's name (`payment_details.feature`); `payment-qr` itself keeps its rules, `%` included, until 1.4 removes it. The cases are in `shared-cases/payment/details.json`, which only the backend runs.
- `messages.accountVerification` with `accountVerificationAmountMinor` (100 hellers, 1 Kč) is the payment that adds a donor's bank account (see "Donor's bank accounts"): the import recognises a payment of exactly that amount whose message contains `OVERENI UCTU` (`DonationPurpose`), so the browser takes both from here instead of knowing them.
- Caching: `Cache-Control: private, max-age=300` (no `Pragma`, no `Expires`), so a browser keeps the answer five minutes and no shared cache keeps the bank details; the frontend nginx adds `Cloudflare-CDN-Cache-Control: no-store` as on every `/api` answer. `ETag` is the strong SHA-256 hex of the body, quoted; a request whose `If-None-Match` holds it answers 304 without a body, with the same `ETag` and `Cache-Control`; any other `If-None-Match` gets the 200.
- 429 `donations/rate-limited` after 120 requests per 15 minutes from one client address (`PaymentDetailsRateLimiter`, counted before any work, a 304 included); that answer carries Spring Security's `no-store`.

Import cycle (`donations/application/importing`, `donations/infrastructure/fio`):

- `FioImportScheduler` exists only when `FIO_TOKEN` is set; it runs `ImportBankPaymentsService.importIncomingPayments` 30 seconds after start (`STARTUP`) and then with a fixed delay of one hour (`HOURLY`), on Boot's single-thread `TaskScheduler` (`@EnableScheduling` in `shared/infrastructure/scheduling`). Overlapping runs are skipped with a WARN. Without a token the `FioClient` bean is `DisabledFioClient` and nothing calls the bank.
- The application owns the downloaded period (`bank_import_state.covered_from/covered_to`). Every run is exactly one `GET /periods/` request from `max(covered_to − 3 days, today − 89 days)` to today (Prague calendar date); the three-day overlap catches late and back-dated bookings, and a movement delivered twice is skipped by its transaction id. The bank-side bookmark (`/last/`, `setLastDownloadedId`, `setLastDownloadedDate`) is never used.
- Only the `STARTUP` run may ask for history Fio keeps locked (older than 90 days): on the first run ever it asks from `FIO_HISTORY_FROM` when set, and at every later start again while `FIO_HISTORY_FROM` lies before `covered_from`. An `HOURLY` run never does. The requested period is what gets covered; for a deep request the period the bank reports is trusted instead (it equals the request in practice). A run that leaves days between the old and the new coverage logs a WARN naming the gap and the `FIO_HISTORY_FROM` that closes it.
- Follow-ups: a 409 (one request per token per 30 seconds) is retried once at the bank's retry time plus a second with the same trigger; a 422 on a period that needed the unlock records `HISTORY_LOCKED` and retries 31 seconds later for the servable window as `HOURLY`; a 422 inside the window is an ERROR about `history-window` and waits for the next hour. At most one follow-up is pending and at most three run per hourly tick. `UNAUTHORIZED` (token missing, not yet active or expired after 180 days) is an ERROR with the renewal instruction; `TRANSPORT`, `INVALID_RESPONSE` and `UNEXPECTED` wait for the next hour. Every failure line carries the kind and the bank's token-masked message (`failed with TRANSPORT (…)`). Every failure lands in `bank_import_state`; the third counted failure in a row, a rejected token and the success after either e-mail the foundation (see "Import outage alerts"); `/actuator/health` never depends on Fio.
- The adapter (`FioBankStatementSource`, over the `io.github.bzumik1:fio-api` client) drops outgoing, zero and non-CZK movements and an amount that is not a whole number of hellers (each with a WARN naming the movement id), takes the counterparty account and bank code as the bank sent them (columns 2 and 3), parses the sender from them into a canonical Czech account (`SenderAccount.parse`; an IBAN or a missing bank code gives no sender), keeps the raw variable symbol next to its matching form and stores the bank's Czech type label (`typeLabel`). The library refuses a whole answer with a payment symbol that is not digits of the allowed length (variable and specific 1–10, constant 1–4) as `INVALID_RESPONSE`. The client is built with `RateLimit.failFast()`: it never waits for the 30-second slot itself, so a 409 or a request it holds back is `RATE_LIMITED` with its retry time and becomes a follow-up. Payments, donations, learned accounts and the coverage are written in one transaction per run.

Pairing rules (`donations/domain/pairing/PaymentPairingPolicy`, applied by `PaymentPairingService` over every unpaired payment at the end of each import and, for one donor, right after a registration). Each import pairs in three passes over the unpaired payments: by symbol (rule 1), then by account (rule 3), then by confirmed symbol (rule 8), so an account learned in the run counts for both later passes:

1. Symbol first. A payment whose `matching_variable_symbol` equals a donor's symbol becomes that donor's donation (`paired_by = VARIABLE_SYMBOL`), even when the sender account was learned by someone else: the payer named the donor. Such a payment also teaches the donor its sender account, which is the only way an account is ever learned (`DonorRecord.learnSenderAccountFrom` refuses any other payment). It teaches nothing when the donor already has any link to that account (a disconnected one included: only the donor reconnects it), when the account is excluded (rule 7), or when it has no Czech sender. A link awaiting a payment (after a reconnect) is proved by such a payment booked on or after its start and becomes `ACTIVE`.
2. A symbol nobody has pairs only through the donor's confirmed claim (rule 8); otherwise it stays unpaired whatever the account. It never teaches an account (a mistyped symbol must not become someone's gift).
3. No symbol: exactly one donor must have a proved link to the sender account whose period covers the payment's booking day; then the payment is theirs (`paired_by = SENDER_ACCOUNT`, `sender_account_id` = that link). A newly learned link has no start, so it also pairs the donor's older payments from the account; when other donors' proved links to the account ended (they disconnected them), the new link starts the day after the latest such end, whether or not those donors have connected the account again since (`DonorRecord.releasedSenderAccountOn`), so the new owner never gets a previous owner's history. A donor whose link to the account never ended has no such end, so with only such donors the new link has no start and the account is shared over its whole history. A previous holder's reconnect, once a payment proves it, covers the days from its own start, so from then on the account is shared with the new link, whichever of the two proving payments was handled first. A disconnected link pairs payments up to and including its last day. Two or more owners leave it unpaired (one WARN per account and run, naming the bank transaction id); no owner, or no Czech sender, leaves it unpaired. The symbol pass runs over the whole unpaired set before the account pass, so an account learned today pairs older payments without a symbol in the same run.
4. A variable symbol of `0` (what Fio sends for some standing orders) counts as no symbol: it is stored raw, its matching form is null, and the payment goes to the account rule.
5. The sender's name is never used for pairing, also not to check that the account belongs to the donor (Jakub's decision of 18 October 2026: a donor who proves an account with their symbol gets its payments even when the bank names someone else). Only the type check of the question about an older variable symbol reads it (see "Older variable symbol confirmation").
6. The hourly run never re-points or removes a donation: a payment keeps its donor when imported again, and an account that a second donor proves with their own symbol leaves the first donor's earlier account-based donations in place while later payments from it without a symbol stay unpaired. Disconnecting an account changes no donation either; a donation the donor says is not theirs is for the admin.
7. Excluded accounts (`pairing.excluded-accounts`, for example a payment gateway's or a collection account many people pay through) are never learned and never pair a payment without a symbol (`EXCLUDED_SENDER_ACCOUNT`); a payment from them with a donor's symbol still pairs by the symbol.
8. Confirmed symbols. A donor's `CONFIRMED` claim (donor, sender account and symbol in `donor_symbol_claim`) pairs a payment from that account whose `matching_variable_symbol` is the claimed symbol and belongs to no registered donor, when exactly one donor's proved link to the account covers the payment's booking day and that donor is the claimant: `paired_by = CONFIRMED_SYMBOL`, `sender_account_id` = that link, `symbol_claim_id` = the claim. This is the account rule (rule 3) applied to the confirmed symbol: another donor's link covering the day leaves the payment unpaired (`AMBIGUOUS_SENDER_ACCOUNT`, in an import one WARN per account and run naming the bank transaction id and the claim id), no covering link of the claimant leaves it unpaired (`UNKNOWN_VARIABLE_SYMBOL`), and an excluded account pairs nothing (`EXCLUDED_SENDER_ACCOUNT`, also when the donor learned it before it was excluded). A `DECLINED` claim pairs nothing. A claim never teaches, starts or ends a link, so the days after a disconnect and before a proved reconnect stay unpaired. A registered donor's symbol always wins (rule 1): once someone registers with a claimed symbol, new payments with it are theirs and the donations the claim paired stay. `PaymentPairingService.pairConfirmedSymbol(claim)` pairs one claim's unpaired payments the same way, for the answer endpoint, and returns them.
9. Symbol in the message (Jakub, 29 October 2026). A payment without a variable symbol whose message for the recipient holds exactly one ten-digit number starting with 1–9 that is not part of an account number (`VariableSymbols.inMessage`: no digit, `/` or `-` next to it; the same number twice counts once) and that number is a donor's symbol becomes that donor's donation as in rule 1 (`paired_by = VARIABLE_SYMBOL`, and it teaches the sender account, so a 1 Kč verification sent from a bank without a symbol field proves the account). A number no donor holds changes nothing: the payment goes to the account rule (3). The stored `variable_symbol` and `matching_variable_symbol` stay as the bank sent them (null), so only the pairing reads the message.

Every pairing writer (`pairUnpaired` at the end of an import, `pairPaymentsOf` after a registration and `pairConfirmedSymbol`) first takes the transaction-scoped PostgreSQL advisory lock `pg_advisory_xact_lock(20261022)` through the `PairingLock` port (`infrastructure/persistence/PostgresPairingLock`, which refuses to run outside a transaction). The writers therefore run one after another, each reads what the one before it committed, and the lock is released when the transaction ends; `uq_donation_bank_payment` stays the last guard. The import's INFO line and its `ImportCounts` report the payments paired by symbol, by account and by confirmed symbol separately, with the accounts learned and the payments left unpaired.

#### Donor's bank accounts

A donor sees the accounts their payments without a symbol are paired from and can disconnect one or connect it again. Every account is proved the same way: a payment with the donor's variable symbol from it (one koruna is enough). There is no other way to add an account and no check of the holder's name. The dashboard calls disconnect and reconnect "Vypnout párování" and "Zapnout párování" (a disconnected row says "Párování vypnuto"); the API keeps the names below.

`GET /api/donations/me/bank-accounts` (401 without a token; a donor without a record gets an empty list):

```json
{
  "items": [
    {
      "id": "0192f0f1-...",
      "accountNumber": "2900233333/2010",
      "status": "ACTIVE",
      "verifiedOn": "2026-10-17",
      "connectedFrom": null,
      "disconnectedOn": null,
      "donationCount": 2,
      "totalAmountMinor": 50000,
      "currency": "CZK",
      "lastDonationOn": "2026-10-12",
      "shared": false,
      "pairingExcluded": false,
      "verificationPaymentOn": "2026-10-16",
      "symbolOffer": { "variableSymbol": "6123456789", "paymentCount": 14, "firstMonth": "2025-01", "lastMonth": "2026-10" },
      "confirmedSymbols": []
    }
  ]
}
```

- One item per link (`donor_sender_account` row), live ones first, then newest first; a reconnected account appears twice, the old period as `DISCONNECTED`. An excluded account appears only when it was learned before it was excluded; it keeps its donations and pairs nothing more.
- `status`: `ACTIVE` pairs payments; `AWAITING_PAYMENT` was reconnected and waits for a payment with the symbol booked from `connectedFrom`; `DISCONNECTED` ended on `disconnectedOn` (its last paired booking day, the Prague date of the disconnect).
- `verifiedOn` is the Prague date the proving payment was paired, null while awaiting. `connectedFrom` is the link's first booking day, null when it pairs the account's whole history.
- `donationCount`, `totalAmountMinor` and `lastDonationOn` cover the `RECEIVED` donations paired by account (`paired_by = SENDER_ACCOUNT`) through this link (`donation.sender_account_id`); donations paired by symbol or by a confirmed symbol are not counted here, so the dashboard's „N darů bez VS“ stays true.
- `shared` is true for an active link when another donor also has an active link to the account; payments without a symbol from it then stay unpaired (rule 3). Another donor's link that still awaits its payment does not count, and an excluded account is never shared.
- `pairingExcluded` is true when the account is in `pairing.excluded-accounts` (rule 7): it pairs only payments with the symbol. Disconnect works as for any other link. Reconnect answers 204 too, but an excluded account is never learned (rule 7), so a payment never proves its new link: it stays `AWAITING_PAYMENT` and pairs nothing. The dashboard shows a live excluded row with its own hint and no "Vypnout párování", except an `AWAITING_PAYMENT` one, which reads "Jen s variabilním symbolem" instead of "Čeká na platbu" and keeps "Vypnout párování" so the donor can end the wait; the newest disconnected excluded row of its number says why it offers no "Zapnout párování".
- `verificationPaymentOn` is the booking day of the donor's latest verification payment from the account (a `RECEIVED` donation with purpose `ACCOUNT_VERIFICATION` paired by the donor's symbol), the same on every row of the account, `null` when there is none. It lets the add-account dialog see that a one-koruna payment arrived from an account that was already verified.
- `symbolOffer` is the question about an older variable symbol (see "Older variable symbol confirmation"), `null` unless the row asks it: the symbol in its matching form, `paymentCount` (at least 1), and `firstMonth` and `lastMonth` (`YYYY-MM`) of the payments a confirmation would pair. It never carries amounts or names.
- `confirmedSymbols` lists the symbols the donor confirmed for the account, oldest answer first, on the account's first row (the newest link of that number) and empty on its other rows; a declined symbol is not listed.

`POST /api/donations/me/bank-accounts/{id}/disconnect` answers 204 and ends the link today (Prague date): payments booked up to today still pair, later ones without a symbol stay unpaired, the donations paired before stay. 404 `donations/bank-account-not-found` for an unknown id or another donor's link, 409 `donations/bank-account-already-disconnected` when it is already disconnected. A later payment with the symbol does not connect it again.

`POST /api/donations/me/bank-accounts/{id}/reconnect` answers 204 and creates a link `AWAITING_PAYMENT` from today for the same account; it becomes `ACTIVE` (not for an excluded account, see `pairingExcluded`) with the next payment with the donor's symbol from that account booked from today and pairs payments without a symbol booked from today on, never the gap. 404 as above, 409 `donations/bank-account-already-connected` when the donor already has a live link to the account (also for an `ACTIVE` id).

`POST /api/donations/me/bank-accounts/{id}/symbol-claim/confirm` with the body `{"variableSymbol": "6123456789"}` answers "yes" to the row's question: it stores the answer and pairs the payments the question counted, and answers 200:

```json
{ "pairedCount": 14, "changedYearlyReceipts": [2026] }
```

- `pairedCount` is the number of payments paired now; later ones pair in the import (pairing rule 8).
- `changedYearlyReceipts` lists, ascending, the years from the first receipt year on that gained a donation and already have an active yearly receipt. The next download of such a year issues a replacement (see "PDF receipts"), and the dashboard says „Potvrzení za rok 2026 se změnilo, stáhněte si nové.“

`POST /api/donations/me/bank-accounts/{id}/symbol-claim/decline` with the same body answers "no": it stores the answer, pairs nothing, and answers 204.

Both endpoints share their errors:
- 400 `validation` with the field `variableSymbol` when the symbol is missing or is not one to ten digits without a leading zero (the symbol goes in the body, not the path, so it stays out of access logs);
- 401 without a token;
- 404 `donations/bank-account-not-found` for an unknown id or another donor's link;
- 409 `donations/symbol-claim-already-answered` („Na tuto otázku jste už odpověděli“) when the donor already answered that symbol for the account, either way;
- 409 `donations/symbol-offer-not-available` („Tato otázka už neplatí“) when the row does not ask about that symbol now: it never did, or the bank data or the account changed since the list was read.

Code: `domain/donor/SenderAccountLink` (status, period, proof) inside the `DonorRecord` aggregate, `ExcludedSenderAccounts`; `application/bankaccount/DonorBankAccountsService` and `BankAccountView`; `interfaces/rest/DonorBankAccountsController`; `infrastructure/bank/PairingProperties`; Liquibase `donations/006_link_sender_accounts_over_time.xml`, which gives every existing row an id, keeps it `ACTIVE` without a period and fills `donation.sender_account_id` for donations already paired by account. Receipts do not change: a receipt lists donations, not accounts, and a donation added later through a proved account replaces the receipt by the fingerprint rule of "PDF receipts". `features/donations/donor_bank_accounts.feature` covers the list, the one-koruna proof with the earlier payments, disconnect, reconnect, the take-over without history (also while the previous holder's reconnect awaits its payment), the shared account, an excluded account, an account learned before it was excluded, the 404 and 409 answers and 401.

##### Older variable symbol confirmation

Long-standing donors often send a standing order with an older variable symbol of their own that no registered donor has, so its payments stay unpaired (pairing rule 2). Once a donor verifies an account with the one-koruna payment, the account's row may ask whether such a symbol is theirs, and "yes" pairs its payments from that account like payments without a symbol (Jakub's decision of 22 October 2026, variant a′; the background is in `parovani-stary-vs.md`). The question is derived on every read and never stored; only the answer is (`donor_symbol_claim`). Accounts verified before the feature get the question too, and a deeper import, a new registration or a second donor withdraws a question that no longer holds.

A row asks about a symbol when all of these hold (`domain/pairing/SymbolClaimOfferPolicy`, fed by `application/bankaccount/SymbolClaimOffers`):

1. **Trigger.** The donor has a verification payment from the account: a `RECEIVED` donation with purpose `ACCOUNT_VERIFICATION` (exactly 1 Kč with „OVERENI UCTU“ in the message) paired by the donor's own symbol. It does not matter whether that payment proved the link or the link was learned earlier from an ordinary gift. An ordinary gift with the symbol, a one-koruna payment without the message, and one without the symbol ask nothing.
2. **The row.** It is the donor's `ACTIVE` link today; an `AWAITING_PAYMENT` or `DISCONNECTED` row asks nothing.
3. **The account.** It is not excluded (rule 7). No other donor's link covers today and no other donor holds an `ACTIVE` link to it, so a `shared` row asks nothing, nor does a row whose account another donor has already taken over from tomorrow.
4. **Exactly one candidate.** T is the booking day of the donor's earliest verification payment from the account. The candidates are the matching variable symbols of the payments from the account, paired or not, booked on or before T on days one of the donor's links to the account covers, minus the donor's own symbol (which also removes the verification payments). Exactly one symbol must remain, and no registered donor may hold it. Two or more symbols (a family or collection account), or a registered donor's symbol among them, ask nothing. A symbol first sent after T is never asked about and does not count against the earlier one. So a donor whose verification payment took the account over on the day the previous holder turned pairing off has no covered day up to T (the new link starts the day after) and is not asked.
5. **Type check.** Every verification payment from the account is checked against the donor's type (`domain/bank/CounterpartyNames`). A person is not asked when the bank names the counterparty like a legal entity, by a Czech legal form or a word of one: `s.r.o.`, `spol.`, `a.s.`, `z.s.`, `o.p.s.`, `v.o.s.`, `k.s.`, `z.ú.`, `s.p.`, `p.o.`, `SE`, `SVJ`, `společenství` (as in `společenství vlastníků jednotek`), `společnost` (as in `akciová společnost` or `společnost s ručením omezeným`), `ústav` (as in `zapsaný ústav`), `družstvo`, `nadace`, `nadační fond`, `spolek`, `obec` or `město`, tolerant of spaces, dots, case and diacritics. A form counts only as a whole word (`družstvo` in any case ending), so `Pospíšil`, `Obecný` or `Městský` is a person. A company is not asked when the name is present but does not look like one. A payment without a name is not checked. The check can misread a name either way. A legal entity whose form is missing from the list (a spelled-out `příspěvková organizace` or `státní podnik`, a `farnost`), or whose name the bank cut before its form, reads as a person, so a person may be asked about that account and a company is not. A person's initials or surname read as a form (`Novák A. S.`, `Jan de Vos`) keep a person donor from being asked, and let a company donor be asked about that account. A sole trader registered as a company, whom the bank names as a person, is not asked; they are asked only when that name reads as a form, as above, or the verification payment carries no name.
6. **Not answered.** The donor has not answered that symbol for the account, either way, and no other donor has confirmed it for the account. This is judged after "exactly one", so a declined symbol never leaves room to ask about a second one.
7. **Something to pair.** `paymentCount` counts the unpaired payments from the account with the symbol, before and after T, that a confirmation would pair: rule 8's covering test, exactly one donor's proved link covering the booking day, and that link is the donor's. The months are those of the first and last of them. A count of 0 asks nothing. So the count in the question is what "yes" pairs.

Answers (`application/bankaccount/SymbolClaimService`): confirm and decline each run as one transaction that first takes the pairing lock (see "Fio import and pairing"). The transaction then:

1. finds the caller's link (404);
2. refuses a symbol the donor already answered for the account (409 `symbol-claim-already-answered`);
3. derives the question again and refuses a different symbol or a question that is gone (409 `symbol-offer-not-available`);
4. stores the answer with its time (an answer stored by a concurrent request gives 409 `symbol-claim-already-answered`).

Confirm then pairs the counted payments in the same transaction (`PaymentPairingService.pairConfirmedSymbol`), so an answer commits together with its donations or not at all. Every later payment with the symbol from the account pairs in the hourly import and the bank check (pairing rule 8). A claim never teaches, starts or ends a link. Once the account is excluded, the claim pairs nothing more.

The donor cannot change an answer, and the question does not come back after either one. A mistake is fixed by an administrator on `/sprava/starsi-symboly` (see "Administration" → "Symbol claims"): the page lists the answers; it reverses a mistaken yes by deleting the claim's donations and turning the answer into `DECLINED`, under the pairing lock and the donor's `donor_record` row lock, and refuses while an issued receipt may certify one of them (a single receipt of the donation, or a yearly receipt of its year, superseded or not, issued at or after its `recorded_at`); and it deletes a mistaken no, after which the question comes back if it still holds. The INFO and WARN log lines of an answer and of pairing by a claim carry only ids (donor, link, claim, bank payment) and counts; the symbol and the account appear only in the pairing's existing DEBUG lines, and no line of the claim or the pairing carries a name.

Code: `domain/donor/SymbolClaim`, `SymbolClaimRepository`, `SymbolOfferNotAvailable`, `SymbolClaimAlreadyAnswered`; `domain/pairing/SymbolClaimOffer` and `SymbolClaimOfferPolicy`; `domain/bank/CounterpartyNames`; `application/bankaccount/SymbolClaimOffers`, `SymbolClaimService` and `SymbolClaimConfirmation`; `interfaces/rest/SymbolClaimRequest` and `SymbolClaimConfirmationResponse` on `DonorBankAccountsController`. `features/donations/symbol_claims.feature` asks and answers through these endpoints. It covers:
- the trigger after a one-koruna proof and after a gift;
- the cases that ask nothing: no genuine verification, two symbols, a registered donor's symbol, another donor's confirmation, a symbol after T, the type check, an excluded account, a shared account, an awaiting reconnect, and a take-over on the verification day;
- declining;
- the ambiguous days, a later registration, and the disconnect gap;
- leading zeros;
- a deeper import that withdraws a question or pairs older payments;
- the changed yearly receipt;
- 400, 401, 404 and both 409 answers.

It seeds a claim through `SymbolClaimRepository` only where no question can be asked: a claim from before the account was excluded, and one at an account the donor never verified. `application/admin/AdminSymbolClaimsServiceIntegrationTest` proves the correction against PostgreSQL: the reversal refused by a single receipt and by a yearly receipt issued after the pairing, the reversal allowed by a yearly receipt issued before it (nothing pairs again, the account asks nothing, the earlier receipt is served again), a declined claim refused, the reset with the question back, a confirmed claim that cannot be reset, and the listing.

#### Bank check on demand

The dashboard calls `POST /api/donations/me/bank-check` every time it opens and when the donor presses "Zkontrolovat nové platby", so a payment the bank has already booked shows up without waiting for the hourly run. The hourly run stays.

```json
{ "bankDataAsOf": "2026-10-18T08:05:30.123456Z", "checking": true }
```

- `bankDataAsOf` is `bank_import_state.last_succeeded_at` (null before the first successful import); `checking` is true while an import is queued, running or waiting for a follow-up after a 409.
- `BankCheckService.requestCheck` asks for an import only when `bank_import_state.last_attempted_at` is older than `import.on-demand-cooldown`. The limit is global, not per donor (anyone can register several accounts), so the bank never sees more than one request per 30 seconds however many donors open the overview. Requests arriving while one is queued join it.
- `FioImportScheduler` implements the `application/importing/BankImportRequests` port: the request is queued on the same single-thread `TaskScheduler` as the hourly run, so the two never overlap, and runs `ImportBankPaymentsService.importOnDemand`, which checks the cooldown again against the stored state and then imports like an hourly run (`ON_DEMAND` trigger, never the locked history). A 409 becomes a follow-up as for any run. Without `FIO_TOKEN` the port is `DisabledBankImportRequests`: nothing is asked and `checking` is always false.
- The dashboard shows "Údaje z banky k {čas}" (Prague time) or "Kontrolujeme nové platby v bance…", polls `GET` every 2 seconds for at most 90 seconds while `checking` is true, and loads the summary and the list again whenever the check ends (a cooldown answer included, so a payment imported by another donor's check or the hourly run shows too); after the donor's "Zkontrolovat nové platby" it says how many gifts are new, that none is, or that the bank is still busy. A note under the payments says that an instant payment usually shows within a minute, an ordinary transfer from another bank can take until the next business day, and that pairing needs the donor's variable symbol.

`spring.task.scheduling.pool.size` is 1; on shutdown the scheduler drops tasks still waiting for their time (the next hourly tick, a pending follow-up) and waits up to 30 s only for a running import. Logging: the token is never logged (`FioImportProperties.toString()` masks it and the Fio library masks it in every message); counterparty names, account numbers and symbols are never logged, at any level. At DEBUG `FioBankStatementSource` names each incoming movement by its transaction id and says only whether it carries a sender account, a payer name and a variable symbol (`given` or `missing`), and `PaymentPairingService` names payments by transaction id, donors by id and learned sender accounts by their link id, with the pairing method or the reason a payment stays unpaired (again only whether a symbol and a sender account are given). At INFO every run logs what the bank answered (`FioBankStatementSource`) and one completion line `Fio import {trigger} {period} completed: ... covered {coverage}` with the counts (`ImportBankPaymentsService`); the pairing after a registration logs one INFO line with its counts.

#### Monthly report

Every full hour (Prague time) the backend checks whether the report for the previous calendar month has gone out and, if not and the settings' send day and hour have come (`ReportSettings.dueAt`: a later day, or the send day from the send hour on), e-mails it to the foundation. With the default settings it leaves on the 1st at 7:00; an administrator can move the day (1–28) and the hour (0–23, Jakub 2026-10-23), change the recipients and leave sections out under `/api/admin/donations/report` (see "Monthly report settings and overview"), and can send the report of any ended month again by hand. When the backend was down at that hour it leaves at the next hourly check. Besides telling the foundation how the site is doing, it keeps the Brevo SMTP key alive: Brevo cancels a key that has sent nothing for 90 days.

- Content (Czech, `donations.monthlyReport.email.*` in the bundles, multipart text and HTML from `templates/email/donations/monthly-report.html`, subject "Měsíční přehled Nová naděje – září 2026"): donors registered by the end of the month (`donor_record.registered_at` before the first Prague midnight of the next month) and the new ones in the month; everything received in the month ("Přijaté dary": the `RECEIVED` donations by `donation.received_on`, refunds left out, plus the incoming payments booked in the month that no donation references, unpaired at the time of sending), the part of it paired with registered donors, and everything received since 1 January in the same way (count and CZK sum each); the unpaired incoming payments of the month on their own (`bank_payment.booked_on`); the last successful bank import and, when the last attempt failed, its time and a Czech line for its `ImportFailureKind`. Amounts read "1 234,50 Kč", times are Prague time.
- Once per month: `application/report/MonthlyReportService.sendDueReport` answers `NOT_DUE` while today is before the send day (`ReportSettings.dueOn`), otherwise picks the month before today (`FoundationCalendar`), and in one transaction inserts the month into `donation_monthly_report` (`report_month`, the first day of the month, primary key; `sent_at`) with `on conflict do nothing`, compiles the report and sends it. A month already recorded sends nothing; a second instance waits on the row and then finds it recorded. A send failure (`MonthlyReportNotDelivered`) rolls the row back, so the next morning tries again. `sendReportFor(ReportMonth)` refuses a month that has not ended.

#### Import outage alerts

Not an endpoint. The foundation is e-mailed once when the Fio import stops working and once when it works again, so an outage is noticed before the monthly report. The decision happens inside the import transaction that records the attempt, which also queues the alert (`donation_import_alert`, an outbox); after every run, whether it succeeded or failed, `ImportBankPaymentsService` delivers the waiting alerts on the scheduler thread, so a refused send never fails the import and is retried after the next run.

- When: `BankImportState.failed` counts `TRANSPORT`, `INVALID_RESPONSE`, `UNEXPECTED` and `UNAUTHORIZED` failures in a row (`consecutive_failures`); `RATE_LIMITED` and `HISTORY_LOCKED` neither count nor reset the streak (they are expected and retried by themselves). The third counted failure in a row opens an outage, a rejected token (`UNAUTHORIZED`) opens one at once, and an open outage of another kind is reported once more when the token gets rejected (the fix differs). The kind reported is kept in `reported_outage`, so a restart neither repeats nor forgets the alert; while it is open, further failures send nothing. A successful import closes it (`BankImportState.succeeded`), resets the count and sends the recovery.
- Alerts (`donations/domain/importing`): the sealed `ImportAlert` is `ImportOutage(kind, consecutiveFailures, lastSucceededAt, detectedAt)` or `ImportRecovery(outageKind, failures, lastSucceededBefore, recoveredAt)`. `application/importing/BankStatementRecorder` queues it through `ImportAlertRepository` before it saves the state (a recovery first marks a still waiting outage `DROPPED`, so a mail server that was down the whole outage sends only the recovery) and logs the outage at ERROR (`Fio import outage: TRANSPORT failed 3 times in a row, the foundation is being told`) and the recovery at INFO. `ImportAlertDelivery` sends the waiting alerts oldest first, marks each `SENT` after the mail server accepted it and stops at the first refusal with a WARN (`Fio import alert <id> was not delivered; it is sent again after the next import`), so the order holds; a failure of the delivery itself is logged at ERROR and never changes the run's report.
- E-mails (`infrastructure/report/ImportAlertEmailSender`, the `ImportAlertSender` port, synchronous on the scheduler thread with the SMTP timeouts of `spring.mail.properties` (10 s), Czech, `donations.importAlert.email.*`, to the recipients of the report settings (`ReportSettings`; until saved, `app.donations.report.recipient`) from `app.mail.sender-email`): the outage e-mail (subject "Stahování plateb z banky selhává – Nová naděje", `templates/email/donations/import-outage.html`) says how many attempts failed in a row and when the last one was, or that Fio rejected the token, then the reason and what to do for the kind (`outage.reason.<KIND>`, `outage.action.<KIND>`: renew the token per `deploy/README.md`, check the connection, read the backend log), the last successful download (or "zatím žádné"), that donors see no new gifts meanwhile, and that the next message comes with the recovery; the recovery e-mail (subject "Stahování plateb z banky zase funguje – Nová naděje", `import-recovered.html`) says when the import worked again, how many attempts had failed (Czech plural by `ChoiceFormat`) and the last success before the outage. The sender logs `Fio import alert e-mail sent: outage TRANSPORT` at INFO and a refused send at ERROR with the alert and the exception class (`The Fio import alert e-mail (outage UNAUTHORIZED) could not be sent: MailSendException`); a refused alert stays queued and goes out after the next import run (hourly), once.
- Liquibase `donations/012_track_import_outages.xml` adds `consecutive_failures` and `reported_outage` to `bank_import_state`; `donations/017_queue_import_alerts.xml` adds `donation_import_alert` (`kind` `OUTAGE`/`RECOVERY`, `failure_kind`, `failures`, `last_succeeded_at`, `occurred_at`, `created_at`, `outcome` null while waiting, then `SENT` or `DROPPED`, `settled_at`; partial index on the waiting ones). `features/donations/import_outage_alerts.feature` covers the third failure (and the silent fourth), the rejected token, the recovery (and the silent next success), the rate limit and locked history not counting, two failures and a success sending nothing, the refused outage e-mail sent after the next run and only once, and a waiting outage replaced by the recovery; `BankImportStateTest` has the rules, `ImportAlertDeliveryTest` the order and the retry, `JpaImportAlertRepositoryTest` the queue, `ImportAlertEmailSenderTest` the texts (previews `backend/build/email-preview/import-outage*.html`, `import-recovered.html`).

#### Bank payments

`donations/interfaces/rest/AdminPaymentsController`. `GET /api/admin/donations/payments?pairing=unpaired` (the default) → `application/admin/AdminPaymentsService.listUnpaired()` (read-only): every `bank_payment` without a `donation`, newest booking day first, then the higher bank transaction id. `pairing=paired&year=2026` → `listPaired(Optional.of(year), filter)`: the donations received in that Prague calendar year with their payment; without `year` the paired payments of every year, newest booking day first (since Jakub's decision of 2026-10-24 the page `/sprava/platby` searches them by text and period instead of picking a year), read only for the years from the earliest to the newest with a donation and within `from`–`to`, and a `from` after `to` answers an empty list without reading; `availableYears` lists every year with a donation, newest first. #### Backups

`operations/interfaces/rest/AdminBackupsController` (the `operations` context: how the server runs, nothing about donors or gifts; `application/backup/BackupAdministrationService`). **The backup key** (Jakub, 2026-10-28: backups are always encrypted; the key is shown in the first setup and in the administration, every view needs a fresh second factor). **The key as 24 words** (Jakub, 2026-10-29): the same 32 bytes of the X25519 identity are also written as 24 words of the Czech BIP39 wordlist (`domain/backup/BackupKeyWords`, the list `bip39-czech.txt` beside it, pinned by its SHA-256 `7e80e161…95fc` in `BackupKeyWordsCasesTest`): the 256 bits plus the first byte of their SHA-256 as the checksum, 11 bits a word. The words are the raw key, not a seed (no PBKDF2, no passphrase), so both forms open the same backups and `BackupKey.parse` turns either into the canonical `AGE-SECRET-KEY-1…` (bech32 encoded again, upper case). A typed word is read after NFKD with the marks dropped, in lower case, and only its first four letters decide (every word of the list has a unique four-letter prefix; what follows must still be a prefix of the word); anything that is not 24 words with a valid checksum is not a key. The shared cases `test-cases/backup-key-words.json` (keys with their words, typed words, pasted texts) run in `BackupKeyWordsCasesTest` and in the frontend's `backup-key-words.spec.ts`. `checkPositions` are three distinct positions (1–24, ascending) drawn by the server with `SecureRandom` for this reveal: `BackupKeyWordChallenges` keeps them in memory per administrator for 30 minutes and five attempts, so the confirmation cannot choose its own words.

`POST /api/admin/operations/backups/key/confirmation` with `{"words": [{"position": 2, "word": "komora"}, …]}` (exactly three, each `position` 1–24 and `word` `@NotNull`, at most 40 characters) → `BackupKeyService.confirm(adminId, words)`: the positions must be the three asked at the administrator's last reveal and each word the key's word there, read as above; 400 `operations/backup-key-check-mismatch` otherwise (nothing stored, one attempt spent), 409 `operations/backup-key-confirmation-expired` without a reveal in the last 30 minutes, after the fifth wrong answer or after a restart (the page then hides the key and asks to show it again). A right answer ends the challenge. 200 with the `key` object as in `GET` and `AdminActionPerformed(adminId, "CONFIRM_BACKUP_KEY", empty, "Potvrzeno uložení klíče k zálohám", now)`. #### Logs

`operations/interfaces/rest/AdminLogsController` → `application/logs/LogReadingService` over the port `LogStore` (`infrastructure/logs/FileLogStore`, folder `app.operations.logs.directory`, `/logs` in production, the same folder the backend writes `backend.log` into; `build/cucumber/logs` in the acceptance tests). Claude reads the whole history of the logs and searches it through the API instead of the connector's own file access, so the rule "connector tokens open `/api/admin/**` only" also covers the logs.

`GET /api/admin/operations/logs` → `{"available": true, "files": [{"name": "backend.log", "sizeBytes": 120, "changedAt": "2026-10-23T10:00:02Z", "compressed": false}, {"name": "backend.log.2026-10-22.0.gz", …, "compressed": true}]}`: every regular file of the folder whose name matches `LogFile.isValidName` (`[A-Za-z0-9][A-Za-z0-9._-]*`, at most 120 characters), sorted by name, `compressed` for `.gz`; `available` false with an empty list when the folder is not mounted.

`GET /api/admin/operations/logs/{name}?from=&bytes=` → a window of whole lines as `{"name", "sizeBytes", "from", "to", "hasOlder", "hasNewer", "text"}`. `sizeBytes` is the uncompressed size (the gzip trailer for `.gz`). Without `from` the window is the last `bytes` bytes (20 000 by default, 1–200 000, 400 `validation` outside); with `from` (≥ 0) it starts at the first line beginning at or after that offset and ends at the end of the line that holds `from + bytes`, so `from` and `to` are line boundaries and the next page is `from = to` (newer) or `bytes` ending at `from` (older): `hasOlder` says a line precedes `from`, `hasNewer` that one follows `to`. A line longer than 2 000 bytes is cut. `.gz` files are streamed from the start to the window (`GZIPInputStream`), so the oldest rotated file costs one decompression per page, which is fine for 10 MB files. 404 `operations/log-not-found` for a missing file or a name outside the pattern (a path can never be built), 409 `operations/logs-unavailable` when the folder is not mounted.

`GET /api/admin/operations/logs/{name}/search?pattern=&limit=&before=` → `{"name", "sizeBytes", "matches": [{"offset": 83, "line": "2026-10-23T10:00:02 INFO third line"}, …], "moreOlder": false, "scannedFrom": 0}`: the lines matching the Java regular expression `pattern` (case-insensitive, 1–200 characters; 400 `operations/invalid-log-pattern` when it does not compile), newest first, at most `limit` (50 by default, 1–200), only lines starting before `before` when given; `offset` is the line's start, so `GET …/{name}?from={offset}&bytes=…` shows its context; `moreOlder` says older matches exist and `scannedFrom` is then the offset of the oldest returned match, the `before` of the next page. The whole file is scanned line by line, nothing is indexed; a search that runs longer than five seconds (a pattern that backtracks) stops with 400 `operations/log-search-too-slow`. Only regular files are served: a symbolic link in the folder (one a container sharing `/logs` could plant towards `/proc/self/environ`) is never listed, found or opened (`NOFOLLOW_LINKS`).

Storage: table `operations_setting` (`name` varchar(64) primary key, `value` varchar(4000), `sealed`, `updated_at`) and the one-row `operations_setup` (`completed_at`), Liquibase `operations/002_store_settings.xml`. A secret is sealed with AES-256-GCM under `app.operations.settings.key` (`SETTINGS_KEY`, which the backend entrypoint generates once into `/secrets/settings-key`) and stored as `v1:<base64 nonce+ciphertext>`; no API ever returns it. With the `prod` profile (`app.operations.settings.from-database: true`) `infrastructure/settings/DatabaseSettingsEnvironmentPostProcessor` reads the table over JDBC before the context starts and adds it as the highest-priority property source `storedSettings` under the env names, so `${PUBLIC_URL:…}` placeholders and every `@ConfigurationProperties` record see the stored values exactly as they saw the env; it logs `Loaded N stored settings` (or that there are none yet) and warns about secrets the key cannot open (the administration shows them as unreadable). A secret the key cannot open is tried once more with the settings key carried in `operations_carried_settings_key` (one row: `wrapped` varchar(120) `v1:<base64 nonce+ciphertext>`, `stored_at`; changelog `operations/006_carry_settings_key.xml`), opened with a key derived by HKDF-SHA256 from `BACKUP_KEY`; after the start the backend seals such secrets again under its own key and keeps the row wrapping its current `SETTINGS_KEY`, so every backup carries the secrets readable with the backup key (Jakub 2026-10-29). A property set directly by its own name (tests) is not overridden. Saving restarts the backend: `ExitingApplicationRestarter` exits after the commit and Docker's `restart: unless-stopped` starts it again with the new values, so nothing reloads at runtime. Before anything is stored, `StartupBindingSettingsValidator` binds the candidate values to the same properties records the startup binds, so a value that would stop the backend is refused with 400 instead of a restart loop.

Validation answers 400 `operations/invalid-settings` with `errors[{field, code, message}]`: `field` is the setting name (empty for a failure of the whole set), `code` one of `required`, `too-long`, `invalid-text`, `placeholder` (a value containing `${`), `invalid-url`, `invalid-host`, `invalid-port`, `invalid-boolean`, `invalid-email`, `invalid-email-list`, `invalid-date`, `invalid-year`, `rejected-at-startup`, `backup-key` (a secret setting whose value starts with `AGE-SECRET-KEY-1`, in any case: a password manager that offers the saved backup key fills it into a password field), and `message` the localized sentence (`operations.settings.problem.*`). A secret given without a settings key answers 409 `operations/settings-key-missing`. An unknown name or a setting outside the endpoint's list answers 400 `validation`. An empty value removes the stored row, so the default from `application.yml` applies again.

**First setup** (public, `permitAll`, `SetupController` → `application/settings/SetupService`; 20 requests per 15 minutes per address for the three `POST`s and the upload, 429 `operations/rate-limited`):

- `POST /api/operations/setup/unlock` with `{ "code": "K7QM-2XPA-9TRD" }` → 204, or 403 `operations/setup-locked`. The body is streamed into `/restore/<UUIDv7>.upload` (`.part` first; nginx forwards it unbuffered with `client_max_body_size 4g` and 15-minute timeouts) and must start with `age-encryption.org/v1` (an encrypted backup) or `PGDMP` (an older plain custom-format dump) (400 `operations/not-a-backup`, nothing kept). An encrypted upload needs its key in the header `X-Nfnn-Backup-Key`, as `AGE-SECRET-KEY-1…` or as its 24 words (at most 600 characters, turned into the canonical form before it is written; the wizard converts words itself and sends the canonical form; 400 `operations/backup-key-required` without it, `operations/invalid-backup-key` for a malformed one); the key is written beside it as `/restore/<UUIDv7>.key` (mode 600) for the container, which copies it into its own memory-backed `/tmp`, decrypts with it and after a successful restore records its recipient in `/backups/status/adopted-key` and writes it as `/restore/backup-key.adopt`, which the backend entrypoint adopts as `/secrets/backup-key` at its next start only when the recipients match, so the new server keeps encrypting with the key the operator already holds and stay within `app.operations.backups.max-upload-size` (4 GB; 400 `operations/backup-too-large`, the part deleted); then a `source=upload` restore request is written and the backend restarts as above (no audit row: no administrator exists yet; the restored history and administrators come with the dump). A restore already pending answers 409 `operations/restore-pending`. The container deletes the upload and its key after the restore and any upload or key older than an hour. Not transactional on purpose: the stream can take minutes.

### `contact` — contact form

Implemented.

| Method | Path | Auth | Purpose |
|---|---|---|---|
| `POST` | `/api/contact/messages` | public | Send a message; backend stores it and emails it asynchronously after commit. 202. |

Request:
```json
{ "fullName": "...", "email": "...", "message": "...", "website": "" }
```

- `fullName` `@NotBlank @Size(max=120)`, `email` `@NotBlank @Email(regexp = EmailAddress.SHAPE_REGEX) @Size(max=254)` (so an address without a dot in its domain, such as `jana@example`, answers 400 `validation` with one `errors[]` entry for `email`, as the other address fields do, and never reaches the `EmailAddress` value object's generic refusal; its message is `contact.message.email.invalid`, "Zadejte e-mail ve tvaru jmeno@domena.cz.", for every malformed address, because the form shows it at the field), `message` `@NotBlank @Size(max=5000)`. There is no subject field: the prototype's form has none, and the email subject is built from the sender's name.
- `website` is a honeypot — must be empty. If non-empty, return 202 but store and send nothing.
- Rate limit: 5/hour per client address (fixed window, Caffeine-backed, in-memory). The 6th request answers 429 with type `contact/rate-limited`. The client address is `getRemoteAddr()` after `ForwardedHeaderFilter`, so behind the nginx in `frontend/` it is the visitor's address from `X-Forwarded-For`; that nginx resolves the visitor's address itself and rewrites the header, so a client cannot choose it (see "Password reset").
- The forwarded email goes to `app.contact.recipient-email` (`CONTACT_RECIPIENT`) from `app.mail.sender-email` (`MAIL_FROM`, defaults to the recipient; `shared/infrastructure/mail/MailSenderProperties`, shared with the password reset e-mail) with `Reply-To` set to the visitor, body from `templates/email/contact/message-received.html`.
- Retention: the privacy policy promises that a message stays in the web database for a year. Every day at 03:30 Prague time `infrastructure/retention/ContactMessageRetentionScheduler` runs `application/ContactMessageRetentionService.deleteExpiredMessages`, which deletes the `contact_message` rows whose `received_at` lies before now (the application `Clock`) minus `retention.max-age`, in one `DELETE` statement (`ContactMessageRepository.deleteReceivedBefore`) served by the index `ix_contact_message_received_at`. A message therefore goes at the first run after it turns 365 days old, at most a day later. The run logs the count and the cutoff at INFO when it deleted something, never a message's content or sender; a failure is one ERROR line with the exception class, and the next day's run tries again. The copy forwarded by e-mail lives in the foundation's mailbox, which the application cannot reach; the daily `pg_dump` backups keep a deleted row until they are themselves deleted after about 30 days (`deploy/compose.yml`).

## Cross-context events

Events consumed by another context live in `shared/application/event/` and carry only shared types and JDK types; events consumed inside their own context stay in `<context>/application/event/`. All are immutable Java `record`s published from application services through `ApplicationEventPublisher`; they never carry JPA entities, only IDs and value objects. Three kinds of listener:

- Side-effect listeners (mail) run `@Async @TransactionalEventListener(phase = AFTER_COMMIT)`, off the request thread.
- A projection another context's correctness depends on runs `BEFORE_COMMIT` in the publisher's transaction, so the source row and the projection commit together or neither does.
- Follow-up work on that projection runs synchronously `AFTER_COMMIT` in its own `REQUIRES_NEW` transaction and must only log on failure, never fail the request.

|---|---|---|---|
| `DonorRegistered` | `donors/application` (`DonorEmailVerificationService.confirm`, once the e-mail is confirmed; never for an unconfirmed registration) | `donations/infrastructure/events/DonorRecordSynchronizer`, `BEFORE_COMMIT` | `DonorRecordService.register`: copies the donor into `donor_record` in the confirmation transaction (an upsert, so a replayed event changes nothing). ## UX notes affecting the API

- **Language switcher in nav.** For unauthenticated visitors it switches the UI locale only (cookie or `localStorage`). For authenticated donors it persists `preferredLocale` via `PATCH /api/donors/me` so receipts issued from then on come out in the chosen language (an issued receipt keeps its language).
- **Password rules.** Frontend shows the 12-character minimum and disallow-list hint inline; backend is the source of truth for validation.
- **Refresh on 401.** Angular HTTP interceptor catches 401 with `type` `auth/expired-token`, calls `POST /api/donors/auth/refresh` with `withCredentials: true`, retries the original request. On a second 401 the session ends: the donor is sent home and the sign-in dialog opens (`donorGuard` and the dashboard); there is no sign-in page.

## Decisions made (recap)

| Topic | Decision |
|---|---|
| Admin auth | Role on `Donor`, no separate context. The administration is reachable from the internet; `ADMIN` is in the JWT only for a session opened with the TOTP second factor (Jakub, 22 October 2026). The role is granted and taken away in the administration (`/sprava/spravci`), the first administrator comes from `ADMIN_EMAILS`; nothing is administered by SQL (Jakub, 22 October 2026). No recovery codes: a lost authenticator is turned off by another administrator in the administration, with an e-mail to the donor. |
| Passkeys | Optional WebAuthn passkeys beside the password; a passkey sign-in counts as the second factor, so it opens the administration too (Jakub, 23 October 2026). Discoverable keys with user verification, no attestation, at most 10 per donor; an administrator removes a lost device's keys in `/sprava/darci`. |
| Refresh token transport | HttpOnly Secure SameSite=Strict cookie, path `/api/donors/auth` (sent to refresh and logout). |
| Money | `amountMinor` + `currency`, `Money` value object in `shared`. |
| ID format | UUIDv7 string. |
| Public content URLs | By `slug`. |
| Home content storage | Static sections in component markup, news and projects in the database. |
| CMS i18n | Czech only for now; structure ready (`Accept-Language`) for adding `content_translation` table later. |
| Images | Site images in `frontend/public/`; photos uploaded by administrators are stored as WebP variants in `content_media_variant` and served at `/api/content/media/{id}`. |
| Donation statuses | `RECEIVED`, `REFUNDED`. |
| Bank reconciliation | Random 10-digit variable symbol per donor; hourly Fio API import pairs by symbol, then by learned sender account for payments without a symbol, then by an older symbol the donor confirmed for that account; no CSV import. |
| Older variable symbol | A payment with a symbol no registered donor has pairs only through the donor's confirmed answer, never merely because the donor verified the account. The bank accounts card asks after a one-koruna verification, when exactly one such symbol came from the account up to that day; the question is derived and only the answer is stored, and the donor cannot change it. On from the merge, with no switch (Jakub, 22 October 2026, variant a′). |
| Yearly receipt edge cases | 404 for a completed year without donations, 400 while the year is not completed (Prague calendar). |
| First receipt year | Receipts only for donations received from 1 January 2026 (`RECEIPT_FIRST_YEAR`); older donations are listed without a PDF and both receipt endpoints answer 400 `receipt-before-first-year` (Jakub, 22 October 2026). |
| Receipt of someone else's donation | 404 `donation-not-found`, not 403: no existence leak. |
| Receipts | Frozen documents: the first download issues, numbers (`YYYY-NNNNNN`) and stores the template and data it rendered; changed certified data issues a replacement with a new number that names the replaced one. Language: the donor's preference at issue, `en` bilingual. |
| Rate limiting | Own `FixedWindowRateLimiter` over Caffeine, in memory, per client address (`ClientAddressKey`: IPv6 by its /64), at most 50 000 keys per limiter by default, 1 000 for the administrator-only backup key limiter (`shared/infrastructure`). |
| Antispam (contact) | Honeypot + rate limit. No captcha until needed. |
| PDF preview | None: the dashboard downloads the file. |
| CORS | Not configured (same-origin in prod, dev proxy in dev). |
