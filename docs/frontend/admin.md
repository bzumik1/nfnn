Since 2.20c the settings page (`/sprava/nastaveni`, where "Uložit svou verzi" opens the restart confirmation again instead of saving at once, since a save restarts the site) and Lidé fondu (the founders' note and the line under the board, each with its own version; the order's answer moves a text's version forward only while its form is untouched) use the same sheet, and the donor's profile card shows the refusal inline instead (`.profile-changed`): the form takes at once every field the donor did not touch from the refusal's `current` and keeps the touched ones, the callout names a field both sides changed, and it offers "Uložit své úpravy" (the merged form with the refusal's version; the form's own save button is hidden meanwhile) or "Zahodit své úpravy a načíst uložené údaje"; "Zrušit" after a refusal reloads the stored profile when online. An edit keeps the id of the donor it started for and closes unsaved when the tab switches account, so one account's typed data never go to another; an edit started from the device copy, whose profile has no version and a placeholder language, first reads the stored profile and merges onto it the same way, so it never sends an empty `If-Match`. A version is not stable across releases, so `core/version/held-record-retry.ts` (`heldRecordRetryInterceptor`, before `authInterceptor`) resends a refused write once with the refusal's version when the request carries the record the page held (`ifMatch(version, held)`, an `HttpContext` value) and the two records are equal key for key (key order ignored; a key on one side only counts as a difference unless it is `version`, `createdAt`, `updatedAt` or named by the request as allowed to differ, as `sentReports` of the report settings; at least one compared key besides `id`). The held records follow the backend's `current` shapes (`storedSymbolClaimOf`, `storedPageTextOf`, `storedProfileOf`, `storedNewsArticleOf`, `storedProjectOf`): `core/version/stored-records.json` lists their keys, `scripts/stored-records.test.mjs` (in `npm run lint`) checks the list against the Java records and `held-records.spec.ts` each caller's held keys against the list, so a new backend column fails first: the record only looks changed because its hash changed with a deploy. A page passes a held record only while the version it sends is the one it last received with that record, never for a draft started from an older version or for "Uložit svou verzi", so the retry never bypasses a real conflict; the payments, the account links and the settings pass none, because what they hold is not the refusal's row shape.
