- `core/connectivity/` (plan v3 2.7): `Connectivity` (root, started by `connectivityAtStart` in `app.config.ts`) decides from what the API answers whether the app is offline; the one exception is the browser saying it is offline (`navigator.onLine` false at the start or its `offline` event), which is trusted at once, because a phone in airplane mode leaves requests hanging instead of failing them (Jakub 2026-11-06), and the probe that starts with it brings the app back online if the server answers; `navigator.onLine` true says nothing. `connectivityInterceptor` (the last interceptor) reports every `/api` outcome: an answer of the server (any status, or a gateway status with an `application/problem+json` body) counts as reached, while status 0 and 502, 503, 504 or 520–530 without a problem body (`isUnreachable`) count as failed; after a failure it probes at once and goes offline after 3 s (`OFFLINE_AFTER_MS`) without a success, then probes every 30 s (`PROBE_EVERY_MS`) while the tab is visible, at the window's `online` event and when the tab becomes visible again; the window's `offline` event and an answer the service worker served from its cache (`mayComeFromServiceWorker`, with a `Date` more than 15 s older than the server's clock, which it learns from network answers) only start a probe; a fresher one counts as contact while the app is online, but once it is offline it too only starts a probe, since a copy kept seconds ago reached no server. The probe (`connectivity-probe-api.ts`) is `GET /api/operations/setup` without the token, so it bypasses the service worker, with a 5 s timeout (`PROBE_TIMEOUT_MS`), after which the app is offline at once (cause `network`), without the 3 s wait a failed request starts; a probe's 5 s or a failure's 3 s that run out more than 1 s late (`SLEEP_TOLERANCE_MS`, measured with `Date.now()`) mean the device slept meanwhile (a locked iPhone or the app in the background freezes its timers, which then fire at once on waking), so the app asks the server once more instead of going offline (Jakub 2026-11-12: the label showed "Offline" after the phone woke up while the server answered in milliseconds); `wentOffline` emits each time the app goes offline. `cause` is `network` for status 0, a 504 of the worker or a browser that says offline, else `server`; `tryAgain()` probes on request. `kept-answer-refresh.ts` (`keptAnswerRefreshInterceptor`, before `serviceWorkerBypassInterceptor`): for the home content, the news and project lists and pages: while the app is offline and no service worker controls the page (so nothing can answer), an answer that does not come within 1.5 s (`OFFLINE_ANSWER_WAIT_MS`) fails as offline (status 0); with a worker in control the wait is the worker's own, which answers from its copy or gives up within 5 s, so a slow start of the worker on an old phone fails nothing it kept, so the page says it could not load and offers to try again instead of waiting; and only a request that asks for it (`REFRESH_AFTER_KEPT_COPY` through `refreshedAfterKeptCopy()`: `HomeApi.load`, both `publishedBySlug` and `NewsApi.publishedWithLatest` of the Aktuality list), answered with a copy whose `Date` is more than 15 s older than the server's clock while the app is not offline, gets the copy at once and the same request once more past the worker (`ngsw-bypass`), whose answer reaches the page as a second value only when its body differs and which gives up after 5 s (`REFRESH_WAIT_MS`);
