# Security overview

How the site is secured today. The rules a change must keep are in `.claude/rules/security.md`; this file is the mechanism behind them and changes in the same PR as the code. Endpoint shapes and problem codes are in `docs/api-contract.md`.

Threat model: a public site (the repository is public since 2026-10-22) whose donor accounts yield tax receipts in the donor's name, with an administration reachable from the browser and from connected AI clients. Attacks to prevent: reading another donor's gifts, a receipt in another name, administrator takeover, abuse of e-mail sending, exhausting the server.

## Donor authentication

- Passwords: 12–128 characters, refused (`RawPassword`) when it is one of the 10,000 most common passwords of 12 characters or more (SecLists, MIT; `donors/domain/common-passwords.txt`, compared in lower case); stored as BCrypt (cost 12) over the password's SHA-256 hex digest (`BCryptPasswordHasher`), so all 128 characters count. A sign-in with an unknown e-mail, or with a password on an account that has none, costs a real BCrypt compare against `UNKNOWN_DONOR_HASH` and answers `auth/invalid-credentials`.
- Tokens: access token HS256 JWT, 15 min, kept in memory only; refresh token 14 days in an HttpOnly Secure SameSite=Strict cookie on `/api/donors/auth`, stored hashed, rotated on use (`used_at`), and a replayed one revokes every session of the donor (`revoked_at`).
- Password reset: a 43-character secret in the URL fragment only, stored as SHA-256, single use, 1 h, at most 3 live per donor; confirming it revokes all sessions.
- E-mail verification: the same kind of link, 24 h. An unconfirmed account cannot sign in (401 `auth/email-not-verified` only with the right password), has no `donor_record` and gets no reset link. Registration always answers 202, so no address can be enumerated.
- Changes while signed in: the password and the e-mail change only with the current password; a new address must be confirmed by the same kind of link, the old address is told, and both changes revoke every other session.

## Second factor (TOTP)

`donors/domain/{SecondFactor,Totp}`, RFC 6238. Any donor may turn it on (password → secret and QR, the first code confirms; password + code turns it off; both revoke every other session); an administrator must. With it on, the right password answers 401 `auth/second-factor-required` with a stored challenge (hash only, 5 min, 5 wrong codes, once) and `/login/second-factor` completes it; a code counts once per 30-second step (`last_used_step`). The TOTP secret is stored in plain text because the server needs it, so a database leak needs the password too. There are no recovery codes: a lost authenticator is turned off by another administrator (`POST /api/admin/donors/{id}/second-factor/reset`: factor deleted, every session ended, audited, e-mail to the donor) or by the donor's own payment (Jakub 2026-10-23, contract "Recovery by payment"): after the right password the code step opens a recovery whose one-time code (`OBNOVA` + 8 characters, 40 bits, SHA-256 only, 14 days, single use, a new one replaces the open one) must arrive as the message of exactly 1 Kč from a sender account that is not excluded, linked to that donor alone and proven at least 7 days before the booking day. So an attacker needs the password and the donor's own bank account for a week, which is more than the reset e-mail (refused to an administrator) gives. The start checks the sign-in challenge without spending an attempt, counts against `SecondFactorRateLimiter` before any work and never names the donor's accounts, only the earliest day. Success revokes every session and e-mails the donor; for an administrator it is audited as `RECOVER_SECOND_FACTOR` and every other administrator is e-mailed.

## Passkeys (WebAuthn)

Jakub 2026-10-23. `donors/{domain,application}/…Passkey…`, webauthn4j only in `donors/infrastructure/webauthn`. Optional beside the password; adding one needs the current password and e-mails the donor. Discoverable credentials with user verification required, attestation `none`, RP id = host of `PUBLIC_URL`, expected origin = `PUBLIC_URL`; each key stores the RP id it was made for (`donor_passkey.relying_party_id`), and at every start `PasskeySiteCleanupService` first marks the keys stored without one (written before the column) with the current RP id and then deletes the keys of any other RP id, so the staging keys go at the switch to nfnn.cz (they could never verify there anyway) without SQL. Challenges stored as SHA-256, 5 min, once, marked used before any check; the signature counter must grow when kept. A passkey sign-in opens a session with `second_factor_verified` (it counts as the second factor, so an administrator gets `ADMIN`); every sign-in failure is the same 401 `auth/invalid-passkey`; an erased or unconfirmed account cannot sign in with one. An administrator who holds a second factor (the code or a passkey) adds or removes a passkey and sets up the code only from a session opened with it (403 `donors/second-factor-session-required`), so a password reset through a stolen mailbox cannot enrol the attacker's factor. A lost device is handled by an administrator (`DELETE /api/admin/donors/{id}/passkeys`: keys deleted, every session ended, audited, e-mail to the donor; web only, no MCP tool).

Accounts without a password (Jakub 2026-10-23): `password_hash` may be null. Every change that needs the current password accepts instead a passkey assertion of the donor's own key over a fresh sign-in challenge (marked used before any check, `DonorConfirmations`); only the first key of an account with neither password nor key goes without confirmation; the last way in (the last key without a password, the password without a key) cannot be removed. Recovery from the reset link adds a passkey only with the TOTP code when the factor is on, spends the link, ends every session and e-mails the donor, and is refused to an administrator (another administrator helps).

## Authorization and the administrator role

- Everything under `/api` requires the donor JWT unless listed `permitAll` in `ApiSecurityConfiguration`; resources are found by the JWT subject; another donor's resource answers 404, never 403.
- Role `ADMIN` gates `/api/admin/**` (`hasRole`, 403 `auth/forbidden`). It is granted and taken away by another administrator under `/api/admin/donors/administrators`, never by oneself, and only to an account with a confirmed e-mail (`Donor.grantAdministration`, 409 `donors/administrator-email-not-confirmed`), so an account someone registered with another person's address and their own password never holds the role; the first one comes from `ADMIN_EMAILS` in the first setup, and only while the site has no administrator, so a restart never returns a removed role; nothing by SQL (Jakub 2026-10-22). The role travels in the JWT, so it applies from the next sign-in or refresh. `ADMIN` enters the JWT only for a session opened with the second factor (`Donor.sessionRoles`, `donor_refresh_token.second_factor_verified`), so without it an administrator is a plain donor. Taking the role away also ends every session of the donor; access tokens already issued (at most 15 minutes, including the API token the connector caches) keep the role until they expire.
- Every administrator's change publishes `AdminActionPerformed`, so `admin_action` records who did what, when, and through which connected application (`admin_action.client`).

## Connected applications (OAuth 2.1 for the MCP connector)

`donors/{domain,application}/…OAuth…`, `AuthorizationServerService`.

- Clients only by Client ID Metadata Documents over `https`: no manual registration, every resolved address checked against the non-public IPv4 and IPv6 ranges (`PublicAddresses`: private, loopback, link-local, shared, reserved, multicast, documentation, ULA, NAT64, 6to4, Teredo), 5 s for the whole exchange including the body, 16 kB, no redirects, outside any database transaction; describing a client and approving it share a limit of 20 per 15 minutes per address because each fetches the document. PKCE S256 required; the redirect must be listed in the document (loopback on any port only for a loopback-registered client); the resource must be `{public-url}/mcp`.
- Only an administrator's session opened with the second factor may approve, and every approval carries a fresh second factor besides (Jakub 2026-10-23): `secondFactorCode` (checked by `FreshSecondFactorCheck` with the replay guard of the sign-in, so the code the session was opened with is refused; 400 `donors/second-factor-code-rejected`, limited by `SecondFactorRateLimiter` like the sign-in code) or `passkey`, an assertion over a fresh sign-in challenge by one of the administrator's own keys (`DonorConfirmations`, 400 `donors/passkey-confirmation-rejected`); without either 400 `donors/fresh-second-factor-required`. A stolen session token alone therefore cannot connect an application. The check runs after the request is validated, so an invalid request spends no code. The consent page grants `admin:write` only when the administrator ticks it (reading only by default); the connector's 401 challenge asks for both scopes but requires only `admin:read`. The code is single-use (spent by one conditional update before any check), five minutes, hashed.
- The client's access token carries `aud` `{public-url}/mcp`, so it cannot be used at `/api` as it is; the API accepts only `aud` `{public-url}/api`. It is swapped for an API token only by token exchange (RFC 8693) and only for that resource. The token endpoint is public, so whoever holds a connector token can exchange it: the boundary is the scope plus the browser-session guard below, not the audience.
- The client's refresh token is a `donor_refresh_token` row tied to its client, rotated; a replay ends every session of the donor; a removed administrator cannot refresh. The administrator can revoke a connection in the account card; its access tokens already issued stay valid until they expire (at most 15 minutes).
- Scopes `admin:read` and `admin:write` travel in the JWT `scope` claim and the client's host in its `client` claim (carried over by the token exchange, recorded in `admin_action.client`). A change under `/api/admin/**` needs `admin:write` (`AdminWriteAuthorizationManager`; browser tokens have no claim).
- Browser-session guard: a token with a `scope` claim opens `/api/admin/**` only. Every other path (the administrator's own account, `POST /api/donors/oauth/authorize`), the backup download `GET /api/admin/operations/backups/*` and the restore `POST /api/admin/operations/backups/*/restore` accept only a token without the claim (`BrowserSessionAuthorizationManager`, 403), so a connection can never approve a wider connection for itself or export the database (security review 2026-10-23). By decision (Jakub 2026-10-23) the other dangerous or irreversible administration actions are web-only too: deleting news, projects or account links, reversing or deleting an older-symbol answer, granting or taking away the administrator role, resetting a second factor or passkeys, GDPR erasure, uploading or removing the receipt signature (the mark on tax receipts in the foundation's name; the connector only reads whether one is set). `ApiSecurityConfiguration` enforces the browser session for all of them (`BROWSER_ONLY_DELETES`, `BROWSER_ONLY_POSTS`, matched before the generic `/api/admin/**` rules; security audit 2026-10-23), and a scenario outline in `connected_apps.feature` sends each with an exchanged `admin:write` token and expects 403. `AdminSettingsController` refuses the secrets and `PUBLIC_URL` to a token with a `scope` claim.

## MCP connector (`mcp/`, container `nfnn-mcp`)

- A resource server only. It holds no secret and reads no env file; it learns the issuer from the backend's metadata and verifies a bearer token solely by exchanging it at the backend's token endpoint, so a forged, expired or API token is refused by the backend and the connector never validates a signature itself.
- Every tool call reaches `/api/admin/**` with the exchanged API token (`aud` `/api`, the connection's `scope`, the administrator's roles), so authorization, auditing, rate limits and the `admin:write` rule stay the backend's. A writing tool without `admin:write` changes nothing and answers a tool error telling the administrator to reconnect with „Změny“.
- The frontend nginx limits `/mcp` to 10 requests/s per address (burst 20); the container publishes no port. The token exchange carries the visitor's address (nginx's `X-Real-IP`, as `X-Forwarded-For`), so the token endpoint's limit counts per visitor.
- It has a tool for every setting and all data of the administration but none for what is dangerous or irreversible (Jakub 2026-10-23, list above).
- Logs: the connector reads no file itself and writes only its own `/logs/mcp.log` (the same ids and outcomes as its console; every request with its JSON-RPC method and tool name, never the arguments). The log tools call `GET /api/admin/operations/logs…`; the backend serves only files of its own `/logs` folder with safe names (`[A-Za-z0-9][A-Za-z0-9._-]*`, so no path), windows of at most 200 kB and at most 200 search matches. A log level raised through `PUT /api/admin/operations/loggers/{logger}` is audited, lasts at most 24 h and never survives a restart (which loggers may be raised: Logs below). The backend opens log files without following links (`NOFOLLOW_LINKS`), so a link planted in the shared folder never leads elsewhere, and a search gives up after 5 s. The thread dump names code, never a donor. A new tool that would reveal names or addresses beyond what the API already returns to an administrator is a security change.
- Photos (Jakub 2026-10-23) are the connector's only outbound requests and its only way in besides `/mcp`. `nfnn_upload_photo` downloads `https` addresses only and refuses every private, loopback, link-local, shared, reserved, IPv4-mapped and NAT64 address after resolving the name itself (an IP literal too, a fresh connection each time, at most 3 redirects with the same checks, 15 s, 10 MB, `image/*` or `application/octet-stream`), so it cannot reach the backend, the database, the server or the LAN. `PUT /mcp-photos` (nginx: the `/mcp` rate limit, 11 MB) takes a body only with a ticket from `nfnn_photo_upload_link` (an `admin:write` tool): 32 random bytes held in memory as SHA-256 with the administrator's API token, single use, at most 10 minutes and never past that token, at most 100 live. Either way the bytes go to `POST /api/admin/content/media`, which validates and re-encodes them. A photo address is never logged.

## Abuse limits

Per client address, answered 429 before any work: contact 5/h, sign-in 10/15 min, registration 5/h, reset request 5/h, verification request 5/h, password change 10/15 min, e-mail change request 5/h, second-factor codes at sign-in 10/15 min (the passkey options of the reset-link recovery and the start of a recovery by payment share this bucket), second-factor set-up/confirm/disable together 10/15 min, OAuth token endpoint 30/15 min, OAuth client description and approval together 20/15 min, passkey sign-in (options and answers) 20/15 min, passkey creation options 10/15 min, first setup 20/15 min; bank check 30 s global. The per-address limits are built on `FixedWindowRateLimiter`; the bank check is a global cooldown (`on-demand-cooldown`).

The address is the request's remote address after the frontend nginx resolved the visitor: `set_real_ip_from` the private ranges, client values overwritten, `X-Forwarded-For $remote_addr` sent and `Forwarded` emptied. The backend trusts forwarded headers from any peer (`server.forward-headers-strategy: framework`), which is safe only because nothing but the frontend nginx and the connector reaches port 8080: that port is never published, and the containers sit on their own networks, `nfnn-edge` (frontend, backend, connector) and `nfnn-internal` (`internal: true`, no way out: postgres, backup, backend), never on the default bridge every other app on the server shares; every service runs with `no-new-privileges`, a read-only root file system (`tmpfs` where it writes) and `cap_drop: ALL` plus only the capabilities its entrypoint needs (`deploy-ci.md`, Hardening), so a hole in an image has no raw sockets, no device nodes and no way to change files outside its volumes. The backend logs in to PostgreSQL as `novanadeje_app`, an ordinary role (no superuser, no role or database creation, member of no role) that owns the site's database and tables: an SQL injection could read and change the site's data but not run programs or read files on the database server (`COPY … PROGRAM`, `pg_read_server_files`), not touch other databases and not create roles. The superuser `novanadeje` is used only inside the database container and by the backup container (dumps, test restores, the restore swap).

## Secrets

- On the server there is no env file. `db-password` (superuser), `db-app-password` (`novanadeje_app`), `jwt-secret` and `settings-key` are generated once into `/DATA/AppData/nfnn/secrets/` (root, mode 600); the last three reach Java only through the backend's entrypoint, and `db-password` never reaches the backend at all (which starts as root for that, for `/restore` and for the log folder, then drops to `app` with `setpriv`).
- The SMTP password and the Fio token are settings stored sealed with AES-GCM under `settings-key` (`operations_setting`, `v1:` prefix). They are never returned by any API (the administration sees only set / not set / unreadable), the SMTP password goes only to the server it was saved for (moving `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME` or `MAIL_STARTTLS` needs the password in the same change, 400 `password-for-new-mail-server`; the mail test uses the stored one only against the running server), SMTP requires STARTTLS whenever it is on, and every SMTP wait times out after 10 s. They are never logged (audit and logs name the setting only), and changed only in the browser: a token with a `scope` claim is refused for a secret with 403, and the MCP tools have no secret in their schema.
- Locally only `.env`. `JWT_SECRET` and `SETTINGS_KEY` have defaults only in `application-dev.yml`. Records that carry a token or secret mask it in `toString` (token records, `TokenResponse`, `AuthResponse`, `SecondFactorEnrolment` and its response, `CodeExchange`, `JwtProperties`).
- The PR check fails when `deploy/compose.yml` names one of `POSTGRES_PASSWORD`, `PGPASSWORD`, `DB_PASSWORD`, `JWT_SECRET`, `SETTINGS_KEY`, `MAIL_PASSWORD`, `FIO_TOKEN`, when a service reads an env file, when `secrets/` is mounted beyond postgres, backend and (read-only) backup, or when `JWT_SECRET`, `SETTINGS_KEY`, `DB_PASSWORD`, `FIO_TOKEN` or `MAIL_PASSWORD` reaches the database, backup, connector or frontend containers, in their configuration or their main process's environment (`deploy-ci.md`).

## Logs

Every log carries ids and outcomes only, never names, e-mails, addresses, query strings, tokens or message bodies, at any level an administrator can set: the loggers that would write SQL values, Hibernate's entity listing, request and response bodies, raw requests with their headers, JDBC driver or mail traffic (`ProtectedLoggers`: `org.hibernate.orm.jdbc.bind`, `org.hibernate.orm.jdbc.extract`, `org.hibernate.internal.util.EntityPrinter`, `org.springframework.web.servlet.mvc.method.annotation`, `org.springframework.web.client`, `org.apache.coyote`, `org.apache.tomcat.util.http`, `org.postgresql`, `jakarta.mail`) are pinned at INFO in `application.yml` and refused (400 `operations/protected-logger`), so raising `ROOT` never reaches them, and TRACE is refused for every logger outside `cz.novanadeje.app`. Production logs (`/DATA/AppData/nfnn/logs/`) are readable from outside the server only through `/api/admin/operations/logs…` (an administrator's session or connector token; no container serves the folder itself). The frontend nginx writes `nginx-access.log` in the `anonymous` format, without the client address and the query string (searches and OAuth parameters travel in it); its console uses the same format, and nginx empties `X-Forwarded-Host`, `-Port`, `-Prefix` and `-Ssl` before proxying. A failed contact-form mail is logged with the message id and the exception class only.

## First setup

`/api/operations/setup` is public until completed, then 409. It opens without a code only for a request that came straight from the home network (the frontend nginx's `X-Nfnn-Direct` when no forwarding header arrived, plus a private client address at the backend); every other request needs the 12-character code the backend prints at each start to its standard output only (never `backend.log` or the log API); 20 requests per 15 min per address; values are validated against the startup binding before they are stored. Until the setup is done anyone in the home network could fill it in, which is accepted (Jakub 2026-10-23); afterwards settings change only through `/api/admin/**`.

The same unlock opens `PUT /api/operations/setup/restore`, which replaces the empty database with an uploaded dump (must start with `PGDMP`, at most 4 GB, streamed into `/restore`, never parsed by the backend). `pg_restore` runs it as `novanadeje`, the superuser of the postgres image, so a crafted dump can run arbitrary SQL inside PostgreSQL: accepted for the same reason (only while the setup is open, only from the home network or with the code, and the database is empty then). A restore never carries `secrets/settings-key`, so sealed secrets of another server stay unreadable and must be typed again.

## Browser and transport

TLS ends at Nginx Proxy Manager (Cloudflare in front later: in the same change Nginx Proxy Manager must pass the visitor from `CF-Connecting-IP`, `deploy/README.md`, else every limit applies per Cloudflare edge). The frontend nginx adds `nosniff`, `X-Frame-Options SAMEORIGIN`, `Referrer-Policy`, `Permissions-Policy` and the Content-Security-Policy in `frontend/nginx-security-headers.conf`: `default-src 'self'`; scripts, fonts and connections only from the site; styles also `'unsafe-inline'` because Angular injects component styles; images also `data:` (the saved QR code is drawn through one); `object-src 'none'`; `base-uri`, `form-action` and `frame-ancestors` `'self'`. `inlineCritical` stays off in `angular.json` because its inline `onload` handler would be blocked. CORS stays unconfigured (same origin). XSS defence is the policy plus Angular's bindings and Thymeleaf `th:text`. The Markdown of news and project bodies (`shared/ui/markdown`) is parsed into a tree of plain values and rendered by the template's own elements and `{{ }}` bindings, never through `innerHTML`, so a tag in the text shows as text; a link is kept only for `http`, `https`, `mailto:` and site-relative addresses, so no `javascript:` address reaches an `href`.
