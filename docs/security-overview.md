# Security overview

How the site is secured today. The rules a change must keep are in `.claude/rules/security.md`; this file is the mechanism behind them and changes in the same PR as the code. Endpoint shapes and problem codes are in `docs/api-contract.md`.

Threat model: a public site (the repository is public since 2026-10-22) whose donor accounts yield tax receipts in the donor's name, with an administration reachable from the browser and from connected AI clients. Attacks to prevent: reading another donor's gifts, a receipt in another name, administrator takeover, abuse of e-mail sending, exhausting the server.

## Donor authentication

- Passwords: 12–128 characters, refused (`RawPassword`) when it is one of the 10,000 most common passwords of 12 characters or more (SecLists, MIT; `donors/domain/common-passwords.txt`, compared in lower case); stored as BCrypt (cost 12) over the password's SHA-256 hex digest (`BCryptPasswordHasher`), so all 128 characters count. A sign-in with an unknown e-mail, or with a password on an account that has none, costs a real BCrypt compare against `UNKNOWN_DONOR_HASH` and answers `auth/invalid-credentials`.
- Tokens: access token HS256 JWT, 15 min, kept in memory only; refresh token 14 days in an HttpOnly Secure SameSite=Strict cookie on `/api/donors/auth`, stored hashed, rotated on use (`used_at`), and a replayed one revokes every session of the donor (`revoked_at`).
- Password reset: a 43-character secret in the URL fragment only, stored as SHA-256, single use, 1 h, at most 3 live per donor; confirming it revokes all sessions.
- E-mail verification: the same kind of link, 24 h. An unconfirmed account cannot sign in (401 `auth/email-not-verified` only with the right password), has no `donor_record` and gets no reset link. Registration always answers 202, so no address can be enumerated. The optional `returnTo` of a registration or a new-link request (Jakub 2026-10-24) accepts only the paths of `RegistrationReturn` (`/#prispet`), so a registrant cannot place an address or text of their own into the foundation's e-mail; the page reads it from the fragment against its own list and navigates only inside the app, so it is no open redirect.
- Changes while signed in: the password and the e-mail change only with the current password; a new address must be confirmed by the same kind of link, the old address is told, and both changes revoke every other session. Only the newest change link works: a new request or "Poslat znovu" (`POST /api/donors/me/email-change/resend`, no password, because it repeats what the password allowed) deletes the earlier change links and stores a new random secret as SHA-256; "Zrušit" (`DELETE /api/donors/me/email-change`) deletes them. The pending address shows only to the donor who asked for it, and it is stored the same way whether or not another account has it, so the profile reveals nothing about other accounts.

## Second factor (TOTP)

`donors/domain/{SecondFactor,Totp}`, RFC 6238. Any donor may turn it on (password → secret and QR, the first code confirms; password + code turns it off; both revoke every other session and e-mail the owner, so a thief who holds the password and the code and turns the factor off, or enrols their own, is noticed at once); an administrator must. With it on, the right password answers 401 `auth/second-factor-required` with a stored challenge (hash only, 5 min, 5 wrong codes, once) and `/login/second-factor` completes it; a code counts once per 30-second step (`last_used_step`; the fresh check behind approving a connection and showing the backup key stores the step only by `update … where last_used_step < :step`, so two requests racing with one code cannot both pass, security review 2026-10-29). The TOTP secret is stored in plain text because the server needs it, so a database leak needs the password too. There are no recovery codes: a lost authenticator is turned off by another administrator (`POST /api/admin/donors/{id}/second-factor/reset`: factor deleted, every session ended, audited, e-mail to the donor) or by the donor's own payment (Jakub 2026-10-23, contract "Recovery by payment"): after the right password the code step opens a recovery whose one-time code (`OBNOVA` + 8 characters, 40 bits, found by its SHA-256, 14 days, single use; while it is open a new start returns the same code, Jakub 2026-10-24, so the code is kept beside its hash, which gives a database reader nothing the plain-text TOTP secret does not) must arrive as the message of exactly 1 Kč from a sender account that is not excluded, linked to that donor alone and proven at least 7 days before the booking day. So an attacker needs the password and the donor's own bank account for a week, which is more than the reset e-mail (refused to an administrator) gives. The start checks the sign-in challenge without spending an attempt, answers the payment's QR code itself (the public `payment-qr` endpoint takes no message, so it cannot be used to draw a QR code with a text of the caller's choosing), counts against `SecondFactorRateLimiter` before any work and never names the donor's accounts, only the earliest day. Success revokes every session and e-mails the donor; for an administrator it is audited as `RECOVER_SECOND_FACTOR` and every other administrator is e-mailed.

## Passkeys (WebAuthn)

Jakub 2026-10-23. `donors/{domain,application}/…Passkey…`, webauthn4j only in `donors/infrastructure/webauthn`. Optional beside the password; adding one needs the current password and e-mails the donor, and removing one e-mails the donor too. Discoverable credentials with user verification required, attestation `none`, RP id = host of `PUBLIC_URL`, expected origin = `PUBLIC_URL`; each key stores the RP id it was made for (`donor_passkey.relying_party_id`), and at every start `PasskeySiteCleanupService` first marks the keys stored without one (written before the column) with the current RP id and then deletes the keys of any other RP id, so the staging keys go at the switch to nfnn.cz (they could never verify there anyway) without SQL. Challenges stored as SHA-256, 5 min, once, marked used before any check; the signature counter must grow when kept. A passkey sign-in opens a session with `second_factor_verified` (it counts as the second factor, so an administrator gets `ADMIN`); every sign-in failure is the same 401 `auth/invalid-passkey`; an erased or unconfirmed account cannot sign in with one. An administrator who holds a second factor (the code or a passkey) adds or removes a passkey and sets up the code only from a session opened with it (403 `donors/second-factor-session-required`), so a password reset through a stolen mailbox cannot enrol the attacker's factor. A lost device is handled by an administrator (`DELETE /api/admin/donors/{id}/passkeys`: keys deleted, every session ended, audited, e-mail to the donor; web only, no MCP tool).

Accounts without a password (Jakub 2026-10-23): `password_hash` may be null. Every change that needs the current password accepts instead a passkey assertion of the donor's own key over a fresh sign-in challenge (marked used before any check, `DonorConfirmations`); only the first key of an account with neither password nor key goes without confirmation; the last way in (the last key without a password, the password without a key) cannot be removed. Recovery from the reset link adds a passkey only with the TOTP code when the factor is on, spends the link, ends every session and e-mails the donor, and is refused to an administrator (another administrator helps).

## Authorization and the administrator role

- Everything under `/api` requires the donor JWT unless listed `permitAll` in `ApiSecurityConfiguration`; resources are found by the JWT subject; another donor's resource answers 404, never 403.
- Role `ADMIN` gates `/api/admin/**` (`hasRole`, 403 `auth/forbidden`). It is granted and taken away by another administrator under `/api/admin/donors/administrators`, never by oneself, and only to an account with a confirmed e-mail (`Donor.grantAdministration`, 409 `donors/administrator-email-not-confirmed`), so an account someone registered with another person's address and their own password never holds the role; the first one comes from `ADMIN_EMAILS` in the first setup, and only while the site has no administrator, so a restart never returns a removed role; nothing by SQL (Jakub 2026-10-22). The role travels in the JWT, so it applies from the next sign-in or refresh. `ADMIN` enters the JWT only for a session opened with the second factor (`Donor.sessionRoles`, `donor_refresh_token.second_factor_verified`), so without it an administrator is a plain donor. Taking the role away also ends every session of the donor; access tokens already issued (at most 15 minutes, including the API token the connector caches) keep the role until they expire.
- Every administrator's change publishes `AdminActionPerformed`, so `admin_action` records who did what, when, and through which connected application (`admin_action.client`).
- Sign-ins to the administration (Jakub 2026-10-29): the last two times an administrator opened a session carrying `ADMIN` are kept on the `donor` row (`last_signed_in_at`, `previous_signed_in_at`) for the block "Od posledního přihlášení" on `/sprava`. `GET /api/admin/donors/me/previous-sign-in` answers only the caller's own (the id comes from the token's subject, never from the request), so no administrator reads another's; a connected application reads the one of the administrator who connected it, like any other read. Nothing is recorded for donors without the role and taking the role away clears both, so the privacy policy for donors is unchanged; the times carry no address or device. The logs say nothing new.

## Connected applications (OAuth 2.1 for the MCP connector)

`donors/{domain,application}/…OAuth…`, `AuthorizationServerService`.

- Clients only by Client ID Metadata Documents over `https`: no manual registration, every resolved address checked against the non-public IPv4 and IPv6 ranges (`PublicAddresses`: private, loopback, link-local, shared, reserved, multicast, documentation, ULA, NAT64, 6to4, Teredo), 5 s for the whole exchange including the body, 16 kB, no redirects, outside any database transaction; describing a client and approving it share a limit of 20 per 15 minutes per address because each fetches the document. PKCE S256 required; the redirect must be listed in the document (loopback on any port only for a loopback-registered client); the resource must be `{public-url}/mcp`.
- Only an administrator's session opened with the second factor may approve, and every approval carries a fresh second factor besides (Jakub 2026-10-23): `secondFactorCode` (checked by `FreshSecondFactorCheck` with the replay guard of the sign-in, so the code the session was opened with is refused; 400 `donors/second-factor-code-rejected`, limited by `SecondFactorRateLimiter` like the sign-in code) or `passkey`, an assertion over a fresh sign-in challenge by one of the administrator's own keys (`DonorConfirmations`, 400 `donors/passkey-confirmation-rejected`); without either 400 `donors/fresh-second-factor-required`. A stolen session token alone therefore cannot connect an application. The check runs after the request is validated, so an invalid request spends no code. The consent page grants `admin:write` only when the administrator ticks it (reading only by default); the connector's 401 challenge asks for both scopes but requires only `admin:read`. The code is single-use (spent by one conditional update before any check), five minutes, hashed.
- The client's access token carries `aud` `{public-url}/mcp`, so it cannot be used at `/api` as it is; the API accepts only `aud` `{public-url}/api`. It is swapped for an API token only by token exchange (RFC 8693) and only for that resource. The token endpoint is public, so whoever holds a connector token can exchange it: the boundary is the scope plus the browser-session guard below, not the audience.
- The client's refresh token is a `donor_refresh_token` row tied to its client, rotated; a replay ends every session of the donor; a removed administrator cannot refresh. The administrator can revoke a connection in the account card; its access tokens already issued stay valid until they expire (at most 15 minutes).
- Scopes `admin:read` and `admin:write` travel in the JWT `scope` claim and the client's host in its `client` claim (carried over by the token exchange, recorded in `admin_action.client`). A change under `/api/admin/**` needs `admin:write` (`AdminWriteAuthorizationManager`; browser tokens have no claim).
- Browser-session guard: a token with a `scope` claim opens `/api/admin/**` only. Every other path (the administrator's own account, `POST /api/donors/oauth/authorize`), the backup download `GET /api/admin/operations/backups/*` and the restore `POST /api/admin/operations/backups/*/restore` accept only a token without the claim (`BrowserSessionAuthorizationManager`, 403), so a connection can never approve a wider connection for itself or export the database (security review 2026-10-23). By decision (Jakub 2026-10-23) the other dangerous or irreversible administration actions are web-only too: deleting news, projects or account links, reversing or deleting an older-symbol answer, granting or taking away the administrator role, resetting a second factor or passkeys, GDPR erasure, uploading or removing the receipt signature (the mark on tax receipts in the foundation's name; the connector only reads whether one is set), and showing or confirming the backup key (Jakub 2026-10-28; the connector only reads whether it exists and was confirmed). `ApiSecurityConfiguration` enforces the browser session for all of them (`BROWSER_ONLY_DELETES`, `BROWSER_ONLY_POSTS`, matched before the generic `/api/admin/**` rules; security audit 2026-10-23), and a scenario outline in `connected_apps.feature` sends each with an exchanged `admin:write` token and expects 403. `AdminSettingsController` refuses the secrets and `PUBLIC_URL` to a token with a `scope` claim. Issuing a donor's first receipt (`POST /api/admin/donations/donors/{donorId}/receipts`, `nfnn_issue_receipt`, 1.7) is open to a connection with `admin:write` (A8), on these conditions: it goes through the donor's own issuer under the donor lock, so it is idempotent (unchanged data return the active receipt with its number and record nothing) and keeps one active receipt per donation and per donor and year (the partial unique indexes of `issued_receipt`); the donation must be the donor's named in the path (`findByIdAndDonorId`, 404 `donations/donation-not-found` otherwise, a scenario in `admin_receipts.feature`), and the name and address always come from that donor's own record, so no input names anyone else; an erased donor gets none (409 `donations/donor-erased`); every new number is audited as `ISSUE_RECEIPT` with the connection's `client`, inside the issuing transaction, so no receipt is issued unrecorded; the connector never gets a PDF. Replacing a receipt is web-only: a replacement cannot be undone (the receipt the donor holds stays REPLACED for good and its number is spent), and a connection can bring one about by itself, since pairing or unpairing a payment (`nfnn_pair_payment`, `nfnn_unpair_payment`) changes the gifts of a yearly receipt, so a stolen or misled connection could otherwise replace one receipt after another. So when the data changed since the active receipt, a token with a `scope` claim gets 403 `donations/receipt-replacement-in-browser-only`, decided under the donor lock before the cap is counted or a serial taken, and nothing is stored or audited; the controller tells the issuer which kind of token asks (`AdministrationChannel`), as `AdminSettingsController` checks the claim for secrets, and a scenario in `connected_apps.feature` proves it (the lead's decision for 1.7, open to Jakub). A browser administrator's replacements count against the donor's cap of 20 in 24 hours with the donor's own, and each is in the audit trail with the number it replaces. The reads (`GET /api/admin/donations/receipts`, `…/receipts/{id}`, `…/receipt-images/{sha256}`, `nfnn_receipts`, `nfnn_receipt`) need `admin:read` like every other read; the list carries no name or address; the detail carries the donor's name and address as the receipt states them. An erased donor's receipts stay as issued (A6), and a browser session reads them whole as the tax record they are, but a token with a `scope` claim gets them with the erased record's placeholders for the name, company identifier and address and without the QR text, which carries them, so the person's data never go to an AI client after the erasure (the controller checks the claim; scenario in `admin_receipts.feature`; the lead's decision for 1.7, open to Jakub). Every handler under `/api/admin/` is classified as connector-reachable or browser-only in `shared/infrastructure/security/AdminHandlerReach`, and `AdminHandlerClassificationTest` (1.7) reads every handler from `RequestMappingHandlerMapping` and fails on one the table does not name or a name no handler answers, asks the security chain for each with a browser token, a reading and a writing connection and fails when a decision differs from the class, and fails when the outline rows of `connected_apps.feature` are not exactly the browser-only handlers, so a new endpoint cannot reach a connection by omission. Two classes are connector-reachable with a refusal after the security chain, `CONNECTOR_SECRETS_IN_BROWSER_ONLY` (the settings) and `CONNECTOR_REPLACEMENTS_IN_BROWSER_ONLY` (issuing a receipt): the test checks them only as connector-reachable, since the security chain sees neither the request body nor the stored data; their refusals are proved by the scenarios of `settings.feature` (`operations/secret-settings-in-browser-only`) and `connected_apps.feature` (`donations/receipt-replacement-in-browser-only`). Classifying an item of the web-only list as connector-reachable is a security change that needs Jakub's OK. Setting and removing the photo of the About section (`PUT /api/admin/content/about`, `nfnn_update_about`, 2026-10-30) is not on the list: removing takes the photo off the site and deletes it, as replacing a cover photo with `nfnn_update_news` already does, and an administrator can upload it again; a guard on removal alone would control nothing, since any replacement deletes the old photo, and a quick takedown protects the child on the photo when consent is withdrawn (Jakub allowed it on 2026-10-30, the one exception to web-only deletions). Removing a person of the foundation (`DELETE /api/admin/content/people/{id}`, `nfnn_remove_person`) is a second exception, allowed by Jakub on 2026-10-30 (decision card in the Lidé fondu thread): the removal deletes the person's portrait, which `nfnn_update_person` could replace and so delete anyway, and their web signature. Setting and removing the web signature of a person of the foundation (`POST`/`DELETE /api/admin/content/people/*/web-signature`, `nfnn_set_web_signature`, `nfnn_remove_web_signature`) is the third, allowed by Jakub on 2026-10-30 ("Klidně ať to konektor umí, to není nebezpečné"): it is a separate public image shown under the founders' note, never the receipt signature, which stays web-only. Until then the web signature was browser-only and `AdminPeopleController` refused a connection renaming or removing a person who had one (403 `content/web-signature-in-browser-only`), so a connection could not relabel or delete a signature; with the signature itself open to a connection those checks protected nothing and are gone. `PeopleAdminService` still refuses an image as a portrait when it is anyone's web signature and as a web signature when it is anyone's portrait (400 `content/person-image-in-use`), so an image always keeps the one role it was uploaded for (security review of PR #241, 2026-10-30), and the connector's descriptions say that a signature, like a photo of a person, goes up only as a file through `nfnn_photo_upload_link`, never from a public address. The people's personal and fund e-mails (`content_person.personal_email`, `fund_email`, Jakub 2026-10-30) are stored for the administration only: the administration's answers and the connector's tools carry them, `GET /api/content/home` never does (a scenario checks the public answer for any address), and neither the audit details (the person's id only) nor any log line names them.

## MCP connector (`mcp/`, container `nfnn-mcp`)

- A resource server only. It holds no secret and reads no env file; it learns the issuer from the backend's metadata and verifies a bearer token solely by exchanging it at the backend's token endpoint, so a forged, expired or API token is refused by the backend and the connector never validates a signature itself.
- Every tool call reaches `/api/admin/**` with the exchanged API token (`aud` `/api`, the connection's `scope`, the administrator's roles), so authorization, auditing, rate limits and the `admin:write` rule stay the backend's. A writing tool without `admin:write` changes nothing and answers a tool error telling the administrator to reconnect with „Změny“.
- The frontend nginx limits `/mcp` to 10 requests/s per address (burst 20); the container publishes no port. The token exchange carries the visitor's address (nginx's `X-Real-IP`, as `X-Forwarded-For`), so the token endpoint's limit counts per visitor. The nginx limit counts by the full address, IPv6 included, on purpose: it is only a flood guard (a /64 map in nginx would break on compressed IPv6 notation), and the backend's limits behind it, `OAuthTokenRateLimiter` for the token exchange among them, still count per /64.
- It has a tool for every setting and all data of the administration but none for what is dangerous or irreversible (Jakub 2026-10-23, list above). `nfnn_receipts` lists issued receipts without names or addresses; `nfnn_receipt` and `nfnn_issue_receipt` (1.7) answer a receipt with the donor's name and address as the API returns them to a connection (an erased donor's without them and without the QR text), without the frozen texts, plus the QR text as `verificationLink`; no PDF. `nfnn_issue_receipt` issues only first receipts and has no `destructiveHint`, because the backend refuses it every replacement. `nfnn_since_last_sign_in` (2026-10-29) reveals only counts, totals and the connecting administrator's own previous sign-in, no name or address.
- Logs: the connector reads no file itself and writes only its own `/logs/mcp.log` (the same ids and outcomes as its console; every request with its JSON-RPC method and tool name, never the arguments). The log tools call `GET /api/admin/operations/logs…`; the backend serves only files of its own `/logs` folder with safe names (`[A-Za-z0-9][A-Za-z0-9._-]*`, so no path), windows of at most 200 kB and at most 200 search matches. A log level raised through `PUT /api/admin/operations/loggers/{logger}` is audited, lasts at most 24 h and never survives a restart (which loggers may be raised: Logs below). The backend opens log files without following links (`NOFOLLOW_LINKS`), so a link planted in the shared folder never leads elsewhere, and a search gives up after 5 s. The thread dump names code, never a donor. A new tool that would reveal names or addresses beyond what the API already returns to an administrator is a security change.
- Photos (Jakub 2026-10-23) are the connector's only outbound requests and its only way in besides `/mcp`. `nfnn_upload_photo` downloads `https` addresses only and refuses every private, loopback, link-local, shared, reserved, IPv4-mapped and NAT64 address after resolving the name itself (an IP literal too, a fresh connection each time, at most 3 redirects with the same checks, 15 s, 10 MB, `image/*` or `application/octet-stream`), so it cannot reach the backend, the database, the server or the LAN. `PUT /mcp-photos` (nginx: the `/mcp` rate limit, 11 MB) takes a body only with a ticket from `nfnn_photo_upload_link` (an `admin:write` tool): 32 random bytes held in memory as SHA-256 with the administrator's API token, single use, at most 10 minutes and never past that token, at most 100 live. Either way the bytes go to `POST /api/admin/content/media`, which validates and re-encodes them. A photo address is never logged.

## Business register lookup (ARES)

`donors/application/CompanyLookupService`, `donors/infrastructure/ares/AresCompanyRegistry` (Jakub 2026-10-24).

- The backend's third outbound call, after the Fio API and the client metadata documents. The browser never calls ARES (the Content-Security-Policy stays as it is); the public `GET /api/donors/company-lookup` does, for the registration form signed out.
- No address comes from the visitor: the host is the fixed `https://ares.gov.cz/ekonomicke-subjekty-v-be/rest/ekonomicke-subjekty/`, and the IČO, the only input, is validated as 8 digits with the mod-11 check digit before the limiter, the cache or ARES see it, so it can never alter the path. Every resolved address of the host is checked by `PublicAddresses` (moved to `shared/infrastructure/net`, shared with the client metadata fetch), redirects are not followed, `https` only, 3 s for the connection and 3 s for the whole answer including the body, at most 64 KiB, `application/json` only, no database transaction held.
- 20 lookups per 15 minutes per client address (`CompanyLookupRateLimiter`), answers cached 10 minutes, and a circuit breaker (3 failures in a row: ARES skipped for 5 minutes), so neither a visitor nor a dead ARES can slow registrations or spend the register's 500 requests a minute. Every failure answers 204 like an unknown IČO and is logged as one `warn` with the outcome only, never the IČO (a sole trader's IČO identifies a natural person); the request's query string is not in `nginx-access.log` either.
- What comes back is public register data the donor sees and may change before registering; it is shown through Angular bindings only and validated again like any typed value when the registration is sent.

## Receipt signing key (verification QR)

Plan v3, 1.5 (D6, D7, D9). Every receipt is to carry a QR code whose proof the browser checks against the foundation's published keys, so a forged or altered receipt does not verify.

- The key is an Ed25519 seed of 32 random bytes generated by the backend's entrypoint into `secrets/receipt-signing-key` (root, mode 600) at the first start and handed to Java as `RECEIPT_SIGNING_KEY`; it is never in compose, the database, a backup, a log, an API or the connector, and never copied to another server or to staging (`deploy/README.md`, "Klíč k ověřovacímu QR"). `ReceiptSigningProperties` requires it outside dev (empty, not Base64 or not 32 bytes stops the startup) and masks it in `toString`; dev and the tests sign with the RFC 8032 test seed of test 1 (key id `21fe31df`), which is public. Outside the dev profile `ReceiptSigningConfiguration` refuses at startup every public RFC 8032 test seed (key ids `21fe31df` (test 1), `39f713d0` (test 2), `dac073e0` (test 3), `91384c41` (test 1024) and `5f9b247e` (test SHA(abc)), `ReceiptSigningKeyId.PUBLIC_TEST_KEY_IDS`), naming the variable and never the value, because anyone could sign with them (security reviews 2026-10-30). The same `PublicTestKeyPolicy` keeps a row of any of those ids out of the published list and away from adoption outside dev, so a dev database restored on the server or a planted row cannot make the list carry a key anyone can sign with (ERROR, red flag on `/sprava`); the verification page of 1.8 refuses them as well. JCA signing is confined to `donations/infrastructure/signing` by ArchUnit (`ReceiptSigningKeyRulesTest`). Signatures are deterministic (RFC 8032), so the same receipt always has the same proof.
- The signed message is the domain tag `nfnn.cz/receipt/v1`, a zero byte, the foundation's IČO (4 bytes) and the proof body, so a proof cannot be replayed for another foundation or another format. The body carries every gift and the total (D7), and the reader refuses a total that differs from the gifts' sum, a reserved flag, trailing bytes and a non-minimal number, so one signed message has exactly one reading.
- Key list: `receipt_signing_key` (key id, public key, registration time, status `active | revoked`, seal). At start, before anything else runs on `ApplicationReadyEvent`, `ReceiptSigningKeyRegistration` registers the server's own public key if it is new: the row, an `admin_action` `REGISTER_RECEIPT_SIGNING_KEY` with the server as the actor (`AdminActionPerformed.SERVER`, the nil UUID) and a WARN line naming the key id. No endpoint, setting or connector tool writes a key: ArchUnit (`ReceiptSigningKeyRulesTest`) allows a call of any key repository method but `findAll` only from the registrar (the web-only withdrawal of 1.13 will be the second writer), the key tables' JPA entities and Spring Data repositories only from their adapter, and the table name only in those entities, the adoption repository and changelog `donations/021`, each with a planted case.
- Seal: each row is sealed with HMAC-SHA256 under a key derived by HKDF-SHA256 from `settings-key` (`shared/application/seal/RecordSeals`, implemented by `operations/infrastructure/settings/SettingsKeyRecordSeals`, prefix `v1:`), over the key id, the public key, the registration time and the status; a row whose key id is not the first 4 bytes of SHA-256 of its public key counts as broken whatever its seal (`ReceiptSigningKey.idMatchesPublicKey`). Only a row sealed under this server's `settings-key` is published. A row whose seal fails is never published, logs ERROR with its key id, shows a red row on `/sprava` and in the receipt card of `/sprava/nastaveni`, and sets `receiptSigningKeys.attention` in `nfnn_status`; so does a missing row of the server's own key (`currentKeyPublished: false`).
- After a restore: a row from a backup of another server is sealed under that server's settings key, which the dump carries wrapped under the backup key (`operations_carried_settings_key`), so `SettingsKeyRecordSeals` answers `SEALED_BY_CARRIED_KEY`. Such a row is not published until the registrar adopts it, and it adopts it only at the first start after a restore that the backup container confirms: its status file `backups/status/restore` (read through the shared port `shared/application/restore/FinishedRestores`, implemented by `operations/infrastructure/backup/BackupStoreFinishedRestores`; the backend mounts `backups/` read-only, so neither the backend nor SQL can write it) must show a successful restore that finished within the hour before this start, and its request id (or, for a dump left in the restore folder by hand, its finish time) must not have been used before (`receipt_signing_key_adoption`, recorded at that first start whether or not a row needs it). Then the row is sealed again under this server's key, audited as `ADOPT_RECEIPT_SIGNING_KEY` (server actor, details with the key id and the restore) and logged at WARN per key. Without that evidence the row stays unpublished with an ERROR, and once `CarriedSettingsKeyStartup` has replaced the carried key the row fails its seal for good (recovery: the restore again). So the seal's anchor is `settings-key` **or** the backup key together with a restore: whoever holds `settings-key`, or holds the backup key and can have a backup restored, can add a key (security review 2026-10-30, M1). The detective controls are the audit trail (`REGISTER_…` and `ADOPT_…`), the WARN lines and the key list in `/sprava/nastaveni`, which names every earlier key it publishes.
- What the seal does not do: it has no freshness. An old row with its old seal stays valid, so someone who can write to the database can put back a row from before a later change, and deleting a row of an earlier key makes its receipts unknown without a flag. The withdrawal of 1.13 and 2.32 must design against that replay (plan: a start-time check of the rows against the `REGISTER`, `ADOPT` and withdrawal audit entries); someone who holds the database and the audit trail together stays beyond any MAC.
- Publication: `GET /api/donations/receipt-keys` is public (`permitAll`, 60 per 15 minutes per address, `ReceiptKeysRateLimiter`) and answers everyone alike with the foundation's name and IČO and the published keys, with their status, `Cache-Control: public, max-age=3600` and an ETag (304 on `If-None-Match`). It reveals only public keys. The edge stores nothing (`Cloudflare-CDN-Cache-Control: no-store` on `/api/`); a browser may keep the list for an hour, so the verification page of 1.8 fetches it with `cache: 'no-cache'` (a cheap 304), refetches whenever online and replaces its stored copy wholesale, so a withdrawn key or one that left the list is not trusted from an old copy. The administrator's `GET /api/admin/donations/receipt-signing-keys` adds which key is the server's and which rows fail their seal; it is read-only.
- A receipt whose proof needs more than one QR symbol of version 40 holds (2 893 bytes, near 550 gifts in a year) is refused with 400 `donations/receipt-too-long` and an ERROR line with the receipt id and the size, never with a name.
- Signing (1.6): the issuer signs every receipt it issues, under the donor lock, with the server's own key, and freezes the key id and the proof with it in `issued_receipt`; nothing re-signs an issued receipt, and the only way to a new proof is a new receipt with a new number. The row's `status_sha256` (SHA-256 of the signed message and the signature) is unique, so one proof names one receipt. `signing_key_id` must name a row of `receipt_signing_key` (foreign key), so a server whose own key failed to register at start issues no receipt rather than one no published key verifies (security review of 1.6, m2); a row stored but failing its seal is not caught at issue. The donor's receipt endpoints (`/api/donations/me/receipts…`) find everything by the JWT subject: another donor's receipt id answers 404 `donations/receipt-not-found`, and the signature image answers only a digest one of the caller's own receipts names (404 `donations/receipt-image-not-found` for any other, so the endpoint never confirms which images exist). The image is the scan the PDF printed before; the frozen data repeats what the receipt states (the donor's own name, address and gifts) and the receipt texts, nothing more.

## Abuse limits

Per client address, answered 429 before any work: contact 5/h, sign-in 10/15 min, registration 5/h, company lookup 20/15 min, reset request 5/h, verification request 5/h, password change 10/15 min, e-mail change request and its re-send together 5/h, second-factor codes at sign-in 10/15 min (the passkey options of the reset-link recovery and the start of a recovery by payment share this bucket), second-factor set-up/confirm/disable together 10/15 min, OAuth token endpoint 30/15 min, OAuth client description and approval together 20/15 min, passkey sign-in (options and answers) 20/15 min, passkey creation options 10/15 min, first setup 20/15 min (the backup key in the setup included), receipt keys 60/15 min, issuing receipts 30/15 min (`ReceiptIssuanceRateLimiter`: `POST /api/donations/me/receipts` and both old PDF downloads together, checked before the donor lock; each new number writes a frozen row and the numbering ends at 999 999, so changing the address between issues must not use it up, security review of 1.6, and the issuer warns from serial 900 000 on; a donor id is no `ClientAddressKey`, so it counts per address only, and the per-donor cap below bounds what rotating addresses would still allow), backup key reveal and confirmation together 10/15 min, test e-mail 10/h (the first setup's and the administration's together, `TestEmailRateLimiter`: it sends mail and opens an outbound SMTP connection to a typed host); bank check 30 s global. The per-address limits are built on `FixedWindowRateLimiter`, which takes only a `ClientAddressKey` (`shared/infrastructure/ratelimit`), so every per-address limiter counts by the same key: an IPv4 address is its own key; an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`) counts as that IPv4 address, so two IPv4 clients never share a bucket; every other IPv6 address counts by its /64 network, the block one subscriber is given, so a client cannot dodge a limit by rotating through its own /64 (a client holding a /48 still has 65 536 buckets, the price of never putting two subscribers of one provider into one bucket); the zone of a link-local address is ignored; the address is stripped of surrounding spaces; a missing value or one that is no IP literal (the frontend nginx never sends one) falls into one shared bucket instead of a bucket of its own, and the limiter logs a warning without the value at most once a minute. Each limiter keeps at most 50 000 keys by default (Caffeine `maximumSize`, about 11 MB per limiter); the backup key's limiter, behind the administration, keeps at most 1 000 (`FixedWindowRateLimiter.ADMINISTRATOR_ONLY_MAXIMUM_TRACKED_KEYS`), so the 19 limiters stay under about 198 MB of the backend's heap even when all are flooded; the test e-mail's limiter keeps the default, because the public setup test e-mail reaches it before any access check. A flood of more keys than a limiter keeps can end any window of that limiter early, the flooder's own included (it fails open); it never refuses an address that has not used up its own limit. The `/mcp` limit of the frontend nginx counts by the full address as a flood guard only (see the connector section). The bank check is a global cooldown (`on-demand-cooldown`). Per donor, not per address: at most 20 replacements in any 24 hours (`DonationReceiptIssuer`, counted from the `issued_receipt` rows with `supersedes_id` set under the donor lock before a serial is taken, so it survives restarts and cannot be rotated around; 409 `donations/receipt-issue-limit`, nothing logged; security review of 1.6, rounds 2 and 3). Using up the numbering cheaply needs replacements, since each first issue needs a paired gift of its own (at least 1 Kč from the payer's account), so a first issue is never counted or refused and a donor with many gifts gets each one's receipt on one day; returning a receipt whose data is unchanged does not count either. The administration issues through the same issuer under the same cap, counted with the donor's own issues and with no exemption (1.7, the lead's decision), so `POST /api/admin/donations/donors/{donorId}/receipts` answers the same 409; a connected application gets no replacement at all (403 above), and the cap refusal logs nothing. It has no per-address limiter, like the rest of `/api/admin/**`: it needs the role with the second factor or a connection with `admin:write`, and every connector call comes from the connector's one address, so a per-address count would bound nothing the per-donor cap does not.

The address is the request's remote address after the frontend nginx resolved the visitor: `set_real_ip_from` the private ranges, client values overwritten, `X-Forwarded-For $remote_addr` sent and `Forwarded` emptied. The backend trusts forwarded headers from any peer (`server.forward-headers-strategy: framework`), which is safe only because nothing but the frontend nginx and the connector reaches port 8080: that port is never published, and the containers sit on their own network `nfnn-edge`, never on the default bridge every other app on the server shares (one network for all five: ZimaOS attaches a service only to the first network it lists, so a separate database network left the backend unreachable; the database answers only the backend's and the backup's passwords); every service runs with `no-new-privileges`, a read-only root file system (`tmpfs` where it writes) and `cap_drop: ALL` plus only the capabilities its entrypoint needs (`deploy-ci.md`, Hardening), so a hole in an image has no raw sockets, no device nodes and no way to change files outside its volumes. The backend logs in to PostgreSQL as `novanadeje_app`, an ordinary role (no superuser, no role or database creation, member of no role) that owns the site's database and tables: an SQL injection could read and change the site's data but not run programs or read files on the database server (`COPY … PROGRAM`, `pg_read_server_files`), not touch other databases and not create roles. The superuser `novanadeje` is used only inside the database container and by the backup container (dumps, test restores, the restore swap).

## Secrets

- On the server there is no env file. `db-password` (superuser), `db-app-password` (`novanadeje_app`), `jwt-secret`, `settings-key`, `receipt-signing-key` and `backup-key` are generated once into `/DATA/AppData/nfnn/secrets/` (root, mode 600); all but `db-password` reach Java only through the backend's entrypoint, and `db-password` never reaches the backend at all (which starts as root for that, for `/restore` and for the log folder, then drops to `app` with `setpriv`).
- The SMTP password and the Fio token are settings stored sealed with AES-GCM under `settings-key` (`operations_setting`, `v1:` prefix). They are never returned by any API (the administration sees only set / not set / unreadable), the SMTP password goes only to the server it was saved for (moving `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME` or `MAIL_STARTTLS` needs the password in the same change, 400 `password-for-new-mail-server`; the test e-mail uses the stored one only against the running host, port, user and STARTTLS, and sends none to another server), SMTP requires STARTTLS whenever it is on, and every SMTP wait times out after 10 s. The test e-mail (Jakub, 2026-10-24) cannot be used as a mail relay: in the administration it goes only to the signed-in administrator's own address (looked up from the JWT subject, never taken from the request) and is audited as `SEND_TEST_EMAIL`; in the first setup it goes to the typed first administrator, only while the setup is open and only from the home network or with the setup code; both count against 10 an hour per address, and the answer is an outcome code, never the server's or the exception's text. They are never logged (audit and logs name the setting only), and changed only in the browser: a token with a `scope` claim is refused for a secret with 403, and the MCP tools have no secret in their schema.
- Backups (Jakub 2026-10-28: always encrypted): every dump is encrypted with age to `backup-key` (X25519, authenticated), so a copy of a dump outside the server, a downloaded one or one in a cloud folder is unreadable without the key. The backup container reads the key read-only from `secrets/`; the backend holds it in memory (`BACKUP_KEY`, masked `toString`) only to show it. It is shown only to a browser session of an administrator who proves a fresh second factor (a new code from the authenticator app, never the one the session was opened with, or a passkey assertion over a fresh challenge, as for approving a connection) at every view; each view is audited (`VIEW_BACKUP_KEY`) and e-mailed to every administrator, each refused second factor is audited (`VIEW_BACKUP_KEY_REFUSED`, in its own transaction) and five refusals of one administrator within 15 minutes pause the reveal for that administrator (`BackupKeyRevealRefusals`, counted from the audit trail; the per-address limiter alone would let a stolen session guess codes from many addresses, security review 2026-10-29); each view is answered `Cache-Control: private, no-store`, never logged, and refused to a connected application (`BROWSER_ONLY_POSTS`, outline row in `connected_apps.feature`). The first setup shows it under the setup's own guard (home network or the code) and completes only when three of its words are retyped. The key is the one secret whose loss loses every backup, and whoever holds it and a dump reads every donor's data, so the administration nags until saving is confirmed.
- The backup key as 24 words (Jakub 2026-10-29, security review 2026-10-29): the words encode the raw 32 bytes of the age identity with the BIP39 Czech wordlist and its 8-bit checksum, no key derivation, so they are exactly as strong as the key (256 bits) and need no passphrase; the list is pinned by its SHA-256 on both sides, so a changed list cannot silently turn saved words into another key. Saving is confirmed by retyping three words at positions the server drew with `SecureRandom` at the reveal and keeps in memory per administrator (`BackupKeyWordChallenges`: 30 minutes, five attempts, then the key must be revealed again with a fresh second factor), so neither a stolen session nor the page itself can confirm without the words; in memory on purpose, since losing the challenges on a restart only means showing the key again. The page shows the key only as its 24 words (Jakub 2026-10-29), and the check is a separate step: after "Mám uloženo, ověřit" the words disappear and the three fields ask for them, so they are typed from the saved copy, not from the screen ("Ukázat slova znovu" goes back). The word fields switch off autocomplete, autocorrect, autocapitalization and spellcheck, so no keyboard learns the words. The page hands nothing to the browser's password manager (a button that did was removed, Jakub 2026-10-29: Safari ignores a password it did not see typed); the words are copied by hand. Because a manager may still fill a saved key into another password field, every secret setting refuses a value shaped like the key (`SettingProblem.BACKUP_KEY`), so the key never ends up stored as the SMTP password or the Fio token. The downloaded file carries the `AGE-SECRET-KEY-1…` line for `age` and the words, so a printout of it is complete. A restore on a new server brings its key with the upload (`/restore/<id>.key`, mode 600, deleted after the restore or an hour); the backup container copies it into its own `tmpfs` before using it, and after a successful restore records its public recipient in `backups/status/adopted-key` (the backend mounts `backups/` read-only) and hands the key over as `/restore/backup-key.adopt`; the backend entrypoint (root) replaces `secrets/backup-key` with it only when its recipient (`age-keygen -y`) equals the recorded one, keeps the previous key as `backup-key.replaced-<time>` and logs a warning, the one case in which a generated secret is overwritten, so the new server keeps the key the operator already saved and `app`, which can write to `/restore`, cannot plant a key root would adopt. A restore and a test restore decrypt into a pipe straight into `pg_restore` and never write a plain copy, since `backups/` is the folder that is copied off the server (both from the security review 2026-10-29).
- Carried settings key (Jakub 2026-10-29: the backup carries the SMTP password and the Fio token): the database holds `settings-key` wrapped with AES-256-GCM (fixed associated data, random nonce) under a key derived by HKDF-SHA256 from `backup-key` (`operations_carried_settings_key`), so a dump plus the backup key yields the sealed secrets as well, and a restore on a new server that adopted the backup key reads them at once and seals them again under its own `settings-key`. Without the backup key the row is as opaque as the dump itself, which is encrypted to the same key, so this adds nothing for whoever lacks it; whoever holds the backup key and a dump already reads every donor's data, and now the SMTP password and the Fio token (read-only) too. The wrapped key never leaves the database in any API, log or connector answer.
- Locally only `.env`. `JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY` and `RECEIPT_SIGNING_KEY` have defaults only in `application-dev.yml` (the backup key and the signing seed there are public test keys). Records that carry a token or secret mask it in `toString` (token records, `TokenResponse`, `AuthResponse`, `SecondFactorEnrolment` and its response, `CodeExchange`, `JwtProperties`, `ReceiptSigningProperties`). The transcript recorder replaces the signing seed in every spelling (Base64, unpadded, base64url, hex) with `<secret>`, and the baseline hygiene check fails on either RFC 8032 test seed in any of those spellings and on a JSON field named after a seed, signing key or private key that is not `<secret>` or empty.
- The PR check fails when `deploy/compose.yml` names one of `POSTGRES_PASSWORD`, `PGPASSWORD`, `DB_PASSWORD`, `JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `RECEIPT_SIGNING_KEY`, `MAIL_PASSWORD`, `FIO_TOKEN`, when a service reads an env file, when `secrets/` is mounted beyond postgres, backend and (read-only) backup, when a dump is not an age file or the backup key reaches a log file, or when `JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `RECEIPT_SIGNING_KEY`, `DB_PASSWORD`, `FIO_TOKEN` or `MAIL_PASSWORD` reaches the database, backup, connector or frontend containers, in their configuration or their main process's environment, or when the first start leaves no 32-byte `receipt-signing-key`, registers no key or writes the seed into `backend.log` (`deploy-ci.md`).

## Logs

Every log carries ids and outcomes only, never names, e-mails, addresses, query strings, tokens or message bodies, at any level an administrator can set: the loggers that would write SQL values, Hibernate's entity listing, request and response bodies, raw requests with their headers, JDBC driver or mail traffic (`ProtectedLoggers`: `org.hibernate.orm.jdbc.bind`, `org.hibernate.orm.jdbc.extract`, `org.hibernate.internal.util.EntityPrinter`, `org.springframework.web.servlet.mvc.method.annotation`, `org.springframework.web.client`, `org.apache.coyote`, `org.apache.tomcat.util.http`, `org.postgresql`, `jakarta.mail`) are pinned at INFO in `application.yml` and refused (400 `operations/protected-logger`), so raising `ROOT` never reaches them, and TRACE is refused for every logger outside `cz.novanadeje.app`. The site's own DEBUG lines, which an administrator or a connection raises for a while, keep to the same rule: the bank import and the pairing name movements, payments, donors and sender-account links by id and say only whether a symbol, a sender account or a payer name was given (`FioBankStatementSourceTest` and `PaymentPairingServiceTest` capture them at DEBUG). Production logs (`/DATA/AppData/nfnn/logs/`) are readable from outside the server only through `/api/admin/operations/logs…` (an administrator's session or connector token; no container serves the folder itself). The frontend nginx writes `nginx-access.log` in the `anonymous` format, without the client address and the query string (searches and OAuth parameters travel in it); its console uses the same format, and nginx empties `X-Forwarded-Host`, `-Port`, `-Prefix` and `-Ssl` before proxying. A failed contact-form mail is logged with the message id and the exception class only.

## First setup

`/api/operations/setup` is public until completed, then 409. It opens without a code only for a request that came straight from the home network (the frontend nginx's `X-Nfnn-Direct` when no forwarding header arrived, plus a private client address at the backend); every other request needs the 12-character code the backend prints at each start to its standard output only (never `backend.log` or the log API); 20 requests per 15 min per address; values are validated against the startup binding before they are stored. Until the setup is done anyone in the home network could fill it in, which is accepted (Jakub 2026-10-23); afterwards settings change only through `/api/admin/**`.

The same unlock opens `GET /api/operations/setup/backup-key` (the server's backup key, `no-store`, so it can be saved before the setup completes) and `PUT /api/operations/setup/restore`, which replaces the empty database with an uploaded dump (must start with `age-encryption.org/v1` and come with its key, as the `AGE-SECRET-KEY-1…` text or its 24 words, or with `PGDMP` for an older plain dump; at most 4 GB, streamed into `/restore`, never parsed by the backend). `pg_restore` runs it as `novanadeje`, the superuser of the postgres image, so a crafted dump can run arbitrary SQL inside PostgreSQL: accepted for the same reason (only while the setup is open, only from the home network or with the code, and the database is empty then). A restore carries `secrets/settings-key` only wrapped under the backup key (Carried settings key, below): with the backup key the sealed secrets of the old server are read and sealed again, otherwise (an older dump) they stay unreadable and must be typed again.

## Browser and transport

TLS ends at Nginx Proxy Manager (Cloudflare in front later: in the same change Nginx Proxy Manager must pass the visitor from `CF-Connecting-IP`, `deploy/README.md`, else every limit applies per Cloudflare edge). The frontend nginx adds `nosniff`, `X-Frame-Options SAMEORIGIN`, `Referrer-Policy`, `Permissions-Policy` and the Content-Security-Policy in `frontend/nginx-security-headers.conf`: `default-src 'self'`; scripts, fonts and connections only from the site; styles also `'unsafe-inline'` because Angular injects component styles; images also `data:` (the saved QR code is drawn through one); `object-src 'none'`; `base-uri`, `form-action` and `frame-ancestors` `'self'`. `inlineCritical` stays off in `angular.json` because its inline `onload` handler would be blocked. CORS stays unconfigured (same origin). Every answer nginx proxies (`/api/`, `/mcp`, `/mcp-photos`, `/.well-known/…`) also carries `Cloudflare-CDN-Cache-Control: no-store`, which Cloudflare obeys ahead of `Cache-Control`, so no edge cache keeps one even under a "Cache Everything" rule; that includes the public photos at `/api/content/media/{id}` until edge caching is decided (plan v3, 2.6). For browsers the backend's `Cache-Control` decides: `no-store` on every answer (Spring Security's default, or set by the controller) except the photos (`public, max-age=31536000, immutable`), `receipt-keys` (`public, max-age=3600`, with an ETag) and, once it exists, `payment-details` (`private, max-age=300`), which set no cookie and answer a signed-in donor as anyone else. Answers nginx writes itself (413, 502, 503) carry no `Cache-Control`. The `stack` job's `frontend/scripts/probe-edge-caching.mjs` asserts the edge header and `no-store` on 200, 401, 404 and 429 answers and the exact headers of the two cacheable endpoints (`receipt-keys` compared with a signed-in donor's answer through `PROBE_ACCESS_TOKEN`, the probe donor the `stack` job registers). XSS defence is the policy plus Angular's bindings and Thymeleaf `th:text`. The Markdown of news and project bodies (`shared/ui/markdown`) is parsed into a tree of plain values and rendered by the template's own elements and `{{ }}` bindings, never through `innerHTML`, so a tag in the text shows as text; a link is kept only for `http`, `https`, `mailto:` and site-relative addresses, so no `javascript:` address reaches an `href`.
