# System overview

How each bounded context works today. Keep it current in the same PR as the change; the rules for new work are in `CLAUDE.md` and `.claude/rules/`, the HTTP shapes in `docs/api-contract.md`, the frontend in `docs/frontend-overview.md`, operations in `deploy/README.md`.

## contact

- `POST /api/contact/messages` stores the message in `contact_message` and forwards it by e-mail after commit (the foundation's mailbox copy is never touched by the web).
- Retention: every day at 03:30 Prague time `infrastructure/retention/ContactMessageRetentionScheduler` runs `application/ContactMessageRetentionService`, one `DELETE` over `ix_contact_message_received_at` of rows with `received_at` before now minus `app.contact.retention.max-age` (`P365D`). Cron `app.contact.retention.cron`, `-` turns it off (every `@SpringBootTest` does). The privacy policy promises the year for the web database only.

## donors

- Registration (person, or company with IČO), sign-in, refresh-token sessions, sign-out and the profile: `/api/donors/auth/**`, `/api/donors/me`. The API is an OAuth2 resource server validating its own HS256 JWTs. Passwords are stored as BCrypt (cost 12) of their SHA-256 hex digest (`infrastructure/security/BCryptPasswordHasher`), so all 128 characters count where BCrypt alone reads 72 bytes.
- E-mail verification: a registration answers 202, stores the donor with `donor.email_verified_at` null and sends the verification e-mail (also the welcome e-mail) with `{app.site.public-url}/potvrzeni-emailu#token=…`; `POST /api/donors/auth/email-verification/confirm` marks the e-mail confirmed, publishes `DonorRegistered` (only then does `donations` get its `donor_record`) and opens a session (200 with the auth response); `POST .../request` (always 202, 5 per hour per address, at most 3 live links of 24 hours in `donor_email_verification_token`) sends a new link to an unconfirmed account. Sign-in at an unconfirmed account with the right password answers 401 `auth/email-not-verified`; a reset request for it sends nothing. Registering an address again: a confirmed account's owner gets the "Váš dárcovský účet už existuje" e-mail and nothing changes; an unconfirmed registration is replaced by the new one. `application/DonorEmailVerificationService`, `infrastructure/mail/DonorRegistrationEmailSender`, `interfaces/rest/DonorEmailVerificationController`. Donors from before the change were marked confirmed by changelog `donors/004`. Contract: "E-mail verification".
- Limits per client address, every request counted, a limited one answers 429 `donors/rate-limited` before any hashing or work: sign-in 10 per 15 min (`interfaces/rest/SignInRateLimiter`), registration 5 per hour (`RegistrationRateLimiter`), reset request 5 per hour (`PasswordResetRateLimiter`); all built like the reset limiter. A sign-in with an unknown e-mail is compared against a real BCrypt cost-12 hash (`UNKNOWN_DONOR_HASH` in `DonorAuthenticationService`), so it costs the same as a real one. Contract: "Sign-in and registration limits".
- Credentials while signed in: `PUT /api/donors/me/password` (current + new password → 200 with a new session, every other refresh token revoked, 10 attempts per 15 min per address) and `POST /api/donors/me/email-change` (new address + password → always 202, 5 per hour per address): a free address gets the confirmation link (a `donor_email_verification_token` row with `new_email`, 24 h, confirmed through the same `/potvrzeni-emailu` page and confirm endpoint, which then switches the address, revokes every session, opens a new one and e-mails the previous address), an address another account has gets the "jiný účet chtěl použít vaši adresu" notice instead. `application/DonorCredentialsService`, `infrastructure/mail/DonorEmailChangeEmailSender`, `interfaces/rest/DonorCredentialsController`; changelog `donors/005`. Contract: "Changing the password and the e-mail".
- Password reset: `POST /api/donors/auth/password-reset/request` (always 202) and `POST .../confirm` (204). `application/DonorPasswordResetService` keeps at most three live links per donor in `donor_password_reset_token` (SHA-256 of a 43-character `LinkSecret`, valid `app.donors.password-reset.token-ttl`, one hour) and publishes `DonorPasswordResetRequested`; `infrastructure/mail/PasswordResetEmailSender` (`@Async AFTER_COMMIT`; a failure logs the donor id and the exception class only) sends the multipart e-mail with `{app.site.public-url}/obnova-hesla#token=…` from `app.mail.sender-email`. The confirm marks the token used atomically, deletes the donor's other links, revokes every refresh token and clears the refresh cookie; the donor signs in by hand. Contract: "Password reset".

## donations

- QR payment: `GET /api/donations/payment-qr` (public). `domain/payment/QrPayment` builds the SPAYD string, ZXing renders the PNG, the account comes from `app.donations.bank-account.*`.
- Fio import: every hour `FioImportScheduler` runs `ImportBankPaymentsService`, which asks the Fio API once for the period since `bank_import_state.covered_to` minus three days (the first run after a start may ask for locked history down to `FIO_HISTORY_FROM`), stores incoming CZK movements in `bank_payment` and pairs them into `donation`. The client is the Maven Central library `io.github.bzumik1:fio-api` with `RateLimit.failFast()`, so a refused or held-back request becomes a follow-up instead of blocking the scheduler thread; `io.github.bzumik1.fio..` is allowed only in `donations/infrastructure/fio` (ArchUnit). Without `FIO_TOKEN` the `FioClient` bean is `DisabledFioClient` and there is no scheduler bean; every `@SpringBootTest` pins `app.donations.fio.token=`. Contract: "Fio import and pairing".
- Pairing (`PaymentPairingService`): by variable symbol first; a payment without a symbol goes to the one donor whose `SenderAccountLink` period covers the booking day. A link is learned only from a payment with the donor's symbol; a newly learned link pairs the account's earlier payments unless another donor disconnected the account, then it starts the day after the latest such last day, whether or not they reconnected since. Accounts in `app.donations.pairing.excluded-accounts` (`PAIRING_EXCLUDED_ACCOUNTS`) are never learned; one learned before the exclusion is listed with `pairingExcluded`. Third, a payment whose symbol no registered donor holds goes, as `CONFIRMED_SYMBOL` with `donation.symbol_claim_id`, to the donor who confirmed that symbol for its sender account, when that donor's link is the only proved one covering the booking day and the account is not excluded. The import, the pairing after a registration and an answer each take `application/pairing/PairingLock` first (`infrastructure/persistence/PostgresPairingLock`: `pg_advisory_xact_lock(20261022)`, only inside a transaction).
- Donor's bank accounts: `GET /api/donations/me/bank-accounts`, `POST .../{id}/disconnect|reconnect` (`application/bankaccount/DonorBankAccountsService`). A disconnect ends the link today and keeps its donations; a disconnected account is never relearned automatically; a reconnect creates a link `AWAITING_PAYMENT` from today that the next payment with the symbol proves. Links live in `donor_sender_account` (one row per period, at most one live per donor and account); `donation.sender_account_id` names the link a donation was paired through. The rows count `SENDER_ACCOUNT` donations only and also carry `verificationPaymentOn` (the latest 1 Kč verification payment from the account) and `confirmedSymbols`. Contract: "Donor's bank accounts".
- Older variable symbol confirmation: an `ACTIVE`, unshared, not excluded account with a verification payment carries a `symbolOffer` when exactly one symbol other than the donor's own came from it on or before the earliest such payment and no registered donor holds that symbol (a registered donor's symbol among them asks nothing) (derived on every read by `domain/pairing/SymbolClaimOfferPolicy` through `application/bankaccount/SymbolClaimOffers`, never stored; `domain/bank/CounterpartyNames` checks the bank's payer name against the donor's type). `POST /api/donations/me/bank-accounts/{id}/symbol-claim/confirm|decline` with `{"variableSymbol"}` (`application/bankaccount/SymbolClaimService`, one transaction under the pairing lock) stores the one answer per donor, account and symbol in `donor_symbol_claim` (409 `donations/symbol-offer-not-available` or `donations/symbol-claim-already-answered`); a confirmation pairs the counted payments at once and answers `pairedCount` and `changedYearlyReceipts`, a decline 204. A mistaken answer is listed and reversed with the SQL in `deploy/README.md`, which `DeployReadmeSymbolClaimSqlTest` runs with `psql` in the test container (the test task declares the README as an input). Contract: "Older variable symbol confirmation".
- Bank check on demand: `POST /api/donations/me/bank-check`, polled with `GET`. `application/importing/BankCheckService` requests an import through the `BankImportRequests` port (`FioImportScheduler` queues an `ON_DEMAND` run on the scheduler thread; `DisabledBankImportRequests` without a token) unless `bank_import_state.last_attempted_at` is younger than `app.donations.import.on-demand-cooldown` (30 s, global), and answers `bankDataAsOf` (last success) and `checking`. Tests use `support/SynchronousBankImportRequests` (`@Primary`), which imports in the request thread.
- Overview: `GET /api/donations/me` (optional `year`, newest first, total and count of `RECEIVED` ones; an item paired by a confirmed symbol carries `confirmedSymbol`, and `receiptAvailable` says whether it has a receipt) and `GET /api/donations/me/summary` (total, count, last receipt day, totals per year). `interfaces/rest/DonorDonationsController` calls the read-only `application/overview/DonorDonationsService`, which builds `DonationList` and `DonationSummary` from `DonationRepository.findByDonorNewestFirst`. The purpose text comes from `donation.purpose.<PURPOSE>` in the message bundles by `Accept-Language`; `domain/donation/DonationPurpose` is `ACCOUNT_VERIFICATION` when the payment is exactly 1 Kč and its message contains "OVERENI UCTU" (as the account-adding QR sends it), else `GENERAL`.
- Receipts: `GET /api/donations/me/{id}/receipt` (one `RECEIVED` donation) and `GET /api/donations/me/receipts/yearly?year=` (a completed Prague calendar year from 1 January; `FoundationCalendar` holds the zone). `interfaces/rest/DonationReceiptController` → `application/receipt/DonationReceiptService` → `DonationReceiptIssuer`, one `REQUIRES_NEW` transaction per download with the donor's `donor_record` row locked: it serves the active receipt or, on the first download and whenever the certified data (donations, the donor's name and address, hashed into a fingerprint) changed, renders a new one with the next number `YYYY-NNNNNN` from `donation_receipt_number_seq` that supersedes the old. An issued receipt never changes and keeps the donor's preferred language of that moment (`en` is bilingual). No PDF is stored: `donation_receipt` keeps the pre-formatted `data` (JSON) and the SHA-256 digests of the template bundle (markup plus `receipt.*` texts, in `receipt_template`), the logo and the signature (in `receipt_image`), each stored once; every download renders it again byte for byte (CreationDate is `issued_at`, `/ID` from the number). `ReceiptRenderingLimit` lets `app.donations.receipt.concurrent-renders` (3) render at once. `infrastructure/pdf/ThymeleafPdfReceiptRenderer` (`freeze`, `render`, render profile 1) uses its own string-template Thymeleaf engine and openhtmltopdf with the embedded DejaVu Sans fonts (`resources/fonts/`, pinned by `ReceiptTemplateHistoryTest`, which also renders every recorded bundle in `src/test/resources/receipts/history/` from its sample data). Identity, issue place, signatory and the optional signature image come from `app.donations.receipt.*` (`RECEIPT_SIGNATORY_NAME`, `RECEIPT_SIGNATORY_ROLE`, `RECEIPT_SIGNATURE_IMAGE`; `deploy/README.md`). openhtmltopdf, PDFBox and Thymeleaf are allowed only in `..infrastructure..` (ArchUnit). Receipts cover only donations received from 1 January of `app.donations.receipt.first-year` (`RECEIPT_FIRST_YEAR`, 2026; `domain/receipt/FirstReceiptYear`): both endpoints refuse an older donation or year with 400 `donations/receipt-before-first-year`, and the summary names the year as `receiptsAvailableFrom`. Contract: "PDF receipts".
- `donor_record` is the donations copy of each donor, filled by `infrastructure/events/DonorRecordSynchronizer` from the shared `DonorRegistered` (copy `BEFORE_COMMIT`, pairing synchronously `AFTER_COMMIT` in `REQUIRES_NEW`) and `DonorProfileChanged` events.
- Monthly report: every day at 07:00 Prague time `infrastructure/report/MonthlyReportScheduler` (`app.donations.report.cron`; off with `-` or empty, pinned to `-` in every `@SpringBootTest`) runs `application/report/MonthlyReportService.sendDueReport`, which e-mails the previous month's statistics (registered and new donors, `RECEIVED` donations of the month and of the year to date, unpaired incoming payments of the month, the last import success and failure; `domain/report/MonthlyReport`, `templates/email/donations/monthly-report.html`) to `app.donations.report.recipient` (`REPORT_RECIPIENT`, default `CONTACT_RECIPIENT`) from `app.mail.sender-email`. The month is recorded in `donation_monthly_report` in the sending transaction, so a restart, a second instance or a missed 1st still sends once, and a refused send rolls back and is retried the next morning. It also keeps the Brevo SMTP key alive (cancelled after 90 days unused). Contract: "Monthly report".

## shared

Value objects `EmailAddress`, `UuidV7`, `Money`, `Currency`, `Iban`, `VariableSymbol`, `PostalAddress`, `LocaleCode`, `DonorType`; the sealed `DomainException` family; the cross-context events in `shared/application/event/`; the security filter chain and JWT configuration; the problem+json exception handler; the rate limiter; the `Clock` bean; `@EnableScheduling` in `shared/infrastructure/scheduling/SchedulingConfiguration` (Boot's `TaskScheduler` has one thread); `shared/infrastructure/mail/MailSenderProperties` (`app.mail.sender-email` from `MAIL_FROM`, falling back to `CONTACT_RECIPIENT`: the `From` of every outgoing e-mail, the contact forwarder included); `shared/infrastructure/mail/BrandedEmails`, which composes every outgoing e-mail from an `EmailDraft` (locale, recipient, subject, title, the content fragment's template name and variables, the plain-text part, a footer note): `From` is the sender address with the name `email.senderName`, the HTML part is `templates/email/layout.html` (site look with inline styles and table layout for Gmail and Outlook: the logo `receipt/logo.png` attached inline as `cid:logo`, Playfair/Georgia title, white card on `#f0f4ff`, footer with the note, `email.layout.identity` and a link to `app.site.public-url`) that inserts the context's fragment `th:fragment="content"` with `th:text` only, so every variable is escaped; the senders (`contact/infrastructure/mail/ContactMessageEmailForwarder`, `donors/infrastructure/mail/PasswordResetEmailSender`, `donations/infrastructure/report/MonthlyReportEmailSender`) build the draft and the plain text and send the result. `EmailTemplateColoursTest` keeps every colour under `templates/email/` equal to a `--color-*` token of `frontend/src/styles/themes/_nova-nadeje.scss` (the test task declares the theme as an input); the sender tests write previews to `backend/build/email-preview/`. `shared/infrastructure/config/PublicUrlProperties` (`app.site.public-url` from `PUBLIC_URL`, the address visitors use, validated at startup, for links in e-mails). Contract: "Shared pieces".

## Frontend

See `docs/frontend-overview.md`. In short: the public site and the donor portal are components; the contact form, the QR payment, the donor account (sign-in, registration, e-mail confirmation, password reset), the dashboard (summary, donations, receipts, bank check, bank accounts) talk to the backend through one HTTP service per feature behind `authInterceptor`.
