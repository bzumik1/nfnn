# System overview

How each bounded context works today. Keep it current in the same PR as the change; the rules for new work are in `CLAUDE.md` and `.claude/rules/`, the HTTP shapes in `docs/api-contract.md`, the security mechanisms in `docs/security-overview.md`, the frontend in `docs/frontend-overview.md`, operations in `deploy/README.md`.

## contact

- `POST /api/contact/messages` stores the message in `contact_message` and forwards it by e-mail after commit (the foundation's mailbox copy is never touched by the web). The request checks the address with `EmailAddress.SHAPE_REGEX` as the donor requests do, so a malformed address is a field error before the value object sees it. The sender gets no confirmation e-mail: the form is public, and one would let anybody send mail to any address.
- Retention: every day at 03:30 Prague time `infrastructure/retention/ContactMessageRetentionScheduler` runs `application/ContactMessageRetentionService`, one `DELETE` over `ix_contact_message_received_at` of rows with `received_at` before now minus `app.contact.retention.max-age` (`P365D`). Cron `app.contact.retention.cron`, `-` turns it off (every `@SpringBootTest` does). The privacy policy promises the year for the web database only.

## donors

- Registration (person, or company with IČO), sign-in, refresh-token sessions, sign-out and the profile: `/api/donors/auth/**`, `/api/donors/me`. The API is an OAuth2 resource server validating its own HS256 JWTs. Passwords are stored as BCrypt (cost 12) of their SHA-256 hex digest (`infrastructure/security/BCryptPasswordHasher`), so all 128 characters count where BCrypt alone reads 72 bytes.
- E-mail verification: a registration answers 202, stores the donor with `donor.email_verified_at` null and sends the verification e-mail (also the welcome e-mail) with `{app.site.public-url}/potvrzeni-emailu#token=…` (plus `&returnTo=%2F%23prispet` for a registration started in "Přispět": the request's optional `returnTo`, checked against `domain/RegistrationReturn`, travels in `DonorEmailVerificationRequested` into the link and is never stored, so it also works when the e-mail is opened in another browser; a request for a new link may name it again); `POST /api/donors/auth/email-verification/confirm` marks the e-mail confirmed, publishes `DonorRegistered` (only then does `donations` get its `donor_record`) and opens a session (200 with the auth response); `POST .../request` (always 202, 5 per hour per address, at most 3 live links of 24 hours in `donor_email_verification_token`) sends a new link to an unconfirmed account. Sign-in at an unconfirmed account with the right password answers 401 `auth/email-not-verified`; a reset request for it sends nothing. Registering an address again: a confirmed account's owner gets the "Váš dárcovský účet už existuje" e-mail and nothing changes; an unconfirmed registration is replaced by the new one. `application/DonorEmailVerificationService`, `infrastructure/mail/DonorRegistrationEmailSender`, `interfaces/rest/DonorEmailVerificationController`. Donors from before the change were marked confirmed by changelog `donors/004`. Once a registration has waited a day unconfirmed, `infrastructure/reminder/RegistrationReminderScheduler` (hourly, `app.donors.registration-reminder.cron`, `-` turns it off and every `@SpringBootTest` pins it) has `application/DonorRegistrationReminderService` send one reminder with a fresh link (`DonorRegistrationReminderDue`, template `email/donors/registration-reminder`), only within a week of the registration and recorded in `donor_registration_reminder` (changelog `donors/012`) so it never repeats. Contract: "E-mail verification".
- Limits per client address, every request counted, a limited one answers 429 `donors/rate-limited` before any hashing or work: sign-in 10 per 15 min (`interfaces/rest/SignInRateLimiter`), registration 5 per hour (`RegistrationRateLimiter`), reset request 5 per hour (`PasswordResetRateLimiter`); all built like the reset limiter. A sign-in with an unknown e-mail is compared against a real BCrypt cost-12 hash (`UNKNOWN_DONOR_HASH` in `DonorAuthenticationService`), so it costs the same as a real one. Contract: "Sign-in and registration limits".
- Credentials while signed in: `PUT /api/donors/me/password` (current + new password → 200 with a new session, every other refresh token revoked, 10 attempts per 15 min per address) and `POST /api/donors/me/email-change` (new address + password → always 202, 5 per hour per address): a free address gets the confirmation link (a `donor_email_verification_token` row with `new_email`, 24 h, confirmed through the same `/potvrzeni-emailu` page and confirm endpoint, the link marked `&change=email` only so the page words its success as a changed address, which then switches the address, revokes every session, opens a new one and e-mails the previous address), an address another account has gets the "jiný účet chtěl použít vaši adresu" notice instead, its change stored all the same so nothing tells the two apart. One change is pending at a time: `DonorEmailVerificationService.issueChangeLink` deletes the donor's earlier change links before it stores the new one (registration links keep their limit of 3), `DonorViews` reads the newest live one into `GET /api/donors/me` as `pendingEmailChange` (`EmailVerificationTokenRepository.findPendingChangeOf`), `POST /api/donors/me/email-change/resend` issues it again with a new secret (sharing the request's limiter; `NoPendingEmailChange` 409 without one) and `DELETE /api/donors/me/email-change` deletes the change links (Jakub 2026-10-24). `application/DonorCredentialsService`, `infrastructure/mail/DonorEmailChangeEmailSender`, `interfaces/rest/DonorCredentialsController`; changelog `donors/005`. Contract: "Changing the password and the e-mail".
- Roles: `donor_role` holds `DONOR` and, for administrators, `ADMIN`; both travel in the JWT as `ROLE_*` authorities. The role is granted and taken away by another administrator (`AdminDonorsController`, `application/AdministratorService`: `GET/POST /api/admin/donors/administrators`, `DELETE .../administrators/{id}` ends every session of the donor; audited as `GRANT_ADMINISTRATION` / `REVOKE_ADMINISTRATION`) and, for the first administrator, by `ADMIN_EMAILS` from the first setup (`application/AdministratorProperties`, `AdministratorBootstrap` on `ApplicationReadyEvent` and on a confirmed registration, only while the site has no administrator, so a restart never gives a removed administrator the role back); nothing by SQL (Jakub, 2026-10-22). `POST /api/admin/donors/{id}/second-factor/reset` turns a donor's lost two-factor authentication off (factor deleted, sessions ended, `RESET_SECOND_FACTOR` audited, e-mail `email/donors/second-factor-reset` through `DonorSecondFactorResetEmailSender`). `GET /api/admin/donors?query=` and `GET /api/admin/donors/{id}` (`application/DonorAdministrationService`, read-only; `DonorRepository.search` over name, e-mail and the start of the symbol, paged: 20 per page by default, at most 100) serve the donor search and the account half of the donor card `/sprava/darci/{id}`, which also offers the two-factor reset for any donor. `DELETE /api/admin/donors/{id}` (`application/DonorErasureService`) is the GDPR erasure: the account keeps its id, symbol and locale and gets the placeholders of `shared/domain/ErasedPersonalData` (`Donor.erase`, `donor.erased_at`, changelog `donors/007`), the factor, sessions and link tokens go, `DonorErased` tells `donations`, `ERASE_DONOR` is audited and `DonorAccountErasedEmailSender` tells the former address; an administrator cannot be erased, an erased donor cannot sign in or get a reset link, the address can register again. `GET /api/admin/donors/actions?before=&limit=` (`application/AdministratorActivityService`) reads the audit trail through the shared port `shared/application/audit/AdminActionTrail` and names the administrators, and the donors the changes concern, with one `DonorRepository.findByIds`; the page `/sprava/historie` shows it. Each entry also carries a sentence for a person (`summary`, Jakub 2026-10-24) made at read time, not stored: `application/AdminActionFacts` recognises the fixed shape of each action's `details` (Czech, and English for rows written before 2026-10-24) and takes out ids, amounts, days and codes, and `interfaces/rest/AdminActionSummaries` (an adapter, because it reads `MessageSource`) fills the `admin.action.summary.*` text of the request's language with the donor's name, amounts in crowns and dates. Reading instead of storing a second text needs no migration, gives the old English rows the same Czech sentence, and keeps the stored `details` (with their ids) as the record of what happened; the price is that the publishers' texts are a format: a use case that changes the wording of its details changes its shape in `AdminActionFacts` in the same PR (`AdminActionFactsTest` holds a Czech and an English example of every action), and an unknown shape falls back to the stored details. News and projects are named by their title (Jakub's testers 2026-10-29: the slug means nothing to an administrator): since 2026-10-29 `NewsAdminService` and `ProjectAdminService` end their details with "; titulek „<title>“" (the title the administrator also sees in the lists; public content, not personal data, and never written to a log, which keeps only the ids), recognised as the `withTitle` variant (`admin.action.summary.<ACTION>.withTitle`); older rows keep the slug in their sentence. `ADMIN` enters the JWT only for a session opened with the second factor (`Donor.sessionRoles`; the refresh token remembers it in `second_factor_verified`), so `/api/admin/**` (403 `auth/forbidden` otherwise) opens for an administrator only after they turn the second factor on and sign in with the code; the administration is `/sprava` in the frontend. Contract: "Authentication", "Administration".
- Sign-ins to the administration (Jakub 2026-10-29): `donor.last_signed_in_at` and `previous_signed_in_at` (nullable, `donors/016`) are written only by `DonorSessionService.signIn`, the session a completed sign-in opens (password, password and code, passkey, the e-mail confirmation link), and only when that session carries `ADMIN`; `DonorSessionService.open` (the session reopened after a password, second-factor or password-removal change) and the refresh write nothing. `DonorRepository.recordSignIn` shifts the last one into the previous one in one `update` (`JpaDonorRepository`, a native query; the entity maps `previous_signed_in_at` read-only, so saving a donor never overwrites it), there is no ordering constraint so a clock step back never fails a sign-in, and `AdministratorService.revoke` forgets both. Only administrators are recorded, so nothing new is kept about donors (data protection); the 1 Kč recovery opens no session, the sign-in after it counts. `GET /api/admin/donors/me/previous-sign-in` → `AdministratorService.previousSignIn(adminId)` answers the administrator's own, from the JWT subject.
- Second factor (TOTP, RFC 6238, any donor, mandatory for administrators): `POST /api/donors/me/second-factor/setup` (password → secret, `otpauth://` link and its QR code modules through the shared `QrCodeEncoder`), `.../confirm` (the first code → on, every other session revoked, a verified session opens) and `.../disable` (password + code → off), each e-mailing the owner `AFTER_COMMIT` (`DonorSecondFactorEnabled` / `DonorSecondFactorDisabled` → `infrastructure/mail/DonorSecondFactorEmailSender`, templates `email/donors/second-factor-enabled` and `-disabled`, always sent like every security e-mail); 10 changes per 15 min per address. With it on, `POST /api/donors/auth/login` answers 401 `auth/second-factor-required` with a `challenge` (SHA-256 in `donor_second_factor_challenge`, 5 minutes, 5 wrong codes, once) and `POST /api/donors/auth/login/second-factor` completes the sign-in (a code is accepted once per 30-second step, `last_used_step`; 10 codes per 15 min per address). `domain/{SecondFactor,Totp,TotpSecret,SecondFactorChallenge}`, `application/DonorSecondFactorService`, `DonorAuthenticationService.completeSecondFactor`, `application/DonorViews` (builds the profile view with `secondFactor.enabled` / `neededForAdministration`), `interfaces/rest/DonorSecondFactorController`; changelog `donors/006`; a lost authenticator is turned off by an administrator in the administration (see Roles) or by the donor with a payment of 1 Kč from a bank account the foundation has known for at least 7 days (`SecondFactorRecoveryService`: the code step opens a recovery with a one-time `OBNOVA …` code, changelog `donors/014`, or returns the donor's open one with the same code and expiry, which is why `donors/015` keeps the code beside its hash; the instructions carry the payment QR code, drawn by `donations` through `SecondFactorRecoveryTargets.paymentQrFor`; `donations` recognises the payment during the import and publishes `SecondFactorRecoveryPaid`, which `donors` handles in the import's transaction with a plain `@EventListener`, not `BEFORE_COMMIT`, because turning off an administrator's factor publishes `AdminActionPerformed`, whose `BEFORE_COMMIT` audit listener would not run once the commit had started; a failure rolls the import back and the next run retries), no recovery codes. Contract: "Second factor", "Recovery by payment".
- Passkeys (WebAuthn, optional, any donor; Jakub 2026-10-23): `POST /api/donors/me/passkeys/options` (password → creation options with a registration challenge), `POST /api/donors/me/passkeys` (attestation verified, `donor_passkey` row, e-mail `email/donors/passkey-added`), `GET`, `PATCH` (rename) and `DELETE /api/donors/me/passkeys[/{id}]` (e-mail `email/donors/passkey-removed`); sign-in through `POST /api/donors/auth/passkey/options` and `POST /api/donors/auth/passkey` (assertion verified against the stored key and counter; the session opens as verified by the second factor, so an administrator gets `ADMIN` and a TOTP donor is not asked for the code). Challenges in `donor_passkey_challenge` (SHA-256, 5 minutes, once, marked used before any check); RP id = host of `PUBLIC_URL`, stored with each key (`relying_party_id`, changelog `donors/013`), and at every `ApplicationReadyEvent` `infrastructure/startup/PasskeySiteCleanupAtStart` runs `PasskeySiteCleanupService`, which marks the keys without one as made for the current host and deletes the keys of other hosts (the staging keys after the switch to nfnn.cz; the count of donors goes to the log, nobody is e-mailed, a failure waits for the next start); at most 10 keys per donor; 20 sign-in requests and 10 creation options per 15 min per address. `domain/{Passkey,PasskeyChallenge,PasskeyUserHandle}`, `application/{DonorPasskeyService,DonorPasskeySignInService,PasskeyCeremonies}`, `infrastructure/webauthn/WebAuthnPasskeyCeremonies` (the only user of webauthn4j), changelog `donors/010`. An administrator who holds a second factor (the code or a passkey) adds or removes a passkey and starts the code set-up only from a session opened with it, else 403 `donors/second-factor-session-required` (`application/SecondFactorSessionGuard`), so a reset password alone cannot enrol an attacker's factor. An administrator removes all of a donor's keys on the donor card (`DELETE /api/admin/donors/{id}/passkeys`, sessions ended, `REMOVE_PASSKEYS` audited, e-mail `email/donors/passkeys-removed`); the erasure deletes them too. Contract: "Passkeys".
- Accounts without a password (Jakub 2026-10-23, after #113): `donor.password_hash` nullable (changelog `donors/011`), registration with `password: null`, the first key from the e-mail-link session without confirmation, every change confirmed by the password or a passkey assertion (`application/{Confirmation,DonorConfirmations}`), `POST /api/donors/me/password/remove`, 409 `donors/last-sign-in-method` for the last way in, `hasPassword` in the profile. Recovery from the reset link adds a passkey (`application/DonorPasskeyRecoveryService`, `POST /api/donors/auth/password-reset/passkey[/options]`): the code from the app when it is on, the link spent, every session ended, refused to administrators. Contract: "Accounts without a password".
- Connected applications: the site is the OAuth 2.1 authorization server of the MCP connector. `GET /.well-known/oauth-authorization-server` describes it; the consent page `/pripojeni` describes the client through `GET /api/donors/oauth/client` (Client ID Metadata Documents fetched by `infrastructure/oauth/HttpClientMetadataSource`, nothing registered by hand), lets the administrator grant reading only (the default) or reading and changes, and posts the decision with the granted scopes and a fresh second factor (a new code from the app or a passkey answer, `application/FreshSecondFactorCheck`) to `POST /api/donors/oauth/authorize` (`application/AuthorizationServerService`, a five-minute single-use code in `oauth_authorization_code` with the PKCE challenge, the scopes `admin:read` / `admin:write` and the resource `{public-url}/mcp`); `POST /api/donors/oauth/token` exchanges the code, refreshes (a `donor_refresh_token` row with `client_id`, `scope`, `granted_at`; rotated with `used_at`, a replay of a used token ends every session of the donor while a revoked one only answers `invalid_grant`, a removed administrator's connection ends) and swaps a connector token for an API token (RFC 8693). Access tokens carry `aud` (`{public-url}/mcp` for the connector, `{public-url}/api` for the API, `app.security.jwt.audience`) and a connector's `scope`; `shared/infrastructure/security/AdminWriteAuthorizationManager` refuses a change under `/api/admin/**` to a token without `admin:write`, and `BrowserSessionAuthorizationManager` keeps a token with a `scope` claim out of everything but `/api/admin/**` (no approving a connection, no account change, no backup download; security review 2026-10-23, task 15). `GET/DELETE /api/donors/me/connections` list and revoke the connections (`application/ConnectedAppsService`); changelogs `donors/008` and `donors/009`. Contract: "Connected applications".
- Company lookup (Jakub 2026-10-24): `GET /api/donors/company-lookup?companyIdentifier=` (public, 20 per 15 min per address, `CompanyLookupRateLimiter`) gives the registration form a company's name and seat from ARES. `application/CompanyLookupService` asks the port `CompanyRegistry`, implemented by `infrastructure/ares/AresCompanyRegistry` (JDK `HttpClient`, fixed `https` host checked by `shared/infrastructure/net/PublicAddresses`, no redirects, 3 s, 64 KiB, answers cached 10 min in Caffeine) and `AresAnswers` (maps `obchodniJmeno` and `sidlo` to `RegisteredCompany` with an optional `PostalAddress`). The service has no `@Transactional`: it touches no database. It is the circuit breaker: after 3 failures in a row (each within 5 minutes of the previous) it skips ARES for 5 minutes, so a dead register costs registrations nothing; the state is in memory, guarded by `synchronized` around the counters only, never around the call. Any failure answers 204 like an unknown IČO and logs one `warn` with the outcome, never the IČO. Contract: "Company lookup (ARES)".
- Password reset: `POST /api/donors/auth/password-reset/request` (always 202) and `POST .../confirm` (204). `application/DonorPasswordResetService` keeps at most three live links per donor in `donor_password_reset_token` (SHA-256 of a 43-character `LinkSecret`, valid `app.donors.password-reset.token-ttl`, one hour) and publishes `DonorPasswordResetRequested`; `infrastructure/mail/PasswordResetEmailSender` (`@Async AFTER_COMMIT`; a failure logs the donor id and the exception class only) sends the multipart e-mail with `{app.site.public-url}/obnova-hesla#token=…` from `app.mail.sender-email`. The confirm marks the token used atomically, deletes the donor's other links, revokes every refresh token and clears the refresh cookie; the donor signs in by hand. Both the confirm and the signed-in change publish `DonorPasswordChanged`, which `infrastructure/mail/DonorPasswordChangedEmailSender` turns into the "Heslo k vašemu účtu bylo změněno" e-mail. Contract: "Password reset".

## donations

- QR payment: `GET /api/donations/payment-qr` (public). `domain/payment/QrPayment` builds the SPAYD string, the shared `QrCodeEncoder` (ZXing, level H) turns it into the module matrix the frontend draws, the account comes from `app.donations.bank-account.*`.
- Fio import: every hour `FioImportScheduler` runs `ImportBankPaymentsService`, which asks the Fio API once for the period since `bank_import_state.covered_to` minus three days (the first run after a start may ask for locked history down to `FIO_HISTORY_FROM`), stores incoming CZK movements in `bank_payment` and pairs them into `donation`. `ImportBankPaymentsService` has no transaction of its own: the Fio call runs outside one and `BankStatementRecorder` writes each statement in a short one. The client is the Maven Central library `io.github.bzumik1:fio-api` with `RateLimit.failFast()`, so a refused or held-back request becomes a follow-up instead of blocking the scheduler thread; `io.github.bzumik1.fio..` is allowed only in `donations/infrastructure/fio` (ArchUnit). Without `FIO_TOKEN` the `FioClient` bean is `DisabledFioClient` and there is no scheduler bean; every `@SpringBootTest` pins `app.donations.fio.token=`. `BankImportState` counts the failures in a row (`bank_import_state.consecutive_failures`, `reported_outage`): the third counted failure (`TRANSPORT`, `INVALID_RESPONSE`, `UNEXPECTED`, `UNAUTHORIZED`; a rate limit or a locked history neither counts nor resets), or a rejected token at once, queues an `ImportOutage` and the success after it an `ImportRecovery` (`domain/importing/ImportAlert`) in the outbox `donation_import_alert` (changelog `donations/017`; a recovery drops an outage still waiting), and after every run `application/importing/ImportAlertDelivery` sends the waiting alerts oldest first through `infrastructure/report/ImportAlertEmailSender` (one Czech e-mail each to the monthly report's recipients, `ReportSettings`; `REPORT_RECIPIENT` until an administrator saves them; `templates/email/donations/import-outage.html`, `import-recovered.html`; on the scheduler thread with 10 s SMTP timeouts); a refused send stays queued and goes out after the next run. Contract: "Fio import and pairing" and "Import outage alerts".
- Administration: `GET /api/admin/donations/import-state` (`interfaces/rest/AdminImportStateController`, `application/importing/ImportStatusService`) shows the import's state (covered period, last attempt and success, last failure, failures in a row, reported outage) to administrators. Bank payments (`interfaces/rest/AdminPaymentsController`): `GET /api/admin/donations/payments?pairing=unpaired|paired&year=&query=&from=&to=&donorId=&offset=&limit=` lists the unpaired payments newest first or the paired ones (one year's, or without `year` every year's within the period) with donor, method and whether a receipt exists, filtered by `application/admin/PaymentFilter` (text without case and diacritics, or an amount in crowns, the booking period, the donor) and paged with the total (`application/admin/AdminPaymentsService`, read-only; `DonationRepository.findReceivedYearsNewestFirst` gives the years; the paired list without a year reads the donations received from the earliest to the newest year with one, narrowed by the period, in one query, since the page `/sprava/platby` searches by text and period instead of a year select, Jakub 2026-10-24), each item says `accountVerification` (`AdminPaymentView.accountVerification`, derived from the payment by `DonationPurpose.of` on every read, never stored), `GET .../donors?query=` searches `donor_record` by name or the start of the symbol (20 at most; `donor_record` keeps no e-mail, so the pairing dialog asks the `donors` context's `GET /api/admin/donors` with the same query beside it and shows each donor's e-mail by id), `POST .../payments/{id}/pair {donorId}` and `POST .../payments/{id}/unpair` run `application/pairing/ManualPairingService` under the pairing lock and the donor's row lock: pairing stores a `PairingMethod.MANUAL` donation (no account learned), unpairing deletes the donation unless a receipt references it (409 `donation-has-receipt`) and stamps `bank_payment.unpaired_by_admin_at`, which every automatic pairing query skips, so a payment with a known symbol does not come back at the next import. Both publish `AdminActionPerformed` (`PAIR_PAYMENT`, `UNPAIR_PAYMENT`) and answer the yearly receipts that change (`FirstReceiptYear` admits the year and the donor holds an active yearly receipt). Liquibase `donations/013`. Contract: "Administration" → "Bank payments". The donor card (`interfaces/rest/AdminDonorAccountsController`, `application/admin/AdminDonorAccountsService`): `GET /api/admin/donations/donors/{id}` answers the donor's record, bank accounts, donations and every receipt (`DonationReceiptRepository.findByDonorNewestFirst`); `POST .../bank-accounts/{linkId}/disconnect|reconnect` run the donor's own disconnect and reconnect for them (`DISCONNECT_SENDER_ACCOUNT`, `RECONNECT_SENDER_ACCOUNT`); `DELETE .../bank-accounts/{linkId}` removes a wrongly learned account under the pairing lock and the donor's row lock: refused (409 `bank-account-has-receipt`) while an issued receipt covers a donation paired through it (`application/admin/ReceiptCoverage`, shared with the symbol-claim reversal), otherwise deletes those donations (`DonationRepository.findBySenderAccountLink`) and the donor's symbol answers at the account, removes the link (`DonorRecord.removeSenderAccountLink`, `DonorRecordRepository.deleteSenderAccountLink`) and audits `REMOVE_SENDER_ACCOUNT_LINK`; the payments are unpaired again and stay so. Contract: "Administration" → "Donor accounts". The GDPR erasure arrives as the shared `DonorErased` event (`DonorRecordSynchronizer` → `DonorRecordService.erase`, `BEFORE_COMMIT`, under the pairing lock): `DonorRecord.erase` puts the placeholders on the copy (`donor_record.erased_at`, changelog `donations/014`), the donations paired through a link or an answer keep only their method (`Donation.withoutPairingSources`; the check constraints allow a `CONFIRMED_SYMBOL` row without both sources), every link and symbol answer of the donor is deleted, the donations and receipts stay; an erased record claims nothing by its symbol and the pairing-dialog search leaves it out.
- Pairing (`PaymentPairingService`): by variable symbol first, also when the payment has no symbol but its message carries exactly one donor's ten-digit symbol (`BankPayment.pairingSymbol`, `VariableSymbols.inMessage`, contract pairing rule 9; such a payment is paired in the symbol pass and skips the account pass, while a number no donor holds leaves it to the account pass); a payment without a symbol goes to the one donor whose `SenderAccountLink` period covers the booking day. A link is learned only from a payment with the donor's symbol; a newly learned link pairs the account's earlier payments unless another donor disconnected the account, then it starts the day after the latest such last day, whether or not they reconnected since. Accounts in `app.donations.pairing.excluded-accounts` (`PAIRING_EXCLUDED_ACCOUNTS`) are never learned; one learned before the exclusion is listed with `pairingExcluded`. Third, a payment whose symbol no registered donor holds goes, as `CONFIRMED_SYMBOL` with `donation.symbol_claim_id`, to the donor who confirmed that symbol for its sender account, when that donor's link is the only proved one covering the booking day and the account is not excluded. Every pairing writer takes `application/pairing/PairingLock` first (the list is in `.claude/rules/reliability.md`; `infrastructure/persistence/PostgresPairingLock`: `pg_advisory_xact_lock(20261022)`, only inside a transaction).
- Donor's bank accounts: `GET /api/donations/me/bank-accounts`, `POST .../{id}/disconnect|reconnect` (`application/bankaccount/DonorBankAccountsService`). A disconnect ends the link today and keeps its donations; a disconnected account is never relearned automatically; a reconnect creates a link `AWAITING_PAYMENT` from today that the next payment with the symbol proves. Links live in `donor_sender_account` (one row per period, at most one live per donor and account); `donation.sender_account_id` names the link a donation was paired through. The rows count `SENDER_ACCOUNT` donations only and also carry `verificationPaymentOn` (the latest 1 Kč verification payment from the account) and `confirmedSymbols`. The change is audited as `CHANGE_ABOUT_PHOTO` or `REMOVE_ABOUT_PHOTO` without a subject: `admin_action.subject_id` names an article, a project or a donor elsewhere, and the photo id is in the details. A removed photo leaves the site and the database at once and the backups within 30 days (a downloaded backup keeps it, and restoring a dump older than the removal brings it back, so `deploy/README.md` "Obnova" says to check `/sprava/o-nas` after a restore); a browser that already loaded it may keep its copy, because media are served `immutable` under an id that is never reused. The connector reads it with `nfnn_about` and changes it with `nfnn_update_about`.

The block "Kdo fond vede" of the About section comes from the people of the foundation an administrator keeps at `/sprava/lide-fondu` (Jakub 2026-10-30). `PeopleAdminService` keeps `content_person` (`Person`: `PersonDetails` with the name, role, board membership and note, the featured flag, the portrait and `PersonEmails`, plus the position and the web signature) and `FoundersNoteService` the one row of `content_founders_note`; `PublicPeopleService` builds `people` of `GET /api/content/home`: the featured people as cards, the board line, and the note with the web signatures of the featured people, or nothing while no person is kept, so the site shows its built-in block. Images are uploaded like the photos of the news; replacing, dropping or removing a portrait or a web signature deletes it unless a news article, project, the About section or another person still uses it, and `deleteIfUnused` and the daily cleanup check both columns of `content_person`. The web signature is a separate public image for the site only, never the receipt signature (receipts keep `RECEIPT_SIGNATORY_*` and their own signature until v3 1.16 reads the signatory from these people by the person id); a browser session and a connected application with `admin:write` set and remove it alike (Jakub 2026-10-30), and the connector removes a person with or without one. The personal and the fund e-mail (`EmailAddress`) are administration data: they reach the administration's answers and the connector, never the public view (whose records have no field for them), the audit details (only ids) or a log. The changes are audited as `ADD_PERSON`, `UPDATE_PERSON`, `REMOVE_PERSON`, `ORDER_PEOPLE`, `CHANGE_FOUNDERS_NOTE`, `CHANGE_WEB_SIGNATURE` and `REMOVE_WEB_SIGNATURE` without a subject, like the About photo, with the person's id in the details. Every writer locks the rows it reads before it saves them (`findByIdForUpdate` for one person, `findAllInOrderForUpdate` for adding and ordering, both `PESSIMISTIC_WRITE`), because each writer saves the whole row: without the lock a connector's edit or an ordering that read the row before a browser set the web signature would write it back without the signature (security review of PR #241). Two additions into an empty table have no row to lock and could share a position or pass the 30 people by one, which nothing depends on (the list orders by position, then by the time of adding, and the next ordering numbers everyone again). An image is either a portrait or a web signature, never both (`PersonImageInUse`). The connector reads them with `nfnn_people` and changes them with `nfnn_add_person`, `nfnn_update_person`, `nfnn_remove_person`, `nfnn_order_people`, `nfnn_update_founders_note`, `nfnn_set_web_signature` and `nfnn_remove_web_signature`.

## operations

How the server itself runs: backups and restore, diagnostics and logs, settings and the first setup. Backups (contract "Backups"): The container `nfnn-backup` (image `ghcr.io/bzumik1/nfnn-backup` from `deploy/backup/`: `backup.sh` on `postgres:17-alpine`) dumps the database at every start and every night at the planned time (03:00 Prague time by default) into `/DATA/AppData/nfnn/backups/nfnn-<date>_<time>[-rucni|-pred-obnovou].dump.age` (custom format, zstd 19, then encrypted with age to the backup key, 30 days kept; Jakub 2026-10-28: backups are always encrypted), once a week at the planned day and time (Sunday 04:00 by default) restores the newest dump into a temporary database `nfnn_restore_test` and counts its tables and applied changesets (`databasechangelog`, both must be above 0) and checks that every table holds as many rows as the dump carries for it, and restores a backup in the GUI (Jakub 2026-10-23: nothing outside the GUI, foolproof): an administrator's "Obnovit" on `/sprava/zalohy` (`POST .../backups/{file}/restore`, browser session with the second factor only, no MCP tool) or a `.dump.age` uploaded with its key in the first-setup wizard of a new server (`PUT /api/operations/setup/restore`, same unlock as the wizard, streamed into `/restore/<id>.upload`) becomes a `<id>.restore` request file in `backups/requests/`; the backend then exits (`ApplicationRestarter`) and its entrypoint (`backend/docker-entrypoint.sh`) waits while the request, the container's `status/restore.running` marker or a `/restore/*.dump` exists (a request not taken within 5 minutes is dropped). The container takes the request within 10 s, dumps the current database as `-pred-obnovou` when it has tables, restores into the staging database `nfnn_restore_staging`, refuses it without tables or applied changesets, clears a Liquibase lock caught in the dump and only after success swaps it in by `ALTER DATABASE … RENAME` (rolled back on failure, an interrupted swap repaired at the next container start); between the two renames every `public` sequence of the staging database is set to the higher of its own and the retired database's value (`keep_sequences_ahead`), so `donation_receipt_number_seq` never hands out a number issued after the backup again. So a failed restore leaves the data as they were and never blocks the backend. A dump left in `/DATA/AppData/nfnn/restore/` by hand is still restored at the container's start (empty database, or `*.force.dump` for a full one), the same way; it ends as `.done`, `.failed` or `.skipped`. After the restart `BackupRestoreService.recordFinishedRestore` writes `BACKUP_RESTORED` or `BACKUP_RESTORE_FAILED` into the audit trail once per request (`operations_restore_record`, changelog `operations/003`). Encryption (contract "Backups", "The backup key"): `backend/docker-entrypoint.sh` generates `secrets/backup-key` with `age-keygen` once, as it does the other secrets, and exports it to Java as `BACKUP_KEY`; the backup container reads the same file read-only and runs `pg_dump … | age --encrypt --identity`, so no plain dump ever touches the disk. The test restore and a restore decrypt into a pipe (`age --decrypt | pg_restore --single-transaction`, and the row check decrypts the dump once more into `pg_restore --data-only --file=-`), so no plain copy is ever written, because `backups/` is the folder an operator copies off the server (security review 2026-10-29); plain `nfnn-*.dump` files left from before the change are encrypted in place at the container's start (keeping their dates, so the 30-day retention still applies) and a plain upload still restores. The script waits at start until the key exists, so a backup is never written unencrypted. The backend never reads `secrets/` as `app`: the key reaches it by environment, and a key brought by a restore on a new server travels the other way through `/restore`: the upload's key is written beside it (`<id>.key`), the container first copies it into its own `tmpfs` (`/tmp`, mode 600) and deletes the upload's copy, decrypts with that copy and on success records the key's public recipient in `backups/status/adopted-key` and writes the key as `/restore/backup-key.adopt`; the entrypoint (root), after the restore wait and before Java starts, adopts it into `secrets/backup-key` only when `age-keygen -y` of it equals that recorded recipient, keeping the previous key as `secrets/backup-key.replaced-<UTC time>`. The record is the check because `app` can write to `/restore` (it streams the upload there) but mounts `backups/` read-only, so a compromised backend cannot plant a key of its own for root to adopt (security review 2026-10-29). It is generated before that wait so the container never waits for a key the backend has not written yet. Whether an administrator saved the key is stored as the key's SHA-256 fingerprint (`operations_backup_key_confirmation`, changelog `operations/005`), so a different key on another server counts as unsaved; the first setup records it when three of its words are retyped. The key is also written as 24 words of the Czech BIP39 list over its raw 32 bytes (`domain/backup/BackupKeyWords`, contract "The key as 24 words"); the frontend computes the same words from the key it already received (`features/operations/backup-key/backup-key-words.ts`, local first), and both sides run the cases in `test-cases/backup-key-words.json` at the repository root, so neither can drift from the other. The three positions an administrator must retype are drawn at the reveal and kept in memory (`application/backup/BackupKeyWordChallenges`, 30 minutes and five attempts per administrator) rather than in a table: a challenge is worth keeping only as long as the key stays on screen, and a restart that drops it costs one more reveal; the first setup draws positions at every request and checks whichever three come back, because before the first administrator exists there is nobody to bind them to. Showing the key needs a fresh second factor, which belongs to `donors`: `operations` asks through the shared port `shared/application/secondfactor/FreshSecondFactor` (`FreshSecondFactorProof` carries a code or a passkey assertion), implemented by `donors/infrastructure/secondfactor/FreshSecondFactorAdapter` over `FreshSecondFactorCheck`, the check that guards approving a connection. A refused second factor is recorded by `BackupKeyRevealRefusals.record` with `REQUIRES_NEW` on purpose: the refusal rolls the reveal's own transaction back, and the audit row must survive it, because five of them within 15 minutes pause the reveal for that administrator (`paused` counts them through `AdminActionTrail.countPerformedSince`). A view publishes the shared event `BackupKeyRevealed`, and `donors/infrastructure/mail/BackupKeyRevealedEmailSender` (after the commit, `@Async`) e-mails every administrator (`AdministratorService.contacts()`). The settings key `secrets/settings-key` is never in a dump as it is, only wrapped under the backup key (below, Jakub 2026-10-29), so only a restore of an older dump or one without its backup key leaves the sealed `MAIL_PASSWORD` and `FIO_TOKEN` unreadable, and `/sprava/nastaveni` asks for them again. Every run ends in a `key=value` status file (`backups/status/{backup,test-restore,restore}`), which the backend reads (`infrastructure/backup/FileBackupStore`). An administrator sees it all at `/sprava/zalohy` (`GET /api/admin/operations/backups`), starts a backup or a test restore (`POST .../requests` drops an empty request file into `backups/requests/`, the container picks it up within 10 s) and downloads a dump (`GET .../{fileName}`); and plans the runs (Jakub 2026-10-23: the times are set in the GUI, the defaults stay 03:00 and Sunday 04:00): `PUT .../schedule` stores the plan in `operations_backup_schedule` (changelog `operations/004`) and writes it as `backups/requests/schedule`, which the container reads on every pass (an invalid value keeps its default) and reports back as `backups/status/schedule`; at every start `BackupSchedulePublisher` writes the stored plan again, so a new container and a restored database follow the plan in the database, and the page warns while the container reports another plan or none (an older image). The plan file is written outside the transaction's commit, on purpose before it: when the folder is missing the change fails with 409 and nothing is stored, and a commit that fails afterwards is corrected by the next start's handover. The actions are audited (`REQUEST_BACKUP`, `REQUEST_TEST_RESTORE`, `CHANGE_BACKUP_SCHEDULE`, `DOWNLOAD_BACKUP`, `RESTORE_BACKUP`). Every day at 07:15 `BackupWatchScheduler` (`app.operations.backups.check-cron`) assesses the status (`domain/backup/BackupHealth`: no, failed or stale backup, 26 h; no, failed or stale test restore, 8 days; folder not mounted) and e-mails the monthly report's recipients once per outage and once on recovery (`backup_alert_state`, `BackupAlertEmailSender`, addresses through the shared port `AlertRecipients`). No copy leaves the server yet. Changelog `operations/001`.

Diagnostics (contract "Logs", "Log levels", "Diagnostics"): the backend reads its own log folder (`app.operations.logs.directory`, `/logs`; `infrastructure/logs/FileLogStore`) and serves it to administrators as a list of files, windows of whole lines by byte offset (the tail by default, 20 kB, at most 200 kB, rotated `.gz` files decompressed on the fly) and a regular-expression search newest first with paging, so the whole 14-day history is readable page by page from the web and from the connector. An administrator raises a logger (`LogLevelService` over Spring Boot's `LoggingSystem`) to DEBUG, or TRACE for the site's own code only, for 1–1440 minutes (the loggers that would write SQL values or bodies are pinned and refused) (30 by default); a timer on the shared scheduler puts the level back, an earlier reset is a `DELETE`, a restart forgets every override, and both changes are audited (`CHANGE_LOG_LEVEL`, `RESET_LOG_LEVEL`). `GET …/diagnostics` describes the JVM (heap, threads, GC, load), the database (a timed `SELECT 1`, the Hikari pool), the log, backup and restore folders (mounted, free space) and the active overrides; `…/diagnostics/threads` is a plain-text thread dump. Nothing is stored; nothing in it names a donor. An administrator does the same at `/sprava/logy`.

Settings and the first setup (contract "Settings and the first setup"; Jakub, 2026-10-23: no env file on the server): the backend generates its own secrets once into `/DATA/AppData/nfnn/secrets/` (`backend/docker-entrypoint.sh`: `jwt-secret`, `settings-key`, `receipt-signing-key`, `backup-key`; the image `nfnn-postgres` from `deploy/postgres/` generates `db-password` for the superuser and `db-app-password` for the application role `novanadeje_app`, sets both passwords at every start through a private instance on a temporary socket, creates the role and hands it the database and every table and sequence (`own-by-app-role.sql`; a new database gets the same from its init script, a restored one from the backup container before the swap) and marks it with `db-password.ready`, which the backend and the backup container wait for). The marker comes before a new database is even created, so the backend's entrypoint also waits, up to two minutes, until the database accepts a TCP connection (neither initdb's server nor the password-sync instance listens on TCP) before it starts Java; otherwise the first connection, `DatabaseSettingsEnvironmentPostProcessor`'s, could land between initdb and the real server and the backend would exit and restart once on a fresh install. The backend logs in as `novanadeje_app`, so Liquibase creates every new table as that role; the superuser stays with the database and backup containers (`security-overview.md`). Everything else the server needs is stored in `operations_setting` (secrets sealed with AES-GCM under `settings-key`) and loaded before the context starts by `DatabaseSettingsEnvironmentPostProcessor` as the top property source under the env names, so the configuration records stay as they were. The backup carries `settings-key` too (Jakub 2026-10-29): at every start `CarriedSettingsKeyStartup` makes sure the one-row table `operations_carried_settings_key` (changelog `operations/006`) holds `settings-key` wrapped with AES-256-GCM under a key derived by HKDF-SHA256 from `backup-key` (`BackupKeySettingsKeyCarrier`), so every dump carries it, readable only with the backup key. After a restore on a new server that adopted the old backup key, `DatabaseSettingsEnvironmentPostProcessor` opens the carried key to read the secrets the new `settings-key` cannot, and `CarriedSettingsKeyService` then seals them again under the new key and carries the new key instead, in one transaction. A dump from before this change, or one restored without the old backup key, still leaves the secrets unreadable, and `/sprava/nastaveni` names them as before. A fresh install has no rows: every public page sends the browser to `/prvni-nastaveni`, which opens without a code for a request straight from the home network (the frontend nginx marks it with `X-Nfnn-Direct` when no proxy header came) and otherwise asks for the code the backend prints only to its standard output at each start. Completing it or saving in `/sprava/nastaveni` validates the values against the startup binding, stores them, audits `CHANGE_SETTINGS` (names only) and exits; Docker starts the backend again with them. Changelog `operations/002`. Before saving, both pages send a real test e-mail with the typed values (Jakub, 2026-10-24): `SetupService.sendTestEmail` to the typed first administrator, `SettingsService.sendTestEmail` to the signed-in administrator's own address (`AccountEmails`), the running password only for the running server; `infrastructure/settings/JavaMailServerProbe` sends it through a one-off `JavaMailSenderImpl` with the 10 s timeouts and `SmtpFailures` turns the exception chain into an outcome (`SENT`, `UNREACHABLE`, `TIMEOUT`, `STARTTLS_UNAVAILABLE`, `SIGN_IN_REFUSED`, `SENDER_REFUSED`, `RECIPIENT_REFUSED`, `FAILED`) that the pages explain in plain Czech. Neither method is `@Transactional` on purpose: the SMTP conversation can take up to 30 s and holds no database connection; the administration's `SEND_TEST_EMAIL` audit row is written afterwards in its own short transaction (`TransactionOperations`), so the audit listener's `BEFORE_COMMIT` has a transaction to join.

- Logs: in the `prod` profile the backend also writes `/DATA/AppData/nfnn/logs/backend.log` (rotated, `application-prod.yml`) and the backup container appends to `backup.log` there, the frontend nginx writes `nginx-access.log` (no client address, no query string) and the connector `mcp.log` into the same folder, both rotated daily into `.gz` and kept 14 days, so the administration and the connector read every request and every connector call too; the backend logs `Backend revision <short sha> is ready` at start and answers `/actuator/info` with `build.revision` (`shared/infrastructure/config/BuildRevision`, `APP_REVISION` baked into the image by `images.yml`). Nothing serves the folder directly: administrators read it at `/sprava/logy` and Claude through the connector, both via `/api/admin/operations/logs…`; when the backend does not start, `docker logs` on the server covers it. Operator notes: `deploy/README.md` "Logy".

## mcp

The connector `nfnn-mcp` (`mcp/`, Node 24, MCP TypeScript SDK v2) sits behind the frontend nginx at `/mcp` and `/.well-known/oauth-protected-resource/mcp`; its contract and tool list are in `docs/api-contract.md` "MCP connector", its security in `docs/security-overview.md`. It learns the issuer from the backend's authorization server metadata at startup, verifies every bearer token by exchanging it for an API token at the backend (RFC 8693, cached until expiry) and answers 401 with `resource_metadata` and `scope="admin:read admin:write"` (the client asks for both and the administrator chooses on the site; the connector itself requires only `admin:read`). Every tool calls the same `/api/admin/...` endpoints as the web, so the audit trail is the administrator's and names the connected application (`admin_action.client`); a writing tool on a read-only connection answers a readable tool error (reconnect with „Změny“). It has a tool for every reading view and every reversible change of the administration (Jakub 2026-10-23), including the issued receipts (`nfnn_receipts`, `nfnn_receipt` with the frozen data and the verification link, an erased donor's without the name, address and link, `nfnn_issue_receipt` for first receipts only, a replacement being web-only; 1.7: the connector never gets a PDF, which only a browser draws), the logs and diagnostics of `operations`, settings without secrets and photos (`nfnn_upload_photo` from a public https address, `nfnn_photo_upload_link` for a one-time `PUT /mcp-photos` upload, both posting to `POST /api/admin/content/media`; `main.ts` serves through `node-handler.ts`, which hands `/mcp-photos` its raw request stream instead of the SDK's `toNodeHandler`, since that one decodes bodies as UTF-8 text and caps them at 4 MB); deletions, the administrator role, second-factor and passkey resets, older-symbol reversals, GDPR erasure, secrets, the backup key and the backup download and restore stay on the web. Answers are compact JSON: amounts as numbers of crowns, instants in ISO 8601 with the Prague offset, lists paged. No secret and no env file in the container; `mcp.log` has a line per request with its JSON-RPC method, tool name and time, never the arguments.

## Frontend

See `docs/frontend-overview.md`. In short: the public site, the donor portal and the administration (`/sprava`, administrators only, the backups among its pages) are components; the contact form, the QR payment, the donor account (sign-in, registration, e-mail confirmation, password reset, the consent page `/pripojeni` for the MCP connector and the connected applications in the account card), the dashboard (summary, donations, receipts, bank check, bank accounts) talk to the backend through one HTTP service per feature behind `authInterceptor`.

After a deploy an open tab still runs the previous build, whose lazy chunks are gone: nginx answers a missing hashed file with 404 (never `index.html` with 200, which would fail as a MIME error and be cached), and the hashed files that exist are immutable (`.claude/rules/deploy-ci.md`, Proxy, headers, mail). The router's navigation error handler hands a failed dynamic import to `ChunkLoadRecovery`, which loads the page that was asked for from the server once `ReloadGuard` allows it, and otherwise shows "Načíst znovu". It loads the target rather than reloading the page left open, so the visitor lands where they clicked: `location.assign` for another address, and `history.replaceState` plus `location.reload()` when only the fragment differs from the current document, because `assign` of `/#prispet` on `/` only jumps within the page (and after a failed first navigation the router has already taken the fragment off the address). `ReloadGuard` keeps the time of the last automatic reload per reason in `sessionStorage` (`nfnn.reload.<reason>`) and allows one per 60 s: a chunk that is still missing after the fresh load (the server broken) cannot loop the tab, and without a working `sessionStorage` it allows none, because a once-per-load flag in memory is reset by the reload itself. When the browser says it is offline (`navigator.onLine`), it does not claim the reload at all and only offers it, because the reload would end on the browser's own error page. On a flaky mobile network `navigator.onLine` stays true while the chunk request fails with the same message, so before claiming the reload `ChunkProbe` asks the server for the missing chunk (or `/` when the message names no address) with a `HEAD` request past the cache: only a 404 or an HTML page at the chunk's own address (the chunk is gone after a deploy), never after a redirect, lets the reload go; a failed request, a redirect (a login or maintenance page in front of the site), a server error or the chunk still being there leaves only the offer. The probe gives up after 4 s, because a network that takes the connection but never answers would otherwise leave the visitor with nothing at all. The offer is set before the probe, so it shows while the server is asked and stays when a visitor cancels the browser's "leave the page?" prompt, instead of a page that silently did nothing; and an answer that comes after the visitor started another navigation is ignored, so a late probe never takes them back to the page they left. The news and project editors mark their draft as discarded once their own question "Máte neuložené změny" is answered with "Odejít bez uložení", so a lost `loadComponent` behind that answer reloads without the browser's `beforeunload` prompt asking the same thing again; a failed `loadChildren`, which skips the question, keeps the `beforeunload` warning. The automatic load is a new document, so it drops what a navigation carried besides its address: the router's navigation `state` (the editors' `{ state: { deleted } }` after deleting a news article or project, `admin-news-editor.ts`, `admin-project-editor.ts`) is lost and the list shows without its "deleted" line. It also bypasses `canDeactivate`: the router loads `loadChildren` while it matches the address, before the guards run, so a failed `loadChildren` (leaving `/sprava` for the public site, for example) skips `unsavedChangesGuard`, and only the editors' `beforeunload` warning protects a draft then; a failed `loadComponent` comes after the guards, which have passed by then.

## Backend tests

How the suite runs and why it is built so (rules in `.claude/rules/testing.md`, "Keeping the suite fast"). Measured 2026-10-29 in a 4-core cloud container: the full `./gradlew test` took 14 to 19 minutes before these choices and about 3 minutes after on a quiet container (up to 6 when other sessions load it), with the same 2720 tests plus 12 new ones; the Cucumber steps alone went from 658 s to about 120 s.

- Two Gradle tasks: `test` (unit, integration, ArchUnit) and `acceptanceTest` (the Cucumber suites `DonorsAcceptanceTests` and `OtherContextsAcceptanceTests`, split by the `@donors` tag so each feature runs exactly once), both on two forks. The suite is bound to one core per JVM, so forks scale almost linearly. Gradle hands forks one test class file after another in turn, counting every class file, so two suites inside `test` could land on the same fork; `acceptanceTest` sees only the two suite classes and gives each its own fork. `acceptanceTest` is the finalizer of `test`, not a dependency, so `./gradlew test` and `build` still run everything and the scenarios run even when a unit test failed. Each fork has its own Spring context, PostgreSQL container, `MutableClock`, limiters and fakes (receipt numbers start at `000001` in each); only the folders on disk are shared, so the Cucumber context puts them under `build/cucumber/fork-${org.gradle.test.worker}/`. Running scenarios in parallel inside one JVM is not possible: the clock, the database, the recorded mail and the fakes are shared by every scenario.
- The v2 transcripts (`cucumber/transcript`, `.claude/rules/testing.md` "Regression against v2") are recorded by both forks of `acceptanceTest` into the one folder `build/api-transcripts/`. A fork writes only the features it runs, each feature runs whole in one fork, and every recorded scenario starts from the same clock, limits and seeds, so the files do not depend on the split. The folder is emptied by Gradle before the forks start, because a JVM that emptied it on its own start would delete what the other fork had already written.
- `CachingPasswordHasher` (registered by `CachingPasswordHashers`, a `BeanPostProcessor` in `TestSupportConfiguration`) wraps the application's `BCryptPasswordHasher`: the first hash of a password and the first check of a password against a hash go to the real cost-12 BCrypt, later ones are answered from memory. A BCrypt operation at cost 12 takes about a third of a second of one core, and the scenarios register and sign in about a thousand times; the cache keeps the production class and cost in every call while making each distinct check once. The only difference from production: two donors with the same password get the same salt.
- Awaitility's default poll delay is 100 ms even when the condition already holds; the Cucumber glue sets it to zero with a 10 ms interval (`CommonStepDefinitions.pollWithoutDelay`). The deliberate "nothing more arrives" waits keep their explicit 300 ms. Because the scenarios now end sooner, `isolateScenario` first waits until the application task executor has finished every `@Async` task, so an e-mail of the previous scenario can never land in the next one (before, the hidden 100 ms usually covered it).
- `DatabaseCleaner` deletes from every table, children first by the foreign keys read from the catalogue, and restarts every sequence, in one round trip. `TRUNCATE` creates new files for each of the about 40 tables and their indexes and took about 60 ms per scenario; the deletes of a scenario's few rows take a few ms.
- Contexts are cached per configuration, and each new one starts its own PostgreSQL container and Liquibase run (about 3 s). All `@SpringBootTest` classes share `@IntegrationTest` (MockMvc, an unreachable mail server on port 1, revision `f00ba12`, receipts from 2025, `@ScheduledWorkOff`), and the JPA slices of each context share `<Context>PersistenceTestConfiguration`; `TestContextRulesTest` keeps every new `@SpringBootTest` on `@IntegrationTest`. The integration tests that commit empty the database before each test, since they share it.
