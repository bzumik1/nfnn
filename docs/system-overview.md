# System overview

How each bounded context works today. Keep it current in the same PR as the change; the rules for new work are in `CLAUDE.md` and `.claude/rules/`, the HTTP shapes in `docs/api-contract.md`, the frontend in `docs/frontend-overview.md`, operations in `deploy/README.md`.

## contact

- `POST /api/contact/messages` stores the message in `contact_message` and forwards it by e-mail after commit (the foundation's mailbox copy is never touched by the web).
- Retention: every day at 03:30 Prague time `infrastructure/retention/ContactMessageRetentionScheduler` runs `application/ContactMessageRetentionService`, one `DELETE` over `ix_contact_message_received_at` of rows with `received_at` before now minus `app.contact.retention.max-age` (`P365D`). Cron `app.contact.retention.cron`, `-` turns it off (every `@SpringBootTest` does). The privacy policy promises the year for the web database only.

## donors

- Registration (person, or company with IČO), sign-in, refresh-token sessions, sign-out and the profile: `/api/donors/auth/**`, `/api/donors/me`. The API is an OAuth2 resource server validating its own HS256 JWTs. Passwords are stored as BCrypt (cost 12) of their SHA-256 hex digest (`infrastructure/security/BCryptPasswordHasher`), so all 128 characters count where BCrypt alone reads 72 bytes.
- E-mail verification: a registration answers 202, stores the donor with `donor.email_verified_at` null and sends the verification e-mail (also the welcome e-mail) with `{app.site.public-url}/potvrzeni-emailu#token=…`; `POST /api/donors/auth/email-verification/confirm` marks the e-mail confirmed, publishes `DonorRegistered` (only then does `donations` get its `donor_record`) and opens a session (200 with the auth response); `POST .../request` (always 202, 5 per hour per address, at most 3 live links of 24 hours in `donor_email_verification_token`) sends a new link to an unconfirmed account. Sign-in at an unconfirmed account with the right password answers 401 `auth/email-not-verified`; a reset request for it sends nothing. Registering an address again: a confirmed account's owner gets the "Váš dárcovský účet už existuje" e-mail and nothing changes; an unconfirmed registration is replaced by the new one. `application/DonorEmailVerificationService`, `infrastructure/mail/DonorRegistrationEmailSender`, `interfaces/rest/DonorEmailVerificationController`. Donors from before the change were marked confirmed by changelog `donors/004`. Contract: "E-mail verification".
- Limits per client address, every request counted, a limited one answers 429 `donors/rate-limited` before any hashing or work: sign-in 10 per 15 min (`interfaces/rest/SignInRateLimiter`), registration 5 per hour (`RegistrationRateLimiter`), reset request 5 per hour (`PasswordResetRateLimiter`); all built like the reset limiter. A sign-in with an unknown e-mail is compared against a real BCrypt cost-12 hash (`UNKNOWN_DONOR_HASH` in `DonorAuthenticationService`), so it costs the same as a real one. Contract: "Sign-in and registration limits".
- Credentials while signed in: `PUT /api/donors/me/password` (current + new password → 200 with a new session, every other refresh token revoked, 10 attempts per 15 min per address) and `POST /api/donors/me/email-change` (new address + password → always 202, 5 per hour per address): a free address gets the confirmation link (a `donor_email_verification_token` row with `new_email`, 24 h, confirmed through the same `/potvrzeni-emailu` page and confirm endpoint, which then switches the address, revokes every session, opens a new one and e-mails the previous address), an address another account has gets the "jiný účet chtěl použít vaši adresu" notice instead. `application/DonorCredentialsService`, `infrastructure/mail/DonorEmailChangeEmailSender`, `interfaces/rest/DonorCredentialsController`; changelog `donors/005`. Contract: "Changing the password and the e-mail".
- Roles: `donor_role` holds `DONOR` and, for administrators, `ADMIN`; both travel in the JWT as `ROLE_*` authorities. The role is granted and taken away by another administrator (`AdminDonorsController`, `application/AdministratorService`: `GET/POST /api/admin/donors/administrators`, `DELETE .../administrators/{id}` ends every session of the donor; audited as `GRANT_ADMINISTRATION` / `REVOKE_ADMINISTRATION`) and, for the first administrator, by `ADMIN_EMAILS` (`application/AdministratorProperties`, `AdministratorBootstrap` on `ApplicationReadyEvent`, idempotent); nothing by SQL (Jakub, 2026-10-22). `POST /api/admin/donors/{id}/second-factor/reset` turns a donor's lost two-factor authentication off (factor deleted, sessions ended, `RESET_SECOND_FACTOR` audited, e-mail `email/donors/second-factor-reset` through `DonorSecondFactorResetEmailSender`). `GET /api/admin/donors?query=` and `GET /api/admin/donors/{id}` (`application/DonorAdministrationService`, read-only; `DonorRepository.search` over name, e-mail and the start of the symbol, 20 at most) serve the donor search and the account half of the donor card `/sprava/darci/{id}`, which also offers the two-factor reset for any donor. `DELETE /api/admin/donors/{id}` (`application/DonorErasureService`) is the GDPR erasure: the account keeps its id, symbol and locale and gets the placeholders of `shared/domain/ErasedPersonalData` (`Donor.erase`, `donor.erased_at`, changelog `donors/007`), the factor, sessions and link tokens go, `DonorErased` tells `donations`, `ERASE_DONOR` is audited and `DonorAccountErasedEmailSender` tells the former address; an administrator cannot be erased, an erased donor cannot sign in or get a reset link, the address can register again. `GET /api/admin/donors/actions?before=&limit=` (`application/AdministratorActivityService`) reads the audit trail through the shared port `shared/application/audit/AdminActionTrail` and names the administrators with `DonorRepository.findByIds`; the page `/sprava/historie` shows it. `ADMIN` enters the JWT only for a session opened with the second factor (`Donor.sessionRoles`; the refresh token remembers it in `second_factor_verified`), so `/api/admin/**` (403 `auth/forbidden` otherwise) opens for an administrator only after they turn the second factor on and sign in with the code; the administration is `/sprava` in the frontend. Contract: "Authentication", "Administration".
- Second factor (TOTP, RFC 6238, any donor, mandatory for administrators): `POST /api/donors/me/second-factor/setup` (password → secret, `otpauth://` link and its QR code through the shared `QrCodeRenderer`), `.../confirm` (the first code → on, every other session revoked, a verified session opens) and `.../disable` (password + code → off); 10 changes per 15 min per address. With it on, `POST /api/donors/auth/login` answers 401 `auth/second-factor-required` with a `challenge` (SHA-256 in `donor_second_factor_challenge`, 5 minutes, 5 wrong codes, once) and `POST /api/donors/auth/login/second-factor` completes the sign-in (a code is accepted once per 30-second step, `last_used_step`; 10 codes per 15 min per address). `domain/{SecondFactor,Totp,TotpSecret,SecondFactorChallenge}`, `application/DonorSecondFactorService`, `DonorAuthenticationService.completeSecondFactor`, `application/DonorViews` (builds the profile view with `secondFactor.enabled` / `neededForAdministration`), `interfaces/rest/DonorSecondFactorController`; changelog `donors/006`; a lost authenticator is turned off by an administrator in the administration (see Roles), no recovery codes. Contract: "Second factor".
- Password reset: `POST /api/donors/auth/password-reset/request` (always 202) and `POST .../confirm` (204). `application/DonorPasswordResetService` keeps at most three live links per donor in `donor_password_reset_token` (SHA-256 of a 43-character `LinkSecret`, valid `app.donors.password-reset.token-ttl`, one hour) and publishes `DonorPasswordResetRequested`; `infrastructure/mail/PasswordResetEmailSender` (`@Async AFTER_COMMIT`; a failure logs the donor id and the exception class only) sends the multipart e-mail with `{app.site.public-url}/obnova-hesla#token=…` from `app.mail.sender-email`. The confirm marks the token used atomically, deletes the donor's other links, revokes every refresh token and clears the refresh cookie; the donor signs in by hand. Contract: "Password reset".

## donations

- QR payment: `GET /api/donations/payment-qr` (public). `domain/payment/QrPayment` builds the SPAYD string, the shared `QrCodeRenderer` (ZXing) renders the PNG, the account comes from `app.donations.bank-account.*`.
- Fio import: every hour `FioImportScheduler` runs `ImportBankPaymentsService`, which asks the Fio API once for the period since `bank_import_state.covered_to` minus three days (the first run after a start may ask for locked history down to `FIO_HISTORY_FROM`), stores incoming CZK movements in `bank_payment` and pairs them into `donation`. The client is the Maven Central library `io.github.bzumik1:fio-api` with `RateLimit.failFast()`, so a refused or held-back request becomes a follow-up instead of blocking the scheduler thread; `io.github.bzumik1.fio..` is allowed only in `donations/infrastructure/fio` (ArchUnit). Without `FIO_TOKEN` the `FioClient` bean is `DisabledFioClient` and there is no scheduler bean; every `@SpringBootTest` pins `app.donations.fio.token=`. `BankImportState` counts the failures in a row (`bank_import_state.consecutive_failures`, `reported_outage`): the third counted failure (`TRANSPORT`, `INVALID_RESPONSE`, `UNEXPECTED`, `UNAUTHORIZED`; a rate limit or a locked history neither counts nor resets), or a rejected token at once, publishes `BankImportOutageDetected` and the success after it `BankImportRecovered` (`application/event`), which `infrastructure/report/ImportAlertEmailSender` turns after the commit into one Czech e-mail each to `REPORT_RECIPIENT` (`templates/email/donations/import-outage.html`, `import-recovered.html`); a refused send is logged at ERROR and not retried. Contract: "Fio import and pairing" and "Import outage alerts".
- Administration: `GET /api/admin/donations/import-state` (`interfaces/rest/AdminImportStateController`, `application/importing/ImportStatusService`) shows the import's state (covered period, last attempt and success, last failure, failures in a row, reported outage) to administrators. Bank payments (`interfaces/rest/AdminPaymentsController`): `GET /api/admin/donations/payments?pairing=unpaired|paired&year=` lists the unpaired payments newest first or one year's paired ones with donor, method and whether a receipt exists (`application/admin/AdminPaymentsService`, read-only; `DonationRepository.findReceivedYearsNewestFirst` gives the years), `GET .../donors?query=` searches `donor_record` by name or the start of the symbol (20 at most), `POST .../payments/{id}/pair {donorId}` and `POST .../payments/{id}/unpair` run `application/pairing/ManualPairingService` under the pairing lock and the donor's row lock: pairing stores a `PairingMethod.MANUAL` donation (no account learned), unpairing deletes the donation unless a receipt references it (409 `donation-has-receipt`) and stamps `bank_payment.unpaired_by_admin_at`, which every automatic pairing query skips, so a payment with a known symbol does not come back at the next import. Both publish `AdminActionPerformed` (`PAIR_PAYMENT`, `UNPAIR_PAYMENT`) and answer the yearly receipts that change (`FirstReceiptYear` admits the year and the donor holds an active yearly receipt). Liquibase `donations/013`. Contract: "Administration" → "Bank payments". The donor card (`interfaces/rest/AdminDonorAccountsController`, `application/admin/AdminDonorAccountsService`): `GET /api/admin/donations/donors/{id}` answers the donor's record, bank accounts, donations and every receipt (`DonationReceiptRepository.findByDonorNewestFirst`); `POST .../bank-accounts/{linkId}/disconnect|reconnect` run the donor's own disconnect and reconnect for them (`DISCONNECT_SENDER_ACCOUNT`, `RECONNECT_SENDER_ACCOUNT`); `DELETE .../bank-accounts/{linkId}` removes a wrongly learned account under the pairing lock and the donor's row lock: refused (409 `bank-account-has-receipt`) while an issued receipt covers a donation paired through it (`application/admin/ReceiptCoverage`, shared with the symbol-claim reversal), otherwise deletes those donations (`DonationRepository.findBySenderAccountLink`) and the donor's symbol answers at the account, removes the link (`DonorRecord.removeSenderAccountLink`, `DonorRecordRepository.deleteSenderAccountLink`) and audits `REMOVE_SENDER_ACCOUNT_LINK`; the payments are unpaired again and stay so. Contract: "Administration" → "Donor accounts". The GDPR erasure arrives as the shared `DonorErased` event (`DonorRecordSynchronizer` → `DonorRecordService.erase`, `BEFORE_COMMIT`, under the pairing lock): `DonorRecord.erase` puts the placeholders on the copy (`donor_record.erased_at`, changelog `donations/014`), the donations paired through a link or an answer keep only their method (`Donation.withoutPairingSources`; the check constraints allow a `CONFIRMED_SYMBOL` row without both sources), every link and symbol answer of the donor is deleted, the donations and receipts stay; an erased record claims nothing by its symbol and the pairing-dialog search leaves it out.
- Pairing (`PaymentPairingService`): by variable symbol first; a payment without a symbol goes to the one donor whose `SenderAccountLink` period covers the booking day. A link is learned only from a payment with the donor's symbol; a newly learned link pairs the account's earlier payments unless another donor disconnected the account, then it starts the day after the latest such last day, whether or not they reconnected since. Accounts in `app.donations.pairing.excluded-accounts` (`PAIRING_EXCLUDED_ACCOUNTS`) are never learned; one learned before the exclusion is listed with `pairingExcluded`. Third, a payment whose symbol no registered donor holds goes, as `CONFIRMED_SYMBOL` with `donation.symbol_claim_id`, to the donor who confirmed that symbol for its sender account, when that donor's link is the only proved one covering the booking day and the account is not excluded. The import, the pairing after a registration and an answer each take `application/pairing/PairingLock` first (`infrastructure/persistence/PostgresPairingLock`: `pg_advisory_xact_lock(20261022)`, only inside a transaction).
- Donor's bank accounts: `GET /api/donations/me/bank-accounts`, `POST .../{id}/disconnect|reconnect` (`application/bankaccount/DonorBankAccountsService`). A disconnect ends the link today and keeps its donations; a disconnected account is never relearned automatically; a reconnect creates a link `AWAITING_PAYMENT` from today that the next payment with the symbol proves. Links live in `donor_sender_account` (one row per period, at most one live per donor and account); `donation.sender_account_id` names the link a donation was paired through. The rows count `SENDER_ACCOUNT` donations only and also carry `verificationPaymentOn` (the latest 1 Kč verification payment from the account) and `confirmedSymbols`. Contract: "Donor's bank accounts".
- Older variable symbol confirmation: an `ACTIVE`, unshared, not excluded account with a verification payment carries a `symbolOffer` when exactly one symbol other than the donor's own came from it on or before the earliest such payment and no registered donor holds that symbol (a registered donor's symbol among them asks nothing) (derived on every read by `domain/pairing/SymbolClaimOfferPolicy` through `application/bankaccount/SymbolClaimOffers`, never stored; `domain/bank/CounterpartyNames` checks the bank's payer name against the donor's type). `POST /api/donations/me/bank-accounts/{id}/symbol-claim/confirm|decline` with `{"variableSymbol"}` (`application/bankaccount/SymbolClaimService`, one transaction under the pairing lock) stores the one answer per donor, account and symbol in `donor_symbol_claim` (409 `donations/symbol-offer-not-available` or `donations/symbol-claim-already-answered`); a confirmation pairs the counted payments at once and answers `pairedCount` and `changedYearlyReceipts`, a decline 204. A mistaken answer is listed and corrected by an administrator (`interfaces/rest/AdminSymbolClaimsController`, `application/admin/AdminSymbolClaimsService`, `/sprava/starsi-symboly`): `POST /api/admin/donations/symbol-claims/{id}/reverse` deletes the donations paired through a confirmed claim and turns it `DECLINED` under the pairing lock and the donor's row lock, refused while an issued receipt may certify one of them (409 `symbol-claim-has-receipt`); `DELETE .../symbol-claims/{id}` removes a declined claim so the account asks again; both publish `AdminActionPerformed` (`REVERSE_SYMBOL_CLAIM`, `RESET_SYMBOL_CLAIM`). `AdminSymbolClaimsServiceIntegrationTest` proves it against PostgreSQL. Contract: "Older variable symbol confirmation".
- Bank check on demand: `POST /api/donations/me/bank-check`, polled with `GET`. `application/importing/BankCheckService` requests an import through the `BankImportRequests` port (`FioImportScheduler` queues an `ON_DEMAND` run on the scheduler thread; `DisabledBankImportRequests` without a token) unless `bank_import_state.last_attempted_at` is younger than `app.donations.import.on-demand-cooldown` (30 s, global), and answers `bankDataAsOf` (last success) and `checking`. Tests use `support/SynchronousBankImportRequests` (`@Primary`), which imports in the request thread.
- Overview: `GET /api/donations/me` (optional `year`, newest first, total and count of `RECEIVED` ones; an item paired by a confirmed symbol carries `confirmedSymbol`, and `receiptAvailable` says whether it has a receipt) and `GET /api/donations/me/summary` (total, count, last receipt day, totals per year). `interfaces/rest/DonorDonationsController` calls the read-only `application/overview/DonorDonationsService`, which builds `DonationList` and `DonationSummary` from `DonationRepository.findByDonorNewestFirst`. The purpose text comes from `donation.purpose.<PURPOSE>` in the message bundles by `Accept-Language`; `domain/donation/DonationPurpose` is `ACCOUNT_VERIFICATION` when the payment is exactly 1 Kč and its message contains "OVERENI UCTU" (as the account-adding QR sends it), else `GENERAL`.
- Receipts: `GET /api/donations/me/{id}/receipt` (one `RECEIVED` donation) and `GET /api/donations/me/receipts/yearly?year=` (a completed Prague calendar year from 1 January; `FoundationCalendar` holds the zone). `interfaces/rest/DonationReceiptController` → `application/receipt/DonationReceiptService` → `DonationReceiptIssuer`, one `REQUIRES_NEW` transaction per download with the donor's `donor_record` row locked: it serves the active receipt or, on the first download and whenever the certified data (donations, the donor's name and address, hashed into a fingerprint) changed, renders a new one with the next number `YYYY-NNNNNN` from `donation_receipt_number_seq` that supersedes the old. An issued receipt never changes and keeps the donor's preferred language of that moment (`en` is bilingual). No PDF is stored: `donation_receipt` keeps the pre-formatted `data` (JSON) and the SHA-256 digests of the template bundle (markup plus `receipt.*` texts, in `receipt_template`), the logo and the signature (in `receipt_image`), each stored once; every download renders it again byte for byte (CreationDate is `issued_at`, `/ID` from the number). `ReceiptRenderingLimit` lets `app.donations.receipt.concurrent-renders` (3) render at once. `infrastructure/pdf/ThymeleafPdfReceiptRenderer` (`freeze`, `render`, render profile 1) uses its own string-template Thymeleaf engine and openhtmltopdf with the embedded DejaVu Sans fonts (`resources/fonts/`, pinned by `ReceiptTemplateHistoryTest`, which also renders every recorded bundle in `src/test/resources/receipts/history/` from its sample data). Identity, issue place, signatory and the optional signature image come from `app.donations.receipt.*` (`RECEIPT_SIGNATORY_NAME`, `RECEIPT_SIGNATORY_ROLE`, `RECEIPT_SIGNATURE_IMAGE`; `deploy/README.md`). openhtmltopdf, PDFBox and Thymeleaf are allowed only in `..infrastructure..` (ArchUnit). Receipts cover only donations received from 1 January of `app.donations.receipt.first-year` (`RECEIPT_FIRST_YEAR`, 2026; `domain/receipt/FirstReceiptYear`): both endpoints refuse an older donation or year with 400 `donations/receipt-before-first-year`, and the summary names the year as `receiptsAvailableFrom`. Contract: "PDF receipts".
- `donor_record` is the donations copy of each donor, filled by `infrastructure/events/DonorRecordSynchronizer` from the shared `DonorRegistered` (copy `BEFORE_COMMIT`, pairing synchronously `AFTER_COMMIT` in `REQUIRES_NEW`), `DonorProfileChanged` and `DonorErased` events.
- Monthly report: every day at 07:00 Prague time `infrastructure/report/MonthlyReportScheduler` (`app.donations.report.cron`; off with `-` or empty, pinned to `-` in every `@SpringBootTest`) runs `application/report/MonthlyReportService.sendDueReport`, which, once the settings' send day has come, e-mails the previous month's statistics (registered and new donors, `RECEIVED` donations of the month and of the year to date, unpaired incoming payments of the month, the last import success and failure; `domain/report/MonthlyReport`, `templates/email/donations/monthly-report.html`) from `app.mail.sender-email` to the recipients of `domain/report/ReportSettings`: the row of `donation_report_settings` an administrator saved on `/sprava/prehledy` (recipients, send day 1–28, which sections the e-mail carries; `CHANGE_REPORT_SETTINGS` in the audit trail) or, until one was saved, the defaults `app.donations.report.recipient` (`REPORT_RECIPIENT`, default `CONTACT_RECIPIENT`), day 1 and every section. The same page sends the report of any ended month again by hand (`MonthlyReportService.resend`, `SEND_MONTHLY_REPORT`, 502 `donations/report-not-delivered` when SMTP refuses it) and lists the months sent; the import outage alerts go to the same recipients. The administration home `/sprava` shows the year's donations and donors month by month (`AdminOverviewService`, `domain/report/YearOverview`). The month is recorded in `donation_monthly_report` in the sending transaction, so a restart, a second instance or a missed 1st still sends once, and a refused send rolls back and is retried the next morning. It also keeps the Brevo SMTP key alive (cancelled after 90 days unused). Contract: "Monthly report".

## shared

Value objects `EmailAddress`, `UuidV7`, `Money`, `Currency`, `Iban`, `VariableSymbol`, `PostalAddress`, `LocaleCode`, `DonorType`; the sealed `DomainException` family; the cross-context events in `shared/application/event/` (`AdminActionPerformed` among them: `shared/infrastructure/audit/AdminActionLog` writes it to `admin_action` before the publishing use case commits, changelog `shared/001`; no producer yet, manual pairing will be the first); the security filter chain (`/api/admin/**` only with role `ADMIN`) and JWT configuration; `shared/application/qr/QrCodeRenderer` with `shared/infrastructure/qr/ZxingQrCodeRenderer` (moved from `donations` when `donors` needed the authenticator QR); `DomainException.extensions()`, which `ApiExceptionHandler` copies into the problem's properties (the second-factor `challenge`); the problem+json exception handler; the rate limiter; the `Clock` bean; `@EnableScheduling` in `shared/infrastructure/scheduling/SchedulingConfiguration` (Boot's `TaskScheduler` has one thread); `shared/infrastructure/mail/MailSenderProperties` (`app.mail.sender-email` from `MAIL_FROM`, falling back to `CONTACT_RECIPIENT`: the `From` of every outgoing e-mail, the contact forwarder included); `shared/infrastructure/mail/BrandedEmails`, which composes every outgoing e-mail from an `EmailDraft` (locale, recipient, subject, title, the content fragment's template name and variables, the plain-text part, a footer note): `From` is the sender address with the name `email.senderName`, the HTML part is `templates/email/layout.html` (site look with inline styles and table layout for Gmail and Outlook: the logo `receipt/logo.png` attached inline as `cid:logo`, Playfair/Georgia title, white card on `#f0f4ff`, footer with the note, `email.layout.identity` and a link to `app.site.public-url`) that inserts the context's fragment `th:fragment="content"` with `th:text` only, so every variable is escaped; the senders (`contact/infrastructure/mail/ContactMessageEmailForwarder`, `donors/infrastructure/mail/PasswordResetEmailSender`, `donations/infrastructure/report/MonthlyReportEmailSender` and `ImportAlertEmailSender`) build the draft and the plain text and send the result. `EmailTemplateColoursTest` keeps every colour under `templates/email/` equal to a `--color-*` token of `frontend/src/styles/themes/_nova-nadeje.scss` (the test task declares the theme as an input); the sender tests write previews to `backend/build/email-preview/`. `shared/infrastructure/config/PublicUrlProperties` (`app.site.public-url` from `PUBLIC_URL`, the address visitors use, validated at startup, for links in e-mails). Contract: "Shared pieces".
