# System overview

How each bounded context works today. Keep it current in the same PR as the change; the rules for new work are in `CLAUDE.md` and `.claude/rules/`, the HTTP shapes in `docs/api-contract.md`, the security mechanisms in `docs/security-overview.md`, the frontend in `docs/frontend-overview.md`, operations in `deploy/README.md`.

## contact

- `POST /api/contact/messages` stores the message in `contact_message` and forwards it by e-mail after commit (the foundation's mailbox copy is never touched by the web). The request checks the address with `EmailAddress.SHAPE_REGEX` as the donor requests do, so a malformed address is a field error before the value object sees it. The sender gets no confirmation e-mail: the form is public, and one would let anybody send mail to any address.
- Retention: every day at 03:30 Prague time `infrastructure/retention/ContactMessageRetentionScheduler` runs `application/ContactMessageRetentionService`, one `DELETE` over `ix_contact_message_received_at` of rows with `received_at` before now minus `app.contact.retention.max-age` (`P365D`). Cron `app.contact.retention.cron`, `-` turns it off (every `@SpringBootTest` does). The privacy policy promises the year for the web database only.

## donors

- Registration (person, or company with IČO), sign-in, refresh-token sessions, sign-out and the profile: `/api/donors/auth/**`, `/api/donors/me`. A refresh (`application/DonorSessionService.refresh`) reads the presented token under a row lock (`RefreshTokenRepository.findBySecretHashForUpdate`, `PESSIMISTIC_WRITE`, which Hibernate sends as `select … for no key update`), because two refreshes of one cookie at once (two tabs, an app and a tab sharing the cookie jar) must not both see it unused; the second waits, then finds it used with its successor (`donor_refresh_token.successor_id`, `donors/017`, set by `recordSuccessor` in the same transaction) and gets the 60 s reuse grace (`RefreshToken.mayBeReissuedAt`, `REUSE_GRACE`): the unused successor is revoked and marked superseded by a conditional update (`supersedeIfUnused`, so a successor being used at that moment wins and the reuse is a replay; `superseded_at` makes a later presentation of that successor a replay) and a new token is issued in its place. Revoking every session (`revokeAllOf`) first locks the donor's tokens in id order (`lockAllOfInIdOrder`), behind the donor's sessions lock (Devices below), so a replay queues behind a credential change or another replay instead of deadlocking. The plain rotation locks nothing but the presented token; when that token turns out used or superseded (the reuse grace, which also supersedes the successor, or a replay, which ends every session), the attempt is rolled back before it locks anything else and starts again in a new transaction that takes the sessions lock before the token (`DonorSessionService.refresh` runs both attempts through `TransactionOperations`, committing an `InvalidRefreshToken` as `noRollbackFor` did, so `DonorAuthenticationService.refresh` has no transaction of its own and reads the view after the refresh committed). Sign-out (`close`) takes the sessions lock, then the same row lock, and revokes the presented token and its unused successor (`revokeIfUnused` on both); a superseded token presented to sign out revokes every session, as a refresh with it does. Everything else about a used token stays a replay that revokes every session (`docs/security-overview.md`, Tokens). The API is an OAuth2 resource server validating its own HS256 JWTs. Passwords are stored as BCrypt (cost 12) of their SHA-256 hex digest (`infrastructure/security/BCryptPasswordHasher`), so all 128 characters count where BCrypt alone reads 72 bytes.
- Devices (plan v3, slice 2.9; contract "Devices" under "Authentication"): `domain/DonorDevice` is one sign-in of a browser or installed app (`donor_device`, `donors/018`), named by `DeviceDescription` (platform and browser enums that `interfaces/rest/UserAgentDevice` reads from the first 512 characters of `User-Agent`; the header is not stored), with `signed_in_at`, `last_used_at`, `ended_at` and `end_reason` (`DeviceSignOutReason`: `SIGNED_OUT`, `REMOTE_SIGN_OUT`, `CREDENTIALS_CHANGED`, `ADMINISTRATION_CHANGED`, `ERASED`, `REPLAY`, `EXPIRED`). Every browser refresh token belongs to a device (`donor_refresh_token.device_id`, nullable for connected applications and for tokens from before 2.9; `DonorSessionService.deviceOf` gives such a token a device signed in at its issue at its next refresh, or, when the token was already used within the reuse grace, the device its successor is on, refused unless that device is still active and the donor's; a used token presented again within the grace whose device, or its successor's, has ended is refused before the grace's own checks, so it ends no other session, while a superseded token or one presented after the grace stays a replay), and the access token carries the device as `sid` (`JwtAccessTokenIssuer`). `shared/infrastructure/security/LiveSessionValidator` runs after the timestamp, issuer and audience checks of `JwtConfiguration.jwtDecoder` and asks the port `shared/application/session/SessionLiveness`, implemented by `donors/infrastructure/session/DeviceSessionLiveness`: a Caffeine cache of 30 s per device (at most 10 000, ticking with the injected `Clock`, so the scenarios move it) in front of `DonorDeviceRepository.isSignedIn` (not ended and holding a refresh token neither used, revoked nor expired), because one indexed query per request would double the work of every API call while a sign-out must still take effect at once: `DeviceSignOuts` publishes `DeviceSignedOut` (a cross-context event in `shared/application/event/`, which `operations`' `PushSubscriptionLifecycle` also consumes `BEFORE_COMMIT` to delete the device's push subscription) and `DeviceSessionLiveness.forget` drops the cached answer `AFTER_COMMIT` (with `fallbackExecution`, so a sign-out outside a transaction is forgotten too), so the next request reads the committed state. The backend runs as one instance, so the cache needs no distribution. `application/DeviceSignOuts` is the only writer of bulk sign-outs, by donor or by device (`Propagation.MANDATORY`, so it always joins its caller's transaction and a refused change ends nothing; the rotation of one token and the revocation of the presented one on sign-out stay in `DonorSessionService`). Every path first takes the donor's sessions lock (`RefreshTokenRepository.lockSessionsOf`: `AdvisoryLock.DONOR_SESSIONS`, `pg_advisory_xact_lock(20261109, <hash of the donor id>)`, database audit #453) and then locks the donor's refresh tokens in id order before it touches a device row (`lockAllOf`, also the first step of `revokeAllOf`; `architecture/DeviceSignOutRulesTest` keeps `lockAllOf` inside `DeviceSignOuts`), so two concurrent bulk sign-outs of one donor wait for each other instead of deadlocking. A path that holds one of the donor's tokens before it sweeps them all takes the sessions lock before that token too, because otherwise it holds a row that another sweep needs early in its id order while it waits for one that sweep holds (two devices signing out at once, a replay during a sign-out, a sign-out during a password change: PostgreSQL aborted one of the two with `40P01`, a 500 that rolled the sign-out or the password change back; `DonorSessionLockOrderTest` runs these pairs against PostgreSQL): a sign-out (`close`) reads the token's donor without a lock (`findDonorOfSecretHash`, a scalar query, so no entity read before the lock stays in the persistence context), takes the sessions lock and only then the token's row lock; a browser refresh that finds its token used or superseded starts again under the sessions lock (above); a connected application's refresh takes it right after reading its token, before `markUsed`. A plain browser refresh never takes it: it locks its own token and then updates the device row, the order every sweep keeps too. The lock is advisory rather than the donor row because it was chosen while the second-factor recovery by payment ended every session from inside the bank import after the pairing lock, where a donor-row lock would have waited for a profile save that holds the row and waits for the pairing lock in its donations listener; since #468 the import completes the recovery before the pairing lock and under the donor row, and the sessions lock stays separate so a refresh and a sign-out never wait for a donor-row writer; two donors whose ids hash alike only queue their sign-outs. The nightly cleanup ends each expired device through `end`, so under its donor's sessions lock, which it keeps until it commits (a sign-out or a replay of such a donor waits for the job, which runs at 04:10; the next run completes one that was aborted), and then deletes the spent tokens of every donor after locking them in id order (`lockSpentBeforeInIdOrder`), the order every sweep keeps, so the delete cannot deadlock with a sweep of a donor whose spent tokens it removes, as the delete in scan order could. The three methods: `endAllOf` revokes every refresh token of the donor (`revokeAllOf`, connected applications included) and ends the active devices, optionally all but the one that is changing the password or the second factor (`RequestingDevice` from the request's `sid` and `User-Agent`; `DonorSessionService.continueOn` then issues the new tokens on that device, so it keeps its place in the list and its earlier access token stays valid, as before 2.9); `endOthersOf` (the donor's "Odhlásit všechna ostatní zařízení") revokes only the device-less browser tokens and ends the other devices, leaving connected applications (Q12); `end` takes the donor and the device id, reads the device only under that lock and ends it only when it is the donor's and still active (otherwise it changes nothing and answers false: the 404 of a single sign-out). Every end is one conditional update (`DonorDeviceRepository.endIfActive`, `… where ended_at is null`, which answers whether it changed the row and clears the persistence context), never a save of the device read earlier, and `DonorDeviceJpaEntity` maps `ended_at` and `end_reason` with `updatable = false`, so a save that records a device's use (`continueOn` after a credential change, a refresh) writes only `last_used_at` and can never put a concurrent end back to null (database audit #447): the cleanup reads its candidates before it takes any lock, and the row it then reads may come from the persistence context rather than the database, so a device another sign-out ended meanwhile would otherwise be ended again. So a concurrent end keeps its reason, the device is neither counted nor announced twice, and only the update that ended it publishes `DeviceSignedOut`; `DonorDevice.end` states the same rule for the domain and the fixtures. `architecture/DeviceSignOutRulesTest` refuses every other caller of `revokeAllOf`, `revokeAllOfDevice` and `revokeDevicelessBrowserTokensOf`, so a new place that ends sessions cannot forget the devices and the cache. `application/DonorDevicesService` lists (`findSignedInOf`, the calling device first, then by last use, then by platform and browser, and only then by id, because two devices signed in at the same moment differ only in the random part of their UUIDv7 ids, which put them in a different order in two recordings of a scenario) and signs out one device (404 `donors/device-not-found` unless it is the donor's and active) or the others; `interfaces/rest/DonorDevicesController` at `/api/donors/me/devices`. The daily `infrastructure/session/SessionCleanupScheduler` (`app.donors.session-cleanup.cron`, 04:10 Prague, `-` turns it off) runs `DonorSessionCleanupService`: it first nulls the readable code of every recovery by payment that is no longer open (used, or expired unused; a use nulls it at once) and deletes the second-factor challenges, recoveries and connection authorization codes that expired more than 30 days ago (`SPENT_SECRET_RETENTION`; a use always comes before the expiry, so this covers used and abandoned ones alike; database audit #454: nothing reads a spent one, an unknown challenge or code answers as an expired one does, and the 30 days only keep a row for looking into a sign-in or recovery a donor reports; the tables are small, so the deletes need no index on `expires_at`), before it takes any sessions lock, so it never waits for a recovery payment in flight while it holds one; then it ends as `EXPIRED` every active device without a usable refresh token, deletes refresh tokens revoked or expired more than 30 days ago (a used token stays until then, so a replay of it is still recognised while it could be valid) and devices ended more than 400 days ago (their tokens with them, `ON DELETE CASCADE`), and logs one INFO line with the three counts (the one-time secrets are not counted there, so the line keeps its shape), or an ERROR line with the exception class only. `shared/infrastructure/security/SignInBearerTokenResolver` reads no bearer token on `POST /api/donors/auth/**`: those endpoints authenticate by the cookie, the password or the link, and a stale access token sent along (a test client, an old tab) must not turn a refresh or a sign-out into 401 `auth/session-ended`; ignoring a token can only make a request anonymous, never grant more.
- Session kinds (plan v3 2.10; contract "Session kinds" under "Authentication"): a sign-in (password, second-factor step, passkey, e-mail confirmation) names its `domain/SessionKind` (`APP`, `REMEMBERED`, `BROWSER`, `PUBLIC`; absent is `SessionKind.UNNAMED`, `REMEMBERED`), which the device keeps (`donor_device.session_kind`, `donors/019`, nullable, so the 2.9 image still inserts and an older row reads as `REMEMBERED`). `domain/SessionLengths` gives each refresh token its end from the issue: `APP` 400 days, `REMEMBERED` `app.donors.session.remember-days` (the setting `SESSION_REMEMBER_DAYS`, 1–30, default 14, checked at startup by `DonorSessionProperties`), `BROWSER` 12 hours, `PUBLIC` the earlier of 1 hour and 12 hours after the device's sign-in; `DonorSessionService.issue` computes it again at every refresh from the device's kind, and `continueOn` (a credential change from a session) keeps the device and its kind, and refuses a change from a session whose device has ended or whose kind's limit has passed (a public computer past its 12 hours) with 401 `auth/session-ended` (`domain/SessionEnded`); the four use cases that continue a session (`DonorCredentialsService.changePassword` and `removePassword`, `DonorSecondFactorService.confirm` and `disable`) ask `requireLasting` after their own checks and before they hash, store, sign out or announce anything, so a refused change leaves no log line or e-mail and its transaction rolls back, so signing out or outliving the limit and changing the password within the 30 s an old access token is still accepted cannot open a fresh session; a session that names no device of the donor (a token from before 2.9) continues on a new `BROWSER` device. `interfaces/rest/RefreshTokenCookie` writes the app's token into `refresh_token_app` and every other kind into `refresh_token` (`Max-Age` only for `APP` and `REMEMBERED`, a session cookie otherwise) and reads the cookie the header `Nfnn-Session: APP` names on refresh and sign-out (`application/SessionCookie`); `refresh` checks that the token was presented in its kind's cookie only after the superseded and reuse checks, so a token in the wrong cookie is refused without ending a session while a replay in either cookie still ends every one. The kind grants nothing: `Donor.sessionRoles` stays the second factor at sign-in (Q1). A restore ends every session: `deploy/backup/backup.sh` `revoke_restored_credentials` runs `revoke-restored-credentials.sql` in one transaction on the staging database before the swap; its `pg_temp.end_sessions()` revokes every refresh token, ends every active device as `EXPIRED` and deletes every push subscription, and `pg_temp.spend_one_time_secrets()` (2.34) marks every unused link, challenge and code of five single-use tables used (the 1 Kč recovery stays open, `RestoreRevocationSqlTest` keeps the list against the schema); both skip a table or column an older dump lacks (`to_regclass`, and for refresh tokens from before `donors/009` the `used_at` column check); each returns how many were still valid, which `status/restore` carries as `sessions_ended` and `one_time_secrets_spent` and `BackupRestoreService.recordFinishedRestore` writes into `BACKUP_RESTORED` (`RestoreRevocations`; a status without both counts, from an older container, gives the older text), because the dump brings back tokens that were valid, or already rotated away, when it was taken; `EXPIRED` because the previous image reads no new reason.
- E-mail verification: a registration answers 202, stores the donor with `donor.email_verified_at` null and sends the verification e-mail (also the welcome e-mail) with `{app.site.public-url}/potvrzeni-emailu#token=…` (plus `&returnTo=%2F%23prispet` for a registration started in "Přispět": the request's optional `returnTo`, checked against `domain/RegistrationReturn`, travels in `DonorEmailVerificationRequested` into the link and is never stored, so it also works when the e-mail is opened in another browser; a request for a new link may name it again); `POST /api/donors/auth/email-verification/confirm` marks the e-mail confirmed, publishes `DonorRegistered` (only then does `donations` get its `donor_record`) and opens a session (200 with the auth response); `POST .../request` (always 202, 5 per hour per address, at most 3 live links of 24 hours in `donor_email_verification_token`) sends a new link to an unconfirmed account. Sign-in at an unconfirmed account with the right password answers 401 `auth/email-not-verified`; a reset request for it sends nothing. Registering an address again: `DonorRegistrationService` first builds the new account, every check and the password hash included, and only then looks the address up, so the answer and its time never depend on whether the address is registered; a confirmed account's owner gets the "Váš dárcovský účet už existuje" e-mail and nothing changes; an unconfirmed registration is replaced by the new one. `application/DonorEmailVerificationService`, `infrastructure/mail/DonorRegistrationEmailSender`, `interfaces/rest/DonorEmailVerificationController`. Donors from before the change were marked confirmed by changelog `donors/004`. Once a registration has waited a day unconfirmed, `infrastructure/reminder/RegistrationReminderScheduler` (hourly, `app.donors.registration-reminder.cron`, `-` turns it off and every `@SpringBootTest` pins it) has `application/DonorRegistrationReminderService` send one reminder with a fresh link (`DonorRegistrationReminderDue`, template `email/donors/registration-reminder`), only within a week of the registration and recorded in `donor_registration_reminder` (changelog `donors/012`) so it never repeats. The same job first deletes the registrations more than 30 days old that nobody confirmed (#455, decided by the database audit's lead on Jakub's delegation, 2026-11-06): `application/DonorRegistrationExpiryService` (`RETENTION`) runs `DonorRepository.deleteUnconfirmedRegisteredBefore`, one statement `delete from donor where id in (select id … where email_verified_at is null and erased_at is null and registered_at < :cutoff order by id for update skip locked)` served by `ix_donor_registered_at`; every table that refers to `donor` cascades (the verification links, the reminder, and nothing else an unconfirmed account can hold: it cannot sign in, and `donor_record` exists only after the confirmation, so donations hold nothing of it), the address and the variable symbol become free, and the job logs only the count. The `for update` in the subquery is what keeps a confirmation safe: a plain `id in (select …)` takes its candidates from the statement's snapshot and deletes a row a confirmation committed meanwhile, because the recheck after the wait looks only at the id; with `for update` PostgreSQL rechecks the whole condition on the newest row, and `skip locked` leaves a row a confirmation, a replacing registration or a request for a new link holds to the next hour instead of waiting for it (`UnconfirmedRegistrationExpiryConcurrencyTest`). A request for a new link reads the account with `findByEmailForUpdate`, so it waits for a deletion in flight and then finds no account, instead of inserting a link for a deleted row and failing on the foreign key with a 500. The symbol of a deleted registration may be drawn again: its owner never saw it (an unconfirmed account cannot sign in and no e-mail names it), so a payment can carry it only by the same chance as any of the nine billion symbols, which `unusedVariableSymbol` does not check against the bank either. The reminder's `window` must stay shorter than `RETENTION` (`RegistrationReminderProperties` refuses it at startup), so the reminder never names a registration the deletion has reached, and the reminder e-mail says the registration goes after those 30 days. Contract: "E-mail verification".
- Limits per client address, every request counted, a limited one answers 429 `donors/rate-limited` before any hashing or work: sign-in 10 per 15 min (`interfaces/rest/SignInRateLimiter`), registration 5 per hour (`RegistrationRateLimiter`), reset request 5 per hour (`PasswordResetRateLimiter`); all built like the reset limiter. A sign-in with an unknown e-mail is compared against a real BCrypt cost-12 hash (`UNKNOWN_DONOR_HASH` in `DonorAuthenticationService`), so it costs the same as a real one. `DonorAuthenticationService.login` has no `@Transactional` (#449): it reads the account in a short read-only transaction, compares the password (about 0.3 s of BCrypt) holding no connection, and opens the session or the second-factor challenge in a second transaction, which reads the account again and refuses the sign-in as wrong credentials unless the same account still holds that address and the hash that was compared; a burst of sign-ins therefore holds pooled connections only for their queries. Contract: "Sign-in and registration limits".
- Credentials while signed in: `PUT /api/donors/me/password` (current + new password → 200 with a new session, every other refresh token revoked, 10 attempts per 15 min per address) and `POST /api/donors/me/email-change` (new address + password → always 202, 5 per hour per address): a free address gets the confirmation link (a `donor_email_verification_token` row with `new_email`, 24 h, confirmed through the same `/potvrzeni-emailu` page, the link marked `&change=email` so the page posts it to `POST /api/donors/auth/email-change/confirm` (`DonorEmailChangeConfirmationController`, `DonorEmailVerificationService.confirmChange`), which switches the address, revokes every session, opens none and e-mails the previous address; the registration confirm takes only registration links, so a change link cannot sign anyone in), an address another account has gets the "jiný účet chtěl použít vaši adresu" notice instead, its change stored all the same so nothing tells the two apart. One change is pending at a time: `DonorEmailVerificationService.issueChangeLink` deletes the donor's earlier change links before it stores the new one (registration links keep their limit of 3), `DonorViews` reads the newest live one into `GET /api/donors/me` as `pendingEmailChange` (`EmailVerificationTokenRepository.findPendingChangeOf`), `POST /api/donors/me/email-change/resend` issues it again with a new secret (sharing the request's limiter; `NoPendingEmailChange` 409 without one) and `DELETE /api/donors/me/email-change` deletes the change links (Jakub 2026-10-24). `application/DonorCredentialsService`, `infrastructure/mail/DonorEmailChangeEmailSender`, `interfaces/rest/DonorCredentialsController`; changelog `donors/005`. Contract: "Changing the password and the e-mail".
- Roles: `donor_role` holds `DONOR` and, for administrators, `ADMIN`; both travel in the JWT as `ROLE_*` authorities. The role is granted and taken away by another administrator (`AdminDonorsController`, `application/AdministratorService`: `GET/POST /api/admin/donors/administrators`, `DELETE .../administrators/{id}` ends every session of the donor; audited as `GRANT_ADMINISTRATION` / `REVOKE_ADMINISTRATION`; the grant asks `application/SecondFactorHoldings`, also behind `SecondFactorSessionGuard`, whether the donor holds a confirmed authenticator app or a passkey, and refuses one without either; the revoke takes the advisory lock `AdvisoryLock.ADMINISTRATORS` (`DonorRepository.lockAdministrators`) before the donor row and refuses, with 409 `donors/last-administrator`, to take the role from the last administrator, database audit #468: two administrators taking the role from each other at once, or one whose own role was taken a moment ago and whose token still reaches the service, left the site without an administrator until a restart with `ADMIN_EMAILS`; the lock makes the second revoke wait and count the administrators after the first committed, and only the revoke takes it, always before any donor row, so it closes no cycle, `AdministratorRevokeConcurrencyTest`) and, for the first administrator, by `ADMIN_EMAILS` from the first setup (`application/AdministratorProperties`, `AdministratorBootstrap` on `ApplicationReadyEvent` and on a confirmed registration, only while the site has no administrator, so a restart never gives a removed administrator the role back); nothing by SQL (Jakub, 2026-10-22). `POST /api/admin/donors/{id}/second-factor/reset` turns a donor's lost two-factor authentication off (factor deleted, sessions ended, `RESET_SECOND_FACTOR` audited, e-mail `email/donors/second-factor-reset` through `DonorSecondFactorResetEmailSender`). `GET /api/admin/donors?query=` and `GET /api/admin/donors/{id}` (`application/DonorAdministrationService`, read-only; `DonorRepository.search` over name, e-mail and the start of the symbol, paged: 20 per page by default, at most 100) serve the donor search and the account half of the donor card `/sprava/darci/{id}`, which also offers the two-factor reset for any donor. `DELETE /api/admin/donors/{id}` (`application/DonorErasureService`) is the GDPR erasure: the account keeps its id, symbol and locale and gets the placeholders of `shared/domain/ErasedPersonalData` (`Donor.erase`, `donor.erased_at`, changelog `donors/007`), the factor, sessions and link tokens go, `DonorErased` tells `donations`, `ERASE_DONOR` is audited and `DonorAccountErasedEmailSender` tells the former address; an administrator cannot be erased, an erased donor cannot sign in or get a reset link, the address can register again. Erasure after a restore (issue #459): the backup container carries a donor's `erased_at` from the database it replaces into the restored copy, together with the empty roles, password and factors, but not the rest of the erasure, which spans both contexts; so at every start `application/RestoredErasures` (on `ApplicationReadyEvent`) reads the erased donors (`DonorRepository.findErased`) and, for each whose personal data are back (`Donor.erasureIncomplete`: anything but the placeholders, a password, a role or a confirmed address), calls `DonorErasureService.completeRestoredErasure`, one transaction per donor under the donor row lock: `Donor.completeErasure` puts the placeholders back and keeps the first `erased_at`, the factor, passkeys, sessions and link tokens go as in an erasure, and `DonorErased` with the first time tells `donations`, which erases its copy, links and answers again; no second `ERASE_DONOR` (the carried trail already holds the original) and no second e-mail to the former address. A completion that fails is logged with the donor id and the exception class and tried again at the next start, and a completed one is no longer incomplete, so the next start skips it. `GET /api/admin/donors/actions?before=&limit=` (`application/AdministratorActivityService`) reads the audit trail through the shared port `shared/application/audit/AdminActionTrail` and names the administrators, and the donors the changes concern, with one `DonorRepository.findByIds`; the page `/sprava/historie` shows it. Each entry also carries a sentence for a person (`summary`, Jakub 2026-10-24) made at read time, not stored: `application/AdminActionFacts` recognises the fixed shape of each action's `details` (Czech, and English for rows written before 2026-10-24) and takes out ids, amounts, days and codes, and `interfaces/rest/AdminActionSummaries` (an adapter, because it reads `MessageSource`) fills the `admin.action.summary.*` text of the request's language with the donor's name, amounts in crowns and dates. Reading instead of storing a second text needs no migration, gives the old English rows the same Czech sentence, and keeps the stored `details` (with their ids) as the record of what happened; the price is that the publishers' texts are a format: a use case that changes the wording of its details changes its shape in `AdminActionFacts` in the same PR (`AdminActionFactsTest` holds a Czech and an English example of every action), and an unknown shape falls back to the stored details. News and projects are named by their title (Jakub's testers 2026-10-29: the slug means nothing to an administrator): since 2026-10-29 `NewsAdminService` and `ProjectAdminService` end their details with "; titulek „<title>“" (the title the administrator also sees in the lists; public content, not personal data, and never written to a log, which keeps only the ids), recognised as the `withTitle` variant (`admin.action.summary.<ACTION>.withTitle`); older rows keep the slug in their sentence. `ADMIN` enters the JWT only for a session opened with the second factor (`Donor.sessionRoles`; the refresh token remembers it in `second_factor_verified`), so `/api/admin/**` (403 `auth/forbidden` otherwise) opens for an administrator only after they turn the second factor on and sign in with the code; the administration is `/sprava` in the frontend. Contract: "Authentication", "Administration".
- Sign-ins to the administration (Jakub 2026-10-29): `donor.last_signed_in_at` and `previous_signed_in_at` (nullable, `donors/016`) are written only by `DonorSessionService.signIn`, the session a completed sign-in opens (password, password and code, passkey, the e-mail confirmation link), and only when that session carries `ADMIN`; `DonorSessionService.open` (the session reopened after a password, second-factor or password-removal change) and the refresh write nothing. `DonorRepository.recordSignIn` shifts the last one into the previous one in one `update` (`JpaDonorRepository`, a native query; the entity maps `previous_signed_in_at` read-only, so saving a donor never overwrites it), there is no ordering constraint so a clock step back never fails a sign-in, and `AdministratorService.revoke` forgets both. - Writes to the donor row (database audit #447): `DonorJpaEntity` has no version column and every writer saves the whole row (Hibernate's UPDATE names every updatable column), so each writer of the `Donor` aggregate first reads it under a row lock, `DonorRepository.findByIdForUpdate` or `findByEmailForUpdate` (`PESSIMISTIC_WRITE`), and holds it until it commits: the profile save, the password change and removal, the password reset, the e-mail confirmation of a registration or of a change, the registration that replaces an unconfirmed account with the same address, the erasure, the start of a second-factor recovery by payment (which writes only its recovery row, but needs one start at a time, Second factor above) and its completion by the bank import (which spends the recovery and deletes the second factor only once it holds the donor), granting and taking away the administrator role (also at startup), and adding or removing a passkey, by the donor, through the e-mail recovery or by an administrator. A password reset and a password change hash the new password with BCrypt while they hold the lock (about 0.3 s), so the row read and the row written are the same; only another write of the same donor waits for it, and `PESSIMISTIC_WRITE` is `for no key update` on PostgreSQL, so inserting a session, token or passkey row that refers to the donor (a `for key share` on it) never waits. `Donor.updateProfile`, `changePassword`, `changeEmail` and `verifyEmail` refuse an erased donor with 409 `donors/already-erased`, so a tab left open after the erasure cannot put personal data back: a browser token is refused anyway (its device ended with the erasure, 401 `auth/session-ended`), but a token without `sid` or a request already past the token check reaches the service; `DonorRecord.changeProfile` refuses an erased record too (an `IllegalStateException`, as `erase` twice: the donors side refuses first, so it only guards the invariant).
- Claiming an address (database audit #450): an address that no account holds yet has no row to lock, so the registration and the confirmation of an e-mail change first take the address lock, `DonorRepository.lockEmail` (`AdvisoryLock.DONOR_EMAIL_ADDRESSES`: `pg_advisory_xact_lock(20261108, <hash of the address>)`, PostgreSQL's two-part key, whose key space the one-part locks do not share; Java's `String.hashCode` of the lowercased address, so the address itself never reaches the query, and two addresses with one hash only wait for each other), held until commit and refused outside a transaction. - Withdrawing a receipt signing key (plan v3, 1.13; contract "Receipt verification proof and signing keys"): `application/signing/ReceiptSigningKeyWithdrawal` is the second writer of `receipt_signing_key` (ArchUnit `ReceiptSigningKeyRulesTest` admits only it and the start-up registrar). It finds a published row (404 otherwise, before the second factor), refuses one already `revoked` (409), pauses after five refused second factors of the administrator within 15 minutes (`ReceiptSigningKeyWithdrawalRefusals`, the backup key's design, each refusal audited in a transaction of its own after the one that checked the code has rolled back), then, in one short transaction (`TransactionOperations`; `withdraw` itself has no `@Transactional`), checks a fresh second factor through the shared port `FreshSecondFactor` (the one the backup key uses; the request record moved to `shared/interfaces/rest/FreshSecondFactorRequest` for both controllers), then locks the row (`lockForWithdrawal`, `PESSIMISTIC_WRITE`; the adapter refreshes the locked entity, because the persistence context still holds the row as it was read before the lock) and refuses it again if it is `revoked` by now, stores the row `revoked` and sealed again (`ReceiptSigningKey.withdrawn`), and publishes `AdminActionPerformed` (`WITHDRAW_RECEIPT_SIGNING_KEY`) and the shared event `ReceiptSigningKeyWithdrawn(adminId, keyId, current, at)`, all in one transaction. The row lock is there because the withdrawal reads, checks and writes the row in one transaction: without it two withdrawals of one key at once (two tabs, two administrators) both found it `active` and both withdrew it, which wrote two audit entries, sent two rounds of e-mails and asked for two restarts; with it the second waits for the first, then finds the row `revoked` and answers 409, auditing nothing (`ReceiptSigningKeyWithdrawalConcurrencyTest`). The pause and the second factor come before the lock (review 1.13 r2), and no request holds two pool connections (review 1.13 r3). While one `@Transactional` spanned the whole use case, a refused code kept its connection while it asked for a second one to audit the refusal (`REQUIRES_NEW`): ten wrong codes at once (what the per-address limiter lets through, and the pool's default size of ten, `spring.datasource.hikari` is not set) each held one and waited for an eleventh, the site had no connection for Hikari's 30 s, most ended in a 500 and their refusals were never counted towards the pause. So the use case opens no transaction: the unlocked read and the pause are short reads of their own, a wrong code fails in the write transaction before the lock, which rolls back and hands its connection back, and only then is the refusal audited, also when the requests outnumber the pool's connections (`ReceiptSigningKeyWithdrawalConcurrencyTest`, with the real second-factor check). The second factor sits inside the write transaction rather than in one of its own because of its replay guard (`donor_second_factor.last_used_step`, a conditional update): the same administrator sending the same code twice at once makes the second request wait on the first one's update of that row until the first withdrawal commits, then find the code used; it re-reads the row before auditing the refusal and, the key being `revoked` by then, answers 409 already withdrawn and audits nothing (same test). In a transaction of its own the first request's use of the code would commit before its withdrawal, and the second could find the code used while the row still looked `active`, auditing a refusal of a right code. That a refused code whose key was withdrawn meanwhile counts nothing gives a guesser nothing: the answer does not depend on the code, and a withdrawn key is refused before any code is checked. As before, a withdrawal refused under the lock (another administrator withdrew the key first) rolls the use of its code back too. Only `donors/infrastructure/mail/ReceiptSigningKeyWithdrawnEmailSender` listens to the event (`@Async`, `AFTER_COMMIT`): it e-mails every administrator, each send caught on its own, and then, in a `finally` on the same thread, publishes the shared `ReceiptSigningKeyWithdrawalAnnounced(keyId, current)`. For the server's own key `operations/infrastructure/backup/ReceiptSeedRenewal` writes the key id into `/restore/receipt-signing-key.renew` (a `.part` file moved atomically) as soon as the withdrawal commits (an `AFTER_COMMIT` listener of `ReceiptSigningKeyWithdrawn` with `@Order(HIGHEST_PRECEDENCE)`, so it runs before the mail sender's listener hands the notices to their thread and the announcement can never come before the request), and on `ReceiptSigningKeyWithdrawalAnnounced` (a plain `@EventListener`) calls `ApplicationRestarter.restartAfterCommit`, which restarts at once outside a transaction, when the request in the restore folder names that key (a request that could not be written restarts nothing). The order is explicit because both used to be `@Async` listeners of the withdrawal: the restart could stop the backend while the notices were still being sent, so administrators were not told of a withdrawal they did not make; now the restart comes only after every notice was sent or refused (a refusal logged with the administrator's id and the exception class first), and a mail server that hangs delays it by at most the mail timeouts (10 s per step, `reliability.md`). Only the restart waits for the notices, never the request (review 1.13 r2): while the request was written on the announcement too, a stop or a crash during the mail run (the async executor does not wait at shutdown) lost it, and the next start ran with the withdrawn key, refusing every receipt until someone renamed the seed by hand; now any later start renews the seed. The restart runs on the mail sender's async thread, never inside the withdrawal's AFTER_COMMIT callback, where the restarter's own after-commit hook would be registered too late and lost. The Java process cannot write `secrets/`, so the backend asks for the new seed instead of making it: the entrypoint (root) checks that the marker names the key of the current seed, keeps the old seed as `secrets/receipt-signing-key.withdrawn-<key id>`, generates a new one and the start registers it. At every start the entrypoint also passes the key ids of the kept seeds as `RECEIPT_SIGNING_KEYS_WITHDRAWN` (`ReceiptSigningProperties.withdrawnKeyIds`, port `application/signing/WithdrawnSeeds`): `ReceiptSigningKeys` and the registrar treat them as withdrawn whatever the database says, so a restore of a backup from before the withdrawal cannot make the key active again. Issuing is ordered against a withdrawal: `DonationReceiptIssuer` asks `ReceiptSigningKeys.currentKeyHeldForIssuing()` first, which takes a shared lock on the server's own row (`lockForIssuing`, `PESSIMISTIC_READ`, `FOR SHARE`; `Propagation.MANDATORY`, so it always runs inside the issuing transaction, never a read-only one) before it reads the row and the trail. The check used to read before anything ordered it against the withdrawal's commit, so a receipt issued in that gap was frozen with the proof of a key withdrawn a moment earlier for good (nothing re-signs an issued receipt); now an issue waits for a withdrawal holding the row and then refuses, and a withdrawal waits for the issues in progress (`DonationReceiptIssuerWithdrawalConcurrencyTest`). Issues share the lock, so they never wait for each other. The refusal logs WARN, not ERROR: between the commit and the restart (the notice run plus about a minute of start-up) it is the expected state, and a seed that was not renewed shows as the registrar's ERROR at start, on `/sprava` and in `nfnn_status`. A restart right away rather than "at the next start": until then the server holds a key everyone was told to distrust and signs nothing, and a server can run for weeks without a restart. Withdrawing an earlier server's key restarts nothing.

Database sessions (#449, `reliability.md`): every wait on the database ends. The backend's pooled sessions start with `lock_timeout=10s`, `statement_timeout=30s` and `idle_in_transaction_session_timeout=2min`, passed as pgjdbc `options` in `spring.datasource.hikari.data-source-properties`, so they bind only the backend's own connections: never `ALTER ROLE`, because the backup container restores as the same `novanadeje_app` role and a restore must not inherit a statement limit, and never the server's settings. `lock_timeout` covers row locks (`FOR UPDATE`) and the advisory locks of `AdvisoryLock` alike, so no `jakarta.persistence.lock.timeout` hint is set. Each value against the slowest legitimate work: lock holders are short transactions (the import's pairing pass under the pairing lock, a receipt issue under the donor lock, the monthly report's send) and a request that waits longer gets a retryable answer instead of holding a Tomcat thread and a connection; the slowest statement (the administration's sync manifest over the whole administration, a growing report query) takes well under a second at the audited volumes, so 30 s only cuts a runaway plan; the longest idle stretch inside a transaction is the monthly report's mail send (10 s timeouts per SMTP step), so 2 min ends only a transaction nothing will finish, releasing its locks. The pool (`HikariCP`): at most 20 connections (Tomcat's request threads, the application executor's 8 and the one scheduler thread share it, and `nfnn-postgres` allows 100 with room for the backup container), 5 kept idle, a request waits at most 10 s for one, a connection lives 30 min, and one held for more than 60 s is reported at WARN by `com.zaxxer.hikari.pool.ProxyLeakTask` with the stack of the thread that took it (no data). A wait that runs out reaches the web layer as Spring's `PessimisticLockingFailureException` (55P03 lock not available, 40P01 deadlock, 40001), `QueryTimeoutException` (57014) or `CannotCreateTransactionException` (no connection) and `ServerBusyHandler` answers 503 `server-busy` with `Retry-After: 5`; the advisory lock of the pairing (`PostgresPairingLock`) is a `@Repository`, so its failure is translated like every other adapter's (`PostgresPairingLockTest`). Every scheduled job already catches its own failures and runs again at its next time (the import at the next hour or follow-up). Liquibase migrates on a connection of its own (`shared/infrastructure/persistence/MigrationDataSourceConfiguration`, the `@LiquibaseDataSource`, a plain driver connection from the same connection details, also with `logServerErrorDetail=false`): no statement limit, so a long data migration is never cut, and `lock_timeout` of `app.database.migration.lock-timeout` (2 min), so a migration blocked by a lock (a `pg_dump` running at the deploy) fails the start, which Docker repeats, instead of hanging. `DatabaseWaitLimitsTest` reads the settings of both kinds of session and the pool, and holds an e-mail address's lock in another session while that address registers: the request answers 503 after the lock limit and stores nothing.

The backend reads nothing from the request header `Nfnn-App` the browser app sends, logs it nowhere and stores it nowhere. It compares `Nfnn-App-Api`, the generation the app is built for, with its own: a write (`POST`, `PUT`, `PATCH`, `DELETE`) that names another valid generation is answered by the filter itself with 426 `app/update-required` and never reaches the security chain or a controller, because the app learns of a new generation only from an answer, so the first write a tab sends after a deploy would otherwise reach the server in the old shape; the session refresh, the sign-out and the receipt status question pass, as in the browser (Frontend below). A request without the header (the connector, an app built before 2.3, a script) is handled as before, so this is a compatibility measure, not a control. The generation counts breaking API changes only: it moves when a release removes or changes something an app of the previous release still uses, which the compatibility rule (`.claude/rules/backend.md`, API versions and compatibility) allows only together with the bump. `ApiGenerationTest` keeps it equal to the generation the browser app is built for (`frontend/src/app/core/version/api-generation.json`, which `api-generation.spec.ts` keeps equal to `API_GENERATION` in `api-generation.ts`), so an image pair built from one commit always agrees and only a tab opened before a deploy can disagree.

Stale writes (plan v3 2.18, D4, contract in `api-contract.md`, "Stale writes"): a versioned write takes `ExpectedVersion` (`shared/application/version/`), which `shared/interfaces/rest/ExpectedVersionArgumentResolver` (registered by `ExpectedVersionConfiguration`) reads from `If-Match` after the security chain and the body's validation: a browser session without it gets 428 `shared/version-required` (`VersionRequiredException`), a connected application (a token with `scope`) without it gets `ExpectedVersion.none()`, which admits any version, so the connector works as before. The version is `RowVersions` (`shared/infrastructure/json/CanonicalRowVersions`: the first 16 hex characters of the SHA-256 of the `CanonicalRows` text of the stored fields), computed in the application layer by `donations/application/sync/AdminDonationsRows` (payments with their gift, links, answers, report settings; the same rows the administration's device copy holds, so a chunk row, a list item and a refusal carry one version) and `content/application/ContentVersions` (news articles and projects). Each use case compares it after its locks and before it changes anything, and throws the context's `ChangedMeanwhile` (409, with the version and the record now stored): manual pairing and unpairing, the link writes and the answer reversals and resets under `PairingLock`, the report settings under their own advisory lock `pg_advisory_xact_lock(20261106)` (`AdvisoryLock.REPORT_SETTINGS_CHANGES`, taken by `JpaReportSettingsRepository.lockForChange`, so two saves of the singleton serialise, and the version is read after the lock), news and projects under `SELECT … FOR UPDATE` of their row (`findByIdForUpdate`). A version is compared inside the same transaction that writes, never before the lock, so two writes made from one version cannot both pass. The clock is read after the lock too, so a write that waited behind another stores a later `updatedAt` and audit time than the one it followed. The report settings' change answers the row it wrote with the version over it from its own transaction (`SavedReportSettings`), never from a second read, which could already show another administrator's save. Whether a payment's row leaves out the payer is decided in one place, `AdminDonationsRows.paidPayment(payment, gift, giver)` from the gift's donor record (the list, the chunk and the write's check all ask it, and an unpaired payment, `unpaidPayment`, keeps its payer), so the three cannot drift into versions the write never accepts. The clock ticks in microseconds (`ClockConfiguration.STORED_PRECISION`), the precision PostgreSQL stores, so an instant a use case writes and returns hashes to the same version as the row read back later; with nanoseconds the answer's version would differ from the stored one and the next write from it would always be refused. Only stored fields count (never `symbolOffer`, `shared`, `donationCount` or `live`), so a computed field never makes a record look changed. Records 2.18 leaves without a version (operations settings, the backup plan, About, people and their order, the project order, push devices, a donor's own account actions, receipt issuance, the report send) are listed in the contract; drafts kept on the device (2.20e) and the administration's pages from the device copy (2.20a–c) send the version of the row they hold.

Live updates (plan v3 2.16, contract in `api-contract.md`, "Live updates"): `shared/interfaces/rest/LiveController` opens a stream at `GET /api/live` for a browser session and hands it to `shared/infrastructure/live/LiveStreamHub`, which keeps the open streams in memory (none in the database: a restart closes them and every app opens a new one). Writers do not call the hub: the persistence adapters publish `StoredDataChanged(feed, donor)` (`shared/application/event/`, `LiveFeed`) when they save or delete what a feed shows (`JpaDonationRepository` for `donations` and `payments`, since the payments list shows each gift's pairing, `JpaDonorRecordRepository`'s sender account links and `JpaSymbolClaimRepository` for `bank-accounts`, `JpaBankPaymentRepository` for `payments`), and `FioImportScheduler` publishes `bank-import` when a run ends, after its in-progress flags are cleared, so the `GET` of the bank check the hint triggers already reads `checking: false`. Publishing from the adapters rather than from each use case is deliberate: every writer of those tables, present or future, goes through them, so no use case can forget a hint. `LiveHintListener` takes the event `AFTER_COMMIT` (`fallbackExecution`, so a write outside a transaction still hints), so a rolled-back change never hints and a hint never arrives before its data can be read; the hub only queues the feed on each matching stream and two daemon threads of its own (`live-hub-N`) send, so a slow client never holds a request or the committing thread, and a feed changed several times before the send goes out once; a stream queues its hints until its revision is written, so the revision always comes first. The scheduler removes cancelled timers (`setRemoveOnCancelPolicy`), so a closed stream keeps no timer, and with it no emitter, in its queue for the rest of the token's life; while the hub is not running (start, shutdown) it answers 503 `live-unavailable` rather than an ended session, so the app retries instead of refreshing. `JpaRefreshTokenRepository.revokeAllOf`, the one place every "end every session of this donor" goes through (a password change or removal, turning the second factor on or off, a change from a link, the administrator role taken away, an erasure, a second-factor reset, a refresh-token replay), publishes `DonorSessionsEnded`; the hub closes that donor's streams opened with a token issued before that second and refuses such a token for an access token's lifetime plus a minute, so a session that continues (the tab that changed the password, which `continueOn` gives new tokens) refreshes and opens again, while the others cannot. Signing out one device or every other device revokes no other session (`DeviceSignOuts.end` and `endOthersOf`, Devices above), so the hub also hears `DeviceSignedOut`: `LiveHintListener` hands each to it after the commit, and it closes the streams whose token carries that device's `sid` and refuses that `sid` for the same time; a stream of a token without `sid` (issued before 2.9) ends only with its token or with `DonorSessionsEnded`. The hub is a `SmartLifecycle` in the default phase, which stops before the web server's graceful shutdown, so open streams are completed first and never hold the drain; it takes a fresh scheduler at every start, because a lifecycle can start again after a stop (the test framework pauses cached contexts so). `LiveController` has no `@Transactional`: it reads nothing. The caps (5 per account, 50 in all, the last 10 for `ADMIN`, `app.live.*`, `LiveProperties`) keep at most 50 async requests open; a stream holds no request thread (Spring's `SseEmitter` on Tomcat's async support), and the scenario that opens all 50 still reads `/actuator/health`. No log line was added: a stream's opening, end and refusal are not logged.

When an edit changes an address, the old one is kept in `content_former_slug` and still answers the article or project (the site then shows the current address), until another article takes an article's old address or another project a project's; deleting the item deletes its old addresses. The old addresses of the two kinds are kept apart, as the live ones are (`/aktuality/x` and `/projekty/x` never collide): a slug has at most one row per kind (the partial unique indexes `uq_content_former_slug_news` and `uq_content_former_slug_project`, changeset `content/016`), so an article and a project that both left `x` both keep leading from it, and taking an address forgets only the old address of the taker's kind. The row's key is a surrogate `id` whose default `gen_random_uuid()` stays, so an older image, which inserts without it and reads by `slug`, keeps working; it fails only on a slug that has a row of both kinds, which only this code writes: there its `findById` meets two rows, so both old links of that slug answer 500 and saving an article or project at that address fails until the newer image is back or one row is deleted (`deploy/README.md`, Návrat na předchozí verzi). Remembering an old address updates the row of its kind when one is left over instead of deleting and inserting, because Hibernate flushes inserts before deletes and the insert would hit the unique index. A photo goes up as JPEG, PNG or WebP up to 10 MB; `ImageIoImageProcessor` turns it upright by its EXIF tag and stores only WebP copies of 480, 960 and 1 440 px (never wider than the original) in `content_media_variant`, so the daily database dump holds the photos too; `UploadImageService` decodes and re-encodes outside the transaction and stores through a `TransactionTemplate`. A photo or a receipt signature is refused from its header above 8 000 px on a side, 48 million pixels or 8 bits per sample, and each adapter decodes one upload at a time: in the security audit of 2026-11-06 a 16-bit 8 000 × 8 000 PNG of a few MB decoded to about 512 MB plus its copies, more than the backend's heap. The WebP codec (`webp-imageio`) needs its native libwebp, which the library extracts from its jar into `java.io.tmpdir` and loads from there; on the server `/tmp` is a `noexec` tmpfs (the backend's root file system is read-only), so the loaded copy could not be mapped and every upload answered 500 with an `UnsatisfiedLinkError` until 2026-10-30. The backend image therefore extracts the library for its architecture at build time into `/app/native` (root-owned, read-only), and `docker-entrypoint.sh` starts Java with `-Djava.library.path=/app/native` and points the library's extraction folder (`com.luciad.imageio.webp.tmpdir`) at that same read-only folder: the extraction fails at once (one line on standard error, `….lck (Read-only file system)`) and the loader falls back to `java.library.path`. This keeps `/tmp` `noexec` instead of mounting it `exec`; tests and `bootRun` outside the image extract into a normal temporary folder as before. The `stack` job proves it on the hardened production stack: an administrator signed in with the second factor uploads a JPEG and a WebP photo and reads each back as WebP. A photo may carry a focal point (slice 2.23b, Jakub 2026-10-31): the spot an administrator taps in the editor of the article, the project or the About section, kept as whole percent from the left and the top in `content_media.focal_x` and `focal_y` (Liquibase `content/013`, nullable, a check allows both or neither and only 0–100, so the previous image, which never writes them, works on), set by `FocalPointService` through `PUT /api/admin/content/media/{id}` and answered with every cover image and the About photo (one `findFocalPoints` query per list, not one per item). It belongs to the photo, not to the article, so every item that shows the photo crops it alike and an app tab that predates the point and saves an article never drops it; a new photo is a new row and starts without one. The point is audited (`CHANGE_PHOTO_FOCAL_POINT`) only when it changes. A photo's cleanup and a save that puts the photo on an item never fail each other on the foreign key (issue #456). The cleanup (`JpaMediaImageRepository`, both `deleteIfUnused` and the daily sweep) first locks the unused candidates with `select … for update skip locked`, which passes over a photo that a save holds, and then deletes, in a second statement and so with a fresh snapshot, only those of the locked ones that are still unused, so a reference committed between the first statement's snapshot and its lock keeps its photo too. Every save that puts a photo on an item (a news or project cover, the About photo, a person's portrait or web signature: `NewsAdminService`, `ProjectAdminService`, `AboutService`, `PeopleAdminService`) first takes the photo's row `FOR KEY SHARE` (`MediaImageRepository.lockForUse`) and only then checks that it exists: a cleanup that has not reached the photo skips it, and one that has locked it makes the save wait until it commits, after which the check finds the photo gone and the save answers 404 `content/media-not-found`. Every article and project answer carries `live`: published and dated up to today in Prague by the server's `Clock` (`NewsArticle.isVisibleOn`, `Project.isVisibleOn`, today from `FoundationZone` in `NewsAdminService` and `ProjectAdminService` as in the public services), so the administration says "Na webu" or "Zveřejní se {date}" and offers the public link without trusting the browser's clock (Jakub 2026-10-24). `GET /api/content/news` and `/news/{slug}`, `GET /api/content/projects` and `/projects/{slug}` serve what is published up to today (Prague), `GET /api/content/home` the three newest news articles and the three newest projects for the home page in one request (`HomeContentService.NEWS_ON_HOME`, `PROJECTS_ON_HOME`), `GET /api/content/media/{id}?w=` the smallest copy at least that wide with a one-year immutable cache; it reads the photo's widths (the index `uq_content_media_variant_width`) and then the bytes of that one copy only, never the other sizes (`MediaVariantWidths`, issue #456), and the receipt's print portrait reads only the largest copy the same way. ## operations

How the server itself runs: backups and restore, diagnostics and logs, settings and the first setup. Backups (contract "Backups"): The container `nfnn-backup` (image `ghcr.io/bzumik1/nfnn-backup` from `deploy/backup/`: `backup.sh` on `postgres:17-alpine`) dumps the database at every start and every night at the planned time (03:00 Prague time by default) into `/DATA/AppData/nfnn/backups/nfnn-<date>_<time>[-rucni|-pred-obnovou].dump.age` (custom format, zstd 19, then encrypted with age to the backup key, 30 days kept; Jakub 2026-10-28: backups are always encrypted; a backup or test restore on request only while no other request waits in `requests/`, 409 `operations/backup-request-pending`, and at most 10 a day per administrator, `interfaces/rest/BackupRequestRateLimiter`, so a connection cannot fill the disk the database shares), once a week at the planned day and time (Sunday 04:00 by default) restores the newest dump into a temporary database `nfnn_restore_test` and counts its tables and applied changesets (`databasechangelog`, both must be above 0) and checks that every table holds as many rows as the dump carries for it, and restores a backup in the GUI (Jakub 2026-10-23: nothing outside the GUI, foolproof): an administrator's "Obnovit" on `/sprava/zalohy` (`POST .../backups/{file}/restore`, browser session with the second factor only, no MCP tool) or a `.dump.age` uploaded with its key in the first-setup wizard of a new server (`PUT /api/operations/setup/restore`, same unlock as the wizard, streamed into `/restore/<id>.upload`) becomes a `<id>.restore` request file in `backups/requests/`; the backend then exits (`ApplicationRestarter`) and its entrypoint (`backend/docker-entrypoint.sh`) waits while the request, the container's `status/restore.running` marker or a `/restore/*.dump` exists (a request not taken within 5 minutes is dropped). The container takes the request within 10 s, dumps the current database as `-pred-obnovou` when it has tables, restores into the staging database `nfnn_restore_staging`, refuses it without tables or applied changesets, clears a Liquibase lock caught in the dump and only after success swaps it in by `ALTER DATABASE … RENAME` (rolled back on failure, an interrupted swap repaired at the next container start); between the two renames every `public` sequence of the staging database is set to the higher of its own and the retired database's value (`keep_sequences_ahead`), so `donation_receipt_number_seq` never hands out a number issued after the backup again. Still between the renames the retired database's decisions since the dump are carried into the staging copy (`carry_forward` with `deploy/backup/carry-forward.sql`, issue #459, the owner's decision: a restore never brings back what was removed for security or GDPR after the dump, and a receipt number never repeats): `pg_temp.facts_to_carry_forward()` reads the retired database's facts as JSON rows (each donor's id, `erased_at` and `password_hash`, every `donor_role`, `donor_passkey`, `donor_second_factor` and `admin_action` row, the count of `issued_receipt`, and a closing row with the number of rows sent), which `COPY … TO STDOUT` pipes straight into `COPY … FROM STDIN` of one transaction on the staging copy, so no credential is ever written to a file; there `pg_temp.carry_forward()` refuses unless the closing row counts exactly the rows that arrived (a reader that failed half way sends none) and then, for every donor present in both databases, makes the newest state win: the roles (an administrator removed since stays removed, one granted since stays granted), the password hash, the passkeys and the second factor are replaced by the retired database's when they differ; a donor erased since gets the retired `erased_at` and keeps the rest of the row for the backend to finish (below); every `admin_action` row the copy lacks is inserted with its id (the trail is append-only, `shared`, and only refuses updates and deletes), so the erasure, the `RESTORE_BACKUP` request and everything else since stay in the history; and when the retired database holds no `issued_receipt` (a new server restoring the last dump of a lost one, or a site that never issued one) the receipt sequence moves 1000 further, because numbers issued after the dump may already be in donors' PDFs. Rows are inserted with the columns the copy and the facts share (`jsonb_populate_record`), so an older dump takes them; one that lacks a table for a fact it needs (passkeys added since into a dump from before passkeys) fails the restore. A donor who registered after the dump, and everything else written since, is still gone; an unconfirmed registration the 30-day sweep deleted after the dump comes back with the dump (it is in the copy only), and the hourly sweep deletes it again at its first run after the restore, before any reminder, since it was already older than 30 days. The counts go into the status file and the `BACKUP_RESTORED` entry, and a failure of the carry renames the retired database back like any failed swap. Before that swap a dump taken before slice 1.10 is refused once the live database has applied `donations/024` and taken a receipt serial since (`rewinds_receipt_numbers`), because Liquibase would run `024` over it at the next start and restart the numbering at 1; the PR check's stack job plants such a dump and expects the refusal with the data and the sequence unchanged. So a failed restore leaves the data as they were and never blocks the backend. A dump left in `/DATA/AppData/nfnn/restore/` by hand is still restored at the container's start (empty database, or `*.force.dump` for a full one), the same way; it ends as `.done`, `.failed` or `.skipped`. After the restart `BackupRestoreService.recordFinishedRestore` writes `BACKUP_RESTORED` or `BACKUP_RESTORE_FAILED` into the audit trail once per request (`operations_restore_record`, changelog `operations/003`); a restore that carried facts forward names their counts there after the revocations (`erasures_carried`, `credentials_carried`, `roles_carried`, `admin_actions_carried`, `receipt_numbers_skipped` in the status file, `domain/backup/RestoreCarryForward`). The erasure itself is finished by the donors context at the same start (donors, "Erasure after a restore"). Encryption (contract "Backups", "The backup key"): `backend/docker-entrypoint.sh` generates `secrets/backup-key` with `age-keygen` once, as it does the other secrets, and exports it to Java as `BACKUP_KEY`; the backup container reads the same file read-only and runs `pg_dump … | age --encrypt --identity`, so no plain dump ever touches the disk. Push alerts of the administration (contract "Push alerts of the administration", slice 2.27; the alerts on failures since 2.28, below; the badge and `/sprava/upozorneni` too): the backend sends Web Push itself, without Firebase or a library. `PushKeyService.current()` finds the VAPID key pair in `operations_push_key` (a singleton row) or generates it (`JcaPushKeyGenerator`, P-256) and stores it with `insert … on conflict do nothing`, so two first requests at once keep one key; the private key is sealed by `SecretSealer` under `settings-key` with the purpose `push-vapid-private-key` as associated data. A subscription (`operations_push_subscription`, at most 10 per administrator, unique by device and by endpoint) belongs to the device of the session that took it (claim `sid`, slice 2.9) and keeps the endpoint, the browser's keys, three alert switches (bank import, backups, mail), the last delivery and the failures in a row. `PushSender` sends one message to every recipient at once, a virtual thread each (a test alert waits for its slowest push service, not for the sum, which stays under nginx's 60 s), through `PushDelivery` (`WebPushDelivery`: RFC 8291 encryption in `WebPushEncryption`, the VAPID token in `VapidToken`, JDK only: `KeyAgreement` ECDH, `javax.crypto.KDF` HKDF-SHA256, AES-GCM, `SHA256withECDSAinP1363Format`, ArchUnit keeps the elliptic-curve classes in `operations/infrastructure/push`) and records each outcome in its own short transaction of an update that touches only a row still there (delivered, failed, or deleted when the service answers 404 or 410), so a device turned off meanwhile is never brought back. `PushSubscriptionService.sendTest` has no `@Transactional` on purpose: it reads the recipients in one short read and calls the push services outside any transaction, so a slow service never holds a database connection. Subscribing takes a transaction-scoped advisory lock (`pg_advisory_xact_lock(20261105)`, `AdvisoryLock.PUSH_SUBSCRIPTION_WRITES`) first, so the limit of 10 and the unique device and endpoint hold for two subscribes at once; changing the alert switches is an update of the switches only. `PushSubscriptionLifecycle` deletes an administrator's devices in a `BEFORE_COMMIT` listener of `AdministrationRevoked` (shared event, published by `AdministratorService.revoke`), inside the revocation's own transaction, so the role and the devices go together, and again on `DonorErased` for a device subscribed with an access token issued before the revocation (it keeps `ADMIN` until it expires), and on slice 2.9's `DeviceSignedOut` it deletes the subscription of the device that ended (its own sign-out, a remote sign-out, the sign-out of every other device, a password or second-factor change), in the sign-out's own transaction, so a device that no longer holds a session is never sent an alert. A subscribe could still outlive its device (database audit #468): it took the device from the token's `sid`, which the token check accepts up to 30 s after the device ended on another node's cache or for a request already past it, so a tab of a phone signed out a moment ago subscribed after the sign-out's delete and kept the alerts. Operational alerts (slice 2.28, contract "Push alerts of the administration"): the bank import, the backups and the mail each have one alert, open or closed, in `operations_alert`. The contexts that find a failure only announce it with the shared event `OperationalAlertRaised` (donations' `BankStatementRecorder` beside its outage and recovery e-mails, operations' `BackupWatchService` beside its own), and operations alone keeps the state, so donations knows nothing of push. `OperationalAlertService.record` runs in the announcing transaction (`BEFORE_COMMIT`, propagation `MANDATORY`) under the advisory lock `pg_advisory_xact_lock(20261107)` (`AdvisoryLock.OPERATIONAL_ALERT_CHANGES`; until #452 it shared 20261106 with the report settings, so a save of the report settings and every alert change waited for each other), opens or resolves the alert only when it changes and counts every change, so the same outage announced twice (two import runs at once, a restart) sends one push, and a rolled-back import sends none. ## mcp

The connector `nfnn-mcp` (`mcp/`, Node 26, MCP TypeScript SDK v2) sits behind the frontend nginx at `/mcp` and `/.well-known/oauth-protected-resource/mcp`; its contract and tool list are in `docs/api-contract.md` "MCP connector", its security in `docs/security-overview.md`. It learns the issuer from the backend's authorization server metadata at startup, verifies every bearer token by exchanging it for an API token at the backend (RFC 8693, cached until expiry) and answers 401 with `resource_metadata` and `scope="admin:read admin:write"` (the client asks for both and the administrator chooses on the site; the connector itself requires only `admin:read`). Every tool calls the same `/api/admin/...` endpoints as the web, so the audit trail is the administrator's and names the connected application (`admin_action.client`); a writing tool on a read-only connection answers a readable tool error (reconnect with „Změny“). It has a tool for every reading view and every reversible change of the administration (Jakub 2026-10-23), including the issued receipts (`nfnn_receipts`, `nfnn_receipt` with the frozen data and the verification link, an erased donor's without the name, address and link, `nfnn_issue_receipt` for first receipts only, a replacement being web-only; 1.7: the connector never gets a PDF, which only a browser draws), the logs and diagnostics of `operations`, settings without secrets, the site address and the mail settings (security audit 2026-11-06), and photos (`nfnn_upload_photo` from a public https address, `nfnn_photo_upload_link` for a one-time `PUT /mcp-photos` upload, both posting to `POST /api/admin/content/media`; `main.ts` serves through `node-handler.ts`, which hands `/mcp-photos` its raw request stream instead of the SDK's `toNodeHandler`, since that one decodes bodies as UTF-8 text and caps them at 4 MB); deletions, the administrator role, second-factor and passkey resets, older-symbol reversals, GDPR erasure, secrets, the backup key and the backup download and restore stay on the web. Answers are compact JSON: amounts as numbers of crowns, instants in ISO 8601 with the Prague offset, lists paged. No secret and no env file in the container; `mcp.log` has a line per request with its JSON-RPC method, tool name and time, never the arguments.

## Frontend

See `docs/frontend-overview.md`. In short: the public site, the donor portal and the administration (`/sprava`, administrators only, the backups among its pages) are components; the contact form, the QR payment, the donor account (sign-in, registration, e-mail confirmation, password reset, the consent page `/pripojeni` for the MCP connector and the connected applications in the account card), the dashboard (summary, donations, receipts, bank check, bank accounts) talk to the backend through one HTTP service per feature behind `authInterceptor`.

Why tabs answer from memory (2026-11-05): the service worker keeps the public content with the `freshness` strategy, so every visit waits for the network first and the page showed its loading line on every tab switch, also in the installed app. Turning the worker to `performance` would show a stale answer across visits and days; the tab's own memory (`KeptPublicAnswers`) serves only what this tab already received in the last 10 minutes, asks the server again at once in the background, and is forgotten with the tab, so a new visit or a reload always starts from the server. It holds only answers that are the same for everyone, so there is nothing to clear at sign-out. The pages of the tab bar are loaded ahead (`TabPagesPreloading`) by a mark in the route data rather than for every route, so the other pages keep loading on demand and a lost chunk is still found when its page is opened.

The receipt verification page `/overit` (plan v3 1.8) verifies a proof entirely in the browser, with the kept key list also when the connection drops after the page has loaded (since 2.4 the service worker also opens the page itself offline once the app has been loaded before), and asks the server only for the key list and, online after a valid signature, the receipt's status by the SHA-256 of the signed message and the signature. Why the choices: the key list is asked again on every online check with the request header `Cache-Control: no-cache` because the app's HTTP backend is XHR (`withXhr()`, for upload progress), which has no fetch `cache` option, and an hour-old list would hide a revocation; it is replaced whole, never merged, so a key once revoked cannot come back from an older copy, while its entries are checked one by one so a single malformed entry cannot freeze an old copy; WebCrypto Ed25519 comes first and `@noble/curves` only as a lazy fallback, so most browsers download no verification library at all; the status `unknown` is never green (Jakub 2026-10-30), since a leaked key would sign a forged receipt with a valid signature and only the foundation's records tell it apart, and for the same reason no usable answer while online (429, 5xx, timeout) is a caution rather than the offline green (lead 2026-10-30), since an attacker can cause it, and a status call that fails once the key list has come in the same check is never read as offline, even with no response at all (1.8 security review round 2), since a reset on a network the attacker controls would otherwise turn `unknown` into green; each request waits at most 5 s, so a weak connection gets its result within about 10 s, and the checking line says when the signature has passed and the foundation is being asked. Trust model: `docs/security-overview.md`, "Receipt verification page". The status question is answered by `donations/interfaces/rest/ReceiptStatusController` (`POST /api/donations/receipts/status`, public, contract "Receipt status") → `application/receipt/ReceiptStatusService` (read-only transaction) → `DonationReceiptRepository.findStandingByStatusDigest`, one JPQL select of `issued_receipt.status` by its unique `status_sha256` with its `withdrawal_reason`, turned into a `ReceiptStanding` (`ReceiptStanding.of`: a withdrawal because the gifts changed is `OUTDATED`, slice 1.26) and mapped to `active`, `replaced`, `withdrawn` or `outdated` by an exhaustive switch (a new standing does not compile until it is given a word) and `unknown` for no row. Why: the digest is validated by the request record and again by `ContentDigest`, and `ReceiptStatusRateLimiter` (60 per 15 minutes, the key list's limit) counts the question before the lookup, as every limiter here counts after validation; nothing on the path audits or stores, and it writes no line per request under the production log levels; at any level an administrator can set, no line names the digest or the address (A12: the server learns only that one receipt was checked). `ReceiptStatusLoggingTest` checks both on the captured output in the shared integration context: `@IntegrationTest` sets `spring.jpa.show-sql=false` for every integration test, because Hibernate's SQL echo goes to standard output, is fixed when the session factory is built and would print the lookup on every question, and the test sets the log levels at runtime (the production ones; then `cz.novanadeje.app` at TRACE and `ROOT`, Spring web, Spring Security and Hibernate SQL at DEBUG). The frontend nginx has a location of its own for the path, to cap the body at 1 KB and to log it without the size of the answer, which would tell the four answers apart.

The donor's receipt PDF (plan v3 1.9) is drawn in the browser from the frozen data the server issued (`frontend-overview.md`, `receipt-pdf/`; trust: `security-overview.md`, "Receipt PDF in the browser"). Why the choices: pdfkit runs in a module worker, so drawing a long year never freezes the page (a 120-gift year takes about 0.4–0.5 s in the worker at CPU 1×, timed in the page from the request to `done` by `e2e/receipt-pdf.spec.ts`, which reports the cold first drawing and five warm ones, each also ×4, and fails only when the median warm drawing exceeds 1 s at CPU 1×, about three times the idle value (349 ms locally since the fonts open once), so three Playwright workers or a busy runner leave it headroom; the plan's acceptance, a cold 120-gift receipt within 2 s on a computer four times slower, is measured by hand and recorded in the PR; Chromium refuses CPU throttling for a dedicated worker, "Operation is only supported for pages, not workers", so the page's 4× throttle the first version of that test set never reached the drawing) and the library stays out of every bundle but its own chunk; the layout reads its colours, sizes and margins from the theme's `--receipt-*` tokens and its fonts from the theme's `receipt/` folder, registered by name and opened once each (the document gets no default font: pdfkit opened a default from the same bytes, and since a registered font that matches an open one is never cached under its name, it parsed the body font again at every switch, which made a 120-gift receipt three times slower and a 366-gift one six), so replacing the theme restyles the PDF as it does the site, while what the receipt says comes only from the frozen data, and a receipt downloaded again carries the same number, values, frozen texts and QR in the current look (the caption beside the QR, "Ověření potvrzení" with "Načtěte kód telefonem a uvidíte, co fond podepsal." (Jakub 2026-10-31), and the images' alternative texts are frozen with the receipt's texts since 1.10, so a receipt downloaded again says them as it was issued; a receipt frozen with an older text set, which only the shared cases still hold since `donations/024` deleted every receipt issued before, is drawn with the app's own captions from `receipt-captions.ts`, the same words); the document is deterministic (creation date from the issue time, font subsets named from the font id), so the same data and theme give the same bytes; the closing (declaration and signature block) is kept on one page, and a verification symbol above version 15 moves to an area of its own so its modules stay at least 0.6 mm for a phone camera (the symbol carries the foundation's star at level H, which needs more modules than v2's M or L, so the code beside the signature grew from 35 to 46.2 mm and the gift rows lost 1.2 mm to keep a year of 12 gifts on one page, Jakub 2026-10-31); on an iPhone or iPad a second tap ("Otevřít potvrzení") hands the file to the share sheet, because Safari drops the click's user activation during the drawing and would refuse both a download and `navigator.share`; a worker chunk missing after a deploy (`tools-missing`) reloads the page once per tab with `?stahnout=`, which resumes the same download in the new build, and a second miss asks the donor to reload instead of looping; nothing is retried silently, and there is no server fallback (roadmap: the drawing switches over at once).

The donor's device copy (plan v3 2.14; `frontend-overview.md`, `core/device/store/`; trust: `security-overview.md`, "Device copies") is kept by `DeviceVault` in the IndexedDB database `nfnn.device` and kept up to date by `DonorCopySync` from the device sync above (2.15). Why the choices: one database with one `readwrite` transaction per change, because a copy that is half deleted or whose entry names records that are gone is worse than either state, and deleting the database is the clean way to wipe it; every sealed record under a random record id, so the stored keys do not show which years hold gifts; the vault's work one at a time per tab and under the Web Lock `nfnn.device-vault` across tabs, because two tabs signing in or out at once must not both decide that a copy is missing and make two; the sync holds a lock of its own per copy (`nfnn.device-copy-write.<id>`), so the tab that took a sync over does not make a second one, and the other tabs only reload the records on `replaced`; a sign-out keeps the copy under its password or PRF wraps, because the roadmap promises that signing out does not delete it and 2.15 opens it offline, while a copy with no such wrap could never open again and is deleted; a session that ends (a refused refresh, 401 `auth/session-ended`, a reload without a session) drops every session wrap on the device, because a session key opens a copy without a secret, but deletes no copy a password or passkey still opens, because 2.9 ends every session of an account after a replay or a credential change and a replay must never wipe a device (the wipe on a remote sign-out or erasure is 2.11's); a copy is found only by the tag of the donor's id, never by the e-mail, because an address can pass to another account; a sign-in without a wrapping secret leaves a copy it cannot open locked rather than replacing it, because the donor's password or passkey still opens it; a sign-in whose secret opens no wrap replaces the copy only when a wrap of that kind refused it, because the server has just accepted that secret, so that wrap is of a changed password, while a copy with no wrap of that kind is still opened by another secret of the donor and stays locked; a refresh that answers for another donor only opens that donor's copy and ends no session first, because ending the sessions would also delete the session wrap the other donor's tab just made; the device salt is drawn again only when the last copy goes, because another account's tags and PRF wraps depend on it; the vault and the sync are loaded with `import()` at the first session event (`device-copies.ts`), so the bundle that loads first grows by under 3 kB; IndexedDB that does not open within 5 s gives a copy in memory and a report, never a blocked sign-in; and the eviction flag in `localStorage` holds only `1`, enough to tell an evicted store from a device that never held one. Since 2.15 the copy syncs whenever it opens, a restored one too, and asks only for the chunks whose digest changed; the donor's Přehled, Moje dary and Potvrzení o daru read their gifts through `DonorDonationsRepository`, which reaches the copy through `DonorCopyLink` (`features/donations/device-copy/donor-copy.ts`), so the donor pages reach it without importing the vault and the specs without one change nothing. Why the choices: the summary shown is the server's, stored with the copy, and the device's own figures (`summarizeDonations`, run on the `donor-summary` and `sync/manifest` shared cases) only check it, because the server is the authority and a mismatch means a defect to report, not a number to prefer; a mismatch downloads the whole copy again at most once an hour and is reported at most once an hour, so a persistent defect costs one full download and one report an hour rather than a loop; every successful sync writes the copy again, even when no chunk changed, so `storedAt` and the summary (with `bankDataAsOf`) are as fresh as the last answer; one sync at a time and at most one queued after it (a request while one is queued joins it, a full one upgrades it, and a catch-up joins whatever runs), because a second sync started beside a first would only ask the same questions; a page with an empty copy reads the API while the first sync runs, so a first sign-in waits no longer than before; a copy whose own figures disagree with its summary is not shown, because its list would contradict its totals, and the pages read the API until a rebuild agrees; a reload whose sync does not store the copy (a failure, a timeout, a session that ended) asks the API, so an ended session reaches the page as a 401 and sends the donor to sign in; the rebuild and report pauses live in the tab's memory, because they guard against a loop, not against several tabs, and an hourly pause per open tab bounds both (so while a copy keeps disagreeing, each reload asks both the copy and the API, at most one catch-up per 30 s); each sync request waits at most 30 s, because the sync holds the copy lock across tabs; the signature and portrait of the active receipts are kept in the copy (each checked against its digest), so a receipt is drawn again when the server cannot be reached (with no connection at all only once the receipt worker and fonts are cached, which the offline unlock after 2.7 ensures), while the PDF itself is never kept, as the roadmap says; the bank accounts page stays on the API in 2.15, and unlocking a copy offline after a reload comes in its own PR after 2.7 (`Connectivity`).

After a deploy an open tab still runs the previous build, whose lazy chunks are gone: nginx answers a missing hashed file with 404 (never `index.html` with 200, which would fail as a MIME error and be cached), and the hashed files that exist are immutable (`.claude/rules/deploy-ci.md`, Proxy, headers, mail). The router's navigation error handler hands a failed dynamic import to `ChunkLoadRecovery`, which loads the page that was asked for from the server once `ReloadGuard` allows it, and otherwise shows "Načíst znovu". It loads the target rather than reloading the page left open, so the visitor lands where they clicked: `history.pushState` plus `location.reload()` for another address, and `history.replaceState` plus `location.reload()` for the same one, never `location.assign`, because the site keeps its own history (`core/navigation/own-history.ts`, #431): the push becomes a step of the site's own stack while the browser keeps its one entry, so the reloaded page still steps back to the page before and Safari gains no page to slide back to; `assign` would also only jump within the page for `/#prispet` on `/` (and after a failed first navigation the router has already taken the fragment off the address). `ReloadGuard` keeps the time of the last automatic reload per reason in `sessionStorage` (`nfnn.reload.<reason>`) and allows one per 60 s: a chunk that is still missing after the fresh load (the server broken) cannot loop the tab, and without a working `sessionStorage` it allows none, because a once-per-load flag in memory is reset by the reload itself. When the browser says it is offline (`navigator.onLine`), it does not claim the reload at all and only offers it, because the reload would end on the browser's own error page. On a flaky mobile network `navigator.onLine` stays true while the chunk request fails with the same message, so before claiming the reload `ChunkProbe` asks the server for the missing chunk (or `/` when the message names no address) with a `HEAD` request past the cache: only a 404 or an HTML page at the chunk's own address (the chunk is gone after a deploy), never after a redirect, lets the reload go; a failed request, a redirect (a login or maintenance page in front of the site), a server error or the chunk still being there leaves only the offer. The probe gives up after 4 s, because a network that takes the connection but never answers would otherwise leave the visitor with nothing at all. The offer is set before the probe, so it shows while the server is asked and stays when a visitor cancels the browser's "leave the page?" prompt, instead of a page that silently did nothing; and an answer that comes after the visitor started another navigation is ignored, so a late probe never takes them back to the page they left. The news and project editors mark their draft as discarded once their own question "Máte neuložené změny" is answered with "Odejít bez uložení", so a lost `loadComponent` behind that answer reloads without the browser's `beforeunload` prompt asking the same thing again; a failed `loadChildren`, which skips the question, keeps the `beforeunload` warning. The automatic load is a new document, so it drops what a navigation carried besides its address: the router's navigation `state` (the editors' `{ state: { deleted } }` after deleting a news article or project, `admin-news-editor.ts`, `admin-project-editor.ts`) is lost and the list shows without its "deleted" line. It also bypasses `canDeactivate`: the router loads `loadChildren` while it matches the address, before the guards run, so a failed `loadChildren` (leaving `/sprava` for the public site, for example) skips `unsavedChangesGuard`, and only the editors' `beforeunload` warning protects a draft then; a failed `loadComponent` comes after the guards, which have passed by then.

Without a network the app must not wait on it (Jakub 2026-11-06, measured in PR "Show the kept copies at once without a network"): an iPhone in airplane mode leaves a request hanging rather than failing it, so every wait for an answer ran into its timeout (the worker's 5 s for each public page, the probe's 10 s plus 3 s, the session refresh's 15 s before `/darce`, `/sprava` or `/aplikace` opened). Therefore the browser's word offline is trusted at once (its word online never), the worker serves public content from its copy and fetches it behind it, the page takes the server's answer as a second value when it differs, and a session restore stops waiting as soon as `Connectivity` knows the network is gone, checking it itself after 1 s without an answer. A wrong offline costs only a label that the probe takes back; a wrong wait cost the visitor every page.

A tab opened before a deploy may also speak an API the server no longer speaks. Every API answer names the server's API generation (`Nfnn-Api`, `shared` above), and `core/version/version-interceptor.ts`, the inner of the two interceptors, hands the headers of every answer (a refusal included, never a status 0, which no server wrote) to `ServerVersion`, which takes them only from an answer marked `no-store`: `payment-details` (5 minutes) and `receipt-keys` (an hour) may come from the browser's cache with the headers of the server that wrote them, and such an answer would otherwise bring back an old generation right after the reload that should clear it. While the service worker controls the page it also skips the public answers the worker may keep (`mayComeFromServiceWorker`, slice 2.4): those are `no-store` too but may be a copy of up to 30 days, written by an older server. While the latest answer names another generation than the app was built for (`mustUpdate`, either direction: a newer one after a deploy, an older one after a rollback, because the generation says the two no longer understand each other), the interceptor sends no request that could change data and answers it locally with the problem `https://nfnn.cz/problems/app/update-required` (status 426, "Web mezitím dostal novou verzi. Nic jsme neodeslali. Načtěte stránku znovu a zkuste to ještě jednou."), and a floating notice offers "Načíst novou verzi". Each call names the app's generation (`Nfnn-App-Api`), so the first write after a deploy, sent before any answer told the app, is refused by the server with the same problem, whose `Nfnn-Api` then turns the state on. A page that shows the API's problem (`describeProblem`) shows that line; the contact form says to copy the message, load the page and send it again (`home.contact.form.error.updateRequired`), and the receipt download shows the problem's title and detail; any other page that keeps a text of its own for a failure shows that text, with the notice saying what to do. Loading the new version is a full load, so what the visitor typed and did not save (an editor draft, a half-written message) is lost unless the visitor keeps it before pressing; a sign-in or a second-factor step is a write too and waits for the load. Why the choices: reading stays allowed, so the visitor keeps what they see; only `POST`, `PUT`, `PATCH` and `DELETE` are held, because an old app's write is what a breaking change can misread, while the session refresh and the sign-out pass, so holding writes never turns into a lost session and the sign-in dialog, and so does the receipt status question of `/overit` (`POST /api/donations/receipts/status`), which only reads; the refusal is local and carries no `Nfnn-Api` of its own, so it never changes the state; the latest answer wins, so a quick rollback lifts the state without a reload; the notice never takes the focus, because it can appear at any answer, also while the visitor is typing (WCAG 3.2.2), and announces itself through its always rendered polite live region (`aria-live`, no `role="status"`, so the page's own status region stays the only one), or through `DialogAnnouncer` when a modal dialog keeps the page behind it inert. Loading the new version (`AppUpdates.loadNewVersion`) first asks the service worker to fetch the new build (at most 10 s, a failure ignored) and then loads the page the visitor is on from the server (`ExternalNavigation.loadFromServer(router.url)`); without a service worker it loads at once, since `index.html` is never cached. `Nfnn-Revision` (`ServerVersion.revision`) is compared with the app's own build: an answer that names another build asks the service worker once per build to look for an update, because the Angular worker looks by itself only when a page is loaded, so a tab kept open for days would otherwise never learn of a deploy (2.16 adds the live stream). Each API call also names the app's own build (`Nfnn-App`, `APP_REVISION`, `dev` without one), which the server ignores today and which tells a later slice (the live stream, a support question) which build spoke.

Live updates in the app (plan v3 2.16): `core/live/live-updates.ts` keeps one stream to `/api/live` (`core/live/live-api.ts`, through `HttpClient` with text streaming, so it passes both interceptors and refreshes once on `auth/expired-token` like any call) while someone signed in has a page open that listens (`changes(feeds)`, counted per subscriber) and the tab is visible; a tab hidden for 30 s closes it and opens it again when shown. A stream that ended after streaming a while opens again within a second; a failure waits 1, 2, 4… up to 60 s, each with jitter, so a restarted server is not hit by every tab at once; a 401 or 403 after the refresh stops until the session is renewed (a new sign-in or the next token refresh). After a reopening the pages that listened while it was lost read everything again, because hints sent while it was closed are lost; so does a page that started listening while the stream waited for a retry, while a page whose arrival opened the stream again has just read it all. Why the choices: `EventSource` cannot send the access token, which lives only in memory, and a token in the URL would reach logs; the XHR backend (`withXhr()`) streams text through download progress. Without a stream the pages work as before, which is the fallback when a proxy buffers the stream (`deploy/README.md`).

## Backend tests

How the suite runs and why it is built so (rules in `.claude/rules/testing-backend.md`, "Keeping the suite fast"). Measured 2026-10-29 in a 4-core cloud container: the full `./gradlew test` took 14 to 19 minutes before these choices and about 3 minutes after on a quiet container (up to 6 when other sessions load it), with the same 2720 tests plus 12 new ones; the Cucumber steps alone went from 658 s to about 120 s.

- Two Gradle tasks: `test` (unit, integration, ArchUnit) and `acceptanceTest` (the Cucumber suites `DonorsAcceptanceTests` and `OtherContextsAcceptanceTests`, split by the `@donors` tag so each feature runs exactly once), both on two forks. The suite is bound to one core per JVM, so forks scale almost linearly. Gradle hands forks one test class file after another in turn, counting every class file, so two suites inside `test` could land on the same fork; `acceptanceTest` sees only the two suite classes and gives each its own fork. `acceptanceTest` is the finalizer of `test`, not a dependency, so `./gradlew test` and `build` still run everything and the scenarios run even when a unit test failed. Each fork has its own Spring context, PostgreSQL container, `MutableClock`, limiters and fakes (receipt numbers start at `000001` in each); only the folders on disk are shared, so the Cucumber context puts them under `build/cucumber/fork-${org.gradle.test.worker}/`. Running scenarios in parallel inside one JVM is not possible: the clock, the database, the recorded mail and the fakes are shared by every scenario.
- The v2 transcripts (`cucumber/transcript`, `.claude/rules/testing-regression.md` "Regression against v2") are recorded by both forks of `acceptanceTest` into the one folder `build/api-transcripts/`. A fork writes only the features it runs, each feature runs whole in one fork, and every recorded scenario starts from the same clock, limits and seeds, so the files do not depend on the split. The folder is emptied by Gradle before the forks start, because a JVM that emptied it on its own start would delete what the other fork had already written.
- `CachingPasswordHasher` (registered by `CachingPasswordHashers`, a `BeanPostProcessor` in `TestSupportConfiguration`) wraps the application's `BCryptPasswordHasher`: the first hash of a password and the first check of a password against a hash go to the real cost-12 BCrypt, later ones are answered from memory. A BCrypt operation at cost 12 takes about a third of a second of one core, and the scenarios register and sign in about a thousand times; the cache keeps the production class and cost in every call while making each distinct check once. The only difference from production: two donors with the same password get the same salt.
- Awaitility's default poll delay is 100 ms even when the condition already holds; the Cucumber glue sets it to zero with a 10 ms interval (`CommonStepDefinitions.pollWithoutDelay`). The deliberate "nothing more arrives" waits keep their explicit 300 ms. Because the scenarios now end sooner, `isolateScenario` first waits until the application task executor has finished every `@Async` task, so an e-mail of the previous scenario can never land in the next one (before, the hidden 100 ms usually covered it).
- `DatabaseCleaner` deletes from every table, children first by the foreign keys read from the catalogue, and restarts every sequence, in one round trip. `TRUNCATE` creates new files for each of the about 40 tables and their indexes and took about 60 ms per scenario; the deletes of a scenario's few rows take a few ms.
- Contexts are cached per configuration, and each new one starts its own PostgreSQL container and Liquibase run (about 3 s). All `@SpringBootTest` classes share `@IntegrationTest` (MockMvc, an unreachable mail server on port 1, revision `f00ba12`, receipts from 2025, `@ScheduledWorkOff`), and the JPA slices of each context share `<Context>PersistenceTestConfiguration`; `TestContextRulesTest` keeps every new `@SpringBootTest` on `@IntegrationTest`. The integration tests that commit empty the database before each test, since they share it.

## Regression against v2 and shared cases

How the regression against v2 and the cases both sides run work today, moved here whole from the rules on 2026-11-06. What a change must keep true is in `.claude/rules/testing-regression.md` and `.claude/rules/testing-shared-cases.md`; the commands to record or extend the baseline are in the skill `regression-baseline`.

### Regression against v2

Plan v3 is checked against v2 as recorded on `main` just before v3 work starts. `regression/v2/` holds the API transcripts and the test inventory, `shared-cases/<topic>/*.json` the cases both sides run (`{source, logic, cases: [{name, input, expected}]}`); every file named its source `v2-baseline` at the baseline commit, and a file changed since names it `edited` (`testing-shared-cases.md`, Logic on both sides). The baseline's anchor is `regression/v2/BASELINE_COMMIT`: it holds the id of the squash-merge commit of the PR that brought these files (#201, `c4a256c2`), whose tree equals the branch they were recorded on, so checking out that commit and running the commands below regenerates every file byte for byte. The file never changes. A tag `v2-baseline` may be put on the same commit, but nothing depends on it (pushing tags is refused to the sessions that build v3). Only fictional fixtures under a fixed clock go in, and the repository is public.
- Recording: `API_TRANSCRIPTS=record ./gradlew acceptanceTest --rerun` (`--rerun`, or `cleanAcceptanceTest` before it, so Gradle cannot skip the run as up to date; `./gradlew test` and `build` record too, since `acceptanceTest` finalizes `test`) writes `backend/build/api-transcripts/<context>/<feature>.json`; copy the folder to `regression/v2/api/`. Recording refuses to start while `MAIL_*`, `APP_*` (Spring's relaxed binding maps them onto `app.*`), `SPRING_APPLICATION_JSON`, a `SPRING_*` name holding `PASSWORD`, `TOKEN`, `SECRET` or `KEY`, a secret setting (`Setting.secrets()`, so a new one is refused without a change here) or a secret the server generates (`JWT_SECRET`, `SETTINGS_KEY`, `BACKUP_KEY`, `RECEIPT_SIGNING_KEY`, `DB_PASSWORD`) is set in the environment (`env -u FIO_TOKEN …`; `ApiTranscriptsTest` fails when `application*.yml` binds a password, token, secret or key it would not refuse), and every scenario, recorded or not, starts at `ApiTranscripts.RECORDING_CLOCK` with every rate-limit window and the company register lookup's pause (`support/CompanyLookupPause`) reset and the backup key's word checks drawn from a fixed seed (`support/BackupKeyWordDraws`), so a transcript does not depend on which scenarios ran before it. On a checkout of the baseline commit, `GOLDEN_FILES=write ./gradlew test --tests "*QrGoldenCasesTest" -PnoCucumber` rewrites the QR cases (the generator is not on `main` since 0.6d). The inventory: `./gradlew test` for the backend JUnit XML (`build/test-results/test/`, and the Cucumber scenarios in `build/test-results/acceptanceTest/`, which `test-inventory.mjs` reads both by default); in `frontend/` `npx ng test --watch=false --reporters=json --output-file=$PWD/test-results/inventory-vitest.json` and `npx playwright test --list --reporter=json > test-results/inventory-playwright.json`; in `mcp/` `npx vitest run --reporter=json --outputFile=test-results/inventory-vitest.json`; then `node scripts/test-inventory.mjs` writes `regression/v2/test-inventory.json` (every test name per suite, sorted, a repeated name with `#n`). The test JVM is pinned to a zone, locale and charset (`-Duser.timezone=Etc/UTC -Duser.language=en -Duser.country=US -Dfile.encoding=UTF-8` in `build.gradle.kts`, guarded by `RecordingEnvironmentTest`), so a recording on another machine writes the same text. The baseline was recorded under `LC_ALL=C.UTF-8`, where the JDK reports `en` without a country; a recording with the pin writes the same bytes (checked with `diff -r` when the pin came in), and a change to the pin needs that check again. Record twice and compare (`diff -r`) before committing: two runs write the same bytes. A recording `acceptanceTest` empties `backend/build/api-transcripts/` before its forks start (Gradle, not the JVM, because the two suites write into the one folder at the same time), so no file of an earlier run survives; each feature runs in one fork, its scenarios in file order, so the ordinals `#n` are the same as in one JVM.
- Before merging the baseline PR: rebase onto the current `main`, record the whole suite again, `diff -r backend/build/api-transcripts regression/v2/api`, commit any difference (with the test inventory and the QR cases, if they changed too), and merge only if `main` has not moved since the rebase; if it has, repeat. ### Shared cases (logic on both sides)

- A computation the backend and the frontend both perform (local first, `backend.md`) is specified once as shared test cases, inputs and expected outputs in one data file, and the backend and the frontend suites both run every case (Jakub 2026-10-28). A change to the computation changes the cases first, so neither side can pass with its own idea of the result. A case is read from its file, never copied: `sharedcases/SharedCaseFilesTest` fails on a file outside `shared-cases/` that holds a case file or a case's expected value as JSON (any field order or spacing, nested anywhere; an expected value of one field is too common to count), equals a case file's text, or holds a case's QR matrix (also split over string pieces), and e2e reads its payment QR matrices from `qr/payment.json` (`e2e/qr-matrices.ts`).
- The case files are the living specification of these computations, not frozen v2 data, and are changed by hand: a PR that changes what one of them gives changes its cases first, in the same PR as the computation. Its first commit edits the cases (and, when the shape changes, the schema), sets the file's `source` from `v2-baseline` to `edited` if it is not already, and the runners fail on exactly the cases that change; the next commits change the computation on each side that has it, until both suites pass. The PR declares every case file and schema it changes in `regression/v2/changes/<slice-or-PR>.json` as `{"kind": "shared-case", "caseFile": "shared-cases/…", "reason", "contract"}` (`*` allowed after the literal `shared-cases/`): `compare-v2.mjs --changed` fails on a changed file under `shared-cases/` that no entry of a changes file the same PR changes names (an older declaration never covers a later PR), and the report lists each with its reason. The case file's diff is the reviewed statement of the new behaviour. Rewriting a case to match code that was not meant to change, or without the computation change it describes, is refused in review. A runner compares the whole value (`SharedCaseRunner.assertGives`), so a field the computation gains or loses fails until the cases carry it, and a new field also fails the schema until the schema names it.
- Files: `shared-cases/<topic>/<name>.json`, `{source, logic, cases: [{name, input, expected}]}` with names unique in the file and `source` `v2-baseline` (still what the v2 generator wrote at the baseline commit) or `edited` (changed by a PR since), each with its JSON Schema (draft 2020-12) `shared-cases/schemas/<topic>/<name>.schema.json` (parts used by several in `schemas/defs/`; `$id` under `https://nfnn.cz/shared-cases/`, resolved from the folder, never fetched). Vitest checks every file against its schema with ajv (`src/testing/shared-cases.spec.ts`; the backend takes no schema library, plan decision 6), so a new file comes with its schema and an expected value of the wrong shape fails even where only the backend computes it yet; the backend's `SharedCaseFilesTest` checks the envelope (the three fields, a known source, every case with `name`, `input` and `expected`, names once) and that every case file has its schema and every schema its file.
- What both sides run, and from which slice (a later slice adds its file and a line here: the verification payload 1.5, frozen receipts `receipts/v1` 1.6, the sync manifest 2.12). ## Suppression guard (Výjimky)

The check `Výjimky` (`.github/workflows/suppressions.yml`, rules in `.claude/rules/deploy-ci.md`) is a tripwire, not a security boundary: it makes a relaxation of tests, checks or CI visible and forces it to be declared with its reason in the PR description, but a change obfuscated on purpose can get past it, and the PR diff and Jakub's review stay the boundary. Its known limits: for most files it judges added lines only, never removals; it judges removed strictness only for the listed settings; it reads code as text, so a relaxation written in a form it does not know passes until a pattern is added; and it cannot tell an arbitrary rewrite of test code (an assertion weakened, a test emptied) from an honest one. The workflow runs on `pull_request_target` (opened, synchronize, reopened and edited, so editing the description runs it again) with `contents: read` only (the description comes from the event), no `needs` or `if:`, apart from `pr-check.yml`: on `pull_request` GitHub runs the PR's own copy of a workflow, so a PR could neutralise a check that lives there, while `pull_request_target` always runs the workflow of the base branch. It checks out the base (which supplies the guard) and fetches the PR's head into a separate folder, both with `persist-credentials: false`, diffs the merge base with `main` against the head there (`git -c core.quotePath=false diff --text --no-ext-diff --no-textconv --unified=0`, so neither a `.gitattributes` of the head nor a NUL byte turns a file into `Binary files … differ`; renames detected, so a pure move adds nothing), sets up Node without a package cache (`package-manager-cache: false`), reads the description from `github.event.pull_request.body` through `env` (never `${{ }}` inside `run:`) and runs the base's `scripts/suppression-guard.mjs` with the head folder as `--root`, which reads only regular files whose real path stays inside it (no symbolic link, no `..`). Invariant: nothing of the PR's head ever runs in this workflow (no npm, no build, no script, no action from it; its files are read as text only), because `pull_request_target` gives a run the base's context and its token on code anyone can push; a change that would run anything from the head is a security change. Every value the guard prints is escaped for workflow commands (`%`, CR and LF, and `:` and `,` in an annotation's `file=`), every finding line starts with `- `, and a file name with a control character is a finding of its own. A `pull_request_target` workflow starts only once it is on `main`, and `Výjimky` blocks a merge only once Jakub adds it as a required check (source GitHub Actions) to the ruleset `main` beside `gate` and `roadmap`. CI definitions fail closed (coordinator decision, review round 6 of #502): any added, changed, removed or renamed file under `.github/workflows/` or `.github/actions/` is one finding per file, naming how many lines changed, so a PR that changes a workflow or a local action declares each such file with its own `Výjimka:` line. This is deliberate: a workflow can be neutralised in too many ways to judge line by line (a top-level `env:` with `BASH_ENV`, `>> "$GITHUB_ENV"`, a second job named `gate`, an `on:` that keeps the real one from running), so a person reads every CI change. The same holds for what decides a required check besides the workflows (review round 7 of #502): every change to a script a required job runs or its pass/fail depends on (`scripts/compare-v2.mjs`, `compare-v2-baseline.mjs`, `compare-screens.mjs` with `png-pixels.mjs`, `compare-recordings.mjs`, `test-inventory.mjs`, `stack-journey.mjs`, `backend-log.sh`, `fake-fio.mjs`; `frontend/scripts/check-e2e-shards.mjs`, `check-receipt-chunks.mjs`, `probe-edge-caching.mjs`, `probe-asset-caching.mjs` with `immutable-locations.mjs`, `security-headers.mjs` and `app-routes.mjs`, `serve-dist.mjs`, which serves every e2e journey with the production headers, and `dev-port.mjs`, which decides the port and checkout marker of the server Playwright tests (`playwright.config.ts`, `serve-dist.mjs`); and those `npm run lint` and `lint:styles` decide by: `check-themes.mjs`, `needs-connection.mjs`, `pinned-libraries.mjs`, `stylelint-hover-media.mjs` and `frontend/eslint-confinement.js`; and those the `agent-context` job measures with: `scripts/agent-context-budget.mjs` and `mcp/src/tool-list.ts`; `CHECK_SCRIPTS` in the guard, a new such script joins it) to the build definition (`settings.gradle*`, `buildSrc/`, the `.gradle(.kts)` init scripts under `gradle/`, `gradle/wrapper/gradle-wrapper.properties`, `.github/docker-bake.hcl`) and to the package manager's configuration (`.npmrc`, `.yarnrc`, `.yarnrc.yml`: a `script-shell=/usr/bin/true` would make every `npm run` exit 0) is one finding per file in the same way, and so is `t3.json`, which names the commands T3 Code runs on Jakub's machine when it sets up and settles a worktree, and any other new or changed file with mode 100755 (executable: `new file mode`, `new mode` or the `index` line of the diff), which a job could run; on purpose this includes the worktree scripts `scripts/setup-worktree.sh`, `install-node-modules.sh` and `clean-worktree.sh`, which T3 Code runs on Jakub's machine for every new worktree (`t3.json`), and the entrypoints, rotation scripts and `backend/gradlew`. `.github/deployed-revision` stays out on purpose: it changes after every deploy and only names where the release rehearsal starts. Their tests (`*.test.mjs`) are judged by their lines like any test. The guard itself (`scripts/suppression-guard.mjs`) counts any change too, removals included, also when renamed or copied (judged under its own path, so the declaration names it); changes to its tests `scripts/suppression-guard.test.mjs` are not judged (they hold the planted patterns) unless another file is moved onto that path. Elsewhere it judges added lines only, never removals. A binary change (`Binary files … differ`, `GIT binary patch`) and a symbolic link (`new file mode 120000`, `new mode 120000`) are findings, since the guard cannot read them. In those configuration files, a line added inside a list of `ignores`, `exclude`, `include`, `testIgnore`, `testMatch`, `grep`, `grepInvert` or `ignoreFiles`, and `'off'`, `'warn'`, `0`, `1` or `null` as the first element of an ESLint or Stylelint rule's array, count even on lines of their own (read from the head). Removed lines that kept a check strict count too: a removed `forbidOnly` or `failOnFlakyTests` in a Playwright config, an `'error'` or `"error"` rule level in an ESLint config, `"strict…"`, `"noUnused…"` or `"noImplicit…"` set to `true` in a tsconfig, and `--max-warnings` in a `package.json`. A skip that depends on the run (`skipIf(!process.env.X)`, `test.skip(!process.env.BASELINE_SCREENS, …)`) passes by design: whether it skips is known only when the tests run. It passes when the description has a line `Výjimka: <path>: <reason>` (the path may stand in backticks, the line may be a list item) naming that file with a reason of at least 10 characters besides any `<placeholder>` ("Done means" 4; the reason lives there because code carries no comments). One line covers every suppression of its file, later pushes included. Lines inside HTML comments or code fences do not count, so the hint of `.github/pull_request_template.md` declares nothing until filled in, and a line without a real reason is reported. Allowed without a line: Playwright's conditional `test.skip(<condition>, '<reason>')` (`testing-frontend.md`: a test WebKit cannot run, a measurement behind its variable), `test.fail(<condition>, …)` (`KNOWN_BREAKS`), Vitest's `skipIf(<condition>)` and `runIf(<condition>)`, Markdown, and the guard's tests. `scripts/suppression-guard.test.mjs` plants each pattern, each allowed form, quoted paths and real git repositories' diffs.
